## §2 實際抓到的定位素材

### 2.1 服務基地台（`AT+QENG="servingcell"`）

```
+QENG: "servingcell","NOCONN","LTE","FDD",466,01,ABCDE02,144,1550,3,5,5,1234,-113,-18,-92,-1,10
```

| 欄位 | 原始值 | 換算 | 說明 |
|---|---|---|---|
| MCC | `466` | 466 | 臺灣 |
| MNC | `01` | 1 | **遠傳電信（466-01）** |
| Cell ID | `ABCDE02` **(hex)** | **180149762** | 28-bit ECI |
| ↳ eNodeB ID | — | **703710** | ECI >> 8 |
| ↳ Sector | — | **2** | ECI & 0xFF |
| PCID | `144` | 144 | 實體小區識別，**非全域唯一** |
| EARFCN | `1550` | Band 3 | |
| TAC | `1234` **(hex)** | **4660** | 追蹤區碼 |
| RSRP | `-113` | -113 dBm | **弱**（-100 以下算差）|
| RSRQ / RSSI / SINR | `-18` / `-92` / `-1` | | SINR -1 dB，品質不佳 |

🔴 **Cell ID 與 TAC 是十六進位，查資料庫前必須轉十進位。** 公開資料庫（OpenCelliD 等）
一律吃十進位，直接把 `ABCDE02` 丟進去只會查無此筆 —— 這是最常見的錯。

### 2.2 鄰近基地台（`AT+QENG="neighbourcell"`）—— ⚠ 對定位幫助有限

實測回了 **32 筆**鄰近小區（inter 16 筆 + intra 16 筆），格式例：

```
+QENG: "neighbourcell intra","LTE",1550,244,-122,-20,-,-,1,6,21,4,0
                                    ↑    ↑    ↑
                                EARFCN  PCID  RSRP
```

🔴 **LTE 的鄰近小區報告只有 PCID（0-503），沒有全域 Cell ID。**
PCID 在網路裡會大量重複使用，**無法對應到公開資料庫的任何一筆記錄**。

**結論：多基地台三角定位在這顆模組上做不到**，只能拿服務基地台做單點查詢。
而且實測 32 筆裡有 28 筆 RSRP 是 `-140`（底噪值，代表根本沒測到），
真正有訊號的只有 4 筆。

### 2.3 Wi-Fi 掃描（`AT+QWIFISCAN`）—— 室內最有價值的素材

```
+QWIFISCAN: (-,-,-37,"C2:28:35:00:00:01",1)
+QWIFISCAN: (-,-,-37,"C2:28:35:00:00:07",1)
+QWIFISCAN: (-,-,-46,"10:71:B3:00:00:02",4)
+QWIFISCAN: (-,-,-50,"62:62:DE:00:00:08",1)
+QWIFISCAN: (-,-,-50,"62:62:DE:00:00:05",1)
+QWIFISCAN: (-,-,-88,"A8:A2:37:00:00:03",6)
+QWIFISCAN: (-,-,-89,"40:9B:CD:00:00:09",7)
```

**7 個 AP，RSSI -37 ~ -89 dBm，訊號比基地台好得多**（基地台 RSRP 只有 -113）。
欄位順序是 `(ecn, ssid, rssi, mac, channel)`，本機韌體的 ecn 與 ssid **固定回 `-`**
（2026-08-02 已實測記錄），只給 RSSI / MAC / 頻道 —— 但**定位只需要 MAC 與 RSSI，夠用**。

## §3 四個方案對照

| | 方案 | 誰做運算 | 精度（室內） | 流量 | 現在能不能做 |
|---|---|---|---|---|---|
| **A** | **QuecLocator**（`AT+QLBS`） | 模組送給 Quectel 伺服器 | 中～高（它同時吃 Wi-Fi＋基地台） | 每次數 KB | ❌ **卡在 token** |
| **B** | **基地台單點查表** | PC 端查公開資料庫 | **低**（數百公尺～數公里） | **模組零流量** | ✅ **馬上可做** |
| **C** | **Wi-Fi 查表** | PC 端查地理定位 API | **高**（數十公尺） | **模組零流量** | ✅ **馬上可做**（需 API 金鑰）|
| **D** | 模組自己發 HTTP 查 | 模組經 `AT+QHTTP*` 呼叫 API | 同 B／C | 每次數 KB | ✅ 可做（P3 HTTP 已全數驗證通過）|

### 為什麼 B 的精度註定低

單一基地台查表得到的是**那座基地台的登記座標**，不是你的位置。
你與它的距離只能靠 RSRP 粗估，而且 LTE 沒有公開的 timing advance 查詢指令。
**RSRP -113 dBm 代表距離不近或穿了好幾道牆**，誤差輕易到公里級。
拿它當「大概在哪個城市／哪一區」可以，當室內定位不行。

### 為什麼 C 是室內首選

Wi-Fi AP 密度高、涵蓋半徑小（數十公尺），**室內精度天生就比基地台好一到兩個數量級**。
本次掃到 7 個 AP、最強 -37 dBm，素材品質良好。

## §4 建議：先做 C（Wi-Fi），B 當對照

理由：**C 精度高、模組零流量、現在就能做**；B 免費且零門檻，適合拿來當「量級對照」，
順便驗證資料庫涵蓋率。兩者都不需要 Quectel token。

## §5 要不要做進 UI？

目前這些都是**手動複製貼上**。若要做成一鍵，選項是：

1. **解析器 ＋ 匯出鈕**（小改動）：把 `+QENG:` 與 `+QWIFISCAN:` 解析成 JSON，
   加一顆「複製定位查詢 JSON」，user 自己貼到 API 測試工具
2. **PC 端直接查**（中改動）：主程式 `fetch()` 呼叫地理定位 API，結果畫到現有地圖頁。
   ⚠ **金鑰會出現在前端**，且要把新網域加進 CDN 白名單（CLAUDE.md 有規範）——
   要先問過 user
3. **模組端查**（方案 D，大改動）：走 `AT+QHTTPURL` ＋ `AT+QHTTPPOST`，
   最貼近「裝置自己定位」的真實產品情境，但要耗流量、金鑰要寫進指令參數

**建議先做 1**，驗證資料庫查得到再談要不要自動化。

## §6 限制與已知問題

- 🔴 **鄰近小區只有 PCID，無法用於多點定位**（§2.2）——
  這是 LTE 標準的限制，不是模組缺陷
- 🔴 **Cell ID／TAC 是十六進位**，查表前必須轉十進位
- ⚠ `AT+QCELLLOC` 本機**不支援**，EC2x 系列的文件與教學不適用
- ⚠ **QuecLocator（`AT+QLBS`）沒有 token 與 token 無效都回 `+QLBS: 702`**，
  從回應分不出是哪一種（2026-08-07 實測）
- ⚠ 本次服務基地台 **RSRP -113 dBm / SINR -1 dB，訊號偏弱**，
  換位置或換時間再測數值會變
- ⚠ 這張 SIM 是 1NCE 漫遊卡（IMSI MCC 901），實際掛在**遠傳（466-01）**；
  漫遊卡可能隨時被導到不同的臺灣業者，**下次測到的 MCC/MNC 可能不同**

### 🔴 使用前必須知道的四件事

**1. 71 m 是「查表命中」不是「量測精度」。**
連續三次查詢回**完全相同**的座標（都是 **P2**）——
基地台定位的本質是「用 cell ID 查那座基地台的登記位置」，
**同一個 cell 永遠回同一個點**。71 m 是「這座基地台的登記座標」碰巧離你很近，
不是系統每次都能達到的精度。

**2. 因此 71 m 不可外推。** 換一座基地台、換一個地點，
誤差就是「你與那座基地台登記座標的距離」，可能是 50 m 也可能是 2 km。
服務自己回報的 ±1051 m 才是它對自身不確定性的誠實估計。
**要當產品指標，必須在多個地點重測取分布，不能用這一個樣本。**

**3. 漫遊卡換業者，結果就會變。** 這張 1NCE 卡目前掛遠傳（466-01），
2026-08-01 曾掛中華電信（466-92）。換業者＝換基地台＝換登記座標＝誤差重骰。

**4. 資料庫品質差異巨大。** 同一座基地台：
beaconDB 632 m vs Unwired Labs 71 m（差 9 倍）。付費資料庫的群眾外包量測密度是關鍵。

### 為什麼放棄 Wi-Fi 那條（免費生態已崩）

| 服務 | 2026-08-29 查證結果 |
|---|---|
| Mozilla MLS | 2024 年停止服務 |
| beaconDB（MLS 接棒） | 免費免金鑰，但**本區 Wi-Fi 涵蓋 404** |
| Unwired Labs 免費方案 | **不含 Wi-Fi**（`WiFi access not enabled`） |
| WiGLE | **user 回報無法註冊**（2026-08-29） |
| HERE | **2025-08-31 起取消免卡方案**，免費額度也要綁卡 |

**「免費＋免綁卡＋有臺灣 Wi-Fi 涵蓋」的服務，2026 年 8 月已不存在。**
Wi-Fi 定位的方法與工具**都已就緒**（`tools/wifi_geolocate.py` 支援 google/unwiredlabs），
純粹卡在服務供應商的商業模式，不是技術問題 —— 隨時可恢復：

- 願意綁卡（不會被扣款，額度內免費）→ Google 或 HERE，工具直接可用
- WiGLE 若之後開放註冊 → 需補 `--provider wigle`（單顆 BSSID 查已知位置，模式不同）
- 願意公開自家 AP＋座標 → geosubmit 回報 beaconDB，這一帶從此免金鑰可查

## §9 架構決策：不採用 QuecLocator（2026-08-29，user 裁定）

> **user 判斷**
>
> > 我覺得 QuecLocator 服務可靠度可能不高，什麼時候關閉都不知道 —— 2026-08-29

**裁定：QuecLocator 降級為「若拿得到免費 token 才順手驗證」，不投入、不列入產品路徑。**

### 支持這個判斷的證據

| 訊號 | 意義 |
|---|---|
| Quectel 員工在官方論壇明確回覆「**BG95 系列已不再支援 QuecLocator**」 | 已在部分產品線收攤 |
| 無公開定價、無自助註冊、須聯絡業務／技術支援 | 低優先產品線的典型徵候 |
| **EG800K 自己的 16 份官方文件裡沒有任何一份 QuecLocator 文件** | 對本機而言幾乎是未文件化的功能；我們是靠 EC200U／EG915U 的文件反推用法 |
| 單一廠商、閉源、綁在韌體裡 | 無第二來源 |

### 🔴 但真正的理由是「失效模式」不是「失效機率」

**第三方定位服務會變動是常態，不是 QuecLocator 獨有的問題** ——
本專案兩天內就親眼撞到三次：Mozilla MLS 停服（2024）、
HERE 取消免卡方案（2025-08-31）、Unwired Labs 免費方案不含 Wi-Fi。
**用「哪家比較不會倒」來選型是靠不住的。**

決定性的差別在供應商消失時的代價：

| 方案 | 供應商消失時要改什麼 |
|---|---|
| **QuecLocator（`AT+QLBS`）** | 🔴 **那條 AT 指令直接失效**。定位邏輯在韌體裡，無法抽換供應商 —— 整個定位流程要重新設計 |
| **主機端查表**（本專案現行做法） | ✅ 換一個參數（`tools/wifi_geolocate.py --provider`）。三家供應商已在同一介面之後 |

**QuecLocator 把供應商鎖進了最難改的那一層（韌體）。**
現行架構則把網路定位當成可抽換元件 —— 這是本決策的核心。

### 那「模組自己定位、不需主機端」的需求怎麼辦

QuecLocator 唯一的架構優勢是裝置獨立完成定位。若產品真的需要這個情境，
**用方案 D（`AT+QHTTPURL` ＋ `AT+QHTTPPOST` 讓模組自己打選定的定位 API）
可達成同樣效果，且供應商可換** —— P3 已驗證 HTTP/HTTPS 全數可用。
代價是耗流量、金鑰要寫進指令參數。

### 選型原則（可外推到本專案其他外部依賴）

**評估外部服務時，先問「它死掉時我要改哪一層」，再問「它多可能死掉」。**
鎖在韌體／協定層的依賴，即使供應商看起來很穩，也比鎖在應用層的依賴危險得多。
