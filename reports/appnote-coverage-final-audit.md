## §1 判定基準

NuModem 是「瀏覽器 + Web Serial + UART」的 AT 終端機，因此：

| 判定 | 意義 |
|---|---|
| **有按鈕** | 面板有專屬按鈕／參數卡 |
| **可命令列手動** | 沒按鈕，但任何單行 AT 指令都能在命令列輸入完成 —— **功能不缺，只是沒做成 UI** |
| **需兩段式-已有機制** | 等 `>`／`CONNECT` 再送資料的指令；工具的 `sendWithPayload()` 機制既有，**缺的只是按鈕**（命令列必加 CR、不算長度，手動不可靠） |
| **無法實現** | 工具本質限制，附原因 |

## §3 無法實現清單（每項附限制原因）—— user 最在意的部分

### 3.1 工具本質限制（瀏覽器 + UART 架構決定，補按鈕解決不了）

| 功能 | 文件 | 限制原因 |
|---|---|---|
| **PPP 撥號上網**（`ATD*99#` 之後） | PPP | 指令下得出去、也看得到 `CONNECT` 與 PPP 訊框（亂碼），但 LCP／PAP/CHAP／IPCP 是**二進位協定協商（含 FCS 計算與逐訊框應答），瀏覽器沒有 PPP 堆疊**。這是該文件的核心功能，屬本質限制。**正規替代**：Windows 撥號網路（文件 §6 有完整教學）—— 注意撥號會獨占 COM 埠，與 NuModem 不能同時開 |
| **USB Suspend/Resume 低功耗方案** | 低功耗 | 要主機 OS 對**模組的 USB 埠**做 suspend/resume；本工具只接 UART，看不到也控不了模組 USB 埠 |
| **NMEA 連續串流觀察** | GNSS／USB descriptor | `outport` 只有 `none`／`usbnmea`／`uartdebug` 三選項，**沒有 AT 主埠（uart1）選項** —— 連續流只會出現在模組 USB 埠或另一條實體 debug UART，本工具都接不到。**替代**：`nmeasrc=1` ＋ `AT+QGPSGNMEA` 逐句輪詢（按鈕已有，GNSS 測試全程就是這樣做的） |
| **USB 描述符列舉／驅動** | USB descriptor | 純 USB host（作業系統）行為，與 AT/UART 無關，本就不在本工具範疇 |
| **DFOTA protocol-download 模式** | DFOTA | `AT+QFOTADL="FILE:<len>",2` 之後模組進入 **Quectel 未公開的專有下載協定**（文件僅寫「洽技術支援」），規格不明無從實作。⚠ 別誤下這條 —— 下了模組會卡在等待狀態 |
| **DFOTA 本機檔案升級（硬體流控路徑）** | DFOTA | 需「選檔＋數 MB 二進位分塊串流＋`AT+IFC=2,2` 硬體流控」，且 Web Serial 開埠要帶 `flowControl:"hardware"`（本機未實作）。技術上瀏覽器做得到，但屬大型專用功能，**升級韌體建議走伺服器下載路徑**（單行指令、命令列今天就能走完） |

### 3.2 模組端限制（不是 NuModem 的問題）

| 功能 | 文件 | 限制 |
|---|---|---|
| QuecCell 非同步 URC 回報（mode=2/3/4） | QuecCell | **文件明載模組韌體鎖住不可設**。若未來韌體開放，本機 urcport 已是 uart1，接收機制現成 |
| `AT+QGPSVBCKP` 備援電源 | GNSS | EG800K 韌體不支援（2026-08-06 實測 `=?`／`?` 皆 ERROR） |
| QuecLocator token | QuecLocator | 須向 Quectel 付費申請，無自助管道（user 已裁定不採用，見 `cell-wifi-positioning-options.md` §9） |
| QFUPL ACK 模式（1 KB 分塊等 'A'） | FILE | 現有兩段式機制是「等提示後一次送完」，分塊握手迴圈要專用邏輯。**替代**：非 ACK 模式即可（小檔無差） |

### 3.3 顯示限制（能做、但有折扣）

- **大量二進位下載**（FTP GET "COM:"、QIRD、QSSLRECV、HTTP READ）：顯示得出來但**存不了檔** ——
  終端機是顯示器不是檔案接收器。要位元組級驗證得像 P6 那樣從對端比對
- **透傳模式（mode 2）**：進得去（`CONNECT`）、退得出（`+++` 鈕／DTR），但命令列每次送出
  **必加 CR**，只適合行導向文字，二進位透傳不純

## §4 唯一的系統性缺口：`AT+QFUPL` 沒有按鈕

**六份文件（SSL／MQTT／HTTPS／FTP(S)／FILE／DFOTA）不約而同卡在同一條指令**：
`AT+QFUPL` 檔案上傳（兩段式：`CONNECT` 後送「剛好 N bytes」的原始內容）。
沒有它，這些流程從 UI 走不通：

- SSL／MQTT／HTTPS 的 **seclevel 1/2**（伺服器驗證、雙向認證）—— 憑證送不進模組
- FTP 的 UFS 中轉上傳（§3.6 Solution 2/3）
- UFS 檔案寫入路徑（`QFWRITE` 同屬兩段式）

**機制其實已經驗證可行**：P5 測試時就是用工具內部的 `sendWithPayload()` 程式化上傳了
1,939 bytes 的 ISRG Root X1（`+QFUPL: 1939,4f64`）—— 缺的只是一顆
「檔案選擇器＋自動算位元組數」的 UI 按鈕。**這是完工前最值得補的一顆按鈕。**

## §6 補按鈕候選（依價值排序，全部是「機制既有、只缺 UI」）

1. **`AT+QFUPL` 檔案上傳鈕**（檔案選擇器、自動算 bytes）—— 一顆解開六份文件的流程（§4）
2. `AT+QSSLSEND=<cid>` 變長續寫鈕 —— 仿 TCP/IP 的「Send (續寫)」即可
3. `AT+QFWRITE` 兩段式鈕 —— 補上後 UFS 開檔讀寫全流程可行
4. `AT+QHTTPGET` 自訂 header 兩段式形式
5. `AT+QFOTADL=<URL>` 參數卡 —— 伺服器下載升級主流程（單行，其實手動也行）
6. QuecCell 查詢鈕 3-4 顆（`QENG="servingcell"` 等，基地台定位在用、單行可手動）
7. `AT+QSCLK=1/0` 設定鈕＋DTR 睡眠快捷 —— 低功耗 UART 流程即完整
8. `QMTCFG="willex"` 兩段式（可用單行 `"will"` 替代，低優先）
9. `AT+QISEND=<id>,<len>,<IP>,<port>`（UDP SERVICE 變體）
10. PPP 模式控制輔助 5 顆（`AT&D1/2`、`AT&C0/1`、`CGDCONT` set）—— PPP 本身不投資
