SSL —— ช่องทาง TLS

หลักการทำงาน: หน้า SSL คือชั้นล่างที่ใช้ร่วมกันของการเชื่อมต่อเข้ารหัส —— SSL context ที่ตั้งไว้ที่นี่กับใบรับรองที่อัปโหลด ใช้ได้พร้อมกันทั้ง SSL raw socket, MQTT over SSL และ HTTPS ตัวเลขวินาทีและพฤติกรรมในหัวข้อนี้คือค่าวัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

การเชื่อมต่อ TLS ครั้งแรก: ห้าขั้นตอน

  1. รันพิธีกรรมเปิดเครื่อง (ดูหัวข้อ "พิธีกรรมเปิดเครื่อง") แล้วกด AT+QIACT? ยืนยันช่องทางข้อมูล —— ต้องตอบ +QIACT: 1,1,…,"IP" ออกมาได้ ไม่มีก็ AT+QIACT=1 ก่อน
  2. ตั้ง context: sslversion กรอก 4 (ทุกเวอร์ชัน เข้ากันได้ดีที่สุด), ciphersuite กรอก 0XFFFF (ทุกชุด), seclevel กรอก 0 ไปก่อน —— ยืนยันว่าช่องทางผ่านก่อน การตรวจสอบเก็บไว้ทีหลัง
  3. เปิดการเชื่อมต่อ: กด AT+QSSLOPEN (เลขท้าย 0) กรอกโฮสต์กับพอร์ต ในการ์ดพารามิเตอร์ ⚠ OK แปลว่าแค่ "รับคำสั่งไว้" สำเร็จหรือไม่ต้องรอ URC: +QSSLOPEN: 4,0 ถึงจะคือสำเร็จ (ทดสอบจริง handshake 2.0 วินาที)
  4. ส่งข้อมูล: กด AT+QSSLSEND (แบบสองขั้น) —— เห็น > แล้วส่งเนื้อหา นับครบความยาวที่ประกาศไว้ก็ส่งออกอัตโนมัติ ไม่ต้องใช้ Ctrl+Z (เพดานต่อแพ็กเก็ต 1460 bytes) ฝั่งโน้นตอบกลับจะเห็น +QSSLURC: "recv",4
  5. อ่านกลับและปิด: AT+QSSLRECV (ครั้งละไม่เกิน 1500) อ่านจนเจอ +QSSLRECV: 0 แปลว่าเก็บเกลี้ยงแล้ว ไม่ใช่ข้อผิดพลาด AT+QSSLCLOSE=4 ปิด (ค่าเริ่มต้นรอนานสุด 10 วินาที; อีกปุ่มระบุจำนวนวินาทีได้ 0 = ทันที)

ระหว่างเชื่อมต่อกด AT+QSSLSTATE ดูการเชื่อมต่อทั้งหมดได้ (=4 ถาม clientID เดี่ยว สถานะ 2 = เชื่อมต่อแล้ว) ระวังพอร์ตฝั่งเครื่องตอบ 0 ตลอด —— เป็นพฤติกรรมของโมดูล ไม่ใช่ข้อผิดพลาด

การตั้งค่า context ทีละรายการ

ไม่แน่ใจว่าเฟิร์มแวร์รองรับรายการย่อยไหนบ้าง ให้กด AT+QSSLCFG=? ก่อน —— ทดสอบจริงตอบ 17 รายการย่อย มากกว่าที่คู่มือประยุกต์ระบุไว้ รายการย่อยที่ใช้บ่อยมีปุ่มตั้งกับปุ่มถามครบคู่ ทดสอบจริงเขียนแล้วอ่านกลับตรงกันเป๊ะ

รายการย่อยค่าโรงงานหน้าที่และประเด็นจากการทดสอบจริง
sslversion—เวอร์ชันโปรโตคอล; 4 = รองรับทั้งหมด
ciphersuite—ชุดเข้ารหัส; 0XFFFF = รองรับทั้งหมด
seclevel00 = ไม่ตรวจสอบ, 1 = ตรวจสอบเซิร์ฟเวอร์ (ต้องอัปโหลดใบรับรอง CA ก่อน), 2 = ยืนยันสองทาง (ต้องมีใบรับรองไคลเอนต์ + คีย์ส่วนตัวเพิ่ม)
cacert—เส้นทางใบรับรอง CA รูปแบบ "UFS:ชื่อไฟล์" ไฟล์ต้องอยู่ใน UFS แล้ว (ดูหัวข้อถัดไป)
sni🔴 0 ต่อ virtual host / CDN ต้องเปิด —— IP เดียวแขวนหลายโดเมน ถ้าไม่ส่ง SNI จะได้ใบรับรองที่ไม่ตรง การตรวจสอบพังแน่นอนด้วย 566
ignorelocaltime🔴 1 สถานะโรงงานต่อให้เปิด seclevel 1 ก็ไม่ตรวจอายุใบรับรอง จะตรวจให้ตั้ง 0 และนาฬิกาโมดูลต้องตรง
negotiatetime300 จำนวนวินาทีรอ TLS handshake นานสุด (10–300)
🔴 ค่าโรงงานสามตัวรวมกัน = ไม่ตรวจสอบใบรับรองเลยแม้แต่น้อย (seclevel 0, sni 0, ignorelocaltime 1) จะตรวจจริงต้องตั้งให้ถูกทั้งสามตัว แถมสามค่านี้กับ cacert ไม่คงอยู่ข้ามการรีบูต (ยืนยันจากการทดสอบจริง) บูตทุกครั้งกลับเป็นค่าโรงงาน; ส่วนไฟล์ใบรับรองใน UFS ตัดไฟก็ไม่หาย

กลุ่มไฟล์ UFS: ใบรับรองเข้าโมดูลได้อย่างไร

UFS คือหน่วยเก็บแฟลชในตัวโมดูล ทดสอบจริงความจุรวม 280 KB แต่ละไฟล์กินหนึ่งบล็อก 4 KB ใบรับรองต้องอัปโหลดมาที่นี่ก่อน cacert ถึงจะมีไฟล์ให้ชี้ การอัปโหลดเดิน UART ไม่กินปริมาณข้อมูลเลย ไฟล์ไบนารีก็ส่งเข้าได้ การ์ด Upload: เลือกไฟล์แล้วชื่อกับขนาดกรอกให้อัตโนมัติ ส่งแล้วเครื่องมือรอโมดูลตอบ CONNECT ก่อนถึงจะส่งไบต์ดิบ (รอไม่ได้ก็ไม่ส่ง) เมื่อเสร็จ เอนจินคำอธิบายจะเทียบให้อัตโนมัติระหว่างขนาดกับ checksum ที่โมดูลรายงาน: ✅ = ครบถ้วนไม่ผิดเพี้ยน, ❌ = ส่งพัง ให้ลบก่อนแล้วส่งใหม่

AT+QFUPL="badssl-root.pem",1939,10
CONNECT                   ← ตามด้วยส่ง 1939 bytes
+QFUPL: 1939,4f64         ← ขนาดที่รับจริง,checksum คำอธิบายเทียบให้อัตโนมัติ ✅
ปุ่มใช้ทำอะไร
AT+QFLSTแสดงไฟล์ทั้งหมดใน UFS พร้อมขนาด —— อัปโหลดแล้วใช้ตัวนี้ยืนยัน (ไม่กินปริมาณข้อมูล)
AT+QFLDS="UFS"ถามพื้นที่เหลือ / รวม เป็น bytes (ไม่กินปริมาณข้อมูล)
AT+QFDELลบไฟล์ที่ระบุ (* = ทั้งหมด); ไฟล์ชื่อซ้ำถ้าไม่ลบก่อน ส่งใหม่จะถูกกัน
พฤติกรรมจากการทดสอบจริงสองอย่างที่คู่มือไม่ได้บอกชัด: (1) รูปแบบรหัสข้อผิดพลาด FILE ไม่คงเส้นคงวา —— ส่งซ้ำชื่อเดิมตอบเป็นข้อความ file already exist แต่หมดเวลาตอบเป็นตัวเลข 421 เครื่องมือนี้อ่านได้ทั้งสองแบบ; (2) กรอกช่องขนาดใหญ่กว่าจริง โมดูลหมดเวลาแล้ว ก็ยังเซฟเนื้อหาที่รับจริงเป็นไฟล์อยู่ดี —— การเทียบ checksum จะจับได้

สนามจริงของการตรวจสอบใบรับรอง: วิธีทดสอบเป็นคู่

ขั้นตอน: อัปโหลดใบรับรองราก → cacert ชี้ไปที่มัน → seclevel 1 → sni 1 → ต่อพอร์ต 443 ของเป้าหมาย ที่ต้องอัปโหลดคือใบรับรองรากชั้นบนสุดของเชน (เชนของ badssl.com มีสี่ชั้น ให้อัปโหลด ISRG Root X1 ตัวยอดสุด) ทดสอบแค่ "ใบรับรองเสียต่อไม่ได้" ยังไม่พอ —— กรณี "ต่อไม่ได้ทั้งหมด" ก็ผ่านเหมือนกัน ต้องทดสอบเป็นคู่: ใบรับรองดีต้องต่อได้ ใบรับรองเสียต้องต่อไม่ได้ เป็นจริงทั้งสองทางถึงจะนับ ทดสอบจริงเทียบ 2×5:

โฮสต์seclevel 0seclevel 1
badssl.com (ตัวเทียบบวก)ต่อได้ ต่อได้ 4,0
expired (หมดอายุ)ต่อได้ปฏิเสธ 566
self-signed (เซ็นเอง)ต่อได้ปฏิเสธ 566
wrong.host (ชื่อโฮสต์ไม่ตรง)ต่อได้ปฏิเสธ 566
untrusted-root (รากไม่น่าเชื่อถือ)ต่อได้ปฏิเสธ 566

ข้อจำกัด: ความผิดของใบรับรองทั้งสี่แบบตอบ 566 หมด โมดูลไม่แยกว่าเป็นแบบไหน AT+QIGETERROR ก็ช่วยไม่ได้ —— มันดูแลชั้น TCP/IP ตอนนั้นตอบแค่ 0,operate successfully

รายการทดสอบเชิงลบให้เลี่ยง expired —— ค่าโรงงาน ignorelocaltime เป็น 1 การหมดอายุโดยตัวมันเอง จะไม่ถูกกัน (ในตารางบนมันถูกกันเพราะขณะเดียวกันไม่ได้อยู่ใต้รากที่อัปโหลดด้วย) จะทดสอบเดี่ยวให้ใช้ wrong.host อีกอย่างระวังปริมาณข้อมูล: ทุก handshake ดาวน์โหลดเชนใบรับรองครบชุด ล้มเหลวก็จ่ายเท่ากัน ทดสอบจริง handshake 30 ครั้งราว 150–200 KB

🔴 กับดัก: เปิดปิดติดต่อกันราว 20 ครั้ง สแต็กข้อมูลเสื่อมทั้งยวง

อาการ: AT+QSSLOPEN ทั้งหมดตอบ 552 หมด ขนาด seclevel 0 ก็ต่อไม่ได้ ทั้งที่การตรวจตัวเองทุกข้อบอกปกติ วิธีจำแนก 30 วินาที: ใช้ TCP ล้วนด้วย AT+QIOPEN ยิงเป้าหมายเดียวกัน —— ล้มเหลวด้วยคือสแต็กข้อมูลพังแล้ว อย่าไปไล่การตั้งค่า SSL ต่อ รีสตาร์ต PDP ช่วยไม่ได้ มีแต่พิธีกรรมเปิดเครื่องแบบเต็มเท่านั้นที่กู้คืนได้ ความเสื่อมจะปนเปื้อนข้อมูลทดสอบ ตัดสินผิดเป็น "ถูกการตรวจสอบใบรับรองกัน" ได้ง่าย —— ก่อนทำการทดสอบเป็นคู่ให้รีบูตล้างให้สะอาดก่อน
