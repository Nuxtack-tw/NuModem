MQTT —— IoT メッセージング

動作原理：MQTT は「broker（メッセージ仲介サーバー）」型のプロトコルです： デバイス同士は直接つながらず、それぞれ broker に接続し、「トピック（topic）」に対してメッセージを発行または購読します。 EG800K 上では 2 層構造です：まず AT+QMTOPEN で「ネットワーク接続」を開き（TCP で broker へ接続）、 次に AT+QMTCONN で「MQTT ログイン」を行い、両方の層が通ってはじめて購読と発行ができます。 先に覚えておくこと：MQTT コマンドの結果はすべて「まず OK、次に URC」のパターンです（FTP と同じ）—— OK はコマンドを受け付けたという意味でしかなく、成否はその後の結果 URC で見ます。

本ページは client 0 に固定しています。ファームウェアは他にマルチ client（0–5）、SSL、クラウドプラットフォーム認証にも対応しており （=? の実測で確認）、上級の使い方は MQTT アプリケーションノートを参照してください。

始める前に：2 つの前提

  1. URC が UART を通っていること：AT+QURCCFG="urcport" が "uart1" を返す必要があります。出荷値は "usbat" で、MQTT の結果はすべて URC —— 変えないとどのコマンドも OK が返るだけで後が続きません （Basic ページにボタンがあります。NVRAM に書かれるので変更は 1 回だけ）。
  2. PDP を先に有効化すること：先に TCP/IP ページで AT+QIACT=1 を押します（最長 150 秒）。有効化していないと +QMTOPEN が 3＝PDP 有効化失敗を返します。 全行程でデータ通信量が発生し、見積もりは約 5 KB です。

どう試すか：4 つの無料公開 broker

AT+QMTOPEN のパラメータカードには broker のドロップダウンが組み込まれています（自由入力も可）。 4 つとも匿名を許可し、登録は不要です。データは 2026 年 8 月の実測（PC 側から 100 件の連射、モジュール側から ping）：

client ID とトピックのランダムサフィックス：再読み込みのたびに変わる

client ID と既定トピックは固定値ではありません：ページ読み込み時に 16 進 6 文字のサフィックスを自動生成し、 numodem-<サフィックス> と test/numodem-<サフィックス> を組み立てます。 Subscribe／Publish／Unsub の 3 ボタンは同じ 1 組を共用します（そうしないとループバックが噛み合いません）。理由は 2 つ：

  • 名前が衝突すると蹴落とされる：MQTT 3.1.1 §3.1.4 は、先に接続していた側を broker が 切断するよう規定しています —— 2 人が同じ固定 ID を使うと蹴り合いになり、症状は「モジュールが訳もなく切断される」ように見えます。
  • 固定トピックは他人のメッセージを受信する：自分が発行したものだと思って受け取ったのに、実は違う —— これは受信できないより悪質です。偽の合格を出してしまうからです。
⚠ ページを再読み込みするたびにサフィックスは別の組になります —— 購読と発行は同じページのライフサイクル内で完了させなければなりません。 しかも本ツールは RTS＝電源なので、ページの再読み込み＝モジュールの電源断で、MQTT 接続はまるごと消えます。 起動シーケンスと AT+QMTOPEN からやり直しです。

完全な動線：接続 → 購読 → 発行 → 自分のメッセージを受け取る

最も説得力のある検証はループバックです：購読した後、同じトピックに発行して 自分のメッセージを自分で受け取れば、送受信の全リンクを一度で検証できます。各ステップは結果 URC を待ってから次へ：

  1. プロトコルバージョンを設定：Ver 3.1.1 を押します（AT+QMTCFG="version",0,4。 3＝3.1、4＝3.1.1）。Version? で現在値を照会できます（値なし＝照会）。 Keepalive のパラメータカードで保活間隔を調整できますが、調整しなくてもテストできます。
  2. ネットワークを開く：Open Net を押します（AT+QMTOPEN=0,"broker",1883）。 まず OK が返り、成否は URC +QMTOPEN: 0,<result> （0＝成功）で見ます。最長 120 秒待ちます。Open? で開いている接続を照会できます （接続が無いときは空の OK が返り、実測で正常）。
  3. MQTT ログイン：Connect を押します（AT+QMTCONN=0,"numodem-<サフィックス>"）。 成功の URC は必ず +QMTCONN: 0,0,0 です。公開 broker はユーザー名とパスワード不要。 必要な場合はパラメータの後ろに自分で ,"user","pass" を足します。 Conn? で状態を照会します（1＝初期、2＝接続中、3＝接続済み、4＝切断中）。
  4. 購読：Subscribe を押します（AT+QMTSUB=0,1,"test/numodem-<サフィックス>",0、 msgid は 1 に固定）。成功の URC は +QMTSUB: 0,1,0,0 のような形です。 以後、このトピックのメッセージは +QMTRECV URC で入ってきます。
  5. 発行：Publish を押します（AT+QMTPUBEX、2 段階。次の段落を参照）。 成功の URC は +QMTPUBEX: 0,<msgid>,0 です。
  6. 受け取る：発行先は購読中のトピックそのものなので、直後に +QMTRECV がトピックとさっきのメッセージ本文を伴って現れます —— ループバック成功。 マルチバイト（漢字）の payload も切り捨てや文字化けはありません。

QMTPUBEX の 2 段階：長さを数え切ると自動送出、Ctrl+Z 不要

AT+QMTPUBEX の末尾パラメータは長さ（バイト数）であって、メッセージ内容ではありません （MQTT アプリケーションノート §3.3.8 で決着 —— メッセージを詰め込む単一行の送り方は必ず ERROR になります）。 正しい流れは 2 段階です：コマンドを送る → モジュールがプロンプト > を返す → ちょうど N バイトを送る。 モジュールは長さを数え切ると自動的に送出し、Ctrl+Z は不要です （TCP ページの AT+QISEND のデータモードとは異なります）。 Publish を押せば全自動：パラメータカードにメッセージ内容を記入するだけで、 長さは UTF-8 のバイト数から自動計算されます（漢字 1 文字は 3 バイト。実測では「測試」→ 6）。

  • payload 型コマンドには「コマンドラインに入力」を提供していません —— コマンドラインからの送出は必ず行末が付き、 その CR が長さに数えられてずれるため、ボタンで送ってください。
  • ファームウェアには他に AT+QMTPUB（データモード変種、Ctrl+Z で締める）もありますが —— 本ツールは一律 QMTPUBEX を使います。2 通り覚える必要はありません。

結果コードの読み方：コマンドごとに値域が違う

A コマンドの結果コード表を B コマンドに当てはめないでください。 +QMTOPEN の 3 は「PDP 有効化失敗」ですが、 +QMTPUBEX にはそもそも 3 という値がありません。

最も読み違えやすいのは +QMTCONN: 0,1 —— これは照会応答の「状態 1＝初期化中」かもしれないし、書き込み結果の「パケット再送中」かもしれません。 1 行だけでは区別できないので、本ツールは両方の読み方を並記し、当て推量はしません。

表を暗記する必要はありません：+QMTOPEN から +QMTRECV／+QMTSTAT までの全結果 URC に、ターミナル領域が MQTT アプリケーションノート v1.5 の 7 枚の対照表に基づいて欄ごとに平易な注釈を付けます。

切断と後始末

  • 受信だけ止めて接続は残したい：Unsub を押します （AT+QMTUNS=0,2,"トピック"、msgid は 2 に固定）。
  • 正常切断：Disconnect を押します（AT+QMTDISC=0、 MQTT DISCONNECT を送出）。+QMTDISC: 0,0 が返ります。 その後 Close Net を押す必要はありません —— AT+QMTCLOSE=0 は「QMTDISC が失敗し、ネットワーク層が固まった」ときの強制クローズ用です。

自分で押していない切断（蹴られた、keepalive タイムアウト、ネットワーク断）は +QMTSTAT の異常切断 URC で報告されます（例：+QMTSTAT: 0,5。ターミナル領域が原因を注釈します）。 このときは AT+QMTOPEN からやり直しです。
