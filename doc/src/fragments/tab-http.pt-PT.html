HTTP —— pedidos web

Princípio de funcionamento: o HTTP do módulo é em três atos: primeiro define-se o URL (um passo que, por sua vez, é em duas fases), depois faz-se o pedido (GET/POST) e por fim lê-se a resposta. O resultado de cada ato não está no OK, mas no URC que chega depois —— por isso o AT+QURCCFG="urcport" tem de ser "uart1" (muda-se na página Hardware); senão, não se vê resultado nenhum. Todos os dados foram medidos no equipamento real em agosto de 2026.

Antes de começar: tenha primeiro o canal de dados

O pré-requisito é o PDP ativo e com IP (o AT+QIACT=1 da página TCP/IP). O grupo Connect desta página só tem verificações de leitura: AT+CPIN?/AT+CGATT?/AT+CGREG?/ AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = não atribuído), AT+QIGETERROR (⚠ só vale para o último comando TCP/IP; depois de uma falha, prima-o imediatamente).

O AT+QIACT? engana. Em teste apanhou-se uma deriva do PDP a meio: todos os pedidos falhavam, com timeout fixo de 30 segundos e erro 716, e o AT+QIACT? continuava a devolver um IP. Cruze com o AT+CGACT?: se não baterem certo, é deriva. Reparação: AT+QIDEACT=1 → AT+CGACT=0,<cid da deriva> → AT+QIACT=1, e só continue depois de um ping passar.

O primeiro GET: quatro passos

  1. Configuração prévia (grupo Config, zero tráfego): no cartão de parâmetros contextid ponha 1 (o PDP context a usar); os três interruptores rspout/auto, requestheader e responseheader ficam a 0 (a razão vem adiante); AT+QHTTPCFG? lê todas as definições de uma vez para conferir, e AT+QHTTPCFG=? lista os itens configuráveis.
  2. Definir o URL (duas fases): o cartão do AT+QHTTPURL só tem um botão «Enviar (duas fases)» —— você preenche o URL, o comprimento é calculado pelo programa. Fluxo: envia-se primeiro AT+QHTTPURL=<comprimento>,80, espera-se o CONNECT que entra no modo de dados, e mandam-se os bytes do URL tal e qual, sem nenhum fim de linha (um CR/LF entraria no comprimento). http://www.example.com/ tem exatamente comprimento 23. No fim, releia com AT+QHTTPURL?: igual letra a letra = não se infiltrou nenhum fim de linha.
  3. Fazer o pedido: AT+QHTTPGET=80 (segundos de espera pela resposta). O OK significa apenas «comando aceite»; o resultado a sério é o URC posterior +QHTTPGET: 0,200; a interpretação vem no parágrafo seguinte.
  4. Ler a resposta: AT+QHTTPREAD=80. Depois do CONNECT vêm só bytes em bruto (no example.com mediram-se 559 bytes), seguidos do OK —— mas a marca de fim é o +QHTTPREAD: 0 sozinho na última linha.

Interpretar o +QHTTPGET: a primeira coluna não é o código de estado HTTP

Os URC de resultado de GET/POST/POSTFILE têm três colunas, <err>,<httprspcode>,<content_length>: err 0 = o comando executou com sucesso; diferente de 0 é erro da camada do módulo (716, 711…); httprspcode é o código de estado HTTP, reportado apenas quando err=0 (o manual di-lo expressamente; a ferramenta traz anotações para 200/403/404/409/411/500); content_length é opcional —— só existe se o cabeçalho da resposta trouxer CONTENT-LENGTH, e um GET normal traz muitas vezes só duas colunas. Portanto o +QHTTPGET: 0,404,0 medido não é uma falha: o comando teve sucesso; foi o servidor que disse «não encontrado».

Ler a resposta: as armadilhas do AT+QHTTPREAD

O parâmetro é «o intervalo máximo, em segundos, entre dois pacotes de dados», não a duração total. O firmware desta unidade só aceita um parâmetro: a leitura por troços =<wait>,<read_len> da application note devolveu em teste um ERROR nu (comprovado pela sondagem com =?), e o botão foi removido —— para ler por troços use o GETEX.

Armadilha de interbloqueio: com rspout/auto a 1, os READ falham todos (o manual di-lo expressamente). Ele faz o módulo despejar a resposta sozinho, ao preço de aniquilar os READ; por isso esse botão tem caixa de confirmação. Se os READ caírem todos de repente, consulte primeiro AT+QHTTPCFG?.

Ler por troços: AT+QHTTPGETEX byte a byte

AT+QHTTPGETEX=<segundos>,<offset inicial>,<comprimento> usa o HTTP Range para apanhar só o troço indicado e poupar tráfego. Medido (endpoint com conteúdo fixo abcdefghijklmnop): offset 0, comprimento 8 devolve +QHTTPGET: 0,206,8 e lê-se abcdefgh; offset 8, mais 8, lê-se ijklmnop. Interpretação: o código de estado tem de ser 206; um 200 com o mesmo conteúdo de cada vez = o servidor não suporta Range, não é o módulo avariado. ⚠ Só executa com requestheader=0.

POST: duas fases e Content-Type

O cartão do AT+QHTTPPOST também é em duas fases: você preenche o body, o comprimento é calculado; envia-se primeiro AT+QHTTPPOST=<comprimento>,<segundos de entrada>,<segundos de resposta>, espera-se o CONNECT e manda-se o body. Três coisas:

  • O CONNECT pode demorar até 125 segundos (o manual di-lo expressamente) —— o timeout de espera do prompt tem de cobrir os 125 segundos; não herde os 5 segundos do MQTT.
  • Body até 1 MB (gama medida com =?: 1–1024000).
  • O Content-Type define-se antes, no cartão de parâmetros contenttype (código de tipo 0 = form-urlencoded).

Medido: POST de Message=HelloQuectel (20 bytes) devolveu +QHTTPPOST: 0,200,440; o JSON lido no READ confirma que o par chave-valor chegou, que o comprimento estava certo e que o Content-Type surtiu efeito; o User-Agent auto-reportado pelo módulo é QUECTEL_MODULE.

Cabeçalhos personalizados e cabeçalhos da resposta

  • reqheader/add: acrescenta um cabeçalho de pedido personalizado (o manual não traz exemplo); o botão de consulta mostra quantos já foram acrescentados; reqheader/remove remove.
  • requestheader a 1 = monta você mesmo o cabeçalho de pedido inteiro; até o GET passa a duas fases, e o GETEX deixa de funcionar. No dia a dia, mantenha 0.
  • responseheader a 1 faz o READ despejar também os cabeçalhos da resposta HTTP (em teste até um X-Test personalizado veio de volta). Terminado o teste, volte a 0.
  • closed/ind: liga o URC de aviso «a sessão foi fechada».

Versão com ficheiros: POSTFILE e READFILE (UFS)

AT+QHTTPPOSTFILE="ficheiro",<segundos> envia um POST usando como body um ficheiro do sistema de ficheiros do módulo (UFS); AT+QHTTPREADFILE="ficheiro",<segundos> guarda a resposta num ficheiro da UFS. ⚠ Esta ferramenta, por agora, não consegue carregar ficheiros para a UFS nem ler o conteúdo de ficheiros da UFS; estes dois comandos destinam-se a fluxos do lado do firmware.

HTTPS: o caminho sem verificação

HTTPS = HTTP + SSL context. O grupo Connect traz preparado o caminho mais curto; prima os cinco por ordem:

AT+QHTTPCFG="sslctxid",1           ← o HTTP passa a usar o SSL context 1
AT+QSSLCFG="sslversion",1,4        ← a versão TLS fica para o servidor negociar
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← conjuntos de cifras todos abertos
AT+QSSLCFG="seclevel",1,0          ← não verifica o certificado (ver abaixo)
AT+QSSLCFG="sni",1,1               ← liga o SNI (de fábrica é 0!)

Depois, troque o URL para começar por https:// e faça GET/READ como sempre —— em teste, o HTML lido foi letra a letra igual ao da versão em claro. O seclevel=0 (sem verificar certificados) é o único caminho que esta ferramenta percorre até ao fim —— para verificar certificados é preciso escrever antes o certificado CA na UFS; os detalhes de SSL (o AT+QSSLCFG=? lista todos os subitens, o negotiatetime ajusta a espera do handshake) estão na secção «SSL —— o túnel TLS». O SNI vem de fábrica a 0: sem o ligar, os sites HTTPS em IP partilhado entregam um certificado que não corresponde e a verificação falha logo. A cadeia de certificados é o grosso do tráfego: uma ronda de HTTPS GET ronda 8–15 KB, em claro fica-se por cerca de 1 KB.

Redirecionamentos e arrumação

Redirecionamentos (o manual não os descreve; esclarecido em teste): o módulo segue automaticamente os 302, mas só aceita Location com caminho absoluto —— um caminho relativo devolve logo o erro 711, falhando de imediato em 1 milissegundo. Arrumação: AT+QHTTPSTOP (grupo Close) cancela o pedido em curso e corta a sessão; com o estado esquisito, ou perante o erro 704 (modo de dados ocupado), prima-o primeiro para limpar tudo.
