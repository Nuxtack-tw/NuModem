TCP/IP —— รากของการเชื่อมต่อข้อมูล

หลักการทำงาน: หน้านี้คือรากฐานของโปรโตคอลข้อมูลทั้งหมด PDP context (ช่องทางข้อมูลที่เครือข่ายมือถือจัดสรรให้) เปิดใช้และปิดใช้ได้ที่หน้านี้เท่านั้น หน้า SSL / HTTP / MQTT / FTP มีแต่การถามค่าอย่างเดียว เพื่อกันไม่ให้คำสั่งเดียวกันสองที่เหยียบกันเอง กับดักและตัวเลขวินาทีในหัวข้อนี้ล้วนวัดจริงกับเครื่องจริงเมื่อเดือนสิงหาคม 2026

ขั้นแรก: เปิดใช้ PDP (QICSGP / QIACT / QIDEACT)

กด Act PDP (AT+QIACT=1): บล็อกได้นานสุด 150 วินาที ระหว่างนั้นอย่าส่งคำสั่งอื่น และจากจุดนี้เริ่มเกิดปริมาณข้อมูล (โรมมิ่งระวังค่าใช้จ่าย) สำเร็จแล้วต้องกด Query IP (AT+QIACT?) ยืนยันว่าตอบ +QIACT: 1,1,1,"ที่อยู่ IP" —— ก่อนเปิดใช้จะตอบแค่ OK จะวางสายกด Deact PDP (AT+QIDEACT=1, นานสุด 40 วินาที) ซึ่งจะบังคับปิดการเชื่อมต่อทั้งหมดที่อยู่ใต้มัน ส่วน Set APN (AT+QICSGP) ปกติไม่ต้องกด —— โมดูลจะซิงก์ APN ที่เครือข่ายจัดให้เองอัตโนมัติ (ทดสอบจริงซิม 1NCE บูตแล้วอ่านกลับมาเป็น iot.1nce.net อยู่แล้ว) จำเป็นเฉพาะ APN องค์กรที่ต้องใช้บัญชีรหัสผ่าน

Act PDP ตอบ ERROR, Last Error 572? ซิมใบนี้อนุญาต PDP แค่เส้นเดียว ตอนบูตเครือข่ายเปิดใช้ให้เองไปแล้วหนึ่งช่องและหมายเลขจะลอยไปมา (ทดสอบจริงเคยเจอ 9 กับ 1) แต่ AT+QIACT แตะได้แค่ 1–8 วิธีแก้: หน้า Network ใช้ AT+CGACT? ดูหมายเลข → AT+CGACT=0,<หมายเลข> สละโควตา → แล้วค่อยกด Act PDP

ทดสอบครึ่งทางแล้วพังหมด? AT+QIACT? หลอกคุณได้ —— ตอน PDP ลอย มันก็ยังตอบ IP ตามปกติ ต้องเทียบไขว้กับ AT+CGACT? ถึงจะมองออก การกู้คืน: Deact PDP → AT+CGACT=0,<หมายเลขที่ลอยไป> → Act PDP → Ping ยืนยัน

เปิดการเชื่อมต่อ: OK แปลว่าแค่ "รับคำสั่งไว้แล้ว"

กด Open TCP แล้วกรอกโฮสต์กับพอร์ตในการ์ดพารามิเตอร์ (AT+QIOPEN=1,0,"TCP","โฮสต์",พอร์ต,0,0; context 1, connectID 0, โหมด buffer ตั้งตายตัวไว้แล้ว) OK แปลว่าแค่รับคำสั่งไว้ สำเร็จหรือไม่ดูที่ URC +QIOPEN: 0,<err>: 0 = สำเร็จ นานสุด 150 วินาที; 563 = connectID ยังเปิดค้างอยู่ ให้กด Close Sock ก่อน All Socks (AT+QISTATE) แสดง socket ทั้งหมด state 2 = เชื่อมต่อแล้ว

ส่งข้อมูล: สามวิธี

ปุ่มคำอธิบาย
Send Text
AT+QISEND=0,<len>		 สองขั้นแบบความยาวตายตัว: รอ > แล้วค่อยส่งเนื้อหา ความยาวคำนวณอัตโนมัติ ไม่ต้องใช้ Ctrl+Z ตัวเลือกแรกสำหรับข้อความล้วน; เพดาน 1460 bytes, รองรับ escape \n \r \t \xHH
Send Var สามปุ่ม
AT+QISEND=0		 แบบความยาวไม่ตายตัว: เข้าโหมดข้อมูลแล้วรับไปเรื่อย ๆ เจอ Ctrl+Z (0x1A) ถึงส่งออก —— เขียนได้หลายรอบ ดูย่อหน้าถัดไป
Send Hex
AT+QISENDEX=0,"hex"		 แบบบรรทัดเดียว ไม่เข้าโหมดข้อมูล ส่งไบต์อะไรก็ได้ (รวม 0x00); hex เพดาน 512 ตัวอักษร = จริง 256 bytes

ส่ง (เขียนต่อ) กดครั้งแรกเข้าโหมดข้อมูล กดครั้งต่อไปเพิ่มต่อทีละท่อน (ถ้าอยู่ในโหมดข้อมูลอยู่แล้วจะไม่ส่งคำสั่งซ้ำ ส่งซ้ำจะกลายเป็นข้อมูล); ส่งแล้วจบอัตโนมัติ เพิ่มท่อนแล้วเติม Ctrl+Z ให้เลย ส่งท่อนเดียวใช้ตัวนี้เร็วสุด; จบ (Ctrl+Z) ส่งเนื้อหาที่สะสมไว้ ออกไปในครั้งเดียว ตอนอยู่ในโหมดข้อมูลเทอร์มินัลจะแสดงป้ายกำกับ; จะยกเลิกกด ESC Cancel (0x1B, ปุ่มหนีเมื่อคำสั่งสองขั้นค้าง) ⚠ ข้อมูลห้ามมี 0x1A (จะถูกตีความว่าจบก่อนกำหนด) ตัวอักษรควบคุมให้เปลี่ยนไปใช้ Send Hex

SEND OK ไม่ได้แปลว่าปลายทางได้รับ แค่บอกว่าข้อมูลถูกมอบให้โมดูลแล้ว กด Check ACK (AT+QISEND=0,0) เช็คส่งแล้ว / ACK แล้ว ดูตัวเลข acked เท่านั้นถึงจะนับ

รับข้อมูล: ไม่โผล่มาเอง ต้องกด Read Data

ในโหมด buffer ข้อมูลที่รับมาจะไม่ปรากฏในเทอร์มินัลเอง: โมดูลส่งแค่การแจ้ง +QIURC: "recv",0 ต้องกด Read Data (AT+QIRD=0,1500) ดึงออกมา และอ่านซ้ำจนกว่าจะตอบ +QIRD: 0 —— อ่านไม่เกลี้ยงจะไม่มีการแจ้งครั้งถัดไป Unread Len (AT+QIRD=0,0) ถามยอดรับรวม / อ่านแล้ว / ยังไม่อ่าน รับส่งเสร็จกด Close Sock (AT+QICLOSE=0, นานสุด 10 วินาที) ⚠ ไม่ได้รับการแจ้ง recv เลย? ไปหน้า Hardware เช็ค AT+QURCCFG="urcport" ว่าเป็น uart1 หรือไม่ —— ค่าโรงงานคือพอร์ต USB URC วิ่งไปที่นั่นหมด

นิสัยสองอย่างของ tcpbin.com ปลายทางในตัว

ปลายทางค่าเริ่มต้นของ Open TCP คือ echo server ฟรี tcpbin.com:4242 ทดสอบจริงพบนิสัยสองอย่าง:

  • echo ทีละบรรทัด ท้ายต้องมีขึ้นบรรทัดใหม่ (0A): ส่ง Hello โดยไม่มี 0A รอ 6 วินาที ไม่มีคำตอบ พอเติม 0A ก็ได้รับกลับใน 0.1 วินาทีทันที Send Text ให้ปิดท้ายด้วย \n, Send Hex ปิดท้ายด้วย 0A
  • หมดเวลาเมื่อว่างงาน 15 วินาที: ว่างงานก็ถูกตัดการเชื่อมต่อและได้รับ +QIURC: "closed",0 เรื่องนี้ไม่เกี่ยวกับ QIRD (มันอ่านแค่บัฟเฟอร์ในเครื่อง ไม่แตะเครือข่าย) จะรักษาการเชื่อมต่อต้องส่งข้อมูลภายในทุก 10 วินาที หลังได้รับ closed แล้ว socket ค้างที่ closing ต้องกด Close Sock ก่อนถึงจะใช้ซ้ำได้ ไม่งั้น QIOPEN ตอบ 563

Ping

พลาดแล้ว: กด Last Error ก่อน แล้วทำการจำแนก 30 วินาที

คำสั่งตอบ ERROR ให้กด Last Error ทันที (AT+QIGETERROR) —— มันเก็บแค่รายการสุดท้าย ถูกข้อผิดพลาดถัดไปทับก็หายไปเลย มันถามชั้นสแต็กของ Quectel; ชั้นเครือข่ายใช้ AT+CEER ของหน้า Network

🔴 สแต็กข้อมูลเสื่อมสภาพ —— หลุมที่เสียเวลาที่สุด อาการ: การเชื่อมต่อทั้งหมดล้มเหลว แต่การตรวจตัวเองบอกปกติหมด (QIACT? มี IP, QIGETERROR ตอบ 0) ทดสอบจริงเปิดปิด SSL ติดต่อกันราว 20 ครั้งแล้วถูกกระตุ้น ขนาด QIOPEN ของ TCP ล้วนยังตอบ 552; QIDEACT + QIACT ช่วยไม่ได้ มีแต่รันพิธีกรรมเปิดเครื่องใหม่เท่านั้นที่กู้คืนได้

วิธีจำแนก 30 วินาที: ใช้ Open TCP ยิงเป้าหมายเดียวกัน —— ล้มเหลวด้วย = สแต็กทั้งตัว พังแล้ว รันพิธีกรรมเปิดเครื่องใหม่; สำเร็จ = ปัญหาอยู่ที่โปรโตคอลชั้นบน ตรวจต่อ

Keepalive: กัน NAT ของผู้ให้บริการได้ แต่กัน tcpbin ไม่ได้

QICFG=? แสดงรายการย่อยกับช่วงค่า, Keepalive? ถามค่าปัจจุบัน, Keepalive On / Off เปิดปิด —— คำสั่งสี่ปุ่มนี้ตัวมันเองไม่กินปริมาณข้อมูล; เปิดใช้แล้วขอแค่มี socket ว่างงานค้างอยู่ แพ็กเก็ตตรวจสอบก็จะนับเข้าปริมาณข้อมูลมือถือ มันกันหมดเวลา 15 วินาทีของ tcpbin ไม่ได้: ทดสอบจริงเปิดแล้วก็ยังถูกปิดที่ 15.1 วินาที —— keepalive เป็นการตรวจสอบเปล่าในชั้น TCP แอปพลิเคชันมองไม่เห็น; แถม interval ต่ำสุด 25 วินาที ใหญ่กว่า 15 อยู่แล้วโดยกำเนิด จะสู้หมดเวลาชั้นแอปพลิเคชันได้มีแต่ส่งข้อมูลจริง (เช่นทุก 10 วินาทีใช้ Send Hex ส่ง 0A) ประโยชน์ตัวจริงของมันคือ keepalive สำหรับ NAT ของผู้ให้บริการ (ซิม IoT ว่างงานไม่กี่นาที NAT ก็ถูกเรียกคืน)

บัญชีปริมาณข้อมูล (ประมาณการ ไม่ใช่ค่าวัดจริง): การตรวจสอบไปกลับหนึ่งรอบราว 80 bytes; ค่าเริ่มต้น idle = 30 วินาที ว่างงานต่อเนื่อง → ราวชั่วโมงละ 9.4 KB, วันละราว 225 KB, เดือนละราว 6.8 MB; idle = 600 วินาที → วันละราว 11 KB ซิมพรีเพดแบบเหมาปริมาณอย่าง 1NCE ต้องปรับ idle ให้ใหญ่ขึ้น ไม่มี socket เปิดอยู่ก็ไม่กินปริมาณข้อมูลเลย
