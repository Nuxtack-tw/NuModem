HTTP — веб-запросы

Принцип работы: HTTP в модуле трёхэтапный: сначала задаётся URL (этот шаг сам по себе двухэтапный), затем отправляется запрос (GET / POST), и в конце читается ответ. Результат каждого этапа приходит не в OK, а в последующем URC — поэтому AT+QURCCFG="urcport" обязана быть "uart1" (меняется на странице Hardware), иначе не увидите ни одного результата. Все данные — замеры на реальной машине в августе 2026 года.

Прежде чем начать: сначала канал данных

Условие — PDP активирован и IP получен (AT+QIACT=1 на странице TCP/IP). Группа Connect на этой странице содержит только проверки на чтение: AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = не выдан), AT+QIGETERROR (⚠ действителен только для последней TCP/IP-команды; после провала нажимать немедленно).

AT+QIACT? обманывает. Замер поймал дрейф PDP на полпути: все запросы проваливаются, стабильный таймаут 30 секунд с ошибкой 716, а AT+QIACT? как ни в чём не бывало возвращает IP. Сверяйте с AT+CGACT?: расхождение = дрейф. Лечение: AT+QIDEACT=1 → AT+CGACT=0,<уплывший cid> → AT+QIACT=1, и продолжать только после успешного ping.

Первый GET: четыре шага

  1. Предварительная настройка (группа Config, без единого байта трафика): карточкой contextid задайте 1 (привязка к нужному PDP context); три выключателя rspout/auto, requestheader, responseheader держите в 0 (причины ниже); AT+QHTTPCFG? читает все настройки разом для сверки, AT+QHTTPCFG=? перечисляет доступные пункты.
  2. Задать URL (двухэтапно): у карточки AT+QHTTPURL одна кнопка «Отправить (двухэтапно)» — вы вписываете URL, длину программа считает сама. Порядок: сначала уходит AT+QHTTPURL=<длина>,80, по CONNECT — вход в режим данных, затем байты URL отправляются как есть, без какого-либо конца строки (CR/LF попали бы в счёт длины). Длина http://www.example.com/ — ровно 23. После отправки нажмите AT+QHTTPURL? и сверьте: совпало посимвольно = конец строки не подмешался.
  3. Отправить запрос: AT+QHTTPGET=80 (секунды ожидания ответа). OK означает лишь «команда принята»; настоящий результат — последующий URC +QHTTPGET: 0,200, чтение — в следующем абзаце.
  4. Прочитать ответ: AT+QHTTPREAD=80. После CONNECT идут сплошные сырые байты (замер example.com — 559 bytes), затем OK — но маркер конца — отдельная последняя строка +QHTTPREAD: 0.

Чтение +QHTTPGET: первое поле — не HTTP-статус

Результирующие URC у GET / POST / POSTFILE — три поля <err>,<httprspcode>,<content_length>: err 0 = команда выполнена успешно, не ноль — ошибка уровня модуля (716, 711…); httprspcode — HTTP-статус, сообщается только при err=0 (прямо сказано в руководстве; инструмент содержит поясняющие сопоставления для 200 / 403 / 404 / 409 / 411 / 500); content_length необязателен — есть лишь когда в заголовках ответа сервера был CONTENT-LENGTH, обычный GET часто приходит с двумя полями. Поэтому замеренный +QHTTPGET: 0,404,0 — не провал: команда удалась, это сервер сказал «не найдено».

Чтение ответа: ловушки AT+QHTTPREAD

Параметр — «максимальный промежуток в секундах между двумя пакетами данных», а не общая длительность. Прошивка этой машины принимает только один параметр: описанное в прикладном документе чтение частями =<wait>,<read_len> по замеру возвращает голый ERROR (подтверждено зондированием =?), кнопка удалена — для выборки частями используйте GETEX.

Ловушка взаимной блокировки: стоит поставить rspout/auto в 1 — всё семейство READ проваливается (прямо сказано в руководстве). Он заставляет модуль выплёвывать ответ сам, ценой гибели всех READ, поэтому у этой кнопки есть диалог подтверждения. READ внезапно умерли все — первым делом смотрите AT+QHTTPCFG?.

Выборка частями: AT+QHTTPGETEX читает по байтам

AT+QHTTPGETEX=<сек>,<начальное смещение>,<длина> через HTTP Range забирает только указанный фрагмент и экономит трафик. Замер (содержимое конечной точки зафиксировано как abcdefghijklmnop): смещение 0, взять 8 — ответ +QHTTPGET: 0,206,8, прочитано abcdefgh; смещение 8, ещё 8 — прочитано ijklmnop. Чтение: статус обязан быть 206; ответ 200 с одинаковым содержимым каждый раз = сервер не поддерживает Range, а не модуль сломался. ⚠ Выполняется только при requestheader=0.

POST: двухэтапность и Content-Type

Карточка AT+QHTTPPOST тоже двухэтапная: вы вписываете body, длина считается сама; сначала уходит AT+QHTTPPOST=<длина>,<сек ввода>,<сек ответа>, по CONNECT отправляется body. Три вещи:

  • CONNECT может заставить ждать до 125 секунд (прямо сказано в руководстве) — таймаут ожидания подсказки ставьте полные 125 секунд, не тащите 5 секунд из MQTT.
  • Предел body — 1 MB (замер =?: диапазон 1–1024000).
  • Content-Type заранее задаётся карточкой contenttype (код типа 0 = form-urlencoded).

Замер: POST Message=HelloQuectel (20 bytes) вернул +QHTTPPOST: 0,200,440; JSON из READ подтверждает: пара ключ-значение дошла, длина посчитана верно, Content-Type сработал, User-Agent модуль сообщает как QUECTEL_MODULE.

Собственные заголовки и заголовки ответа

  • reqheader/add: добавить одну собственную строку заголовка запроса (в руководстве примера нет); кнопка запроса показывает, сколько уже добавлено; reqheader/remove убирает.
  • requestheader в 1 = весь заголовок запроса собираете сами, даже GET становится двухэтапным, и GETEX недоступен. В обычной жизни держите 0.
  • При responseheader в 1 READ выдаёт и HTTP-заголовки ответа (замер: возвращается даже собственный X-Test). После теста верните 0.
  • closed/ind: включает URC-оповещение «session закрыта».

Файловые варианты: POSTFILE и READFILE (UFS)

AT+QHTTPPOSTFILE="имяфайла",<сек> отправляет POST, используя как body файл из файловой системы модуля (UFS); AT+QHTTPREADFILE="имяфайла",<сек> сохраняет ответ файлом в UFS. ⚠ Этот инструмент сейчас не умеет ни загрузить файл в UFS, ни прочитать содержимое UFS-файла обратно — эти две команды для связки с процессами на стороне прошивки.

HTTPS: путь без проверки

HTTPS = HTTP + SSL context. В группе Connect подготовлен кратчайший путь — пять кнопок по порядку:

AT+QHTTPCFG="sslctxid",1           ← HTTP использует SSL context 1
AT+QSSLCFG="sslversion",1,4        ← версию TLS согласует сервер
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← все наборы шифров открыты
AT+QSSLCFG="seclevel",1,0          ← сертификат не проверяется (см. ниже)
AT+QSSLCFG="sni",1,1               ← включить SNI (с завода 0!)

Дальше меняете URL на начинающийся с https:// и делаете GET / READ как обычно — по замеру прочитанный HTML посимвольно совпадает с открытой версией. seclevel=0 (без проверки сертификата) — единственный путь, который инструмент проходит до конца — для проверки сертификата нужно сначала записать CA-сертификат в UFS; детали SSL (AT+QSSLCFG=? перечисляет все подпункты, negotiatetime настраивает секунды ожидания рукопожатия) — в разделе «SSL — канал TLS». SNI с завода 0: не включите — HTTPS-сайты на разделяемом IP получат несоответствующий сертификат и провалят проверку с ходу. Цепочка сертификатов — главный поглотитель трафика: круг HTTPS GET — около 8–15 KB, открытым текстом — лишь около 1 KB.

Перенаправления и завершение

Перенаправления (в руководстве не описаны, выяснено замером): модуль сам следует за 302, но принимает только абсолютный путь в Location — относительный путь сразу даёт ошибку 711, провал за 1 миллисекунду. Завершение: AT+QHTTPSTOP (группа Close) отменяет текущий запрос и разрывает session; когда состояние подозрительное или выскочила ошибка 704 (режим данных занят) — сначала нажмите её и приберитесь.
