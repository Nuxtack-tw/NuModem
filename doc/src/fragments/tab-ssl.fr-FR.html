SSL — le tunnel TLS

Principe de fonctionnement : la page SSL est le socle partagé des connexions chiffrées — le contexte SSL réglé ici et les certificats téléversés servent à la fois au socket SSL brut, à MQTT over SSL et à HTTPS. Toutes les durées et tous les comportements de cette section sont des valeurs mesurées en août 2026 sur un EG800K réel.

Première connexion TLS : cinq étapes

  1. Exécuter le rituel de démarrage (voir la section « Rituel de démarrage »), puis appuyer sur AT+QIACT? pour vérifier le canal de données — il faut obtenir +QIACT: 1,1,…,"IP" ; sinon, d'abord AT+QIACT=1.
  2. Régler le contexte : sslversion à 4 (toutes versions, compatibilité maximale), ciphersuite à 0XFFFF (toutes les suites), seclevel à 0 pour commencer — validez d'abord que le tunnel passe, la vérification viendra ensuite.
  3. Ouvrir la connexion : appuyez sur AT+QSSLOPEN (dernier chiffre 0), remplissez hôte et port dans la carte de paramètres. ⚠ OK signifie seulement « commande acceptée » ; le verdict est dans l'URC : +QSSLOPEN: 4,0 seul signe le succès (poignée de main mesurée à 2.0 secondes).
  4. Envoyer des données : appuyez sur AT+QSSLSEND (en deux temps) — après le >, envoyez le corps ; expédié automatiquement dès que la longueur annoncée est atteinte, sans Ctrl+Z (limite de 1460 bytes par paquet). La réponse du pair arrive en +QSSLURC: "recv",4.
  5. Relire et fermer : AT+QSSLRECV (limite de 1500 par lecture) ; obtenir +QSSLRECV: 0 signifie que tout est vidé, pas une erreur. AT+QSSLCLOSE=4 ferme (attente par défaut de 10 secondes maximum ; un autre bouton accepte un délai en secondes, 0 = immédiat).
AT+QSSLOPEN=1,1,4,"tcpbin.com",4243,0
OK
+QSSLOPEN: 4,0            ← 2.0 secondes, 0 = succès
AT+QSSLSEND=4,15
>
NuModem-P5-SSL            ← envoi automatique aux 15 bytes atteints
SEND OK
+QSSLURC: "recv",4        ← 0.4 seconde
AT+QSSLRECV=4,1500
+QSSLRECV: 15
NuModem-P5-SSL
AT+QSSLCLOSE=4

Pendant la connexion, AT+QSSLSTATE montre toutes les connexions (=4 pour un seul clientID, état 2 = connecté). Notez que le port local répond toujours 0 — comportement du module, pas une erreur.

Les trois modes d'accès (dernier chiffre d'AT+QSSLOPEN)

Dernier chiffreComportement

Réglages du contexte, un par un

En cas de doute sur les sous-réglages supportés par le firmware, commencez par AT+QSSLCFG=? — mesuré : 17 sous-réglages, plus que la liste du manuel d'application. Les plus courants ont chacun un bouton d'écriture et un de lecture ; mesuré : la relecture après écriture est parfaitement identique.

Sous-réglageUsineRôle et points mesurés
sslversion—Version du protocole ; 4 = toutes supportées
ciphersuite—Suites de chiffrement ; 0XFFFF = toutes supportées
seclevel00 = pas de vérification, 1 = vérification du serveur (certificat CA à téléverser d'abord), 2 = authentification mutuelle (certificat client + clé privée en plus)
cacert—Chemin du certificat CA, au format "UFS:nomdefichier" ; le fichier doit déjà être en UFS (voir la section suivante)
sni🔴 0 Indispensable pour les hôtes virtuels / CDN — quand plusieurs domaines partagent une IP, sans SNI on reçoit un certificat qui ne correspond pas, et la vérification échoue à coup sûr en 566
ignorelocaltime🔴 1 En sortie d'usine, même avec seclevel 1, la validité temporelle du certificat n'est pas contrôlée. Pour la contrôler, mettez 0 — et l'horloge du module doit être juste
negotiatetime300 Attente maximale de la poignée de main TLS en secondes (10–300)
🔴 Les trois valeurs d'usine combinées = aucune vérification de certificat (seclevel 0, sni 0, ignorelocaltime 1) : pour vérifier vraiment, il faut régler les trois correctement. Et ces trois réglages ainsi que cacert ne survivent pas au redémarrage (confirmé par mesure) : retour aux valeurs d'usine à chaque démarrage ; les fichiers de certificats en UFS, eux, résistent à la coupure.

Le groupe de fichiers UFS : comment les certificats entrent dans le module

L'UFS est le stockage flash intégré du module : capacité totale mesurée de 280 KB, chaque fichier occupant un bloc de 4 KB. Les certificats doivent d'abord être téléversés ici pour que cacert ait un fichier à pointer. Le téléversement passe par l'UART, zéro trafic de données, et les fichiers binaires passent aussi. Carte Upload : après le choix du fichier, nom et taille se remplissent seuls ; à l'envoi, l'outil attend le CONNECT du module avant d'expédier les octets bruts (sans lui, rien ne part). À la fin, le moteur d'annotation compare automatiquement la taille et le checksum rapportés par le module : ✅ = intact, ❌ = transfert corrompu, supprimez puis retéléversez.

AT+QFUPL="badssl-root.pem",1939,10
CONNECT                   ← envoyer ensuite 1939 bytes
+QFUPL: 1939,4f64         ← taille reçue,checksum ; l'annotation compare automatiquement ✅
BoutonUsage
AT+QFLSTListe tous les fichiers de l'UFS et leurs tailles — à utiliser après chaque téléversement pour vérifier (zéro trafic)
AT+QFLDS="UFS"Interroge l'espace restant / total en bytes (zéro trafic)
AT+QFDELSupprime le fichier indiqué (* = tous) ; un retéléversement sans suppression préalable du fichier homonyme est refusé
Deux comportements mesurés que le manuel tait : (1) la forme des codes d'erreur FILE est incohérente — retéléverser un homonyme répond le texte file already exist, un timeout répond le nombre 421 ; cet outil interprète les deux ; (2) avec une taille déclarée supérieure au réel, le module, après timeout, enregistre quand même ce qu'il a reçu — la comparaison de checksum l'attrape.

Vérification de certificats en pratique : la méthode du test par paires

Procédure : téléverser le certificat racine → pointer cacert dessus → seclevel 1 → sni 1 → se connecter au 443 de la cible. C'est le certificat racine au sommet de la chaîne qu'il faut téléverser (la chaîne de badssl.com a quatre niveaux : téléversez l'ISRG Root X1 tout en haut). Tester seulement « le mauvais certificat est refusé » ne suffit pas — « tout est refusé » passerait aussi. Il faut tester par paires : le bon certificat passe, le mauvais est refusé, et seuls les deux sens réunis comptent. Contrôle croisé 2×5 mesuré :

Hôteseclevel 0seclevel 1
badssl.com (contrôle positif)Passe Passe 4,0
expired (expiré)PasseRefusé 566
self-signed (auto-signé)PasseRefusé 566
wrong.host (nom d'hôte discordant)PasseRefusé 566
untrusted-root (racine non fiable)PasseRefusé 566

Limite : les quatre erreurs de certificat répondent toutes 566, le module ne distingue pas laquelle. AT+QIGETERROR n'aide pas non plus — il couvre la couche TCP/IP et ne répond ici que 0,operate successfully.

Pour un test négatif isolé, évitez expired — ignorelocaltime vaut 1 en usine, l'expiration seule n'est pas bloquée (elle l'est dans le tableau parce que le site n'est pas non plus sous la racine téléversée) ; prenez wrong.host. Et surveillez le trafic : chaque poignée de main télécharge la chaîne complète, échec compris — mesuré : 30 poignées de main pour environ 150–200 KB.

🔴 Piège : après environ 20 cycles d'ouverture-fermeture, la pile de données se dégrade entièrement

Symptôme : tous les AT+QSSLOPEN répondent 552, même en seclevel 0 rien ne passe, et chaque autodiagnostic dit que tout va bien. Discriminant en 30 secondes : visez la même cible en TCP pur avec AT+QIOPEN — échec aussi = la pile de données est morte, cessez d'inspecter les réglages SSL. Redémarrer le PDP n'y peut rien, seul le rituel de démarrage complet restaure l'état. La dégradation contamine les données de test et se fait facilement passer pour « bloqué par la vérification de certificat » — avant un test par paires, redémarrez pour repartir propre.
