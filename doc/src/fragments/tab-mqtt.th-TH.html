MQTT —— การส่งข้อความ IoT

หลักการทำงาน: MQTT เป็นโปรโตคอลแบบ "broker (เซิร์ฟเวอร์ตัวกลางรับส่งข้อความ)": อุปกรณ์ไม่เชื่อมต่อกันตรง ๆ แต่ต่างฝ่ายต่างต่อเข้า broker แล้ว publish หรือ subscribe ข้อความบน "หัวข้อ (topic)" บน EG800K มันเป็นสองชั้น: ใช้ AT+QMTOPEN เปิด "การเชื่อมต่อเครือข่าย" ก่อน (TCP ต่อไปยัง broker) แล้วใช้ AT+QMTCONN ทำ "การล็อกอิน MQTT" สองชั้นผ่านหมดถึงจะ subscribe กับ publish ได้ จำไว้ก่อนเลย: ผลลัพธ์ของคำสั่ง MQTT เป็นแบบ "OK ก่อน แล้ว URC ตามมา" ทั้งหมด (เหมือน FTP) —— OK แปลว่าแค่รับคำสั่งไว้ สำเร็จหรือไม่ดูที่ URC ผลลัพธ์ที่ตามมา

หน้านี้ใช้ client 0 ตายตัว; เฟิร์มแวร์ยังรองรับหลาย client (0–5), SSL และการยืนยันตัวตนกับแพลตฟอร์มคลาวด์ (ยืนยันด้วย =? จากการทดสอบจริงแล้ว) การใช้งานขั้นสูงดู application note ของ MQTT

ก่อนเริ่ม: เงื่อนไขเบื้องต้นสองข้อ

  1. URC ต้องเดิน UART: AT+QURCCFG="urcport" ต้องตอบ "uart1" ค่าโรงงานคือ "usbat" ขณะที่ผลลัพธ์ MQTT เป็น URC ทั้งหมด —— ไม่แก้ ทุกคำสั่งจะตอบแค่ OK แล้วเงียบหาย (หน้า Basic มีปุ่ม; เขียนลง NVRAM แก้ครั้งเดียวพอ)
  2. PDP ต้องเปิดใช้ก่อน: ไปหน้า TCP/IP กด AT+QIACT=1 ก่อน (นานสุด 150 วินาที); ไม่เปิด +QMTOPEN จะตอบ 3 = เปิดใช้ PDP ล้มเหลว ตลอดกระบวนการเกิดปริมาณข้อมูล ประมาณราว 5 KB

จะทดสอบอย่างไร: broker สาธารณะฟรีสี่เจ้า

ทั้งสี่เจ้าเปิดสาธารณะเต็มที่: ใครก็ subscribe หัวข้อของคุณได้ และข้อความของคนอื่นก็อาจปนเข้ามา —— นี่แหละคือปัญหาที่ส่วนท้ายสุ่มมีไว้แก้

ส่วนท้ายสุ่มของ client ID กับหัวข้อ: รีเฟรชทีไรเปลี่ยนชุดใหม่

client ID กับหัวข้อค่าเริ่มต้นไม่ได้เขียนตายตัว: ตอนโหลดหน้าเว็บจะสุ่มส่วนท้ายเลขฐานสิบหก 6 ตัวอักษรอัตโนมัติ ประกอบเป็น numodem-<ส่วนท้าย> กับ test/numodem-<ส่วนท้าย> ปุ่ม Subscribe / Publish / Unsub สามปุ่มใช้ชุดเดียวกันร่วมกัน (ไม่งั้นลูปสะท้อนกลับตัวเองจะจับคู่ไม่ติด) เหตุผลมีสองข้อ:

  • ชื่อชนกันจะถูกเตะหลุด: MQTT 3.1.1 §3.1.4 กำหนดให้ broker เตะตัวที่ต่ออยู่ก่อน ให้หลุดออกไป —— สองคนใช้ ID ตายตัวเดียวกันก็จะเตะกันไปมา อาการดูเหมือน "โมดูลหลุดการเชื่อมต่อแบบงง ๆ"
  • หัวข้อตายตัวจะได้รับข้อความของคนอื่น: คุณนึกว่าที่รับมาคือของที่ตัวเองส่ง แต่จริง ๆ ไม่ใช่ —— แบบนี้แย่กว่ารับไม่ได้ เพราะมันให้ผลผ่านแบบปลอม
⚠ ทุกครั้งที่รีเฟรชหน้าเว็บ ส่วนท้ายจะเปลี่ยนชุดใหม่ —— subscribe กับ publish ต้องทำให้จบภายในวงจรชีวิตหน้าเว็บครั้งเดียวกัน อีกอย่างเครื่องมือนี้ RTS = ไฟเลี้ยง โหลดหน้าใหม่ = โมดูลไฟดับ การเชื่อมต่อ MQTT หายทั้งยวง ต้องเริ่มใหม่ตั้งแต่พิธีกรรมเปิดเครื่องและ AT+QMTOPEN

เส้นทางฉบับเต็ม: เชื่อมต่อ → subscribe → publish → รับข้อความตัวเองกลับมา

การพิสูจน์ที่น่าเชื่อที่สุดคือลูปสะท้อนกลับตัวเอง: subscribe แล้ว publish ไปหัวข้อเดียวกัน รับข้อความของตัวเองกลับมาเอง ตรวจครบทั้งสายรับส่งในรอบเดียว แต่ละขั้นรอ URC ผลลัพธ์ก่อนแล้วค่อยไปต่อ:

  1. ตั้งเวอร์ชันโปรโตคอล: กด Ver 3.1.1 (AT+QMTCFG="version",0,4; 3 = 3.1, 4 = 3.1.1) กด Version? ดูค่าปัจจุบันได้ (ไม่ใส่ค่า = ถาม) การ์ดพารามิเตอร์ Keepalive ปรับช่วง keepalive ได้ ไม่ปรับก็ทดสอบได้
  2. เปิดเครือข่าย: กด Open Net (AT+QMTOPEN=0,"broker",1883) ตอบ OK ก่อน สำเร็จหรือไม่ดู URC +QMTOPEN: 0,<result> (0 = สำเร็จ) รอนานสุด 120 วินาที กด Open? ดูการเชื่อมต่อที่เปิดอยู่ได้ (ไม่มีการเชื่อมต่อตอบ OK เปล่า ๆ ทดสอบจริงเป็นเรื่องปกติ)
  3. ล็อกอิน MQTT: กด Connect (AT+QMTCONN=0,"numodem-<ส่วนท้าย>") URC สำเร็จตายตัวคือ +QMTCONN: 0,0,0 broker สาธารณะไม่ต้องใช้บัญชีรหัสผ่าน; ถ้าต้องใช้ให้เติม ,"user","pass" ท้ายพารามิเตอร์เอง กด Conn? ดูสถานะ (1 = เริ่มต้น, 2 = กำลังเชื่อมต่อ, 3 = เชื่อมต่อแล้ว, 4 = กำลังตัดการเชื่อมต่อ)
  4. subscribe: กด Subscribe (AT+QMTSUB=0,1,"test/numodem-<ส่วนท้าย>",0, msgid ตายตัว 1) URC สำเร็จหน้าตาแบบ +QMTSUB: 0,1,0,0 จากนั้นข้อความของหัวข้อนี้จะเข้ามาเป็น URC +QMTRECV ทั้งหมด
  5. publish: กด Publish (AT+QMTPUBEX, แบบสองขั้น ดูย่อหน้าถัดไป) URC สำเร็จคือ +QMTPUBEX: 0,<msgid>,0
  6. รับกลับมา: เป้าหมายที่ publish คือหัวข้อที่ subscribe อยู่พอดี ถัดมาติด ๆ จะเห็น +QMTRECV พ่วงหัวข้อกับเนื้อหาข้อความเมื่อกี้มาด้วย —— ลูปสะท้อนกลับตัวเองสำเร็จ payload อักษรหลายไบต์ (เช่นอักษรจีน) ก็ไม่ถูกตัดทอน ไม่เพี้ยน

QMTPUBEX แบบสองขั้น: นับครบความยาวส่งเองอัตโนมัติ ไม่ต้องใช้ Ctrl+Z

พารามิเตอร์ตัวท้ายของ AT+QMTPUBEX คือความยาว (จำนวนไบต์) ไม่ใช่เนื้อหาข้อความ (application note ของ MQTT §3.3.8 ปิดคดี —— วิธีส่งบรรทัดเดียวแบบยัดข้อความจะตอบ ERROR แน่นอน) ขั้นตอนที่ถูกคือแบบสองขั้น: ส่งคำสั่ง → โมดูลตอบพรอมต์ > → ส่งให้ครบ N ไบต์พอดี โมดูลนับครบความยาวก็ส่งออกเองอัตโนมัติ ไม่ต้องใช้ Ctrl+Z (ต่างจากโหมดข้อมูลของ AT+QISEND ในหน้า TCP) กด Publish แล้วอัตโนมัติทั้งหมด: แค่กรอกเนื้อหาข้อความในการ์ดพารามิเตอร์ ความยาวคำนวณจากจำนวนไบต์ UTF-8 ให้เอง (อักษร CJK ตัวละ 3 ไบต์ ทดสอบจริงคำภาษาจีนสองตัวอักษร → 6)

  • คำสั่งประเภทมี payload ไม่มีตัวเลือก "ใส่ในบรรทัดคำสั่ง" —— การส่งจากบรรทัดคำสั่งจะเติมท้ายบรรทัดเสมอ CR ตัวนั้นจะถูกนับเข้าความยาวแล้วเหลื่อม ให้ส่งด้วยปุ่ม
  • เฟิร์มแวร์ยังมี AT+QMTPUB (ตัวแปรแบบโหมดข้อมูล ต้องปิดท้ายด้วย Ctrl+Z) —— เครื่องมือนี้ใช้ QMTPUBEX ทั้งหมด ไม่ต้องเรียนสองชุด

การตีความรหัสผลลัพธ์: แต่ละคำสั่งมีช่วงค่าไม่เหมือนกัน

อย่าเอาตารางรหัสผลลัพธ์ของคำสั่ง A ไปครอบคำสั่ง B 3 ของ +QMTOPEN คือ "เปิดใช้ PDP ล้มเหลว" แต่ +QMTPUBEX ไม่มีค่า 3 อยู่เลยด้วยซ้ำ

ตัวที่อ่านผิดง่ายที่สุดคือ +QMTCONN: 0,1 —— มันอาจเป็นคำตอบของการถามที่แปลว่า "สถานะ 1 = กำลังเริ่มต้น" หรือเป็นผลของการเขียนที่แปลว่า "กำลังส่งแพ็กเก็ตซ้ำ" ก็ได้ ดูบรรทัดเดียวแยกไม่ออก เครื่องมือนี้จึงแสดงการอ่านทั้งสองแบบคู่กัน ไม่เดามั่ว

คุณไม่ต้องท่องตาราง: URC ผลลัพธ์ทั้งหมดตั้งแต่ +QMTOPEN ถึง +QMTRECV / +QMTSTAT พื้นที่เทอร์มินัลจะใส่คำอธิบายภาษาคนตามตารางเทียบทั้งเจ็ดของ application note MQTT v1.5 ให้ทีละช่อง

ออฟไลน์กับการปิดงาน

  • แค่อยากหยุดรับข้อความ แต่คงการเชื่อมต่อไว้: กด Unsub (AT+QMTUNS=0,2,"หัวข้อ", msgid ตายตัว 2)
  • ออฟไลน์แบบปกติ: กด Disconnect (AT+QMTDISC=0, ส่ง MQTT DISCONNECT) ตอบ +QMTDISC: 0,0 หลังจากนั้นไม่ต้องกด Close Net อีก —— AT+QMTCLOSE=0 มีไว้บังคับปิดตอน "QMTDISC ล้มเหลว ชั้นเครือข่ายค้าง" เท่านั้น

การหลุดที่ไม่ได้เกิดจากคุณกด (ถูกเตะ, keepalive หมดเวลา, เน็ตขาด) จะถูกรายงานด้วย URC หลุดผิดปกติ +QMTSTAT (เช่น +QMTSTAT: 0,5 พื้นที่เทอร์มินัลจะอธิบายสาเหตุให้) ตอนนั้นต้องเริ่มใหม่จาก AT+QMTOPEN
