TCP/IP —— a raiz das ligações de dados

Princípio de funcionamento: esta página é o alicerce de todos os protocolos de dados. O PDP context (o canal de dados atribuído pela rede móvel) só é ativado e desativado nesta página; as páginas SSL/HTTP/MQTT/FTP têm apenas consultas só de leitura, para evitar que o mesmo comando em dois sítios se pise mutuamente. Todas as armadilhas e segundos desta secção foram medidos em agosto de 2026 no equipamento real.

Primeiro passo: ativar o PDP (QICSGP/QIACT/QIDEACT)

Prima Act PDP (AT+QIACT=1): bloqueia até 150 segundos, não envie outros comandos entretanto, e a partir daqui começa a gerar-se tráfego (em roaming, atenção aos custos). Depois do sucesso, prima obrigatoriamente Query IP (AT+QIACT?) e confirme que devolve +QIACT: 1,1,1,"endereço IP" —— antes da ativação responde apenas OK. Para desligar, prima Deact PDP (AT+QIDEACT=1, até 40 segundos), que força o fecho de todas as ligações por baixo dele. O Set APN (AT+QICSGP) normalmente não é preciso —— o módulo sincroniza sozinho o APN atribuído pela rede (em teste, o cartão 1NCE já lia iot.1nce.net logo após o arranque); só é necessário com APN empresarial com utilizador e password.

Act PDP responde ERROR e o Last Error dá 572? Este cartão só permite um PDP. No arranque a rede já ativou um automaticamente e o número flutua (em teste viram-se 9 e 1); o AT+QIACT só alcança 1–8. Solução: na página Network, AT+CGACT? para ver o número → AT+CGACT=0,<número> para libertar a vaga → prima Act PDP de novo.

A meio dos testes cai tudo? O AT+QIACT? engana —— com o PDP em deriva ele continua a devolver um IP; só cruzando com o AT+CGACT? é que se vê. Recuperação: Deact PDP → AT+CGACT=0,<número da deriva> → Act PDP → validar com Ping.

Abrir uma ligação: OK significa apenas «comando aceite»

Prima Open TCP e preencha no cartão de parâmetros o host e a porta (AT+QIOPEN=1,0,"TCP","host",porta,0,0; context 1, connectID 0 e modo buffer já fixados). O OK significa apenas que o comando foi aceite; o êxito ou a falha vêm no URC +QIOPEN: 0,<err>: 0 = sucesso, até 150 segundos; 563 = o connectID ainda está aberto: prima primeiro Close Sock. All Socks (AT+QISTATE) lista todos os sockets; state 2 = ligado.

Enviar dados: três maneiras

BotãoDescrição
Send Text
AT+QISEND=0,<len>		 Duas fases de comprimento fixo: espera o > e envia o conteúdo; o comprimento é calculado automaticamente e dispensa o Ctrl+Z. A primeira escolha para texto puro; limite de 1460 bytes, com escapes \n \r \t \xHH
Os três botões Send Var
AT+QISEND=0		 Comprimento variável: entra no modo de dados e vai recebendo até ver um Ctrl+Z (0x1A), e só então envia —— pode escrever-se em várias vezes, ver o parágrafo seguinte
Send Hex
AT+QISENDEX=0,"hex"		 De linha única, sem entrar no modo de dados. Envia bytes arbitrários (incluindo 0x00); limite de 512 caracteres hex = 256 bytes reais

Enviar (continuar a escrever): a primeira pressão entra no modo de dados e cada pressão seguinte acrescenta um troço (já no modo de dados o comando não é reenviado —— reenviá-lo tornar-se-ia dados); Enviar e terminar automaticamente acrescenta e remata com Ctrl+Z, o mais rápido quando só há um troço; Terminar (Ctrl+Z) despacha de uma vez o conteúdo acumulado. Enquanto está no modo de dados o terminal assinala-o; para desistir prima ESC Cancel (0x1B, a tecla de fuga quando as duas fases encravam). ⚠ Os dados não podem conter 0x1A (seria tomado por um fim antecipado); para caracteres de controlo use o Send Hex.

SEND OK não significa que o outro lado recebeu; significa apenas que os dados foram entregues ao módulo. Prima Check ACK (AT+QISEND=0,0) para ver enviados/ACK recebidos: só o acked conta.

Receber dados: não aparecem sozinhos, é preciso premir Read Data

No modo buffer, os dados recebidos não aparecem automaticamente no terminal: o módulo emite apenas o aviso +QIURC: "recv",0, e há que os extrair com Read Data (AT+QIRD=0,1500), repetindo a leitura até vir +QIRD: 0 —— sem esvaziar tudo, não haverá próximo aviso. Unread Len (AT+QIRD=0,0) consulta total recebido/lido/por ler. Terminadas as trocas, prima Close Sock (AT+QICLOSE=0, até 10 segundos). ⚠ Não chega nenhum aviso recv? Na página Hardware, confira se AT+QURCCFG="urcport" está em uart1 —— o valor de fábrica é a porta USB, e os URC vão todos para lá.

Os dois feitios do interlocutor incorporado tcpbin.com

O destino por omissão do Open TCP é o servidor echo gratuito tcpbin.com:4242, com dois feitios medidos:

  • Echo linha a linha, com quebra de linha (0A) no fim: enviado Hello sem 0A, 6 segundos sem resposta; acrescentado o 0A, resposta imediata em 0,1 segundos. No Send Text termine com \n, no Send Hex acabe com 0A.
  • Timeout de inatividade de 15 segundos: em inatividade, a ligação é cortada e chega +QIURC: "closed",0. Nada tem a ver com o QIRD (que só lê o buffer local, sem tocar na rede). Para manter a ligação, envie dados em intervalos de menos de 10 segundos. Depois do closed, o socket fica em closing: é obrigatório premir primeiro Close Sock antes de o reutilizar, senão o QIOPEN devolve 563.

O trio de diagnóstico: Ping/DNS Lookup/NTP Sync

Botão (todos exigem Act PDP primeiro)Comportamento e medições
Ping
AT+QPING		 Timeout de 4 segundos ×4, já fixado. Medido em 8.8.8.8: tudo a passar, RTT 160–270 ms. ⚠ Muitos servidores bloqueiam ICMP: o ping falhar não significa que o TCP não ligue; para conectividade, vá direto ao Open TCP
DNS Lookup
AT+QIDNSGIP		 O resultado vem no URC +QIURC: "dnsgip" (até 60 segundos); em teste veio em duas partes e com vários IP
NTP Sync
AT+QNTP		 Até 125 segundos, porta 123 já fixada; o resultado vem no URC +QNTP. ⚠ A hora é UTC mas traz a marca do fuso local (+32 quartos = GMT+8; a diferença medida foi exatamente 8 horas); para a hora local use AT+CCLK?

Deu erro: prima primeiro Last Error, e faça depois a triagem de 30 segundos

Perante um ERROR, prima imediatamente Last Error (AT+QIGETERROR) —— só o último erro fica guardado; coberto pelo seguinte, deixa de se poder consultar. Ele consulta a camada da pilha Quectel; para a camada de rede use o AT+CEER da página Network.

🔴 Degradação da pilha de dados —— o buraco que mais tempo custa. Sintoma: todas as ligações falham, mas os autodiagnósticos dizem que está tudo bem (QIACT? com IP, QIGETERROR devolve 0). Em teste disparou depois de cerca de 20 aberturas e fechos consecutivos de SSL, e até o QIOPEN de TCP puro devolvia 552; QIDEACT+QIACT não salva: só repetir o ritual de arranque recupera.

A triagem de 30 segundos: bata no mesmo destino com Open TCP —— também falha = a pilha inteira está avariada, repita o ritual de arranque; sucesso = o problema está no protocolo de cima, continue a investigar.

Keepalive: aguenta o NAT da operadora, não aguenta o tcpbin

QICFG=? lista os subitens e as gamas, Keepalive? consulta o valor atual, Keepalive On/Off liga e desliga —— estes quatro comandos, em si, são zero tráfego; uma vez ativo, basta haver um socket parado para os pacotes de sonda contarem como tráfego móvel. Ele não trava o timeout de 15 segundos do tcpbin: em teste, mesmo ligado, a ligação caiu aos 15,1 segundos —— o keepalive é uma sonda vazia da camada TCP, invisível para a aplicação; e o interval mínimo é de 25 segundos, à partida maior do que 15. Para aguentar timeouts da camada de aplicação só enviando dados reais (por exemplo, Send Hex com 0A a cada 10 segundos). A verdadeira utilidade é a manutenção do NAT da operadora (o NAT dos cartões IoT é reciclado ao fim de poucos minutos de inatividade).

Contas de tráfego (estimativa, não medição): cada sonda de ida e volta ronda os 80 bytes; com o idle por omissão = 30 segundos em inatividade contínua → cerca de 9,4 KB por hora, cerca de 225 KB por dia, cerca de 6,8 MB por mês; idle = 600 segundos → cerca de 11 KB por dia. Em cartões pré-pagos por volume, como os da 1NCE, aumente o idle. Sem sockets abertos, não gasta tráfego nenhum.
