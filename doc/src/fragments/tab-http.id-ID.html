HTTP — Permintaan Web

Cara kerja: HTTP pada modul ini tiga babak: setel dulu URL (langkah ini sendiri lagi-lagi dua tahap), lalu kirim permintaan (GET / POST), terakhir baca kembali balasannya. Hasil tiap babak tidak berada di dalam OK, melainkan pada URC yang datang kemudian — karena itu AT+QURCCFG="urcport" wajib "uart1" (bisa diubah di halaman Hardware), kalau tidak, tak satu pun hasil akan terlihat. Datanya semua hasil uji perangkat nyata 2026-08.

Sebelum mulai: pastikan ada kanal data

Prasyaratnya PDP sudah aktif dan mendapat IP (AT+QIACT=1 di halaman TCP/IP). Kelompok Connect halaman ini hanya menaruh pemeriksaan baca-saja: AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = belum terjatah), AT+QIGETERROR (⚠ hanya berlaku untuk perintah TCP/IP terakhir; begitu gagal, tekan segera).

AT+QIACT? bisa menipu. Pengujian pernah mengalami PDP hanyut di tengah jalan: semua permintaan gagal, timeout tetap 30 detik membalas error 716, tetapi AT+QIACT? tetap saja membalas IP. Silangkan dengan AT+CGACT?; bila tak konsisten berarti hanyut. Perbaikannya: AT+QIDEACT=1 → AT+CGACT=0,<cid yang hanyut> → AT+QIACT=1, lolos ping dulu baru lanjut.

GET pertama: empat langkah

  1. Setelan awal (kelompok Config, nol kuota): kartu parameter contextid disetel 1 (mengikat PDP context yang akan dipakai); tiga sakelar rspout/auto, requestheader, responseheader tetap 0 (alasannya lihat belakang); AT+QHTTPCFG? membaca kembali semua setelan sekaligus untuk dicek, AT+QHTTPCFG=? menampilkan butir yang bisa disetel.
  2. Setel URL (dua tahap): kartu AT+QHTTPURL hanya punya satu tombol "Kirim (dua tahap)" — Anda mengisi URL, panjangnya dihitung otomatis oleh program. Alurnya: kirim dulu AT+QHTTPURL=<panjang>,80, tunggu CONNECT masuk mode data, lalu kirim byte URL apa adanya, tanpa akhir baris apa pun (CR/LF akan terhitung ke panjang). http://www.example.com/ panjangnya tepat 23. Selesai mengirim, tekan AT+QHTTPURL? untuk membaca kembali; sama huruf demi huruf = akhir baris tak menyusup.
  3. Kirim permintaan: AT+QHTTPGET=80 (detik menunggu balasan). OK hanya berarti "perintah diterima"; hasil sesungguhnya adalah URC yang datang kemudian +QHTTPGET: 0,200, cara membacanya lihat paragraf berikut.
  4. Baca balasan: AT+QHTTPREAD=80. Setelah CONNECT semuanya byte mentah (hasil uji example.com: 559 bytes), disusul OK — tetapi +QHTTPREAD: 0 pada satu baris tersendiri di akhirlah penanda selesainya.

Membaca +QHTTPGET: kolom pertama bukan kode status HTTP

URC hasil GET / POST / POSTFILE semuanya tiga kolom <err>,<httprspcode>,<content_length>: err 0 = perintah berhasil dieksekusi, bukan 0 adalah error lapisan modul (716, 711…); httprspcode adalah kode status HTTP, hanya dilaporkan saat err=0 (manual menulisnya tegas; alat ini menyertakan anotasi rujukan 200 / 403 / 404 / 409 / 411 / 500); content_length opsional — hanya ada bila header balasan server memuat CONTENT-LENGTH; GET biasa sering hanya dua kolom. Maka +QHTTPGET: 0,404,0 hasil uji bukan kegagalan: perintahnya berhasil; servernyalah yang bilang tidak ditemukan.

Membaca balasan: jebakan AT+QHTTPREAD

Parameternya adalah "detik jeda maksimum antara dua paket data", bukan durasi total. Firmware perangkat ini hanya menerima satu parameter: cara baca bertahap =<wait>,<read_len> dari dokumen aplikasi nyatanya membalas ERROR telanjang (dibuktikan lewat probing =?); tombolnya sudah dihapus — untuk pengambilan bertahap pakai GETEX.

Jebakan saling kunci: begitu rspout/auto disetel 1, semua keluarga READ gagal (manual menulisnya tegas). Ia membuat modul otomatis memuntahkan balasan, dengan harga seluruh keluarga READ tumbang; itulah sebabnya tombol ini berdialog konfirmasi. Bila READ mendadak tumbang semua, periksa dulu AT+QHTTPCFG?.

Pengambilan bertahap: AT+QHTTPGETEX membaca byte demi byte

AT+QHTTPGETEX=<detik>,<offset awal>,<panjang> memakai HTTP Range untuk mengambil hanya potongan tertentu, hemat kuota. Hasil uji (isi endpoint dipatok abcdefghijklmnop): offset 0 ambil 8 membalas +QHTTPGET: 0,206,8, terbaca abcdefgh; offset 8 ambil 8 lagi terbaca ijklmnop. Cara membacanya: kode status wajib 206; bila membalas 200 dan isinya sama setiap kali = server tak mendukung Range, bukan modulnya rusak. ⚠ Hanya bisa dieksekusi saat requestheader=0.

POST: dua tahap dan Content-Type

Kartu AT+QHTTPPOST juga dua tahap: Anda mengisi body, panjang dihitung otomatis; kirim dulu AT+QHTTPPOST=<panjang>,<detik input>,<detik balasan>, tunggu CONNECT baru kirim body. Tiga hal:

  • CONNECT bisa menunggu sampai 125 detik (manual menulisnya tegas) — timeout menunggu prompt harus disetel penuh 125 detik; jangan mewarisi 5 detik milik MQTT.
  • Batas body 1 MB (rentang hasil uji =?: 1–1024000).
  • Setel dulu Content-Type lewat kartu parameter contenttype (kode tipe 0 = form-urlencoded).

Hasil uji: POST Message=HelloQuectel (20 bytes) membalas +QHTTPPOST: 0,200,440; JSON yang dibalas READ membuktikan pasangan kunci-nilai sampai, panjang terhitung benar, Content-Type berlaku, dan User-Agent yang dilaporkan modul sendiri adalah QUECTEL_MODULE.

Header kustom dan header balasan

  • reqheader/add: menambah satu header permintaan kustom (manual tak memberi contoh); tombol query bisa melihat sudah berapa yang ditambahkan; reqheader/remove menghapusnya.
  • requestheader disetel 1 = seluruh header permintaan dirakit sendiri, bahkan GET pun berubah dua tahap, dan GETEX tak bisa dipakai. Sehari-hari pertahankan 0.
  • Setelah responseheader disetel 1, READ ikut memuntahkan header balasan HTTP (hasil uji: bahkan X-Test kustom pun terbawa pulang). Selesai menguji, kembalikan ke 0.
  • closed/ind: menyalakan pelaporan URC "session ditutup".

Versi berkas: POSTFILE dan READFILE (UFS)

AT+QHTTPPOSTFILE="namafile",<detik> mengirim POST dengan berkas di sistem berkas modul (UFS) sebagai body; AT+QHTTPREADFILE="namafile",<detik> menyimpan balasan sebagai berkas UFS. ⚠ Alat ini saat ini belum bisa mengunggah berkas ke UFS lebih dulu, dan tak bisa membaca kembali isi berkas UFS; kedua perintah ini disediakan untuk dipadukan dengan alur di sisi firmware.

HTTPS: jalur tanpa verifikasi

HTTPS = HTTP + SSL context. Kelompok Connect menyiapkan jalur terpendek; lima tombol ditekan berurutan:

AT+QHTTPCFG="sslctxid",1           ← HTTP ditunjuk memakai SSL context 1
AT+QSSLCFG="sslversion",1,4        ← Versi TLS diserahkan ke negosiasi server
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← Suite enkripsi dibuka semua
AT+QSSLCFG="seclevel",1,0          ← Tidak memverifikasi sertifikat (lihat bawah)
AT+QSSLCFG="sni",1,1               ← Nyalakan SNI (pabriknya 0!)

Sesudahnya ganti URL berawalan https:// lalu GET / READ seperti biasa — hasil uji: HTML yang terbaca sama huruf demi huruf dengan versi teks polos. seclevel=0 (tanpa verifikasi sertifikat) adalah satu-satunya jalur yang bisa dituntaskan alat ini — untuk memverifikasi sertifikat, sertifikat CA harus ditulis dulu ke UFS; detail SSL (AT+QSSLCFG=? menampilkan semua subitem, negotiatetime mengatur detik tunggu handshake) lihat bagian "SSL — Kanal TLS". SNI dari pabrik bernilai 0: tanpa dinyalakan, situs HTTPS ber-IP bersama mendapat sertifikat tak cocok dan verifikasi langsung gagal. Rantai sertifikat adalah pemakan kuota terbesar: satu putaran HTTPS GET sekitar 8–15 KB, teks polos hanya sekitar 1 KB.

Pengalihan dan penutupan

Pengalihan (manual tak menulisnya; dijernihkan lewat pengujian): modul otomatis mengikuti 302, tetapi hanya menerima Location berjalur absolut — jalur relatif langsung membalas error 711, gagal seketika dalam 1 milidetik. Penutupan: AT+QHTTPSTOP (kelompok Close) membatalkan permintaan yang sedang berjalan dan memutus session; saat status terasa aneh, atau muncul error 704 (mode data sedang terpakai), tekan dulu tombol ini agar bersih.
