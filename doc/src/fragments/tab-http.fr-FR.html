HTTP — requêtes web

Principe de fonctionnement : le HTTP du module est en trois temps : d'abord définir l'URL (cette étape est elle-même en deux temps), puis émettre la requête (GET / POST), enfin relire la réponse. Le résultat de chaque temps n'est jamais dans le OK mais dans l'URC qui arrive ensuite — AT+QURCCFG="urcport" doit donc valoir "uart1" (modifiable sur la page Hardware), sans quoi aucun résultat ne sera visible. Toutes les données sont des mesures d'août 2026 sur le matériel réel.

Avant de commencer : disposer d'un canal de données

Prérequis : PDP activé et IP obtenue (le AT+QIACT=1 de la page TCP/IP). Le groupe Connect de cette page ne contient que des contrôles en lecture seule : AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = non attribué), AT+QIGETERROR (⚠ ne vaut que pour la dernière commande TCP/IP : appuyez immédiatement après l'échec).

AT+QIACT? ment. Mesuré : dérive du PDP en cours de route, toutes les requêtes échouent avec un timeout fixe de 30 secondes et l'erreur 716, mais AT+QIACT? continue de renvoyer une IP. Croisez avec AT+CGACT? : une incohérence = dérive. Réparation : AT+QIDEACT=1 → AT+CGACT=0,<cid de dérive> → AT+QIACT=1, puis un ping réussi avant de continuer.

Premier GET : quatre étapes

  1. Réglages préalables (groupe Config, zéro trafic) : carte de paramètres contextid à 1 (lie le PDP context à utiliser) ; les trois interrupteurs rspout/auto, requestheader, responseheader restent à 0 (raisons plus bas) ; AT+QHTTPCFG? relit tous les réglages d'un coup pour contrôle, AT+QHTTPCFG=? liste les réglages possibles.
  2. Définir l'URL (en deux temps) : la carte AT+QHTTPURL n'a qu'un bouton « Envoyer (en deux temps) » — vous remplissez l'URL, la longueur est calculée par le programme. Déroulé : envoi de AT+QHTTPURL=<longueur>,80, attente du CONNECT qui entre en mode données, puis envoi des octets de l'URL tels quels, sans aucune fin de ligne (un CR/LF serait compté dans la longueur). http://www.example.com/ fait exactement 23. Après l'envoi, relisez avec AT+QHTTPURL? : identique au caractère près = aucune fin de ligne ne s'est glissée.
  3. Émettre la requête : AT+QHTTPGET=80 (secondes d'attente de la réponse). OK signifie seulement « commande acceptée » ; le vrai résultat est l'URC ultérieur +QHTTPGET: 0,200, lecture au paragraphe suivant.
  4. Lire la réponse : AT+QHTTPREAD=80. Après CONNECT, ce ne sont que des octets bruts (mesuré : 559 bytes pour example.com), puis OK — mais c'est le +QHTTPREAD: 0 sur sa propre ligne finale qui marque la fin.

Lire +QHTTPGET : le premier champ n'est pas le code d'état HTTP

Les URC de résultat de GET / POST / POSTFILE ont tous trois champs : <err>,<httprspcode>,<content_length> : err 0 = commande exécutée avec succès, non nul = erreur de la couche module (716, 711…) ; httprspcode est le code d'état HTTP, rapporté seulement quand err=0 (écrit dans le manuel ; l'outil annote 200 / 403 / 404 / 409 / 411 / 500 avec sa table intégrée) ; content_length est optionnel — présent seulement si l'en-tête de réponse porte CONTENT-LENGTH, un GET ordinaire n'a souvent que deux champs. Ainsi le +QHTTPGET: 0,404,0 mesuré n'est pas un échec : la commande a réussi, c'est le serveur qui dit « introuvable ».

Lire la réponse : les pièges d'AT+QHTTPREAD

Le paramètre est « l'intervalle maximal en secondes entre deux paquets », pas la durée totale. Le firmware de cet exemplaire n'accepte qu'un seul paramètre : la lecture par tranches =<wait>,<read_len> de la note d'application répond un ERROR nu (confirmé par sonde =?) ; le bouton a été retiré — pour la récupération par tranches, utilisez GETEX.

Piège de verrouillage croisé : dès que rspout/auto vaut 1, toute la famille READ échoue (écrit dans le manuel). Il fait cracher la réponse automatiquement par le module, au prix de l'anéantissement des READ, d'où la boîte de confirmation sur ce bouton. Si les READ tombent tous d'un coup, vérifiez d'abord AT+QHTTPCFG?.

Récupération par tranches : AT+QHTTPGETEX lit byte par byte

AT+QHTTPGETEX=<secondes>,<offset de départ>,<longueur> passe par HTTP Range pour ne prendre que le fragment voulu et économiser du trafic. Mesuré (contenu du point de terminaison figé à abcdefghijklmnop) : offset 0, longueur 8 → +QHTTPGET: 0,206,8, lecture abcdefgh ; offset 8, encore 8 → lecture ijklmnop. Lecture : le code d'état doit être 206 ; un 200 avec le même contenu à chaque fois = le serveur ne supporte pas Range, le module n'est pas en cause. ⚠ Exécutable seulement quand requestheader=0.

POST : deux temps et Content-Type

La carte AT+QHTTPPOST est aussi en deux temps : vous remplissez le body, la longueur est calculée ; envoi de AT+QHTTPPOST=<longueur>,<secondes de saisie>,<secondes de réponse>, attente du CONNECT, puis envoi du body. Trois choses :

  • Le CONNECT peut se faire attendre jusqu'à 125 secondes (écrit dans le manuel) — réglez le timeout d'attente de l'invite à 125 secondes pleines, ne recyclez pas les 5 secondes de MQTT.
  • Body limité à 1 MB (plage mesurée par =? : 1–1024000).
  • Réglez le Content-Type au préalable avec la carte de paramètres contenttype (code de type 0 = form-urlencoded).

Mesuré : POST de Message=HelloQuectel (20 bytes) → +QHTTPPOST: 0,200,440 ; le JSON relu par READ prouve que la paire clé-valeur est arrivée, que la longueur était juste et que le Content-Type a agi ; le User-Agent auto-déclaré du module est QUECTEL_MODULE.

En-têtes personnalisés et en-têtes de réponse

  • reqheader/add : ajoute un en-tête de requête personnalisé (le manuel ne donne pas d'exemple) ; le bouton d'interrogation compte les en-têtes déjà ajoutés ; reqheader/remove les retire.
  • requestheader à 1 = vous composez vous-même tout l'en-tête de requête, même le GET devient en deux temps, et GETEX devient inutilisable. Restez à 0 en temps normal.
  • responseheader à 1 : READ crache aussi l'en-tête de réponse HTTP (mesuré : même un X-Test personnalisé revient). Repassez à 0 après le test.
  • closed/ind : active l'URC de notification « session fermée ».

Version fichier : POSTFILE et READFILE (UFS)

AT+QHTTPPOSTFILE="fichier",<secondes> envoie un POST dont le body est un fichier du système de fichiers du module (UFS) ; AT+QHTTPREADFILE="fichier",<secondes> enregistre la réponse dans un fichier UFS. ⚠ Cet outil ne sait actuellement ni téléverser un fichier vers l'UFS ni relire le contenu d'un fichier UFS : ces deux commandes servent avec un flux côté firmware.

HTTPS : le chemin sans vérification

HTTPS = HTTP + contexte SSL. Le groupe Connect prépare le chemin le plus court, cinq boutons dans l'ordre :

AT+QHTTPCFG="sslctxid",1           ← HTTP utilisera le contexte SSL 1
AT+QSSLCFG="sslversion",1,4        ← version TLS laissée à la négociation du serveur
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← toutes les suites de chiffrement
AT+QSSLCFG="seclevel",1,0          ← pas de vérification de certificat (voir plus bas)
AT+QSSLCFG="sni",1,1               ← activer SNI (0 en usine !)

Ensuite, une URL en https:// et GET / READ fonctionnent comme d'habitude — mesuré : le HTML relu est identique au caractère près à la version en clair. seclevel=0 (sans vérification) est le seul chemin que cet outil peut parcourir jusqu'au bout — pour vérifier le certificat, il faut d'abord écrire le certificat CA dans l'UFS ; détails SSL (AT+QSSLCFG=? liste tous les sous-réglages, negotiatetime règle l'attente de la poignée de main) dans la section « SSL — le tunnel TLS ». SNI vaut 0 en usine : sans lui, les sites HTTPS sur IP partagée reçoivent un certificat discordant et la vérification échoue aussitôt. La chaîne de certificats est le gros du trafic : un cycle de GET HTTPS pèse environ 8–15 KB, contre environ 1 KB en clair.

Redirections et clôture

Redirections (absentes du manuel, clarifiées par mesure) : le module suit automatiquement les 302, mais n'accepte que les Location en chemin absolu — un chemin relatif répond directement l'erreur 711, échec immédiat en 1 milliseconde. Clôture : AT+QHTTPSTOP (groupe Close) annule la requête en cours et coupe la session ; état bizarre ou erreur 704 (mode données occupé) : appuyez d'abord sur ce bouton pour nettoyer.
