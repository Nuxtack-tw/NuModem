HTTP — בקשות אינטרנט

עקרון הפעולה: ה-HTTP של המודול הוא תלת-שלבי: תחילה קובעים URL (השלב הזה כשלעצמו הוא דו-שלבי), אחר כך שולחים את הבקשה (GET / POST), ולבסוף קוראים בחזרה את התשובה. התוצאה של כל שלב אינה נמצאת ב-OK אלא ב-URC שמגיע אחריו — ולכן AT+QURCCFG="urcport" חייב להיות "uart1" (ניתן לשנות בלשונית Hardware), אחרת לא תראה אף תוצאה. כל הנתונים נמדדו על חומרה אמיתית ב-2026-08.

לפני שמתחילים: צריך ערוץ נתונים

התנאי המקדים הוא ש-PDP כבר מופעל וקיבל IP (AT+QIACT=1 בלשונית TCP/IP). קבוצת Connect בדף הזה כוללת בדיקות לקריאה בלבד: AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS של 0.0.0.0 = לא הוקצה), ו-AT+QIGETERROR (⚠ תקף רק לפקודת TCP/IP האחרונה, ולכן יש ללחוץ עליו מיד אחרי כישלון).

AT+QIACT? משקר. במדידה נתקלנו בסחיפה של ה-PDP באמצע העבודה: כל הבקשות נכשלו והחזירו שגיאה 716 אחרי פקיעת זמן קבועה של 30 שניות, אבל AT+QIACT? המשיך להחזיר IP כרגיל. בצע הצלבה מול AT+CGACT?, ואם השניים אינם עקביים — זו סחיפה. התיקון: AT+QIDEACT=1 ← AT+CGACT=0,<ה-cid שנסחף> ← AT+QIACT=1, ורק אחרי ping מוצלח ממשיכים.

ה-GET הראשון: ארבעה שלבים

  1. הגדרות מקדימות (קבוצת Config, ללא תעבורה): בכרטיס הפרמטרים של contextid קבע 1 (קשירה ל-PDP context שבו רוצים לעבוד); את שלושת המתגים rspout/auto, requestheader ו-responseheader השאר על 0 (הנימוקים בהמשך); AT+QHTTPCFG? קורא בבת אחת את כל ההגדרות לצורך השוואה, ו-AT+QHTTPCFG=? מציג את הפריטים הניתנים להגדרה.
  2. קביעת ה-URL (דו-שלבית): בכרטיס AT+QHTTPURL יש כפתור אחד בלבד, "שליחה (דו-שלבית)" — אתה ממלא את ה-URL, והאורך מחושב אוטומטית על ידי התוכנה. הרצף: תחילה נשלח AT+QHTTPURL=<אורך>,80, ממתינים ל-CONNECT כדי להיכנס למצב נתונים, ואז שולחים את בתי ה-URL כמות שהם, בלי להוסיף שום סוף שורה (CR/LF ייספרו לתוך האורך). האורך של http://www.example.com/ הוא בדיוק 23. אחרי השליחה לחץ AT+QHTTPURL? לקריאה חוזרת, וזהות תו-בתו פירושה שסוף שורה לא התגנב פנימה.
  3. שליחת הבקשה: AT+QHTTPGET=80 (מספר השניות להמתנה לתשובה). OK מעיד רק על "הפקודה התקבלה", והתוצאה האמיתית היא ה-URC שמגיע אחר כך, +QHTTPGET: 0,200, ופענוחו בסעיף הבא.
  4. קריאת התשובה: AT+QHTTPREAD=80. אחרי CONNECT הכול בתים גולמיים (במדידה, example.com החזיר 559 bytes), ואחריהם OK — אבל רק +QHTTPREAD: 0 בשורה נפרדת בסוף הוא סימן הסיום.

פענוח +QHTTPGET: השדה הראשון אינו קוד המצב של HTTP

ה-URC של התוצאה עבור GET / POST / POSTFILE הוא תמיד בן שלושה שדות, <err>,<httprspcode>,<content_length>: err 0 = ביצוע הפקודה הצליח, וערך שאינו 0 הוא שגיאה בשכבת המודול (716, 711…); httprspcode הוא קוד המצב של HTTP, והוא מדווח רק כאשר err=0 (כתוב במפורש במדריך; בכלי משובצות הערות השוואה ל-200 / 403 / 404 / 409 / 411 / 500); content_length הוא אופציונלי — הוא מופיע רק אם בכותרות התשובה של השרת יש CONTENT-LENGTH, ובבקשת GET רגילה יש לעיתים קרובות שני שדות בלבד. לכן +QHTTPGET: 0,404,0 שנמדד אינו כישלון: הפקודה הצליחה, והשרת הוא זה שאומר שלא מצא.

קריאת התשובה: המלכודות של AT+QHTTPREAD

הפרמטר הוא "המרווח המרבי בשניות בין שתי מנות נתונים", ולא משך הזמן הכולל. הקושחה ביחידה הזו מקבלת פרמטר אחד בלבד: שיטת הקריאה המקוטעת של מסמך היישום, =<wait>,<read_len>, החזירה במדידה ERROR חשוף (אושר בבדיקת =?), והכפתור הוסר — לקריאה מקוטעת יש להשתמש ב-GETEX.

מלכודת נעילה הדדית: ברגע ש-rspout/auto מוגדר ל-1, כל פקודות READ נכשלות (כתוב במפורש במדריך). ההגדרה גורמת למודול לפלוט את התשובה אוטומטית, והמחיר הוא חיסול מוחלט של משפחת READ, ולכן לכפתור הזה יש תיבת אישור. אם READ נופל פתאום כולו, בדוק תחילה AT+QHTTPCFG?.

קריאה מקוטעת: AT+QHTTPGETEX קורא בית אחר בית

AT+QHTTPGETEX=<שניות>,<היסט התחלה>,<אורך> משתמש ב-HTTP Range כדי למשוך רק את הקטע המבוקש ולחסוך בתעבורה. במדידה (תוכן נקודת הקצה קבוע על abcdefghijklmnop): היסט 0 באורך 8 החזיר +QHTTPGET: 0,206,8 ונקרא abcdefgh; היסט 8 באורך 8 נוסף החזיר ijklmnop. פענוח: קוד המצב חייב להיות 206; אם מוחזר 200 והתוכן זהה בכל פעם, משמע שהשרת אינו תומך ב-Range, וזו אינה תקלה במודול. ⚠ ניתן להריץ רק כאשר requestheader=0.

POST: דו-שלביות ו-Content-Type

גם כרטיס AT+QHTTPPOST הוא דו-שלבי: אתה ממלא את גוף ההודעה, האורך מחושב אוטומטית, תחילה נשלח AT+QHTTPPOST=<אורך>,<שניות קלט>,<שניות תשובה>, ממתינים ל-CONNECT ואז שולחים את הגוף. שלושה דברים:

  • ל-CONNECT יש להמתין עד 125 שניות (כתוב במפורש במדריך) — יש לקבוע את פקיעת ההמתנה לסימן ההנחיה על 125 שניות מלאות, ולא להשתמש ב-5 השניות של MQTT.
  • גבול הגוף הוא 1 MB (בבדיקת =? הטווח שנמדד הוא 1–1024000).
  • את Content-Type יש לקבוע מראש בכרטיס הפרמטרים contenttype (קוד טיפוס 0 = form-urlencoded).

במדידה: POST של Message=HelloQuectel (20 bytes) החזיר +QHTTPPOST: 0,200,440; ה-JSON שחזר ב-READ מאפשר לאמת שזוג המפתח-ערך הגיע, שהאורך חושב נכון ושה-Content-Type נכנס לתוקף, וש-User-Agent הוא מה שהמודול מדווח על עצמו, QUECTEL_MODULE.

כותרות מותאמות אישית וכותרות תשובה

  • reqheader/add: הוספת כותרת בקשה מותאמת אחת (המדריך אינו מצרף דוגמה); כפתור השאילתה מציג כמה כותרות נוספו עד כה; reqheader/remove מסיר.
  • requestheader על 1 = אתה מרכיב בעצמך את כל כותרות הבקשה, וגם GET הופך לדו-שלבי, וכן GETEX אינו זמין. בשגרה יש להשאיר על 0.
  • אחרי responseheader על 1, פקודת READ פולטת גם את כותרות התשובה של HTTP (במדידה חזרה אפילו כותרת X-Test מותאמת אישית). אחרי הבדיקה החזר ל-0.
  • closed/ind: הפעלת דיווח URC על "ה-session נסגר".

גרסת הקבצים: POSTFILE ו-READFILE (UFS)

AT+QHTTPPOSTFILE="שם קובץ",<שניות> שולח POST שגופו הוא קובץ ממערכת הקבצים של המודול (UFS); AT+QHTTPREADFILE="שם קובץ",<שניות> שומר את התשובה כקובץ ב-UFS. ⚠ הכלי הזה כרגע אינו יכול להעלות קובץ ל-UFS מראש, וגם אינו יכול לקרוא בחזרה את תוכן הקבצים ב-UFS, ושתי הפקודות האלה נועדו לשילוב עם תהליכים שרצים בצד הקושחה.

HTTPS: המסלול ללא אימות

HTTPS = HTTP + SSL context. בקבוצת Connect מוכן המסלול הקצר ביותר, חמישה כפתורים שנלחצים לפי הסדר:

AT+QHTTPCFG="sslctxid",1           ← HTTP יעבוד עם SSL context מספר 1
AT+QSSLCFG="sslversion",1,4        ← גרסת ה-TLS נקבעת במשא ומתן מול השרת
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← כל חבילות ההצפנה פתוחות
AT+QSSLCFG="seclevel",1,0          ← ללא אימות תעודה (ראה בהמשך)
AT+QSSLCFG="sni",1,1               ← הפעלת SNI (ערך היצרן הוא 0!)

לאחר מכן מחליפים את ה-URL לכזה שמתחיל ב-https:// ומריצים GET / READ כרגיל — במדידה, ה-HTML שנקרא היה זהה תו-בתו לגרסה הלא מוצפנת. seclevel=0 (ללא אימות תעודה) הוא המסלול היחיד שהכלי הזה מסוגל להשלים — כדי לאמת תעודה חובה קודם לכתוב תעודת CA ל-UFS; לפרטי SSL (AT+QSSLCFG=? מציג את כל הפריטים, ו-negotiatetime מכוונן את שניות ההמתנה ללחיצת היד) ראה את הסעיף "SSL — ערוץ TLS". ערך היצרן של SNI הוא 0: בלי להפעיל אותו, אתר HTTPS שחולק IP יחזיר תעודה שאינה תואמת, והאימות ייכשל מיד. שרשרת התעודות היא צרכנית התעבורה העיקרית: סבב GET אחד ב-HTTPS צורך כ-8–15 KB, לעומת כ-1 KB בלבד ללא הצפנה.

הפניות וסיום

הפניות (לא כתוב במדריך, הובהר במדידה): המודול עוקב אוטומטית אחרי 302, אבל מקבל רק Location בנתיב מוחלט — נתיב יחסי מחזיר מיד שגיאה 711 ונכשל תוך מילישנייה אחת. סיום: AT+QHTTPSTOP (קבוצת Close) מבטל בקשה שבתהליך ומנתק את ה-session; כשהמצב נראה מוזר, או כשמופיעה שגיאה 704 (מצב הנתונים תפוס), לחץ עליו קודם כדי לנקות.
