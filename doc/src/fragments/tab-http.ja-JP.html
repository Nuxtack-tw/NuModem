HTTP —— Web リクエスト

動作原理：モジュールの HTTP は3 段階です： まず URL を設定し（このステップ自体がまた 2 段階）、次にリクエストを発行し（GET／POST）、最後にレスポンスを読み戻します。 各段階の結果は OK の中にはなく、その後に届く URC にあります —— したがって AT+QURCCFG="urcport" は "uart1" でなければならず（Hardware ページで変更可）、 そうでないと結果は 1 つも見えません。データはすべて 2026-08 の実機実測です。

始める前に：まずデータチャネルを

前提は PDP が有効化され IP を取得済みであること（TCP/IP ページの AT+QIACT=1）。 本ページの Connect グループには読み取り専用チェックしか置いていません： AT+CPIN?／AT+CGATT?／AT+CGREG?／ AT+QIACT?、AT+QIDNSCFG=1（DNS 0.0.0.0＝未割当）、 AT+QIGETERROR（⚠ 最後の 1 本の TCP/IP コマンドにしか有効でないため、 失敗したらすぐに押すこと）。

AT+QIACT? は嘘をつきます。実測で PDP の途中漂流に遭遇しました： すべてのリクエストが失敗、固定 30 秒タイムアウトでエラー 716 なのに、 AT+QIACT? は平然と IP を返します。AT+CGACT? と突き合わせ、 不一致なら漂流です。直し方：AT+QIDEACT=1 → AT+CGACT=0,<漂流した cid> → AT+QIACT=1、 ping を通してから続行。

初めての GET：4 つのステップ

  1. 前準備の設定（Config グループ、通信量ゼロ）：contextid のパラメータカードで 1 を設定（使う PDP context に紐付け）。rspout/auto、 requestheader、responseheader の 3 スイッチは 0 のまま （理由は後述）。AT+QHTTPCFG? で全設定を一度に読み戻して照合し、 AT+QHTTPCFG=? で設定可能項目を一覧します。
  2. URL を設定（2 段階）：AT+QHTTPURL のカードには 「送出（2 段階）」ボタンが 1 つだけあります —— URL を記入すれば長さはプログラムが自動計算。流れ：まず AT+QHTTPURL=<長さ>,80 を送り、CONNECT を待って データモードに入り、URL のバイト列をそのまま送出します。行末は一切付けません （CR/LF は長さに数えられてしまいます）。 http://www.example.com/ の長さはちょうど 23 です。送り終えたら AT+QHTTPURL? で読み戻し、一字一句同じなら＝行末が紛れ込んでいません。
  3. リクエストを発行：AT+QHTTPGET=80（レスポンス待ち秒数）。 OK は「コマンドを受け付けた」の意味でしかなく、本当の結果は少し後の URC +QHTTPGET: 0,200 です。読み方は次の段落を参照。
  4. レスポンスを読む：AT+QHTTPREAD=80。 CONNECT の後はすべて生バイトで（実測では example.com は 559 bytes）、続けて OK —— ただし最後に独立した 1 行の +QHTTPREAD: 0 こそ終了マーカーです。

+QHTTPGET の読み方：第 1 欄は HTTP ステータスコードではない

GET／POST／POSTFILE の結果 URC はいずれも <err>,<httprspcode>,<content_length> の 3 欄です： err は 0 ＝ コマンド実行成功、非 0 はモジュール層のエラー（716、711…）。 httprspcode は HTTP ステータスコードで、err=0 のときだけ報告されます （マニュアル明記。ツールには 200／403／404／409／411／500 の対照注釈を内蔵）。 content_length は任意 —— サーバーのレスポンスヘッダに CONTENT-LENGTH があるときだけ現れ、 普通の GET はしばしば 2 欄だけです。したがって実測の +QHTTPGET: 0,404,0 は 失敗ではありません：コマンドは成功し、サーバーが見つからないと言っているのです。

レスポンスを読む：AT+QHTTPREAD の罠

パラメータは「2 つのパケット間の最大間隔秒数」であって、総時間ではありません。 本機のファームウェアはパラメータを 1 つしか受け付けません：アプリケーションノートの =<wait>,<read_len> という分割読みは実測で裸の ERROR が返り（=? の探索で実証）、ボタンは撤去済みです —— 分割取得は GETEX を使います。

相互ロックの罠：rspout/auto を 1 にすると、READ 系は一律失敗します （マニュアル明記）。モジュールが自動でレスポンスを吐く代わりに READ 系が全滅するため、 このボタンには確認ダイアログが付いています。READ が突然全滅したら、まず AT+QHTTPCFG? を確認。

分割取得：AT+QHTTPGETEX でバイト単位に読む

AT+QHTTPGETEX=<秒>,<開始オフセット>,<長さ> は HTTP Range で指定した断片だけを取り、通信量を節約します。実測（エンドポイントの内容は abcdefghijklmnop に固定）：オフセット 0 から 8 取ると +QHTTPGET: 0,206,8、 読み出しは abcdefgh。オフセット 8 からさらに 8 取ると ijklmnop。 読み方：ステータスコードは 206 でなければなりません。200 が返り毎回内容が同じ ＝サーバーが Range 非対応なだけで、モジュールの故障ではありません。 ⚠ requestheader=0 のときだけ実行できます。

POST：2 段階と Content-Type

AT+QHTTPPOST のカードも 2 段階です：body を記入すれば長さは自動計算。まず AT+QHTTPPOST=<長さ>,<入力秒>,<応答秒> を送り、 CONNECT を待って body を送ります。3 つのこと：

  • CONNECT は最長 125 秒待つ必要があります（マニュアル明記）—— プロンプト待ちのタイムアウトは 125 秒に設定し、MQTT の 5 秒を流用しないこと。
  • body の上限は 1 MB（=? の実測範囲 1–1024000）。
  • Content-Type は先に contenttype のパラメータカードで設定 （型コード 0 ＝ form-urlencoded）。

実測：POST Message=HelloQuectel（20 bytes）は +QHTTPPOST: 0,200,440 を返しました。READ が返す JSON でキーと値の到達、 長さの計算、Content-Type の効きを検証でき、User-Agent はモジュールの自己申告の QUECTEL_MODULE でした。

カスタムヘッダとレスポンスヘッダ

  • reqheader/add：カスタムリクエストヘッダを 1 本追加（マニュアルに実例なし）。 照会ボタンで現在何本追加済みかを確認でき、reqheader/remove で除去します。
  • requestheader を 1 に＝リクエストヘッダ全体を自分で組むことになり、GET まで 2 段階になり、 しかも GETEX が使えません。普段は 0 のまま。
  • responseheader を 1 にすると READ が HTTP レスポンスヘッダも一緒に吐きます （実測ではカスタムの X-Test まで持ち帰れました）。試し終えたら 0 に戻すこと。
  • closed/ind：「session が閉じられた」の URC 報告を有効化。

ファイル版：POSTFILE と READFILE（UFS）

AT+QHTTPPOSTFILE="ファイル名",<秒> はモジュールのファイルシステム（UFS）のファイルを body として POST を送り、AT+QHTTPREADFILE="ファイル名",<秒> はレスポンスを UFS ファイルとして保存します。⚠ 本ツールは現在UFS へのファイル事前アップロードも、UFS ファイル内容の読み戻しもできません。この 2 本はファームウェア側のフローと組み合わせて使うためのものです。

HTTPS：検証なしの経路

HTTPS ＝ HTTP ＋ SSL context。Connect グループに最短経路を用意してあります。5 つを順に押します：

AT+QHTTPCFG="sslctxid",1           ← HTTP に SSL context 1 を指定
AT+QSSLCFG="sslversion",1,4        ← TLS バージョンはサーバーとの交渉に委ねる
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← 暗号スイート全開
AT+QSSLCFG="seclevel",1,0          ← 証明書を検証しない（下記参照）
AT+QSSLCFG="sni",1,1               ← SNI を有効化（出荷時は 0！）

その後 URL を https:// 始まりに替えれば通常どおり GET／READ —— 実測では読み戻した HTML は平文版と一字一句同じでした。 seclevel=0（証明書を検証しない）が本ツールで完走できる唯一の経路です —— 証明書を検証するには先に CA 証明書を UFS へ書き込む必要があります。SSL の詳細（AT+QSSLCFG=? で全サブ項目を一覧、negotiatetime でハンドシェイク待ち秒数を調整）は〈SSL —— TLS チャネル〉の節を参照。 SNI は出荷時 0：有効にしないと、IP を共用する HTTPS サイトは一致しない証明書を受け取り、 検証すれば必ず失敗します。証明書チェーンが通信量の大半です：HTTPS GET 一巡で約 8–15 KB、 平文なら約 1 KB です。

リダイレクトと後始末

リダイレクト（マニュアル未記載、実測で解明）：モジュールは 302 を自動で追いますが、 絶対パスの Location しか受け付けません —— 相対パスは即エラー 711、 1 ミリ秒で即失敗します。後始末： AT+QHTTPSTOP（Close グループ）は進行中のリクエストを取り消して session を切断します。 状態がおかしいとき、またはエラー 704（データモードが占有中）が出たときは、まずこれを押してきれいにします。
