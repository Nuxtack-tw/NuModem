MQTT — Pesan IoT

Cara kerja: MQTT adalah protokol bergaya "broker (server perantara pesan)": perangkat tidak saling terhubung langsung; masing-masing tersambung ke broker, lalu menerbitkan atau berlangganan pesan pada "topik (topic)". Di EG800K ia berlapis dua: pertama AT+QMTOPEN membuka "koneksi jaringan" (TCP ke broker), lalu AT+QMTCONN melakukan "login MQTT"; hanya setelah kedua lapis tembus barulah bisa berlangganan dan menerbitkan. Ingat dulu: hasil semua perintah MQTT berpola "OK dulu, URC kemudian" (sama seperti FTP) — OK hanya berarti perintah diterima; berhasil-gagalnya lihat URC hasil sesudahnya.

Halaman ini selalu memakai client 0; firmware juga mendukung multi-client (0–5), SSL, dan autentikasi platform cloud (dikonfirmasi lewat uji =?); pemakaian lanjutan lihat application note MQTT.

Sebelum mulai: dua prasyarat

  1. URC harus lewat UART: AT+QURCCFG="urcport" wajib membalas "uart1". Nilai pabriknya "usbat", sedangkan hasil MQTT semuanya URC — bila tak diubah, setiap perintah hanya membalas OK tanpa kelanjutan (tombolnya ada di halaman Basic; ditulis ke NVRAM, cukup diubah sekali).
  2. PDP harus diaktifkan dulu: tekan dulu AT+QIACT=1 di halaman TCP/IP (maksimum 150 detik); bila belum, +QMTOPEN membalas 3 = aktivasi PDP gagal. Sepanjang proses kuota data terpakai, perkiraan sekitar 5 KB.

Sufiks acak pada client ID dan topik: setiap refresh berganti satu set

Client ID dan topik default tidak dipatok mati: saat halaman dimuat, otomatis dibangkitkan sufiks 6 karakter heksadesimal, membentuk numodem-<sufiks> dan test/numodem-<sufiks>; tiga tombol Subscribe / Publish / Unsub memakai set yang sama (kalau tidak, loop-balik takkan saling ketemu). Alasannya dua:

  • Nama bentrok berujung ditendang: MQTT 3.1.1 §3.1.4 mewajibkan broker menendang yang tersambung lebih dulu — dua orang memakai ID tetap yang sama akan saling tendang; gejalanya tampak seperti "modul putus tanpa sebab".
  • Topik tetap akan menerima pesan orang lain: Anda mengira yang diterima adalah kiriman sendiri, padahal bukan — ini lebih buruk daripada tak menerima, karena memberi kelulusan palsu.
⚠ Setiap kali halaman di-refresh, sufiks berganti satu set — berlangganan dan menerbitkan wajib diselesaikan dalam satu siklus hidup halaman yang sama. Apalagi pada alat ini RTS = daya; memuat ulang halaman = modul putus daya, koneksi MQTT lenyap seluruhnya, harus mengulang dari ritual boot dan AT+QMTOPEN.

Alur lengkap: sambung → langganan → terbitkan → menerima kembali pesan sendiri

Verifikasi paling meyakinkan adalah loop-balik: setelah berlangganan, terbitkan ke topik yang sama dan terima kembali pesan sendiri — sekali jalan menguji seluruh rantai kirim-terima. Setiap langkah tunggu URC hasil dulu baru lanjut:

  1. Setel versi protokol: tekan Ver 3.1.1 (AT+QMTCFG="version",0,4; 3 = 3.1, 4 = 3.1.1). Tekan Version? untuk melihat nilai kini (tanpa nilai = query). Kartu parameter Keepalive bisa mengatur interval jaga-hidup; tanpa diatur pun tetap bisa diuji.
  2. Buka jaringan: tekan Open Net (AT+QMTOPEN=0,"broker",1883). Ia membalas OK dulu; berhasil-gagalnya lihat URC +QMTOPEN: 0,<result> (0 = berhasil), menunggu maksimum 120 detik. Tekan Open? untuk melihat koneksi yang sudah terbuka (tanpa koneksi, balasannya OK kosong; hasil uji: normal).
  3. Login MQTT: tekan Connect (AT+QMTCONN=0,"numodem-<sufiks>"). URC keberhasilannya selalu +QMTCONN: 0,0,0. Broker publik bebas akun-sandi; bila butuh, tambahkan sendiri ,"user","pass" di belakang parameter. Tekan Conn? untuk melihat status (1 = inisial, 2 = menyambung, 3 = tersambung, 4 = memutus).
  4. Berlangganan: tekan Subscribe (AT+QMTSUB=0,1,"test/numodem-<sufiks>",0, msgid dipatok 1). URC keberhasilannya berbentuk +QMTSUB: 0,1,0,0. Sejak itu semua pesan topik ini masuk lewat URC +QMTRECV.
  5. Terbitkan: tekan Publish (AT+QMTPUBEX, dua tahap, lihat paragraf berikut). URC keberhasilannya +QMTPUBEX: 0,<msgid>,0.
  6. Terima kembali: sasaran penerbitan persis topik yang sedang dilanggan, sehingga segera terlihat +QMTRECV membawa topik beserta isi pesan barusan — loop-balik berhasil. Payload non-Latin pun tak terpotong, tak rusak.

Dua tahap QMTPUBEX: begitu panjang tercapai langsung terkirim otomatis, tanpa Ctrl+Z

Parameter terakhir AT+QMTPUBEX adalah panjang (jumlah byte), bukan isi pesan (application note MQTT §3.3.8 menutup kasusnya — cara kirim satu baris dengan menjejalkan pesan pasti membalas ERROR). Alur yang benar adalah dua tahap: kirim perintah → modul membalas prompt > → kirim tepat N byte, modul otomatis mengirim begitu panjang tercapai, tak butuh Ctrl+Z (berbeda dengan mode data AT+QISEND di halaman TCP). Menekan Publish serba otomatis: cukup isi isi pesan di kartu parameter, panjangnya dihitung otomatis dari jumlah byte UTF-8 (satu aksara CJK 3 byte; hasil uji: dua aksara → 6).

  • Perintah bertipe payload tidak menyediakan "isikan ke baris perintah" — pengiriman dari baris perintah selalu menambahkan akhir baris, dan CR itu ikut terhitung ke panjang sehingga meleset; kirimlah lewat tombol.
  • Firmware juga punya AT+QMTPUB (varian mode data, harus ditutup Ctrl+Z) — alat ini seragam memakai QMTPUBEX; tak perlu mempelajari dua-duanya.

Membaca kode hasil: rentang nilai tiap perintah berbeda-beda

Jangan menempelkan tabel kode hasil perintah A ke perintah B. Angka 3 pada +QMTOPEN berarti "aktivasi PDP gagal", sedangkan +QMTPUBEX sama sekali tak punya nilai 3.

Yang paling mudah salah baca adalah +QMTCONN: 0,1 — ia bisa berarti balasan query "status 1 = sedang inisialisasi", bisa pula hasil penulisan "paket sedang dikirim ulang". Dari satu baris saja tak terbedakan, maka alat ini menampilkan kedua tafsir berdampingan, tidak menebak paksa.

Anda tak perlu menghafal tabel: seluruh URC hasil dari +QMTOPEN sampai +QMTRECV / +QMTSTAT diberi anotasi bahasa awam kolom demi kolom di area terminal, mengikuti tujuh tabel rujukan application note MQTT v1.5.

Offline dan penutupan

  • Hanya ingin berhenti menerima, koneksi tetap ada: tekan Unsub (AT+QMTUNS=0,2,"topik", msgid dipatok 2).
  • Offline secara normal: tekan Disconnect (AT+QMTDISC=0, mengirim MQTT DISCONNECT), dibalas +QMTDISC: 0,0. Sesudahnya tak perlu lagi menekan Close Net — AT+QMTCLOSE=0 disediakan untuk penutupan paksa saat "QMTDISC gagal, lapisan jaringan tersangkut".

Pemutusan yang bukan Anda tekan (ditendang, keepalive timeout, jaringan putus) dilaporkan lewat URC pemutusan abnormal +QMTSTAT (contoh: +QMTSTAT: 0,5; area terminal menganotasi penyebabnya); saat itu harus mengulang dari AT+QMTOPEN.
