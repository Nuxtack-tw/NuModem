WiFiScan — Wi-Fi scanning and network positioning

Working principle: the EG800K is an LTE module with no Wi-Fi connectivity, but it carries a built-in "scan-only, never-connect" Wi-Fi receiver: it passively receives the beacon frames broadcast by nearby 2.4GHz hotspots and reports each hotspot's MAC address (BSSID), RSSI (signal strength) and channel. Scanning is pure RF reception at zero data cost; by itself it produces no coordinates — you must send the MAC + RSSI list to a cloud hotspot-location database to trade it for latitude and longitude; that is network positioning, usable indoors, no satellites needed. Every number and behavior in this section was measured on a physical EG800K in August 2026.

Your first scan: how to click, what you will see

  1. Run the power-up ritual (see the Power-Up Ritual section).
  2. Confirm URCs go to the UART: AT+QURCCFG="urcport" must return "uart1". The factory value is "usbat" — all scan results get sent to the USB port, and here you see only OK, not even a TIMEOUT (the setting is written to NVRAM; change it once).
  3. Click Scan: the module replies OK first, which means "scan started" — not the result. Within seconds (up to the scan time limit) the results are reported one line at a time, each auto-annotated (MAC / RSSI / channel).

Reading the scan results

A measured report looks like this (2026-08-29, 7 hotspots found, RSSI -37 to -89 dBm):

+QWIFISCAN: (-,-,-37,"C2:28:35:00:00:01",1)
+QWIFISCAN: (-,-,-46,"10:71:B3:00:00:02",4)
+QWIFISCAN: (-,-,-88,"A8:A2:37:00:00:03",6)

The field order is (ecn, ssid, rssi, mac, channel). This unit's firmware always returns - for ecn and ssid (measured 2026-08-02), so the list never shows "whose Wi-Fi this is" — which happens to be enough for positioning: the databases eat MAC + RSSI anyway. RSSI intuition: -30 to -50 very close, -60 to -75 average, below -80 very weak.

When no hotspot is found within the time limit it returns +QWIFISCAN:TIMEOUT — a normal ending, not an error (no space after the colon; this tool's parser handles it). To catch more: use the parameter card to raise the hotspot cap from the factory 5 (this unit's ceiling is 10) and the rounds to 2-3 (measured: results are deduplicated across rounds).

Not every hotspot you catch can be used for positioning. Measured 2026-08-29: of 7 hotspots, 4 were "locally administered addresses" (starting C2: / 62: / 9E:, with the 0x02 bit of the first byte set to 1 — virtual BSSIDs of multi-SSID clones); positioning databases usually ignore such addresses outright, leaving only the 3 global addresses as usable material.
Application note V1.2's parameter ranges are wrong for this unit. The note widens rounds to 1-6 and the hotspot cap to 4-30, but this unit's firmware still actually returns rounds 1-3, hotspot cap 4-10 (measured 2026-08-06). Trust what Support? actually returns; do not copy the note's numbers.

The QuecLocator (QLBS) button group: read the truth before clicking

QuecLocator is Quectel's cloud positioning service: one AT+QLBS command (the Locate button) and the firmware gathers the material itself, sends it to the server for the lookup, and returns coordinates. Three realities:

  1. It needs a token, and it is a paid service. The official document explicitly says to contact Quectel technical support to apply (no self-service signup). This unit's token is empty from the factory.
  2. Not one of the 16 official EG800K documents mentions QuecLocator. The application note on hand is for EC200U / EG915U (syntax and error codes match by testing) — it is not this unit's official document.
  3. This project has ruled it out (2026-08-29): the positioning logic is locked inside the firmware — once the service folds, the whole AT command goes dead and the vendor cannot be swapped (the Quectel forum has confirmed the BG95 series lost support). The buttons remain only for "if a free token ever turns up, verify in passing".
+QLBS: 702 is "server timeout", not a token problem. This project misread 702 as "no token" for three whole weeks — the truth was that the PDP had not been activated first, so the module could not reach the server at all and returned 702 after the full timeout (factory 60 seconds). Controlled experiment 2026-08-29 (token empty throughout): PDP inactive returns 702; once active it returns 10002 (token does not exist) — the server is reachable from Taiwan; the only thing missing is the token. Always run AT+QIACT=1 before AT+QLBS (it consumes data).

All seven configuration sub-items have query / set buttons, and Cfg? (AT+QLBSCFG=?) lists every range in one click (zero data cost). Factory values on this unit and measured highlights:

The alternative route: token-free network positioning (71 meters measured)

Network positioning does not have to go through QuecLocator. The alternative route was proven end to end on 2026-08-29: the module only produces the material (scan hotspots on this page, read the serving cell with AT+QENG="servingcell"), you save the terminal output to a file and hand it to tools/wifi_geolocate.py, which queries public databases on the PC — zero data cost on the module, no Quectel service. Measured (against the same day's GNSS ground truth): cell-tower lookup via Unwired Labs (free signup) was off by 71 meters (the closing conclusion of this positioning thread); via beaconDB (no key needed), 632 meters; Wi-Fi lookup is stuck on the supplier side — the free ecosystem has collapsed (beaconDB has no coverage in this area, Unwired Labs' free plan excludes Wi-Fi, Google / HERE require a credit card) — shelved.

71 meters is a "lookup hit", not "measurement accuracy". Cell-tower positioning looks up the registered coordinates of that tower by Cell ID, so the same cell always returns the same point — switch towers and the error can jump to kilometer scale; the service's own reported ±1051 meters is the honest estimate. Also, Cell ID and TAC are hexadecimal and must be converted to decimal before the lookup (the tool handles this automatically).
