TCP/IP —— データ通信の根

動作原理：このページはすべてのデータプロトコルの土台です。PDP context （通信ネットワークが割り当てるデータチャネル）の有効化と無効化はこのページでのみ行います。SSL／HTTP／MQTT／FTP の各ページには読み取り専用の照会しか置いていません —— 同じコマンドが 2 か所で踏み合うのを避けるためです。 本節の罠と秒数はすべて 2026 年 8 月に実機で実測したものです。

第一歩：PDP を有効化する（QICSGP／QIACT／QIDEACT）

Act PDP（AT+QIACT=1）を押します：最長 150 秒ブロックし、 その間は他のコマンドを打たないでください。ここから通信量が発生し始めます（ローミングでは費用に注意）。成功したら必ず Query IP（AT+QIACT?）を押し、+QIACT: 1,1,1,"IP アドレス" が返ることを確認します —— 有効化前は OK しか返りません。終えるときは Deact PDP（AT+QIDEACT=1、 最長 40 秒）を押します。配下のすべての接続が強制的に閉じられます。Set APN （AT+QICSGP）は普段は押す必要がありません —— モジュールはネットワークの割り当てた APN を自動同期します （実測では 1NCE カードは起動時の読み出しですでに iot.1nce.net）。ユーザー名とパスワードが要る企業向け APN のときだけ必要です。

Act PDP が ERROR、Last Error が 572？ このカードは PDP を 1 本しか許可しません。 起動時にネットワークがすでに 1 本自動有効化しており、番号は浮動します（実測で 9 と 1 を確認）。 AT+QIACT は 1–8 にしか触れません。対処：Network ページで AT+CGACT? で番号を照会 → AT+CGACT=0,<番号> で枠を譲らせる → もう一度 Act PDP。

テストの途中で全滅？ AT+QIACT? は嘘をつきます —— PDP が漂流していても 平然と IP を返すので、AT+CGACT? と突き合わせないと見抜けません。復旧： Deact PDP → AT+CGACT=0,<漂流先の番号> → Act PDP → Ping で検証。

接続を開く：OK は「コマンドを受け付けた」の意味でしかない

Open TCP を押し、パラメータカードにホストとポートを記入します （AT+QIOPEN=1,0,"TCP","ホスト",ポート,0,0。context 1、connectID 0、 buffer モードは固定済み）。OK はコマンドを受け付けたという意味でしかなく、成否は URC +QIOPEN: 0,<err> で見ます：0＝成功、最長 150 秒。 563＝connectID がまだ開いたままなので、先に Close Sock を押します。 All Socks（AT+QISTATE）はすべての socket を一覧し、 state 2＝接続済みです。

データ送信：3 つの方式

ボタン説明
Send Text
AT+QISEND=0,<len>		 固定長の 2 段階：> を待って本文を送り、長さは自動計算、 Ctrl+Z 不要。プレーンテキストの第一選択。上限 1460 bytes、 \n \r \t \xHH のエスケープに対応
Send Var の 3 ボタン
AT+QISEND=0		 可変長式：データモードに入って受け付け続け、Ctrl+Z（0x1A）を見てはじめて送出 —— 分割して書けます。次の段落を参照
Send Hex
AT+QISENDEX=0,"hex"		 単一行式で、データモードに入りません。任意のバイト（0x00 を含む）を送れます。 hex の上限 512 文字＝実質 256 bytes

送出（続けて書く）は最初の 1 回でデータモードに入り、以後は押すたびに 1 区切り追加します （すでにデータモード中はコマンドを再送しません。再送するとデータになってしまいます）。送出後に自動終了は 追加してから Ctrl+Z を補うもので、1 区切りだけ送るときが最速。終了（Ctrl+Z）は蓄積した内容を 一気に送出します。データモード中はターミナルに表示が出ます。やめるときは ESC Cancel（0x1B、2 段階コマンドが固まったときの脱出キー）。 ⚠ データに 0x1A を含めてはいけません（早すぎる終了と見なされます）。制御文字は Send Hex を使ってください。

SEND OK は相手が受け取ったという意味ではなく、データをモジュールに渡しただけです。 Check ACK（AT+QISEND=0,0）で送信済み／ACK 済みを照会し、 acked を見てはじめて確定です。

データ受信：勝手には現れず、Read Data を押す

buffer モードで受信したデータは、ターミナルに自動では現れません：モジュールは +QIURC: "recv",0 という通知を出すだけなので、Read Data （AT+QIRD=0,1500）で取り出し、しかも+QIRD: 0 が返るまで 繰り返し読みます —— 読み切らないと次の通知は二度と来ません。 Unread Len（AT+QIRD=0,0）は総受信／既読／未読を照会します。 送受信を終えたら Close Sock（AT+QICLOSE=0、最長 10 秒）。 ⚠ recv 通知が全く来ない？ Hardware ページで AT+QURCCFG="urcport" が uart1 かどうかを確認してください —— 出荷値は USB ポートで、URC は全部そちらへ流れています。

組み込みの相手 tcpbin.com の 2 つの癖

Open TCP の既定の相手は無料 echo サーバー tcpbin.com:4242 です。 実測で分かった癖が 2 つ：

  • 行単位で echo し、末尾に改行（0A）が必要：0A 無しで Hello を送ると 6 秒待っても 無応答、0A を補うと 0.1 秒で即受信。Send Text は末尾に \n を、 Send Hex は末尾に 0A を付けます。
  • 15 秒の遊休タイムアウト：遊休のままだと切断され +QIURC: "closed",0 を受け取ります。これは QIRD とは無関係です（QIRD はローカルバッファを読むだけで、 ネットワークには触れません）。接続を保つには 10 秒以内ごとに 1 回データを送ります。closed を受けた後 socket は closing で止まり、 先に Close Sock を押さないと再利用できず、QIOPEN が 563 を返します。

エラーが出たら：まず Last Error、次に 30 秒鑑別

コマンドが ERROR を返したらすぐに Last Error （AT+QIGETERROR）を押します —— 最後の 1 件しか保持されず、次のエラーに上書きされると調べられません。 これは Quectel スタック層を照会します。ネットワーク層は Network ページの AT+CEER で。

🔴 データスタックの退化 —— 最も時間を食う落とし穴。症状：すべての接続が一律に 失敗するのに、自己診断は全部問題なしと言う（QIACT? に IP あり、QIGETERROR は 0）。実測では SSL の開閉を連続 約 20 回行った後に発生し、純粋な TCP の QIOPEN まで 552 を返しました。QIDEACT＋QIACT では救えず、 起動シーケンスのやり直しだけが復旧手段です。

30 秒鑑別法：Open TCP で同じ相手を叩く —— これも失敗＝スタック全体が 壊れているので起動シーケンスをやり直す。成功＝問題は上位プロトコルにあるので、調査を続ける。

Keepalive：通信事業者の NAT には効くが、tcpbin には効かない

QICFG=? はサブ項目と範囲を一覧、Keepalive? は現在値を照会、 Keepalive On／Off はスイッチ —— この 4 つのコマンド自体は通信量ゼロです。 有効化後は socket が遊休のままである限り、探査パケットがモバイル通信量に計上されます。 tcpbin の 15 秒タイムアウトは防げません：実測では有効にしても 15.1 秒で切られました —— keepalive は TCP 層の空探査でアプリケーションからは見えず、しかも interval の最小は 25 秒で、 そもそも 15 より大きいのです。アプリケーション層のタイムアウトをしのぐには実データを送るしかありません（例：10 秒ごとに Send Hex で 0A を送る）。本当の用途は通信事業者の NAT の保活です（IoT カードの NAT は数分の遊休で回収されます）。

通信量の勘定（推算であり実測ではありません）：1 回の探査往復は約 80 bytes。 既定の idle＝30 秒で遊休が続くと → 毎時約 9.4 KB、1 日約 225 KB、 1 か月約 6.8 MB。idle＝600 秒なら → 1 日約 11 KB。 1NCE のような総量前払いカードでは idle を大きくしてください。socket を開いていなければ通信量は全く消費しません。
