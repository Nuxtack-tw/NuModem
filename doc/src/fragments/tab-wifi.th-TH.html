WiFiScan —— การสแกน Wi-Fi กับการระบุตำแหน่งผ่านเครือข่าย

หลักการทำงาน: EG800K เป็นโมดูล LTE ไม่มีความสามารถออกเน็ตผ่าน Wi-Fi แต่มีตัวรับ Wi-Fi แบบ "สแกนอย่างเดียว ไม่เชื่อมต่อ" ในตัว: รับเฟรม beacon ที่ฮอตสปอต 2.4GHz รอบตัวกระจายออกมาแบบพาสซีฟ แล้วรายงานที่อยู่ MAC (BSSID), RSSI (ความแรงสัญญาณ) และแชนเนลของแต่ละฮอตสปอต การสแกนเป็นการรับ RF ล้วน ไม่กินปริมาณข้อมูลเลย; ตัวมันเองไม่ผลิตพิกัด —— ต้องเอารายการ MAC + RSSI ส่งไปถามฐานข้อมูลตำแหน่งฮอตสปอตบนคลาวด์ถึงจะแลกเป็นละติจูดลองจิจูดได้; นี่แหละคือการระบุตำแหน่งผ่านเครือข่ายที่ใช้ในอาคารได้ ไม่พึ่งดาวเทียม ตัวเลขและพฤติกรรมทั้งหมดในหัวข้อนี้คือค่าวัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

  3. กด Scan: โมดูลตอบ OK ก่อน ซึ่งแปลว่า "เริ่มสแกนแล้ว" ไม่ใช่ผลลัพธ์ ภายในไม่กี่วินาที (นานสุดถึงเวลาจำกัดการสแกน) ผลลัพธ์จะรายงานมาทีละบรรทัด แต่ละบรรทัดมีคำอธิบายอัตโนมัติแนบมา (MAC / RSSI / แชนเนล)

+QWIFISCAN: (-,-,-37,"C2:28:35:00:00:01",1)
+QWIFISCAN: (-,-,-46,"10:71:B3:00:00:02",4)
+QWIFISCAN: (-,-,-88,"A8:A2:37:00:00:03",6)

ลำดับช่องคือ (ecn, ssid, rssi, mac, channel) เฟิร์มแวร์ของเครื่องนี้ ecn กับ ssid ตอบ - ตายตัว (ทดสอบจริง 2026-08-02) ในรายการจึงมองไม่เห็นว่า "นี่คือ Wi-Fi บ้านใคร" —— แต่สำหรับการระบุตำแหน่งพอดิบพอดี ฐานข้อมูลกินแค่ MAC + RSSI อยู่แล้ว สัญชาตญาณ RSSI: -30 ~ -50 ใกล้มาก, -60 ~ -75 ปานกลาง, ต่ำกว่า -80 อ่อนมาก

ภายในเวลาจำกัดถ้าสแกนไม่เจอฮอตสปอตเลยจะตอบ +QWIFISCAN:TIMEOUT —— จบแบบปกติ ไม่ใช่ข้อผิดพลาด (หลังโคลอนไม่มีช่องว่าง ตัวแยกวิเคราะห์ของเครื่องมือนี้จัดการแล้ว) อยากสแกนได้หลายตัวขึ้น: ใช้การ์ดพารามิเตอร์ปรับเพดานฮอตสปอตจากค่าโรงงาน 5 ให้สูงขึ้น (ขีดสุดของเครื่องนี้ 10), ปรับจำนวนรอบเป็น 2-3 (ทดสอบจริงผลข้ามรอบจะถูกตัดตัวซ้ำให้)

ฮอตสปอตที่สแกนเจอ ไม่ใช่ทุกตัวจะเอาไประบุตำแหน่งได้ ทดสอบจริง 2026-08-29 จาก 7 ตัวมี 4 ตัวเป็น "ที่อยู่แบบบริหารจัดการท้องถิ่น" (ขึ้นต้น C2: / 62: / 9E: คือบิต 0x02 ของไบต์แรกเป็น 1 —— BSSID เสมือนของร่างแยกหลาย SSID) ฐานข้อมูลระบุตำแหน่งมักเมินที่อยู่แบบนี้ไปเลย วัตถุดิบใช้ได้จริงเหลือแค่ 3 ตัวที่เป็นที่อยู่สากล
ช่วงพารามิเตอร์ในเอกสารประยุกต์ V1.2 ผิดสำหรับเครื่องนี้ เอกสารขยายจำนวนรอบเป็น 1-6 เพดานฮอตสปอตเป็น 4-30 แต่เฟิร์มแวร์เครื่องนี้ตอบช่วงจริงคือ จำนวนรอบ 1-3, เพดานฮอตสปอต 4-10 (ทดสอบจริง 2026-08-06) ให้ยึดคำตอบจริงจาก Support? อย่าลอกตัวเลขจากเอกสาร

กลุ่มปุ่ม QuecLocator (QLBS): ก่อนกดดูความจริงก่อน

QuecLocator คือบริการระบุตำแหน่งบนคลาวด์ของ Quectel: AT+QLBS (ปุ่ม Locate) คำสั่งเดียว เฟิร์มแวร์เก็บวัตถุดิบเอง ส่งไปเซิร์ฟเวอร์ค้นฐานข้อมูล แล้วส่งพิกัดกลับมา ความจริงสามข้อ:

  1. ต้องมี token และเป็นบริการเก็บเงิน เอกสารทางการเขียนชัดว่าต้องติดต่อฝ่ายซัพพอร์ตของ Quectel เพื่อขอ (ไม่มีสมัครเองได้) token ของเครื่องนี้จากโรงงานว่างเปล่า
  2. เอกสารทางการ EG800K ทั้ง 16 ฉบับไม่มีฉบับไหนพูดถึง QuecLocator เอกสารประยุกต์ที่มีในมือเป็นของ EC200U / EG915U (ไวยากรณ์กับรหัสข้อผิดพลาดทดสอบจริงแล้วตรงกัน) ไม่ใช่เอกสารทางการของเครื่องนี้
  3. โปรเจกต์นี้ตัดสินแล้วว่าไม่ใช้ (2026-08-29): ลอจิกระบุตำแหน่งถูกล็อกอยู่ในเฟิร์มแวร์ บริการเลิกเมื่อไหร่ คำสั่ง AT ทั้งเส้นก็ใช้ไม่ได้ทันที เปลี่ยนผู้ให้บริการไม่ได้ (ฟอรัม Quectel ยืนยันแล้วว่าซีรีส์ BG95 หยุดซัพพอร์ต) ปุ่มยังเก็บไว้ เผื่อแค่ "ถ้าได้ token ฟรีจะได้ลองยืนยันมือ"
+QLBS: 702 คือ "เซิร์ฟเวอร์หมดเวลา" ไม่ใช่ปัญหา token โปรเจกต์นี้เคยตีความ 702 ผิดเป็น "ไม่มี token" อยู่สามสัปดาห์เต็ม —— ความจริงคือตอนนั้นลืมเปิดใช้ PDP ก่อน โมดูลต่อเซิร์ฟเวอร์ไม่ได้เลย รอจนครบเวลา (ค่าโรงงาน 60 วินาที) ก็ตอบ 702 การทดลองเทียบเมื่อ 2026-08-29 (token ว่างตลอด): PDP ไม่ได้เปิดตอบ 702; เปิดแล้วตอบ 10002 (token ไม่มีอยู่) —— เซิร์ฟเวอร์จากไต้หวันต่อได้ ที่ขาดมีแค่ token ก่อนส่ง AT+QLBS ต้อง AT+QIACT=1 ก่อนเสมอ (เกิดปริมาณข้อมูล)

เส้นทางทดแทน: ระบุตำแหน่งผ่านเครือข่ายแบบไม่ต้องมี token (วัดจริง 71 เมตร)

การระบุตำแหน่งผ่านเครือข่ายไม่จำเป็นต้องพึ่ง QuecLocator เส้นทางทดแทนทะลุครบวงจรแล้วเมื่อ 2026-08-29: โมดูลผลิตแค่วัตถุดิบ (หน้านี้สแกนฮอตสปอต, AT+QENG="servingcell" อ่านสถานีฐาน) เซฟเอาต์พุตของเทอร์มินัลแล้วส่งให้ tools/wifi_geolocate.py ไปค้นฐานข้อมูลสาธารณะบนฝั่ง PC —— โมดูลไม่กินปริมาณข้อมูลเลย ไม่ต้องใช้บริการ Quectel ผลวัดจริง (เทียบกับค่าจริงจาก GNSS วันเดียวกัน): ค้นตารางสถานีฐานด้วย Unwired Labs (สมัครฟรี) คลาดเคลื่อน 71 เมตร (ข้อสรุปปิดท้ายของสายระบุตำแหน่งเส้นนี้), ด้วย beaconDB (ไม่ต้องใช้คีย์) 632 เมตร; ส่วนการค้นตาราง Wi-Fi ติดที่ผู้ให้บริการ —— ระบบนิเวศฟรีพังไปแล้ว (beaconDB ไม่ครอบคลุมย่านนี้, แผนฟรีของ Unwired Labs ไม่รวม Wi-Fi, Google / HERE ต้องผูกบัตร) จึงพักไว้

71 เมตรคือ "ค้นตารางแล้วเจอ" ไม่ใช่ "ความแม่นยำการวัด" การระบุตำแหน่งด้วยสถานีฐานคือใช้ Cell ID ไปเปิดพิกัดจดทะเบียนของสถานีฐานต้นนั้น cell เดียวกันตอบจุดเดิมตลอด —— เปลี่ยนสถานีฐานหนึ่งต้น ความคลาดเคลื่อนอาจเป็นระดับกิโลเมตร; ±1051 เมตรที่บริการรายงานเองต่างหากคือการประเมินที่ซื่อสัตย์ อีกอย่าง Cell ID กับ TAC เป็นเลขฐานสิบหก ก่อนค้นตารางต้องแปลงเป็นฐานสิบ (เครื่องมือจัดการให้ในตัวแล้ว)
