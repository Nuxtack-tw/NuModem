WiFiScan —— scan Wi-Fi e localização por rede

Princípio de funcionamento: o EG800K é um módulo LTE sem capacidade de acesso à Internet por Wi-Fi, mas traz um recetor Wi-Fi «que só escuta, nunca liga»: recebe passivamente as tramas beacon difundidas pelos hotspots de 2,4 GHz em volta e reporta, para cada hotspot, o endereço MAC (BSSID), o RSSI (força de sinal) e o canal. O scan é receção RF pura, zero tráfego de dados; por si só não produz coordenadas —— só enviando a lista de MAC+RSSI a uma base de dados de posições de hotspots na cloud é que se obtêm latitude e longitude; é esta a localização por rede que funciona dentro de casa, sem depender de satélites. Todos os números e comportamentos desta secção são valores medidos em agosto de 2026 num EG800K físico.

O primeiro scan: como se prime e o que se vê

  1. Corra o ritual de arranque (ver a secção «Ritual de arranque»).
  2. Confirme que os URC saem pela UART: AT+QURCCFG="urcport" tem de devolver "uart1". O valor de fábrica é "usbat" —— os resultados do scan iriam todos para a porta USB e aqui só se veria o OK, sem sequer chegar o TIMEOUT (a definição grava em NVRAM; basta mudar uma vez).
  3. Prima Scan: o módulo responde primeiro OK, o que significa «o scan começou», não é o resultado. Em poucos segundos (no máximo, o limite de tempo do scan) os resultados chegam linha a linha, cada uma com anotação automática (MAC/RSSI/canal).

Interpretar os resultados do scan

Um reporte medido tem este aspeto (2026-08-29, 7 hotspots detetados, RSSI de -37 a -89 dBm):

+QWIFISCAN: (-,-,-37,"C2:28:35:00:00:01",1)
+QWIFISCAN: (-,-,-46,"10:71:B3:00:00:02",4)
+QWIFISCAN: (-,-,-88,"A8:A2:37:00:00:03",6)

A ordem dos campos é (ecn, ssid, rssi, mac, channel). No firmware desta unidade o ecn e o ssid devolvem sempre - (medido em 2026-08-02), e a lista não mostra «de quem é este Wi-Fi» —— para localizar chega perfeitamente: as bases de dados só comem MAC+RSSI. Intuição para o RSSI: -30 a -50 muito perto, -60 a -75 normal, abaixo de -80 muito fraco.

Se dentro do limite de tempo não se apanhar hotspot nenhum, vem +QWIFISCAN:TIMEOUT —— fim normal, não é erro (sem espaço a seguir aos dois pontos; o interpretador desta ferramenta já o trata). Para apanhar mais: use o cartão de parâmetros para subir o máximo de hotspots dos 5 de fábrica (limite desta unidade: 10) e as rondas para 2-3 (em teste, os resultados entre rondas são desduplicados).

Nem todos os hotspots apanhados servem para localizar. Na medição de 2026-08-29, dos 7 hotspots, 4 eram «endereços administrados localmente» (começados por C2:/62:/9E:, com o bit 0x02 do primeiro byte a 1 —— BSSID virtuais de clones multi-SSID); as bases de dados de localização costumam ignorar esses endereços, e o material útil ficou reduzido a 3 endereços globais.
As gamas de parâmetros da application note V1.2 estão erradas para esta unidade. O documento alarga as rondas para 1-6 e o máximo de hotspots para 4-30, mas o firmware desta unidade continua a devolver rondas 1-3 e máximo de hotspots 4-10 (medido em 2026-08-06). Fie-se no que o Support? devolve, não copie os números do documento.

O grupo de botões QuecLocator (QLBS): a verdade antes de premir

O QuecLocator é o serviço de localização na cloud da Quectel: com um único comando, AT+QLBS (botão Locate), o firmware recolhe sozinho o material, consulta o servidor e devolve as coordenadas. Três realidades:

  1. Exige token, e é um serviço pago. A documentação oficial diz expressamente que há que contactar o suporte técnico da Quectel para o pedir (sem registo self-service). Nesta unidade o token vem vazio de fábrica.
  2. Nenhum dos 16 documentos oficiais do EG800K menciona o QuecLocator. A application note disponível é a do EC200U/EG915U (sintaxe e códigos de erro conferem com o medido), não é documentação oficial desta unidade.
  3. Este projeto já decidiu não o adotar (2026-08-29): a lógica de localização está fechada no firmware; se o serviço fechar, o comando AT inteiro morre e o fornecedor não pode ser substituído (o fórum da Quectel já confirmou o fim do suporte na série BG95). Os botões ficam, só para «validar de passagem se algum dia houver um token gratuito».
+QLBS: 702 é «timeout do servidor», não um problema de token. Este projeto interpretou mal o 702 como «falta o token» durante três semanas inteiras —— a verdade é que na altura se esquecera de ativar o PDP: o módulo nem chegava ao servidor e, esgotado o timeout (60 segundos de fábrica), devolvia 702. Experiência de controlo de 2026-08-29 (token vazio do princípio ao fim): com o PDP desativado devolve 702; ativado, devolve 10002 (token inexistente) —— o servidor é alcançável a partir de Taiwan; só falta mesmo o token. Antes de enviar AT+QLBS, faça sempre AT+QIACT=1 (gera tráfego).

Os sete subitens de configuração têm botões de consulta e de escrita; o Cfg? (AT+QLBSCFG=?) lista todas as gamas num clique (zero tráfego). Valores de fábrica desta unidade e pontos medidos:

A rota alternativa: localização por rede sem token (71 metros medidos)

A localização por rede não depende do QuecLocator. A rota alternativa ficou fechada de ponta a ponta em 2026-08-29: o módulo só fornece o material (esta página faz o scan dos hotspots, e AT+QENG="servingcell" lê a célula), a saída do terminal é guardada em ficheiro e entregue ao tools/wifi_geolocate.py, que consulta bases de dados públicas no PC —— zero tráfego no módulo e sem serviços Quectel. Medições (comparadas com a verdade GNSS do mesmo dia): consulta de célula com a Unwired Labs (registo gratuito), erro de 71 metros (a conclusão que fecha esta linha de localização); com a beaconDB (sem chave), 632 metros; a consulta Wi-Fi ficou presa nos fornecedores —— o ecossistema gratuito ruiu (a beaconDB não cobre esta zona, o plano gratuito da Unwired Labs não inclui Wi-Fi, Google/HERE exigem cartão de crédito): adiada.

Os 71 metros são um «acerto de tabela», não «precisão de medição». A localização por célula usa o Cell ID para consultar as coordenadas registadas daquela estação; a mesma célula devolve sempre o mesmo ponto —— mudando de estação, o erro pode passar à ordem dos quilómetros; os ±1051 metros que o próprio serviço reporta é que são a estimativa honesta. Além disso, o Cell ID e o TAC vêm em hexadecimal e têm de ser convertidos para decimal antes da consulta (a ferramenta já o faz).
