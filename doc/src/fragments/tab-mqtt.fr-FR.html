MQTT — messagerie IoT

Principe de fonctionnement : MQTT est un protocole à « broker (serveur intermédiaire de messages) » : les appareils ne se connectent pas entre eux, chacun se connecte au broker et publie ou s'abonne à des « sujets (topics) ». Sur l'EG800K, il est à deux étages : d'abord AT+QMTOPEN ouvre la « connexion réseau » (TCP jusqu'au broker), puis AT+QMTCONN effectue la « connexion MQTT » ; il faut les deux étages pour s'abonner et publier. À retenir d'emblée : tous les résultats des commandes MQTT suivent le modèle « OK d'abord, URC ensuite » (comme FTP) — OK signifie seulement que la commande est acceptée, le verdict vient de l'URC de résultat qui suit.

Cette page utilise systématiquement le client 0 ; le firmware supporte aussi plusieurs clients (0–5), SSL et l'authentification des plateformes cloud (confirmé par mesure avec =?) ; usages avancés dans la note d'application MQTT.

Avant de commencer : deux prérequis

  1. Les URC doivent passer par l'UART : AT+QURCCFG="urcport" doit répondre "uart1". La valeur d'usine est "usbat", or tous les résultats MQTT sont des URC — sans ce changement, chaque commande répond OK puis plus rien (bouton disponible sur la page Basic ; écrit en NVRAM, une seule fois suffit).
  2. Le PDP doit être activé : appuyez d'abord sur AT+QIACT=1 dans la page TCP/IP (150 secondes maximum) ; sinon +QMTOPEN répond 3 = échec d'activation du PDP. Toute la séquence consomme des données, environ 5 KB estimés.

Ces quatre brokers sont totalement publics : n'importe qui peut s'abonner à vos sujets, et les messages d'autrui peuvent s'y mêler — c'est exactement le problème que le suffixe aléatoire vient résoudre.

Suffixe aléatoire du client ID et des sujets : il change à chaque rechargement

Le client ID et le sujet par défaut ne sont pas figés : au chargement de la page, un suffixe de 6 caractères hexadécimaux est généré, formant numodem-<suffixe> et test/numodem-<suffixe> ; les trois boutons Subscribe / Publish / Unsub partagent le même (sinon la boucle de retour ne se referme pas). Deux raisons :

  • Une collision de nom fait éjecter : MQTT 3.1.1 §3.1.4 impose au broker d'éjecter le premier connecté — deux personnes avec le même ID fixe s'éjectent mutuellement, symptôme d'apparence « déconnexions inexpliquées du module ».
  • Un sujet fixe reçoit les messages des autres : vous croyez recevoir le vôtre, mais non — c'est pire que de ne rien recevoir, car cela donne un faux succès.
⚠ À chaque rechargement de page, le suffixe change — l'abonnement et la publication doivent se faire dans le même cycle de vie de la page. D'autant que dans cet outil RTS = alimentation : recharger la page = couper le module, et toute la connexion MQTT disparaît ; il faut reprendre au rituel de démarrage et à AT+QMTOPEN.

Parcours complet : connexion → abonnement → publication → réception de son propre message

La validation la plus probante est la boucle de retour : s'abonner, publier sur le même sujet, recevoir son propre message — toute la chaîne d'émission-réception validée d'un coup. Attendez l'URC de résultat à chaque étape avant de continuer :

  1. Fixer la version du protocole : appuyez sur Ver 3.1.1 (AT+QMTCFG="version",0,4 ; 3 = 3.1, 4 = 3.1.1). Version? interroge la valeur actuelle (sans valeur = interrogation). La carte de paramètres Keepalive règle l'intervalle de maintien, mais le test marche sans y toucher.
  2. Ouvrir le réseau : appuyez sur Open Net (AT+QMTOPEN=0,"broker",1883). D'abord OK, puis le verdict dans l'URC +QMTOPEN: 0,<result> (0 = succès), attente jusqu'à 120 secondes. Open? liste les connexions ouvertes (sans connexion, réponse OK vide, mesuré normal).
  3. Connexion MQTT : appuyez sur Connect (AT+QMTCONN=0,"numodem-<suffixe>"). L'URC de succès est toujours +QMTCONN: 0,0,0. Les brokers publics n'exigent pas d'identifiants ; quand il en faut, ajoutez vous-même ,"user","pass" après les paramètres. Conn? interroge l'état (1 = initial, 2 = en connexion, 3 = connecté, 4 = en déconnexion).
  4. S'abonner : appuyez sur Subscribe (AT+QMTSUB=0,1,"test/numodem-<suffixe>",0, msgid figé à 1). L'URC de succès ressemble à +QMTSUB: 0,1,0,0. Dès lors, les messages de ce sujet arrivent en URC +QMTRECV.
  5. Publier : appuyez sur Publish (AT+QMTPUBEX, en deux temps, voir le paragraphe suivant). L'URC de succès est +QMTPUBEX: 0,<msgid>,0.
  6. Recevoir en retour : la cible de publication étant le sujet abonné, apparaît aussitôt +QMTRECV avec le sujet et le corps du message tout juste envoyé — boucle de retour réussie. Un payload en chinois passe sans troncature ni caractères corrompus.

QMTPUBEX en deux temps : envoi automatique à longueur atteinte, sans Ctrl+Z

Le dernier paramètre d'AT+QMTPUBEX est la longueur (en bytes), pas le contenu du message (tranché par la note d'application MQTT §3.3.8 — l'envoi sur une seule ligne avec le message dedans répond invariablement ERROR). La bonne procédure est en deux temps : envoyer la commande → le module répond l'invite > → envoyer exactement N bytes ; le module expédie automatiquement dès que la longueur est atteinte, sans Ctrl+Z (différent du mode données d'AT+QISEND de la page TCP). Le bouton Publish fait tout : remplissez seulement le contenu dans la carte de paramètres, la longueur est calculée automatiquement en bytes UTF-8 (un caractère chinois = 3 bytes ; mesuré : un mot de deux caractères chinois → 6).

  • Les commandes à payload n'offrent pas « recopier dans la ligne de commande » — la ligne de commande ajoute toujours une fin de ligne, et ce CR entrerait dans le décompte de longueur et décalerait tout ; envoyez par le bouton.
  • Le firmware possède aussi AT+QMTPUB (variante en mode données, terminée par Ctrl+Z) — cet outil utilise exclusivement QMTPUBEX, inutile d'apprendre les deux.

Lire les codes de résultat : chaque commande a son propre domaine de valeurs

N'appliquez pas la table de codes de la commande A à la commande B. Le 3 de +QMTOPEN signifie « échec d'activation du PDP », alors que +QMTPUBEX n'a même pas de valeur 3.

Le plus trompeur est +QMTCONN: 0,1 — il peut être la réponse d'interrogation « état 1 = en initialisation », ou le résultat d'écriture « retransmission de paquet en cours ». Une ligne seule ne permet pas de trancher : cet outil affiche donc les deux lectures côte à côte, sans deviner.

Pas besoin d'apprendre les tables par cœur : pour tous les URC de résultat, de +QMTOPEN à +QMTRECV / +QMTSTAT, la zone terminal annote chaque champ en clair d'après les sept tables de correspondance de la note d'application MQTT v1.5.

Déconnexion et clôture

  • Arrêter seulement la réception, en gardant la connexion : appuyez sur Unsub (AT+QMTUNS=0,2,"sujet", msgid figé à 2).
  • Déconnexion propre : appuyez sur Disconnect (AT+QMTDISC=0, envoie un DISCONNECT MQTT), réponse +QMTDISC: 0,0. Inutile d'appuyer ensuite sur Close Net — AT+QMTCLOSE=0 sert à forcer la fermeture quand « QMTDISC a échoué et la couche réseau est coincée ».

Les déconnexions que vous n'avez pas demandées (éjection, timeout de keepalive, perte réseau) sont rapportées par l'URC de déconnexion anormale +QMTSTAT (ex. : +QMTSTAT: 0,5, la zone terminal annote la cause) ; il faut alors reprendre à AT+QMTOPEN.

SymptômeCause et solution
Chaque commande répond OK, puis plus rien Les URC partent vers le port USB — urcport vaut usbat d'usine, basculez sur uart1 (voir prérequis 1)
+QMTOPEN: 0,3 Échec d'activation du PDP — AT+QIACT=1 d'abord (page TCP/IP), puis recommencez
Abonné mais aucun de ses propres messages ne revient La page a été rechargée entre-temps — suffixe changé, module coupé puis redémarré. Refaites tout le parcours dans un même cycle de vie de la page
Des messages reçus que vous n'avez pas envoyés Pollution de sujets des brokers publics (mosquitto est le pire). Le sujet par défaut porte déjà le suffixe aléatoire ; pour un sujet personnalisé, choisissez un nom vraiment distinctif
Une partie des messages se perd en publication massive emqx limite le débit de publication (mesuré : rafale de 100, seuls 40 passent) — passez à mqttgo.io ou hivemq (100/100 sans limitation)
