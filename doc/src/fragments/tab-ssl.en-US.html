SSL — TLS channels

Working principle: the SSL page is the shared substrate of encrypted connections — the SSL context configured here and the certificates uploaded here serve SSL raw sockets, MQTT over SSL and HTTPS alike. All timings and behavior in this section were measured on a physical EG800K in August 2026.

Your first TLS connection: five steps

  1. Run the power-up ritual (see the Power-Up Ritual section), then click AT+QIACT? to confirm the data channel — it must return +QIACT: 1,1,…,"IP"; if not, run AT+QIACT=1 first.
  2. Configure the context: set sslversion to 4 (all versions, best compatibility), ciphersuite to 0XFFFF (all suites), and seclevel to 0 for now — first prove the channel works; leave verification for later.
  3. Open the connection: click AT+QSSLOPEN (trailing code 0), fill host and port in the parameter card. ⚠ OK only means "command accepted"; success rides on the URC: only +QSSLOPEN: 4,0 is success (measured handshake: 2.0 seconds).
  4. Send data: click AT+QSSLSEND (two-stage) — after the > appears, send the payload; it sends automatically once the declared length is counted out, no Ctrl+Z (single-packet limit 1460 bytes). The peer's reply shows up as +QSSLURC: "recv",4.
  5. Read back and close: AT+QSSLRECV (1500 per read) — reading down to +QSSLRECV: 0 means the buffer is drained, not an error. AT+QSSLCLOSE=4 closes (default wait up to 10 seconds; the other button takes a seconds value, 0 = immediate).

While connected you can click AT+QSSLSTATE to see all connections (=4 queries a single clientID; state 2 = connected). Note that the local port always reads 0 — module behavior, not an error.

Context settings, item by item

Unsure which sub-items the firmware supports? Click AT+QSSLCFG=? first — measured, it returns 17 sub-items, more than the application note lists. The common sub-items each have a set and a query button; measured, what is written reads back identically.

Sub-itemFactoryEffect and measured notes
sslversion—Protocol version; 4 = all supported
ciphersuite—Cipher suites; 0XFFFF = all supported
seclevel00 = no verification, 1 = verify the server (requires a CA certificate uploaded first), 2 = mutual authentication (also needs a client certificate + private key)
cacert—CA certificate path, in the form "UFS:filename"; the file must already be in UFS (see the next section)
sni🔴 0 Mandatory for virtual hosts / CDNs — with many domains on one IP, omitting SNI gets you a mismatched certificate and verification always fails with 566
ignorelocaltime🔴 1 From the factory, certificate validity dates are not checked even with seclevel 1. To check them, set 0 — and the module clock must be right
negotiatetime300 Maximum TLS handshake wait in seconds (10–300)
🔴 The three factory defaults together = no certificate verification at all (seclevel 0, sni 0, ignorelocaltime 1); to truly verify, all three must be set right. And these three settings plus cacert do not survive reboots (confirmed by testing) — every boot returns them to factory values; the certificate files in UFS, however, survive power loss.

The UFS file group: how certificates get into the module

UFS is the module's built-in flash storage; measured total capacity 280 KB, each file occupying one 4 KB block. Certificates must be uploaded here first before cacert has a file to point at. Uploads go over the UART at zero data cost, and binary files go through too. The Upload card: after picking a file, the name and size fill in automatically; on submit the tool waits for the module's CONNECT before sending the raw bytes (no CONNECT, nothing is sent). On completion the annotation engine automatically compares the module's reported size and checksum: ✅ = intact, ❌ = corrupted in transit — delete first, then re-upload.

AT+QFUPL="badssl-root.pem",1939,10
CONNECT                   ← now send 1939 bytes
+QFUPL: 1939,4f64         ← received size,checksum; the annotation compares automatically ✅
ButtonPurpose
AT+QFLSTLists every UFS file with its size — use it to verify after upload (zero data cost)
AT+QFLDS="UFS"Queries free / total space in bytes (zero data cost)
AT+QFDELDeletes the named file (* = all); re-uploading without deleting the namesake first gets blocked
Two measured behaviors the manual never spells out: (1) FILE error codes are inconsistent in form — a same-name re-upload returns the text file already exist, a timeout returns the number 421; this tool decodes both. (2) If the size field is larger than the actual file, after the timeout the module still saves what it received as the file — the checksum comparison catches it.

Certificate verification in practice: the paired-test method

Procedure: upload the root certificate → point cacert at it → seclevel 1 → sni 1 → connect to the target's 443. What you upload is the root certificate at the top of the chain (badssl.com's chain has four levels; upload the topmost ISRG Root X1). Testing only "bad certificates fail to connect" is not enough — "nothing connects at all" would also pass. Test in pairs: the good certificate connects and the bad one is refused — it only counts when both directions hold. Measured 2×5 comparison:

Hostseclevel 0seclevel 1
badssl.com (positive control)Connects Connects 4,0
expiredConnectsRefused 566
self-signedConnectsRefused 566
wrong.host (hostname mismatch)ConnectsRefused 566
untrusted-rootConnectsRefused 566

Limitation: all four certificate errors return 566; the module does not distinguish which one it was. AT+QIGETERROR cannot help either — it covers the TCP/IP layer and at this point only returns 0,operate successfully.

For the negative test, avoid expired — the factory ignorelocaltime is 1, so expiry alone is not blocked (it is blocked in the table above only because it also sits outside the uploaded root); for a standalone test use wrong.host. Also watch the data usage: every handshake downloads the full certificate chain, failures included — measured, 30 handshakes cost about 150–200 KB.

🔴 Trap: after about 20 consecutive open/close cycles, the data stack degrades wholesale

Symptom: every AT+QSSLOPEN returns 552 — even seclevel 0 cannot connect, while every self-check says all is well. The 30-second triage: hit the same target with plain-TCP AT+QIOPEN — if that fails too, the data stack is broken; stop auditing SSL settings. A PDP restart cannot save it; only the full power-up ritual recovers. The degradation contaminates test data and is easily misread as "blocked by certificate verification" — reboot to a clean slate before running paired tests.
