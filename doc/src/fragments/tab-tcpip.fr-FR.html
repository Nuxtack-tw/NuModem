TCP/IP — la racine des connexions de données

Principe de fonctionnement : cette page est la fondation de tous les protocoles de données. Le contexte PDP (le canal de données attribué par le réseau mobile) ne s'active et ne se désactive que sur cette page ; les pages SSL / HTTP / MQTT / FTP ne contiennent que des interrogations en lecture seule, pour éviter qu'une même commande se marche dessus depuis deux endroits. Tous les pièges et durées de cette section sont des mesures d'août 2026 sur le matériel réel.

Première étape : activer le PDP (QICSGP / QIACT / QIDEACT)

Appuyez sur Act PDP (AT+QIACT=1) : blocage jusqu'à 150 secondes, n'envoyez aucune autre commande pendant ce temps ; le trafic commence à partir de là (en itinérance, attention aux coûts). Après le succès, appuyez impérativement sur Query IP (AT+QIACT?) et vérifiez la réponse +QIACT: 1,1,1,"adresse IP" — avant activation, elle ne renvoie que OK. Pour raccrocher, appuyez sur Deact PDP (AT+QIDEACT=1, 40 secondes maximum), qui ferme de force toutes les connexions en dessous. Set APN (AT+QICSGP) est inutile en temps normal — le module synchronise tout seul l'APN attribué par le réseau (mesuré : la carte 1NCE relit iot.1nce.net dès le démarrage) ; seuls les APN d'entreprise à identifiants en ont besoin.

Act PDP répond ERROR, Last Error 572 ? Cette carte n'autorise qu'un seul PDP. Au démarrage, le réseau en a déjà activé un et son numéro flotte (mesuré : 9 et 1 selon les fois) ; AT+QIACT ne peut atteindre que 1–8. Solution : page Network, AT+CGACT? pour lire le numéro → AT+CGACT=0,<numéro> pour libérer la place → puis Act PDP.

Tout tombe en plein test ? AT+QIACT? ment — en cas de dérive du PDP, il renvoie encore une IP ; seul le croisement avec AT+CGACT? révèle le problème. Récupération : Deact PDP → AT+CGACT=0,<numéro de dérive> → Act PDP → validation par Ping.

Ouvrir une connexion : OK signifie seulement « commande reçue »

Appuyez sur Open TCP et remplissez hôte et port dans la carte de paramètres (AT+QIOPEN=1,0,"TCP","hôte",port,0,0 ; contexte 1, connectID 0, mode buffer déjà figés). OK signifie seulement que la commande est acceptée ; le verdict vient de l'URC +QIOPEN: 0,<err> : 0 = succès, jusqu'à 150 secondes ; 563 = le connectID est encore ouvert, appuyez d'abord sur Close Sock. All Socks (AT+QISTATE) liste tous les sockets, state 2 = connecté.

Envoyer des données : trois méthodes

BoutonDescription
Send Text
AT+QISEND=0,<len>		 Envoi en deux temps à longueur fixe : attendre > puis envoyer le corps ; longueur calculée automatiquement, pas de Ctrl+Z nécessaire. Premier choix pour du texte pur ; limite 1460 bytes, échappements \n \r \t \xHH acceptés
Les trois boutons Send Var
AT+QISEND=0		 Longueur variable : le mode données absorbe tout jusqu'au Ctrl+Z (0x1A) qui déclenche l'envoi — écriture en plusieurs fois possible, voir le paragraphe suivant
Send Hex
AT+QISENDEX=0,"hex"		 Envoi sur une seule ligne, sans mode données. Accepte tout octet (y compris 0x00) ; limite 512 caractères hex = 256 bytes réels

Envoyer (continuer) : le premier appui entre en mode données, chaque appui suivant ajoute un bloc (en mode données, la commande n'est pas renvoyée — la renvoyer en ferait des données) ; Envoyer puis terminer ajoute le bloc et complète par Ctrl+Z, le plus rapide pour un seul bloc ; Terminer (Ctrl+Z) expédie d'un coup tout le contenu accumulé. Le terminal signale l'entrée en mode données ; pour abandonner, appuyez sur ESC Cancel (0x1B, la touche d'évasion quand un envoi en deux temps se bloque). ⚠ Les données ne doivent pas contenir 0x1A (interprété comme fin prématurée) ; pour les caractères de contrôle, passez par Send Hex.

SEND OK ne prouve pas que l'autre bout a reçu : seulement que les données sont confiées au module. Appuyez sur Check ACK (AT+QISEND=0,0) pour lire envoyé / acquitté : seul acked compte.

Recevoir des données : rien n'apparaît tout seul, il faut Read Data

En mode buffer, les données reçues n'apparaissent pas automatiquement dans le terminal : le module n'émet que la notification +QIURC: "recv",0, et il faut les extraire avec Read Data (AT+QIRD=0,1500), en relisant jusqu'à obtenir +QIRD: 0 — tant que tout n'est pas vidé, aucune nouvelle notification ne viendra. Unread Len (AT+QIRD=0,0) interroge total reçu / lu / non lu. Une fois l'échange terminé, appuyez sur Close Sock (AT+QICLOSE=0, 10 secondes maximum). ⚠ Aucune notification recv du tout ? Vérifiez sur la page Hardware si AT+QURCCFG="urcport" vaut bien uart1 — la valeur d'usine est le port USB, et tous les URC partent là-bas.

Les deux caprices du pair intégré tcpbin.com

Le pair par défaut d'Open TCP est le serveur d'écho gratuit tcpbin.com:4242, avec deux caprices mesurés :

  • Écho ligne par ligne, saut de ligne (0A) obligatoire en fin : Hello sans 0A, 6 secondes sans réponse ; avec le 0A, réponse en 0.1 seconde. Terminez Send Text par \n, Send Hex par 0A.
  • Timeout d'inactivité de 15 secondes : à l'inactivité, la connexion est coupée et vous recevez +QIURC: "closed",0. QIRD n'y change rien (il ne lit que le tampon local, sans toucher au réseau). Pour maintenir la connexion, envoyez des données au moins toutes les 10 secondes. Après le closed, le socket reste en closing : il faut d'abord appuyer sur Close Sock avant de le réutiliser, sinon QIOPEN répond 563.

En cas d'erreur : Last Error d'abord, puis le discriminant des 30 secondes

Dès qu'une commande répond ERROR, appuyez immédiatement sur Last Error (AT+QIGETERROR) — seule la dernière erreur est conservée ; écrasée par la suivante, elle devient introuvable. Il interroge la couche de la pile Quectel ; pour la couche réseau, utilisez le AT+CEER de la page Network.

🔴 Dégradation de la pile de données — le piège le plus chronophage. Symptôme : toutes les connexions échouent systématiquement, mais tous les autodiagnostics disent que tout va bien (QIACT? a une IP, QIGETERROR répond 0). Mesuré : déclenché après environ 20 cycles d'ouverture/fermeture SSL ; même le QIOPEN d'un TCP pur répond 552 ; QIDEACT + QIACT n'y peuvent rien, seul un nouveau rituel de démarrage restaure l'état.

Discriminant en 30 secondes : visez la même cible avec Open TCP — échec aussi = toute la pile est morte, refaites le rituel de démarrage ; succès = le problème est dans le protocole du dessus, continuez à chercher.

Keepalive : tient tête au NAT de l'opérateur, pas à tcpbin

QICFG=? liste les sous-réglages et leurs plages, Keepalive? lit la valeur actuelle, Keepalive On / Off commute — ces quatre commandes sont en elles-mêmes à zéro trafic ; une fois activé, tant qu'un socket reste inactif, les paquets de sonde comptent dans le trafic mobile. Il ne tient pas tête au timeout de 15 secondes de tcpbin : mesuré, coupure à 15.1 secondes malgré l'activation — le keepalive est une sonde vide de la couche TCP, invisible pour l'application ; et l'intervalle minimal est de 25 secondes, déjà supérieur à 15. Pour survivre à un timeout applicatif, il faut envoyer de vraies données (par ex. un 0A en Send Hex toutes les 10 secondes). Son vrai rôle est le maintien du NAT de l'opérateur (le NAT des cartes IoT est recyclé après quelques minutes d'inactivité).

Comptabilité du trafic (estimation, non mesurée) : une sonde aller-retour vaut environ 80 bytes ; idle par défaut = 30 secondes d'inactivité continue → environ 9.4 KB par heure, environ 225 KB par jour, environ 6.8 MB par mois ; idle = 600 secondes → environ 11 KB par jour. Avec une carte prépayée au volume comme 1NCE, augmentez l'idle. Sans socket ouvert, aucune consommation.
