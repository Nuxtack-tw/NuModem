🎯 簡介

NuModem EG800 是一支單一 HTML 檔的 4G modem 控制台。它透過瀏覽器的 Web Serial API 直接對 Quectel EG800K 系列模組下 AT 指令， 不需要安裝任何東西、不需要驅動程式以外的軟體、也沒有後端伺服器。

它跟一般的序列埠終端機差在哪？差在它看得懂 AT 指令。 每一條你送出的指令、每一行模組回來的回應，旁邊都會即時附上一句人話說明 —— 包括那些只有數字的錯誤碼。

這份說明書涵蓋什麼
從打開網頁、接上模組、跑開機儀式開始，一路到十個功能頁簽裡每一組 AT 指令的 工作原理與測試方式。所有的行為描述都來自 2026 年 8 月對實體 EG800K 的實測，不是照抄手冊 —— 手冊寫錯的地方本文會直說。

🚀 快速開始

步驟 1 —— 開啟 NuModem

用 Chrome 或 Edge 開啟 NuModem_EG800.html —— 按兩下就行，不必架伺服器。

步驟 2 —— 接上模組

按左上角的 連線。瀏覽器會跳出接埠選擇視窗，挑你的 USB-UART 橋接器。 右邊的箭頭可以展開下拉選單，直接挑先前授權過的接埠。

授權過一次之後，之後開啟頁面按「連線」就會直接接上，不會再問。 如果你有多個序列裝置，用下拉選單挑會比較快。

步驟 3 —— 確認鮑率

頂端的鮑率選單預設 115200，EG800K 出廠就是這個值，通常不用改。

步驟 4 —— 跑開機儀式

這一步不能跳過。瀏覽器打開序列埠的瞬間會重新拉高 RTS， 而這塊控制板的 RTS 是負邏輯的電源開關 —— 也就是說 連上線的同時模組就被斷電了。 詳細步驟見下一節。

跳過開機儀式最典型的症狀是：你送出的指令終端機都看得到，但完全沒有任何回應。 那不是鮑率錯、也不是線接反，是模組根本沒通電。

🔌 開機儀式（最重要的一節）

EG800K 不是插電就會開機。這塊控制板把兩條 RS-232 的輸出訊號接到了模組的控制腳：

訊號接到哪邏輯
RTS模組電源開關 負邏輯：RTS OFF ＝ 通電、RTS ON ＝ 斷電
DTR模組 Reset 腳 DTR ON ＝ Reset 拉高（可啟動）、OFF ＝ Reset 拉低

標準程序

切到 Hardware 頁簽，那裡有兩顆專用按鈕：

  1. Power —— 讓 RTS 走過一次 ON → OFF。 按鈕亮綠色代表電源已開（也就是 RTS 處於 OFF）。
    ⚠ 直接設 OFF 不保證通電，一定要先 ON 再 OFF。
  2. 停一秒。
  3. Reset —— 這是「按住才生效」的按鈕： 按下時 DTR 拉到 OFF、放開時回到 ON。中間按住約 300 毫秒。
  4. 等終端機出現 RDY。實測數秒內就會出現。

你也可以用訊號列上的 RTS / DTR 直接點，效果一樣， 只是要自己數順序。

怎麼確認開機成功

終端機應該依序吐出這些：

RDY              ← 模組開機完成
+CFUN: 1         ← 射頻已開
+CPIN: READY     ← SIM 就緒
+QUSIM: 1
+QIND: SMS DONE  ← 簡訊初始化完成
+QIND: PB DONE   ← 電話簿初始化完成

然後送一條 ATI 驗證，應該回廠牌、型號、韌體版本三行加 OK。

⚠ 每次重新整理頁面都要重跑一次開機儀式。 重載頁面會重開序列埠，而重開序列埠會重新 assert RTS —— 等於又把模組斷電了一次。這是本工具最常被誤判成「模組壞了」的原因。

開機後建議先下的兩條

指令為什麼
ATE1 開啟複誦。模組會把收到的指令原樣回吐一次， 這樣終端機上「你送的」與「模組真的收到的」可以對照，打錯字一眼就看得出來。
AT+CMEE=2 把錯誤訊息改成文字敘述。沒開的話錯誤只會是乾巴巴的 ERROR； 開了才看得到 +CME ERROR: SIM not inserted 這種可讀訊息。

這兩條都是 session-only，模組重開機後要重下。

🔴 收不到任何 URC 時，第一個要查的是 AT+QURCCFG="urcport"。 模組出廠把 URC（主動回報訊息）送到 USB AT 埠， 走 UART 的本工具一條都收不到 —— 症狀是「指令都回 OK 但就是沒有後續訊息」， GNSS 定位、TCP 資料到達、MQTT 訊息、Wi-Fi 掃描結果全部靜默。 解法：AT+QURCCFG="urcport","uart1"，這條寫 NVRAM、跨重開機有效。

📟 終端機

右半邊就是終端機。它跟一般序列終端機最大的不同是每一行都有註解。

四種顏色都可以自己改，點顏色方塊就會開色盤。

註解引擎

這是 NuModem 的核心。它做兩件事：

  • 解釋你送出的指令 —— 例如送 AT+QSSLSEND=4,18，旁邊會寫「對 clientID 4 送出固定長度 18 bytes： 模組回 > 提示後要『剛好』送滿 18 個位元組才會發出，不必送 Ctrl+Z」。
  • 解讀模組的回應 —— 尤其是那些純數字的碼。 例如 +QFTPSIZE: 627,550 會被拆成兩層： 「錯誤 627：FTP 未執行所請求的動作；伺服器回覆 550：動作未執行：檔案或目錄不存在」。
註解會跟著你實際填的參數走。同一顆按鈕填不同的值， 註解裡的數字就會跟著變 —— 它不是固定的說明文字。

行尾

輸入框右邊可以選行尾。EG800K 必須用 CR， 選 LF 的話模組完全不會回應。這是最容易踩的設定。

其他

  • 底部顯示累計的 RX / TX 位元組數與目前接埠名稱。
  • 右上角一排按鈕：註解開關、行尾、時間戳、自動捲動、清除。
  • 終端區還有衛星狀態與地圖兩個頁簽， GNSS 定位成功後會有內容。

🎛️ AT 指令面板的運作方式

左半邊是十個頁簽、兩百多顆按鈕。在看個別頁簽之前，先理解這幾個共通機制， 之後每一頁都用得上。

兩種按鈕

樣式行為
一般按鈕點下去直接送出
虛線框有參數要填。填好後可以「送出」， 也可以「填入命令列」把組好的指令丟到下方輸入框，自己再改

參數欄位

每個欄位都有自己的說明（滑鼠移上去會出現），寫的是本機實測的範圍， 不是照抄手冊。例如 Wi-Fi 掃描的「輪數」寫的是 1-3， 因為 AT+QWIFISCAN=? 實際就回這個範圍 —— 應用文件寫的 1-6 是錯的。

兩段式送資料

有些指令不是一行送完就結束的。它們的流程是：

送出指令  →  模組回 > 或 CONNECT  →  送出剛好 N 個位元組  →  模組回結果

這類按鈕有一個獨立的「資料內容」欄位，長度會自動計算並填進指令， 你不必自己數。屬於這一類的有 AT+QISEND、AT+QSSLSEND、AT+QMTPUBEX、 AT+QHTTPURL、AT+QHTTPPOST、AT+QFTPPUT。

長度算錯的下場很難看。模組會一直等到收滿你宣告的位元組數為止， 期間 AT 口是「資料模式」—— 你後面打的任何東西都會被當成資料吞掉。

脫身方法：用 Hardware 頁的原始位元組按鈕送一個 ESC（0x1B）。 不必關連線、也不必重開模組。

跳脫序列

資料內容欄位是單行文字框，打不出換行、Tab 這類控制字元。 所以這些欄位支援跳脫序列：

寫法送出的位元組
\n0x0A 換行
\r0x0D 歸位
\t0x09 Tab
\00x00 NUL
\xHH任意位元組，HH 是十六進位
\\反斜線本身

解碼發生在送出前，長度也是以解碼後的位元組數計算。 例如 hello\n 在欄位裡是 7 個字元，但送出去是 6 個位元組， 指令裡填的長度就會是 6。

為什麼這件事很重要：很多測試伺服器是逐行回聲的 （送什麼就回什麼，但要看到換行才動作）。 payload 結尾沒有 \n，你就永遠收不到回應 —— 而且看起來會像「連線壞了」。

逾時標示

有些 AT 指令會阻塞很久。按鈕上的 ⏱ 標示就是手冊寫的最長等待時間， 例如 AT+QIACT=1 最長 150 秒、AT+COPS=? 最長 300 秒。 看到很久沒回應時先看這個標示，多半只是還沒到時間。

確認對話框

會把 AT 口卡在資料模式、或是不可逆的動作（刪除遠端檔案、軟重啟模組、換鮑率） 才會跳確認框。單純「會用到流量」不會擋你 —— 那類提醒改放在按鈕說明裡。

本機開關

少數按鈕下面有一個小勾選框，那是工具端的行為不是 AT 指令。 例如 AT+QICLOSE=0 底下的「偵測到 +QIURC: "closed",0 時自動關閉」。 這些選項會存在瀏覽器裡，下次開啟還在。

Hardware —— 開機與序列埠

工作原理：這一頁是整個工具的地基： Control 是開機儀式的兩顆按鈕（Power／Reset）、Module 是產品識別、 Serial 是 UART 設定、Power 是低功耗、URC 管模組主動訊息的輸出埠， 另有一排原始位元組鈕（Ctrl+Z／ESC／+++）當資料模式的逃生門。 其他頁簽都建立在兩個前提上：模組已照儀式開機、 URC 走 uart1 —— 這兩件事都在本頁完成。 本節行為與數字皆為 2026 年 8 月對實體 EG800K 的實測。

為什麼要有開機儀式：RTS＝電源、DTR＝Reset

本工具搭配的控制板把兩條 RS-232 交握訊號挪作他用，這是理解整頁的鑰匙：

訊號實際接到邏輯
RTS模組電源開關 負邏輯：RTS OFF＝通電、RTS ON＝斷電
DTR模組 Reset 腳 DTR ON＝Reset 拉高（可啟動）、DTR OFF＝Reset 拉低

電路特性（實測確認）：首次連線 RTS 必須先 ON 再 OFF， 電源才會真的打開 —— 直接設 OFF 不保證通電；DTR 也要走 ON→OFF→ON， Reset 才會真的拉高。斷電（RTS ON）是硬切，模組不會送任何告別訊息。

重新整理頁面＝斷電。瀏覽器重開序列埠時會重新拉起 RTS， 模組直接失電 —— 自動重連完成後必須重跑開機儀式。 實測踩過：跳過儀式直接送 17 條指令，全部有去無回（只有 TX 行、零 RX）。 任何「剛剛還好好的、現在全沒反應」，先想到這件事。

Power 與 Reset 鈕：怎麼按、會看到什麼

兩顆鈕就是上表兩條訊號的化身，與訊號列的 RTS／DTR 指示雙向連動 （未連線時反白不可按）。Web Serial 讀不回輸出訊號的實際狀態， 訊號列顯示的是本工具送出的認知值。

  1. Power（切換式）：亮綠＝電源 ON（＝RTS OFF）。 開機儀式要讓 RTS 走過 ON→OFF：鈕若已亮，先點關再點開。
  2. Reset（momentary）：按下＝DTR OFF、放開＝DTR ON， 一按一放就是一次 Reset（標準時序中間停 0.3 秒）。
  3. 等 RDY：數秒內終端機會出現模組的開機宣告 RDY。
  4. ATI 驗證：應回 Quectel／EG800K／ Revision: …／OK。回得出來＝UART 與模組都活著。
開機後建議先確認複誦（ATE）為開（出廠預設開），再下 AT+CMEE=2 —— 沒開只會看到乾巴巴的 ERROR，開了才有 +CME ERROR: … 的可讀文字。兩者皆 session-only，模組每次重開都要重下。

Serial：AT&V 讀參數、IPR 改鮑率

AT Params（AT&V）：列出所有單字母 AT 參數目前值。 ATE／ATQ／ATV 這些單字母指令沒有各自的查詢式， 只有這條讀得到。本機實測 E:1 Q:0 V:1 S3:13 S4:10 —— 複誦開、結果碼文字模式、行尾＝CR（ASCII 13），正是本工具解析回應的前提。

Baud?（AT+IPR?）：查 UART 目前鮑率，出廠 115200。
Baud List（AT+IPR=?）：回兩份清單 —— 前一份是可自動偵測的鮑率、後一份是僅固定模式可用的。跑過這顆之後， Set Baud 的下拉選單會換成本機實際回報的清單。實測本機第二份清單一路列到 1000000 bps —— 手冊 §3.4 的表沒有這個值。

Set Baud（AT+IPR={rate};&W，參數卡）： 按下會先跳確認框 —— 這是全頁最容易把自己鎖在門外的一顆鈕。

改鮑率的三重陷阱（實測全數確認）：
① OK 一回就立即生效， 本工具下一刻起與模組雞同鴨講；
② AT&F（原廠重置）不會把鮑率改回來 —— 別指望它救你；
③ 不加 &W 就不存檔 —— 而重連＝斷電，模組會醒在舊鮑率、 你的埠設定卻停在新鮑率，雙重失聯。 所以本工具強制 ;&W 合體寫法。
復原四步（確認框也會提醒）：斷線 → 改連線區的鮑率 → 重連 → 重跑開機儀式。

Power：QSCLK 低功耗

Sleep?（AT+QSCLK?）：查模組是否允許進入睡眠。 本機實測出廠為 0＝停用、模組常醒。 本頁只提供查詢鈕：睡著的模組會停止回應 AT，手冊的喚醒方式是拉低 DTR —— 但本板的 DTR 已接去當 Reset 腳（見本節開頭）。若在命令列自行開了睡眠而叫不醒， 重跑開機儀式（斷電重開）即可脫困；細節見官方低功耗應用筆記。

URC：收不到訊息時，第一個來這裡

URC（Unsolicited Result Code，非請求結果碼）是模組「未經請求就主動吐出」 的訊息，不是任何指令的回應 —— 開機的 RDY、TCP 資料到達、MQTT 訊息、 Wi-Fi 掃描結果、GNSS 韌體載入通知全是。它的輸出埠 出廠預設是 USB 埠（usbat） —— 走 UART 的本工具一條都收不到， 症狀非常典型：指令都回 OK，就是等不到訊息。

開機之後：RDY 不等於 SIM 就緒

RDY 是模組開機完成時主動送出的 URC。 它只代表 AT 介面活了，SIM 卡還在後面慢慢初始化。 實測：RDY 一出現就送 SIM 相關指令，會回 +CME ERROR: 14（SIM busy）甚至 +CME ERROR: 13（SIM failure）； 等約 6 秒後再送就一切正常。

開始之前：天線決定一切

定位失敗的第一大原因不是指令下錯，是天線收不到訊號。 實測對比：室內、天線不佳時，模組能列出 38 顆衛星的位置卻一顆都聽不到 （SNR 全部 00）；換上主動式（active）GNSS 天線並放到窗邊後， 冷啟動 95 秒內就定位成功。

室內測不了 GNSS，怎麼等都沒用。沒有天空視野時 $GNGGA 會回「使用衛星 00 顆、定位品質 0」， AT+QGPSLOC 永遠回錯誤 516。 請把天線移到窗邊或戶外再開始 —— 這不是耐心問題，是物理問題。

第一次定位：五個步驟

  1. 跑開機儀式（見〈開機儀式〉一節）。 ⚠ 每次重新整理頁面都等於斷電，GNSS 的開啟狀態與收到一半的星曆全部歸零， 要從這一步重來。
  2. 確認 URC 走 UART：AT+QURCCFG="urcport" 要回 "uart1"。出廠值是 "usbat"，不改的話很多結果訊息 會被送去 USB 埠，這裡什麼都看不到（設定寫 NVRAM，改一次就好）。
  3. 開 GNSS：按 AT+QGPS=1。 幾秒內會看到 +QGPS: "firmware",0,0（GNSS 韌體載入成功）。 已經開著再按會回 +CME ERROR: 504，無害。
  4. 看收訊：按 AT+QGPSGNMEA="GSV" 讀可見衛星。 終端區會自動打開衛星頁簽，畫出訊號柱狀圖與天空圖 —— 判讀方式見下段。
  5. 輪詢定位：每 5–10 秒按一次 AT+QGPSLOC=2。 回 DSAT_CME_GNSS_NOT_FIXED_NOW（錯誤 516）代表還沒定到， 繼續等就好。成功時會回座標， 終端區自動打開地圖頁簽並把位置畫上去。

判讀衛星頁：「看得到」不等於「聽得到」

GSV 每顆衛星有四個數字：編號、仰角、方位角、SNR（訊號雜訊比，dB-Hz）。 前三個只是「它應該在天上哪裡」，只有 SNR 才代表真的收到訊號。

SNR意義
（空）或 00完全沒收到 —— 只知道它在哪，聽不到它
14–28邊緣：解調星曆常出錯重來，定位又慢又不穩
30 以上可穩定解調；多數衛星到這個水準，定位就快了
40 以上開闊天空＋好天線的水準

為什麼要等：冷啟動的物理限制與實測時間

定位需要每顆衛星的精確軌道（星曆），而星曆藏在衛星以 50 bps 廣播的訊號裡 —— 一顆要連續正確解調約 18–30 秒， 錯一個位元就重來，還得湊滿至少 4 顆。這就是「冷啟動」慢的原因。 本機實測（同一地點、主動式天線、量測解析度 ±5 秒）：

AGNSS 加速：完整流程

原理：AGNSS 把星曆改成從網路下載（每次約 32–34 KB）， 跳過 50 bps 慢速解調。它不能無中生有衛星訊號 —— 室內照樣定不到位，它省的只有「等星曆」的時間。

兩個最容易漏掉的前提，漏掉任何一個 AGNSS 就靜靜地完全不動作，不會報錯：

前提指令陷阱
AGNSS 已啟用AT+QAGPS=1 ⚠ 重開機才生效（寫 NVRAM，設一次就好）
PDP 已啟用AT+QIACT=1 ⚠ 每次開機都要重下。AT+CGATT? 回 1 不算數 —— 附著只是網路層註冊；要 AT+QIACT? 回得出 +QIACT: 1,1,…,"IP" 才有資料通道

完整順序（每次開機後）：

AT+QIACT=1          ← 開資料通道（最長等 150 秒；產生流量）
AT+QIACT?           ← 必須看到 +QIACT: 1,1,…,"IP"
AT+QGPS=1           ← 開 GNSS；AGNSS 會在此時自動下載輔助資料
AT+QGPSLOC=2        ← 每 5–10 秒輪詢

怎麼確認 AGNSS 真的在動？本機韌體不會發 +QGPS: "agps" 之類的提示（實測確認），要看旁證，三選一即可：

  1. AT+QGDCNT? 在 AT+QGPS=1 前後查兩次， 收方向多了約 30 KB ＝ 輔助資料下載了
  2. GSV 在幾秒內就列出大量衛星的位置（SNR 可能還是 00）—— 位置是下載來的，自己解調不可能這麼快
  3. $GNGGA 的時間欄位有值（時間也是輔助資料的一部分）
偽定位陷阱：零顆衛星的座標不是定位。 AGNSS 啟動約 20 秒後，AT+QGPSLOC 可能回出一筆座標， 但仔細看：HDOP 0.00 / alt 0.0 / nsat 00 —— 那是輔助資料裡的參考位置注入，不是量測結果，誤差可能很大。

真定位的判準：使用衛星數 > 0、定位模式 ≥ 2、HDOP > 0。 寫自動化或產品邏輯時，不能只看「有沒有回座標」。

apflash：斷電重開也能快（有條件）

AT+QGPSCFG="apflash" 出廠即為 1：每次定位成功會把星曆存進 flash，下次開機自動匯入 —— 一小時內斷電重開就從冷啟動變快速熱啟動， 零流量。兩個限制：星曆約一小時就過期； 以及要先成功定位過一次，flash 裡才有東西可匯入 —— 從來沒定位成功的模組，apflash 幫不上忙。

定位成功之後：地圖頁

每次 AT+QGPSLOC 成功，位置就畫進地圖頁： 藍色標記是最新位置、青色線是移動軌跡、每個軌跡點滑鼠移上去有當地時間與高度。 摘要列顯示座標／高度／HDOP／衛星數，時間自動依經度換算當地時區。

TCP/IP —— 資料連線的根

工作原理：這一頁是所有資料協定的地基。PDP context （電信網路配給的資料通道）只在這一頁啟用與停用，SSL／HTTP／MQTT／FTP 各頁只放唯讀查詢，避免同一條指令兩處互踩。 本節陷阱與秒數皆為 2026 年 8 月實機實測。

第一步：啟用 PDP（QICSGP／QIACT／QIDEACT）

按 Act PDP（AT+QIACT=1）：最長阻塞 150 秒、 期間勿下其他指令，從此開始產生流量（漫遊注意費用）。成功後一定要按 Query IP（AT+QIACT?）確認回 +QIACT: 1,1,1,"IP位址" —— 沒啟用前只回 OK。收線按 Deact PDP（AT+QIDEACT=1， 最長 40 秒），會強制關閉其下所有連線。Set APN （AT+QICSGP）平常不必按 —— 模組會自動同步網路配的 APN （實測 1NCE 卡開機讀回已是 iot.1nce.net），要帳密的企業 APN 才需要。

Act PDP 回 ERROR、Last Error 572？這卡只允許一條 PDP。 開機時網路已自動啟用一個且編號會浮動（實測見過 9 與 1）， AT+QIACT 只碰得到 1–8。解法：Network 頁 AT+CGACT? 查編號 → AT+CGACT=0,<編號> 讓出名額 → 再按 Act PDP。

測到一半全掛？AT+QIACT? 會騙人 —— PDP 漂移時 它照樣回 IP，要與 AT+CGACT? 交叉比對才看得出來。復原： Deact PDP → AT+CGACT=0,<漂移編號> → Act PDP → Ping 驗證。

開連線：OK 只代表「指令收下」

按 Open TCP、參數卡填主機與埠 （AT+QIOPEN=1,0,"TCP","主機",埠,0,0；context 1、connectID 0、 buffer 模式已固定）。OK 只代表指令收下，成敗看 URC +QIOPEN: 0,<err>：0＝成功，最長 150 秒； 563＝connectID 還開著，先按 Close Sock。 All Socks（AT+QISTATE）列出所有 socket， state 2＝已連上。

收資料：不會自己出現，要按 Read Data

buffer 模式下收到的資料不會自動出現在終端機：模組只發 +QIURC: "recv",0 通知，要按 Read Data （AT+QIRD=0,1500）取出，且重複讀到回 +QIRD: 0 為止 —— 沒讀乾淨就不會再有下一次通知。 Unread Len（AT+QIRD=0,0）查總收／已讀／未讀。 收發完按 Close Sock（AT+QICLOSE=0，最長 10 秒）。 ⚠ 完全收不到 recv 通知？Hardware 頁查 AT+QURCCFG="urcport" 是不是 uart1 —— 出廠值是 USB 埠，URC 全跑去那邊。

內建對端 tcpbin.com 的兩個脾氣

Open TCP 預設對端是免費 echo 伺服器 tcpbin.com:4242， 兩個實測脾氣：

  • 逐行 echo，結尾要換行（0A）：送 Hello 無 0A 等 6 秒 無回應，補 0A 後 0.1 秒立刻收到。Send Text 結尾加 \n、 Send Hex 尾加 0A。
  • 15 秒閒置逾時：閒置就被斷線並收到 +QIURC: "closed",0。這與 QIRD 無關（它只讀本地緩衝、 不觸網）。要維持連線每 10 秒內送一次資料。收到 closed 後 socket 停在 closing， 必須先按 Close Sock 才能重用，否則 QIOPEN 回 563。

出錯了：先按 Last Error，再做 30 秒鑑別

指令回 ERROR 就立刻按 Last Error （AT+QIGETERROR）—— 只保留最後一條，被下一個錯誤蓋掉就查不到。 它查 Quectel 堆疊層；網路層用 Network 頁的 AT+CEER。

🔴 資料堆疊退化 —— 最耗時的坑。症狀：所有連線一律 失敗，但自檢全說沒事（QIACT? 有 IP、QIGETERROR 回 0）。實測連續開關 SSL 約 20 次後觸發，連純 TCP 的 QIOPEN 都回 552；QIDEACT＋QIACT 救不回， 只有重跑開機儀式能復原。

30 秒鑑別法：用 Open TCP 打同一目標 —— 也失敗＝整個堆疊 壞了，重跑開機儀式；成功＝問題在上層協定，繼續查。

Keepalive：擋得住電信商 NAT，擋不住 tcpbin

QICFG=? 列子項與範圍、Keepalive? 查現值、 Keepalive On／Off 開關 —— 這四顆指令本身零流量； 啟用後只要有 socket 閒置著，探測封包就計入行動流量。 它擋不住 tcpbin 的 15 秒逾時：實測開了仍在 15.1 秒被關 —— keepalive 是 TCP 層空探測，應用程式看不到；且 interval 最小 25 秒， 本來就大於 15。要撐應用層逾時只能送真資料（如每 10 秒 Send Hex 送 0A）。真正用途是電信商 NAT 保活（IoT 卡 NAT 閒置數分鐘就被回收）。

流量帳（推算非實測）：一次探測來回約 80 bytes； 預設 idle＝30 秒持續閒置 → 每小時約 9.4 KB、一天約 225 KB、 一個月約 6.8 MB；idle＝600 秒 → 一天約 11 KB。 1NCE 這類總量預付卡要把 idle 調大。沒 socket 開著就完全不耗流量。

MQTT —— 物聯網訊息

工作原理：MQTT 是「broker（訊息中介伺服器）」式的協定： 裝置不直接互連，各自連上 broker，對「主題（topic）」發布或訂閱訊息。 在 EG800K 上它是兩層的：先 AT+QMTOPEN 開「網路連線」（TCP 連到 broker）， 再 AT+QMTCONN 做「MQTT 登入」，兩層都通了才能訂閱與發布。 先記住：MQTT 指令的結果全是「先 OK 再 URC」模式（與 FTP 相同）—— OK 只代表指令收下，成敗看之後的結果 URC。

本頁固定用 client 0；韌體另支援多 client（0–5）、SSL 與雲平台認證 （=? 實測確認），進階用法見 MQTT 應用筆記。

開始之前：兩個前提

  1. URC 要走 UART：AT+QURCCFG="urcport" 必須回 "uart1"。出廠值是 "usbat"，而 MQTT 的結果全是 URC —— 不改的話每個指令都只回 OK、沒有下文 （Basic 頁有按鈕；寫 NVRAM，改一次就好）。
  2. PDP 要先啟用：先在 TCP/IP 頁按 AT+QIACT=1 （最長 150 秒）；沒開則 +QMTOPEN 回 3＝PDP 啟用失敗。 全程產生數據流量，預估約 5 KB。

client ID 與主題的隨機尾碼：每次重新整理就換一組

client ID 與預設主題不是寫死的：頁面載入時自動產生 6 個十六進位字元的尾碼， 組成 numodem-<尾碼> 與 test/numodem-<尾碼>， Subscribe／Publish／Unsub 三顆按鈕共用同一組（否則自迴路對不起來）。理由有二：

  • 撞名會被踢線：MQTT 3.1.1 §3.1.4 規定 broker 要把先連上的那個 踢下線 —— 兩個人同用固定 ID 就會互踢，症狀看起來像「模組莫名斷線」。
  • 固定主題會收到別人的訊息：你以為收到的是自己發的，其實不是 —— 這比收不到更糟，因為它給出假的通過。
⚠ 每次重新整理頁面，尾碼就換一組 —— 訂閱與發布必須在同一次頁面生命週期內完成。 何況本工具 RTS＝電源，重載頁面＝模組斷電，MQTT 連線整組消失， 要從開機儀式與 AT+QMTOPEN 重來。

最有說服力的驗證是自迴路：訂閱後發布到同一個主題、 自己收回自己的訊息，一次驗完整條收發鏈路。每步等到結果 URC 再往下：

  1. 設協定版本：按 Ver 3.1.1（AT+QMTCFG="version",0,4； 3＝3.1、4＝3.1.1）。按 Version? 可查目前值（不帶值＝查詢）。 Keepalive 參數卡可調保活間隔，不調也能測。
  2. 開網路：按 Open Net（AT+QMTOPEN=0,"broker",1883）。 先回 OK，成敗看 URC +QMTOPEN: 0,<result> （0＝成功），最長等 120 秒。按 Open? 可查已開的連線 （無連線時回空 OK，實測正常）。
  3. MQTT 登入：按 Connect（AT+QMTCONN=0,"numodem-<尾碼>"）。 成功 URC 固定是 +QMTCONN: 0,0,0。公開 broker 免帳密； 需要帳密時在參數後自行加 ,"user","pass"。 按 Conn? 查狀態（1＝初始、2＝連線中、3＝已連線、4＝斷線中）。
  4. 訂閱：按 Subscribe（AT+QMTSUB=0,1,"test/numodem-<尾碼>",0， msgid 固定 1）。成功 URC 形如 +QMTSUB: 0,1,0,0。 此後這個主題的訊息都以 +QMTRECV URC 進來。
  5. 發布：按 Publish（AT+QMTPUBEX，兩段式，見下段）。 成功 URC 為 +QMTPUBEX: 0,<msgid>,0。
  6. 收回來：發布目標就是訂閱中的主題，緊接著會看到 +QMTRECV 帶著主題與剛剛的訊息本文 —— 自迴路成功。 中文 payload 也不截斷、不亂碼。

QMTPUBEX 兩段式：數滿長度自動送，不用 Ctrl+Z

AT+QMTPUBEX 的末參數是長度（位元組數），不是訊息內容 （MQTT 應用筆記 §3.3.8 結案 —— 塞訊息的單行送法必定回 ERROR）。 正確流程是兩段式：送指令 → 模組回提示符 > → 送出剛好 N 位元組， 模組數滿長度就自動送出，不需要 Ctrl+Z （與 TCP 頁 AT+QISEND 的資料模式不同）。 按 Publish 全自動：只要在參數卡填訊息內容， 長度由 UTF-8 位元組數自動計算（中文一字 3 位元組，實測「測試」→ 6）。

  • payload 型指令不提供「填入命令列」 —— 命令列送出一律加行尾， 那個 CR 會被算進長度而錯位，請用按鈕送。
  • 韌體另有 AT+QMTPUB（資料模式變體，要 Ctrl+Z 收尾）—— 本工具一律改用 QMTPUBEX，不必兩套都學。

判讀結果碼：每個指令的值域都不一樣

不要把 A 指令的結果碼表套到 B 指令上。 +QMTOPEN 的 3 是「PDP 啟用失敗」， +QMTPUBEX 根本沒有 3 這個值。

最容易誤讀的是 +QMTCONN: 0,1 —— 它可能是查詢回應的「狀態 1＝初始化中」，也可能是寫入結果的「封包重傳中」。 單看一行分不出來，所以本工具把兩種讀法並陳，不硬猜。

你不必背表：從 +QMTOPEN 到 +QMTRECV／+QMTSTAT 的全部結果 URC，終端區都會依 MQTT 應用筆記 v1.5 的七張對照表逐欄加上白話註解。

離線與收尾

  • 只想停止收訊、連線留著：按 Unsub （AT+QMTUNS=0,2,"主題"，msgid 固定 2）。
  • 正常離線：按 Disconnect（AT+QMTDISC=0， 送 MQTT DISCONNECT），回 +QMTDISC: 0,0。 之後不必再按 Close Net —— AT+QMTCLOSE=0 是給「QMTDISC 失敗、網路層卡住」時強制關閉用的。

不是你按的斷線（被踢、keepalive 逾時、斷網）會以 +QMTSTAT 異常斷線 URC 回報（例：+QMTSTAT: 0,5，終端區會註解原因）， 此時要從 AT+QMTOPEN 重來。

UFS 檔案群：憑證怎麼進模組

UFS 是模組內建快閃儲存，實測總容量 280 KB、每檔佔一個 4 KB 區塊。憑證要先上傳到這裡，cacert 才有檔案可指。 上傳走 UART、零數據流量，二進位檔也送得進去。 Upload 卡：選檔後檔名與大小自動填入，送出後工具等模組回 CONNECT 才送原始位元組（等不到就不送）。完成時 註解引擎自動比對模組回報的大小與 checksum： ✅＝完整無誤、❌＝傳壞了，先刪再重傳。

AT+QFUPL="badssl-root.pem",1939,10
CONNECT                   ← 接著送出 1939 bytes
+QFUPL: 1939,4f64         ← 實收大小,checksum，註解自動比對 ✅

限制：四種憑證錯誤全回 566，模組不區分是哪一種。 AT+QIGETERROR 也幫不上忙 —— 它管 TCP/IP 層， 這時只回 0,operate successfully。

負向測項避開 expired —— 出廠 ignorelocaltime 是 1，過期本身 不會被擋（上表它被擋是因為同時不在上傳的根之下），單測就用 wrong.host。 另外留意流量：每次交握都下載完整憑證鏈、失敗照付， 實測 30 次交握約 150–200 KB。

🔴 陷阱：連續開關約 20 次後，資料堆疊整個退化

症狀：所有 AT+QSSLOPEN 一律回 552，連 seclevel 0 都連不上，而每項自我檢查都說沒事。30 秒鑑別：用純 TCP 的 AT+QIOPEN 打同一目標 —— 也失敗就是資料堆疊壞了，別再查 SSL 設定。PDP 重啟救不回來，只有完整開機儀式能復原。 退化會污染測試資料、易誤判成「被憑證驗證擋掉」—— 做成對測試前先重開機清乾淨。

HTTP —— 網頁請求

工作原理：模組的 HTTP 是三段式的： 先設 URL（這一步本身又是兩段式）、再發請求（GET／POST）、最後把回應讀回來。 每一段的結果都不在 OK 裡，而是之後才到的 URC —— 所以 AT+QURCCFG="urcport" 必須是 "uart1"（Hardware 頁可改）， 否則結果一個都看不到。數據皆為 2026-08 實機實測。

開始之前：先有資料通道

前提是 PDP 已啟用並拿到 IP（TCP/IP 頁的 AT+QIACT=1）。 本頁 Connect 群組只放唯讀檢查： AT+CPIN?／AT+CGATT?／AT+CGREG?／ AT+QIACT?、AT+QIDNSCFG=1（DNS 0.0.0.0＝沒配到）、 AT+QIGETERROR（⚠ 只對最後一條 TCP/IP 指令有效， 失敗後要立刻按）。

AT+QIACT? 會騙人。實測遇過 PDP 中途漂移： 所有請求全部失敗、固定 30 秒逾時回錯誤 716， AT+QIACT? 卻照樣回 IP。用 AT+CGACT? 交叉比對， 不一致就是漂移了。修法：AT+QIDEACT=1 → AT+CGACT=0,<漂移的 cid> → AT+QIACT=1， ping 過再繼續。

第一次 GET：四個步驟

  1. 前置設定（Config 群組，零流量）：contextid 參數卡設 1（綁定要走的 PDP context）；rspout/auto、 requestheader、responseheader 三個開關保持 0 （理由見後）；AT+QHTTPCFG? 一次讀回全部設定核對、 AT+QHTTPCFG=? 列出可設定項。
  2. 設 URL（兩段式）：AT+QHTTPURL 卡片只有一顆 「送出（兩段式）」鈕 —— 你填 URL，長度由程式自動算。流程：先送 AT+QHTTPURL=<長度>,80，等 CONNECT 進入資料模式，再把 URL 位元組原樣送出、不加任何行尾 （CR/LF 會被算進長度）。 http://www.example.com/ 長度恰是 23。送完按 AT+QHTTPURL? 讀回，逐字相同＝行尾沒混進去。
  3. 發請求：AT+QHTTPGET=80（等回應秒數）。 OK 只代表「收下指令」，真正結果是稍後的 URC +QHTTPGET: 0,200，判讀見下段。
  4. 讀回應：AT+QHTTPREAD=80。 CONNECT 之後全是原始位元組（實測 example.com 為 559 bytes），接著 OK —— 但最後獨立一行的 +QHTTPREAD: 0 才是結束標記。

判讀 +QHTTPGET：第一欄不是 HTTP 狀態碼

GET／POST／POSTFILE 的結果 URC 都是 <err>,<httprspcode>,<content_length> 三欄： err 0 ＝ 指令執行成功、非 0 是模組層錯誤（716、711…）； httprspcode 是 HTTP 狀態碼，只在 err=0 時才回報 （手冊明載；工具內建 200／403／404／409／411／500 對照註解）； content_length 選填 —— 伺服器回應標頭有 CONTENT-LENGTH 才有， 一般 GET 常常只有兩欄。所以實測的 +QHTTPGET: 0,404,0 不是失敗：指令成功了，是伺服器說找不到。

讀回應：AT+QHTTPREAD 的陷阱

參數是「兩包資料間的最大間隔秒數」，不是總時長。 本機韌體只吃一個參數：應用文件的 =<wait>,<read_len> 分段讀法實測回裸 ERROR（=? 探測證實），按鈕已移除 —— 分段取回改用 GETEX。

互鎖陷阱：rspout/auto 一設 1，READ 類一律失敗 （手冊明載）。它讓模組自動吐回應，代價是 READ 類全滅， 所以這顆按鈕有確認對話框。READ 突然全掛，先查 AT+QHTTPCFG?。

分段取回：AT+QHTTPGETEX 逐 byte 讀

AT+QHTTPGETEX=<秒>,<起始位移>,<長度> 走 HTTP Range 只抓指定片段、省流量。實測（端點內容固定為 abcdefghijklmnop）：位移 0 取 8 回 +QHTTPGET: 0,206,8、 讀出 abcdefgh；位移 8 再取 8 讀出 ijklmnop。 判讀：狀態碼必須是 206；回 200 且每次內容一樣 ＝伺服器不支援 Range，不是模組壞掉。 ⚠ 只在 requestheader=0 時可執行。

POST：兩段式與 Content-Type

AT+QHTTPPOST 卡片也是兩段式：你填 body、長度自動算，先送 AT+QHTTPPOST=<長度>,<輸入秒>,<回應秒>， 等 CONNECT 再送 body。三件事：

  • CONNECT 最長要等 125 秒（手冊明載）—— 等提示符的逾時要設足 125 秒，別沿用 MQTT 的 5 秒。
  • body 上限 1 MB（=? 實測範圍 1–1024000）。
  • Content-Type 先用 contenttype 參數卡設好 （型別碼 0 ＝ form-urlencoded）。

實測：POST Message=HelloQuectel（20 bytes）回 +QHTTPPOST: 0,200,440；READ 回的 JSON 可驗證鍵值送達、 長度算對、Content-Type 生效，User-Agent 是模組自報的 QUECTEL_MODULE。

自訂標頭與回應標頭

  • reqheader/add：加單條自訂請求標頭（手冊未附實例）； 查詢鈕可查目前加了幾條；reqheader/remove 移除。
  • requestheader 設 1 ＝ 整份請求標頭自己組，連 GET 都變兩段式， 且 GETEX 不能用。平常維持 0。
  • responseheader 設 1 後 READ 連 HTTP 回應標頭一併吐出 （實測連自訂的 X-Test 都帶得回來）。測完改回 0。
  • closed/ind：開啟「session 被關閉」的 URC 回報。

檔案版：POSTFILE 與 READFILE（UFS）

AT+QHTTPPOSTFILE="檔名",<秒> 以模組檔案系統（UFS）的檔案 當 body 送 POST；AT+QHTTPREADFILE="檔名",<秒> 把回應存成 UFS 檔。⚠ 本工具目前無法先上傳檔案到 UFS、也讀不回 UFS 檔內容，這兩條供搭配韌體端流程使用。

HTTPS：免驗證路徑

HTTPS ＝ HTTP ＋ SSL context。Connect 群組備好最短路徑，五顆照序按：

AT+QHTTPCFG="sslctxid",1           ← HTTP 指定用 SSL context 1
AT+QSSLCFG="sslversion",1,4        ← TLS 版本交給伺服器協商
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← 加密套件全開
AT+QSSLCFG="seclevel",1,0          ← 不驗憑證（見下）
AT+QSSLCFG="sni",1,1               ← 開 SNI（出廠是 0！）

之後 URL 換 https:// 開頭照常 GET／READ —— 實測讀回 HTML 與明文版逐字相同。 seclevel=0（不驗憑證）是本工具唯一走得完的路徑 —— 要驗憑證得先把 CA 憑證寫進 UFS；SSL 細節（AT+QSSLCFG=? 列全部子項、negotiatetime 調握手等待秒數）見〈SSL —— TLS 通道〉一節。 SNI 出廠是 0：不開，共用 IP 的 HTTPS 站拿到不匹配的憑證、 一驗就敗。憑證鏈是流量大頭：一輪 HTTPS GET 約 8–15 KB， 明文才約 1 KB。

轉址與收尾

轉址（手冊沒寫，實測釐清）：模組會自動跟隨 302，但 只吃絕對路徑的 Location —— 相對路徑直接回錯誤 711、 1 毫秒立即失敗。收尾： AT+QHTTPSTOP（Close 群組）取消進行中的請求並斷開 session； 狀態怪怪的、或出現錯誤 704（資料模式被佔）時先按這顆收乾淨。

FTP —— 檔案傳輸

工作原理：FTP 有兩條通道：控制通道走命令、 資料通道走檔案內容。登入、改名、刪除、查大小只走控制通道； LIST、上傳、下載要另開一條資料連線 —— 本節大半的怪現象（615、603 連發）都由此而來。 貫穿全節的 Quectel 通則：OK 只代表「指令收下」， 真正結果之後才以 URC 送達。本節回應與數字全是 2026 年 8 月對實體 EG800K 的實測值。

開始之前：兩個前提

  • PDP 要先啟用：本頁第一顆 AT+QIACT? 就是做這個檢查 —— 回得出 +QIACT: 1,1,…,"IP" 才能繼續，只回 OK 就先到 TCP/IP 頁按 Act PDP（PDP 未啟用時 QFTPOPEN 必失敗）。
  • URC 要走 UART：FTP 指令幾乎全是「先 OK、結果再以 URC 送達」， AT+QURCCFG="urcport" 不是 "uart1" 的話， 這裡只看得到一堆 OK（設定見 Hardware 頁）。

登入動線：設定 → 開啟 → 等 URC

  1. 綁 PDP context：AT+QFTPCFG="contextid",1 （出廠即為 1，查詢鈕可讀回確認）。
  2. 設帳密：AT+QFTPCFG="account","帳號","密碼"， 必須在 QFTPOPEN 之前設好。
  3. 模式與型態：transmode 設 1 （被動；NAT 後方一律用它，FTPS 必須）； filetype 純文字檔用 1、其餘用 0。
  4. 登入：AT+QFTPOPEN="主機",21 立即回 OK（只是收下）， 等 +QFTPOPEN: 0,0 才是登入成功（最長 125 秒）。 再按 AT+QFTPSTAT 應回 1（閒置；2＝傳輸中、3＝關閉中）。
AT+QFTPCFG="account","demo","password"
AT+QFTPCFG="transmode",1
AT+QFTPOPEN="test.rebex.net",21
OK                ← 只代表指令收下
+QFTPOPEN: 0,0    ← 這一行才是登入成功

其餘設定項：AT+QFTPCFG=? 一鍵列出全部 10 個可設定項與範圍（零流量）。 rsptimeout（20–180，預設 90 秒）是多數指令的最大回應時間、 也是資料模式中兩包資料的最大間隔；ssltype／sslctxid 是 FTPS 用（純 FTP 維持 0，SSL 參數在 SSL 頁設）； data_address／cache／restenable 屬特殊環境微調，用途見各鈕說明與手冊。

密碼遮蔽（實測，與手冊不符）：查詢 AT+QFTPCFG="account" 讀回時密碼被遮成 *（手冊說原樣印出）。但帳號仍是明文， 設定那一行的密碼也是明碼，截圖錄影要留意的是設定行。
🔴 AT+QFTPCLOSE 是非同步的 —— OK 不代表關好了。 要等 +QFTPCLOSE: 0,0 才算登出完成；期間 AT+QFTPSTAT 回 3（關閉中），下任何 FTP 指令一律回 +CME ERROR: 603（伺服器忙碌）。

症狀極具誤導性：一連串 603 看起來像模組壞了或被伺服器封鎖， 其實只是還沒關完（實測當天就因此繞了一大圈）。等待上限＝rsptimeout。 另外它只登出 FTP；要徹底重置網路，到 TCP/IP 頁按 Deact PDP。

全套伺服器端檔案操作（LIST／NLST／MLSD 要開資料連線，其餘只走控制通道）。 成功回應一律 +QFTPXXX: 0,… —— 第一個數字 0 就是成功：

下載：內容直接印在終端機（COM:）

AT+QFTPGET="檔名","COM:" —— CONNECT 後檔案內容直接吐在終端機， 結尾 +QFTPGET: 0,<位元組數>（實測 readme.txt 回 0,379）。 另一顆分塊下載鈕多帶起點與長度參數，是最推薦的下載方式： 先用 SIZE 查大小、再分塊拿，避免整檔爆流量。 AT+QFTPLEN 查上一次 PUT／GET／LIST／NLST 實際傳了多少 byte。

上傳：兩段式，送滿宣告長度自動結束

AT+QFTPPUT="檔名","COM:",0,<長度>,1 是兩段式指令： 等 CONNECT（進入資料模式）後送出剛好宣告長度的位元組數， 模組數滿自動退出資料模式，不必送 Ctrl+Z。本工具長度自動計算，參數卡貼上內容即可。

AT+QFTPPUT="numodem-test.txt","COM:",0,20,1
CONNECT                        ← 進入資料模式
NuModem-P6-FTP-test\n          ← 送出剛好 20 bytes
OK
+QFTPPUT: 0,20                 ← 伺服器收到 20 bytes

這 20 bytes 實測時特地從主機端用 Python ftplib 抓回逐位元組比對 —— 完全相符。 UFS 中轉形式：手冊另支援檔名寫成 "UFS:xxx"、 以模組內建儲存區中轉，細節見 FTPS 應用筆記；要先把電腦檔案放進 UFS， 用 SSL 頁「UFS 檔案」羣的 Upload 鈕（AT+QFUPL，走 UART 零流量、 自動比對 checksum）。

⚠ +++ 對 FTP 是「中止」不是「暫停」。 手冊（FTPS AN v1.5 p13）寫逃逸後可用 ATO 重回資料模式續傳， 實測不成立（測兩次結果一致）：逃逸後 AT+QFTPSTAT 回 1（閒置）而不是 2（傳輸中），ATO 回 NO CARRIER —— 傳輸已被整個中止，沒有可回復的連線。所以 +++ 只能用來從失控的 資料模式脫身，不能拿來暫停大檔下載。

正確下法：前後各靜默 1 秒、以原始位元組送、不加 CR（加了不生效）—— 本頁的 +++ 鈕已照此規矩送；ATO 鈕依手冊語意保留。

🧪 測試方法

這一節寫的是「怎麼測才不會得到假結論」。都是實際踩過才學到的。

OK 幾乎都不代表完成

Quectel 這類模組有一個共通模式：先回 OK 表示指令收下， 真正的結果走 URC。屬於這類的有 QIOPEN、QSSLOPEN、QMTOPEN、 QFTPOPEN、以及最容易被忽略的 QFTPCLOSE。 把 OK 當成完成然後馬上下一個動作，是本專案繞最多冤枉路的原因。

沒有對照組就不要下結論

兩個實例：

  • 憑證驗證：只測「壞憑證連不上」時，「全部都連不上」也會通過。 要同時證明好憑證連得上。
  • AGNSS 加速：7-2「冷啟動 TTFF」本來就是 7-4 的對照組。 室內沒有衛星訊號時兩邊都定不出來，測了只會得到「兩邊都失敗」。

每輪測試尾端跑一次健康檢查

模組會退化。連續開關連線約 20 次之後， 會進入一種「控制通道還活著、資料通道全滅」的狀態 —— 而且 QSSLSTATE 是空的、QIACT? 有 IP、 QIGETERROR 回 0，看起來完全正常。

這個狀態會污染測試資料。實測中就發生過：退化期間某些主機在「關閉驗證」時也連不上， 差點被判定成憑證驗證的結果。每輪結束前用一個已知可連的目標驗一次， 資料才可信。

鑑別方法：用純 TCP 的 AT+QIOPEN 打同一個目標。 如果它也失敗，那就不是 SSL / FTP 層的問題，是整個資料堆疊壞了。
復原方式：只有完整開機儀式有效。 QIDEACT + QIACT 救不回來。

零流量探測：AT+Q...=?

測試形式（=?）不觸網、不花錢， 而且回的是這顆韌體真正支援的參數範圍 —— 比應用文件可信，因為文件是一整個系列共用的。 本專案就是靠這招抓到 Wi-Fi 掃描的參數範圍與手冊不符。

驗「真的傳對了」要從第三方讀回來

+QFTPPUT: 0,20 只是模組自報它送了 20 bytes。 實測是從電腦端用另一個 FTP 客戶端把檔案抓回來逐 byte 比對 —— 這樣才同時排除了「模組算錯」與「伺服器存壞」兩種可能。

流量

AT+QGDCNT? 回「送出,接收」兩個位元組數。 ⚠ 這個計數器不存 NV，模組每次重開機就歸零； AT+QAUGDCNT 不是累計計數器，是「自動存檔間隔」的設定（0 ＝ 停用）。 要跨階段累計必須每段當場記，事後補不回來。

參考數字：TLS 交握比直覺貴很多， 每次交握都要下載完整憑證鏈，失敗的交握一樣付錢。 實測 11 次交握就用掉 TX 15.3 KB / RX 59.6 KB。

❓ 常見問題

Q：按了連線，但清單裡沒有任何接埠

檢查三件事：（1）是不是用 file:// 開的 —— Web Serial 會被擋； （2）USB-UART 的驅動程式裝了沒；（3）瀏覽器是不是 Chrome / Edge / Opera。

Q：指令送得出去，但模組完全沒有回應

九成是沒跑開機儀式。連上序列埠的瞬間 RTS 會被重新拉高， 而 RTS 在這塊板子上是負邏輯的電源開關 —— 等於連線就斷電。 切到 Hardware 頁跑一次 Power / Reset，等 RDY。

其次是行尾設成了 LF。EG800K 只吃 CR。

Q：指令都回 OK，但完全收不到 URC

下 AT+QURCCFG="urcport"。出廠值是 usbat， URC 全被送到 USB 埠去了。改成 uart1，這條寫 NVRAM 只要設一次。

Q：終端機卡住了，打什麼都沒反應

你多半在資料模式裡 —— 某個兩段式指令的長度算錯， 模組還在等你把位元組數補滿。 用 Hardware 頁的原始位元組按鈕送 ESC（0x1B）脫身。 FTP 的資料模式則要送 +++（前後靜默 1 秒、不加 CR）。

Q：一直回 +CME ERROR: 603

如果剛下過 AT+QFTPCLOSE，那是關閉還沒完成。 等 +QFTPCLOSE: 0,0 出現再繼續。

Q：連線全部失敗，但 AT+QIACT? 顯示還有 IP

模組的資料堆疊退化了。用純 TCP 的 AT+QIOPEN 打一個已知可連的目標確認 —— 如果它也失敗，重跑完整開機儀式。 QIDEACT + QIACT 救不回來。

Q：送了資料給 echo 伺服器卻收不到回聲

檢查 payload 結尾有沒有 \n。很多 echo 服務是逐行的， 沒有換行就不會回送。欄位裡直接打 \n 兩個字元即可， 工具會在送出前解碼成真正的換行，長度也會跟著算對。

Q：GNSS 一直定不出位置

先用 AT+QGPSGNMEA="GSV" 看有沒有衛星。 室內通常一顆都收不到，那就不是設定問題，是沒有天空視野。

Q：怎麼換語言或主題？

右上角。語言 18 種、主題深淺兩套，選擇都會記住。 AT 指令的說明與註解也會跟著翻譯，不只是介面。

Q：這個工具會不會偷偷用到我的流量？

不會。它是純前端的單一 HTML 檔，沒有後端。 會產生行動流量的只有你自己按下去的那些資料類指令， 那些按鈕的說明裡都寫清楚了。查詢類與 =? 測試類指令完全不觸網。
