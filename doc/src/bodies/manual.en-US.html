🎯 Introduction

NuModem EG800 is a 4G modem console in a single HTML file. It sends AT commands straight to Quectel EG800K series modules through the browser's Web Serial API — nothing to install, no software beyond the USB driver, and no backend server.

What makes it different from an ordinary serial terminal? It understands AT commands. Every command you send and every line the module sends back gets a plain-language explanation attached in real time — including the error codes that are nothing but a number.

What this manual covers
From opening the page, hooking up the module and running the power-up ritual, all the way through the working principle and test procedure for every AT command group in all ten function tabs. Every behaviour described here comes from hands-on testing of a physical EG800K in August 2026, not from copying the manual — where the manual is wrong, this document says so.

🚀 Quick Start

Step 1 — Open NuModem

Open NuModem_EG800.html in Chrome or Edge — a double-click is enough, no server needed.

Step 2 — Connect the module

Click Connect in the top left. The browser pops up a port picker; choose your USB-UART bridge. The arrow on the right expands a dropdown so you can pick a previously authorized port directly.

Once a port has been authorized, clicking "Connect" on later visits attaches to it immediately without asking again. If you have several serial devices, the dropdown is faster.

Step 3 — Check the baud rate

The baud rate selector at the top defaults to 115200, which is the EG800K factory value, so you normally leave it alone.

Step 4 — Run the power-up ritual

Do not skip this step. The instant the browser opens the serial port it re-asserts RTS, and on this control board RTS is an active-low power switch — meaning the module loses power at the exact moment you connect. Details in the next section.

The classic symptom of skipping the power-up ritual is this: the terminal shows every command you send, but nothing ever comes back. That is not a wrong baud rate and not swapped wires — the module simply has no power.

🔌 The Power-Up Ritual (the most important section)

The EG800K does not boot just because it has power. This control board wires two RS-232 output signals to the module's control pins:

SignalWired toLogic
RTSModule power switch Active low: RTS OFF = powered, RTS ON = powered off
DTRModule Reset pin DTR ON = Reset held high (can boot), OFF = Reset pulled low

Standard procedure

Switch to the Hardware tab, which has two dedicated buttons:

  1. Power — walks RTS through ON → OFF once. The button turns green when power is on (that is, RTS is OFF).
    ⚠ Setting OFF directly does not guarantee power; you must go ON first, then OFF.
  2. Wait one second.
  3. Reset — this is a press-and-hold button: pressing pulls DTR to OFF, releasing returns it to ON. Hold for roughly 300 ms.
  4. Wait for RDY in the terminal. In testing it appears within a few seconds.

You can also click RTS / DTR on the signal bar directly — same effect, you just have to keep track of the sequence yourself.

How to confirm the module booted

The terminal should spit out this sequence:

RDY              ← module boot complete
+CFUN: 1         ← RF enabled
+CPIN: READY     ← SIM ready
+QUSIM: 1
+QIND: SMS DONE  ← SMS initialization complete
+QIND: PB DONE   ← phonebook initialization complete

Then send ATI to verify: you should get three lines — manufacturer, model, firmware revision — plus OK.

⚠ Every page reload requires running the power-up ritual again. Reloading reopens the serial port, and reopening the serial port re-asserts RTS — which cuts power to the module all over again. This is the number one reason people conclude "the module is dead" when using this tool.

Two commands worth sending right after boot

CommandWhy
ATE1 Turns echo on. The module echoes back every command it receives verbatim, so the terminal lets you compare "what you sent" against "what the module actually received" — typos become obvious at a glance.
AT+CMEE=2 Switches error messages to verbose text. Without it, failures are just a bare ERROR; with it you get readable messages like +CME ERROR: SIM not inserted.

Both are session-only and must be re-sent after the module reboots.

🔴 When no URC ever arrives, the first thing to check is AT+QURCCFG="urcport". The factory setting routes URCs (unsolicited result codes) to the USB AT port, so this tool — which talks over UART — never sees a single one. The symptom is "every command returns OK but nothing else ever happens": GNSS fixes, TCP data arrival, MQTT messages and Wi-Fi scan results all stay silent. Fix: AT+QURCCFG="urcport","uart1", which writes to NVRAM and survives reboots.

The annotation engine

This is the heart of NuModem. It does two things:

  • Explains the command you send — send AT+QSSLSEND=4,18 and the annotation reads "send a fixed length of 18 bytes on clientID 4: after the module prints the > prompt you must send exactly 18 bytes for it to transmit; no Ctrl+Z required".
  • Decodes the module's responses — especially the purely numeric codes. For example +QFTPSIZE: 627,550 is split into two layers: "error 627: FTP did not perform the requested action; server replied 550: action not taken, file or directory not found".
Annotations follow the parameters you actually entered. Fill the same button with different values and the numbers in the annotation change with them — it is not canned help text.

Line ending

The line ending selector sits to the right of the input box. The EG800K requires CR; choose LF and the module answers nothing at all. This is the easiest setting to get wrong.

🎛️ How the AT Command Panel Works

The left half holds ten tabs and over two hundred buttons. Before looking at individual tabs, understand these shared mechanisms — they apply on every page.

Two kinds of buttons

StyleBehaviour
Plain buttonClicking sends immediately
Dashed outlineHas parameters to fill in. Once filled you can "Send", or "Insert into command line" to drop the assembled command into the input box below and edit it yourself

Parameter fields

Every field has its own description (hover to see it) stating the range measured on real hardware, not copied from the manual. For example, the Wi-Fi scan "rounds" field says 1-3, because that is what AT+QWIFISCAN=? actually returns — the 1-6 printed in the application note is wrong.

Two-stage data send

Some commands do not finish in a single line. Their flow is:

Send command  →  module replies > or CONNECT  →  send exactly N bytes  →  module returns the result

Buttons of this kind have a separate "data payload" field, and the length is computed automatically and inserted into the command, so you never count bytes yourself. The commands in this category are AT+QISEND, AT+QSSLSEND, AT+QMTPUBEX, AT+QHTTPURL, AT+QHTTPPOST and AT+QFTPPUT.

Getting the length wrong is ugly. The module keeps waiting until it has received exactly the number of bytes you declared, and during that time the AT port is in "data mode" — anything else you type gets swallowed as payload.

How to escape: send an ESC (0x1B) with the raw-byte button on the Hardware tab. No need to disconnect, no need to reboot the module.

Escape sequences

The data payload field is a single-line text box, so you cannot type newlines, tabs or other control characters. These fields therefore support escape sequences:

NotationByte sent
\n0x0A line feed
\r0x0D carriage return
\t0x09 tab
\00x00 NUL
\xHHAny byte, HH in hexadecimal
\\A literal backslash

Decoding happens before transmission, and the length is computed from the decoded byte count. For example hello\n is 7 characters in the field but 6 bytes on the wire, so the length written into the command is 6.

Why this matters: many test servers echo line by line (they return whatever you send, but only act once they see a newline). If your payload does not end with \n, you will never receive a response — and it will look exactly like a broken connection.

Timeout markers

Some AT commands block for a long time. The ⏱ marker on a button is the maximum wait time stated in the manual, for example AT+QIACT=1 up to 150 seconds, AT+COPS=? up to 300 seconds. When something seems unresponsive, check this marker first — usually the time simply has not elapsed yet.

Confirmation dialogs

A confirmation box appears only for actions that can strand the AT port in data mode, or that are irreversible (deleting a remote file, soft-restarting the module, changing the baud rate). Merely "this will consume data" does not block you — that kind of warning lives in the button's description instead.

Local toggles

A few buttons have a small checkbox underneath. That is a tool-side behaviour, not an AT command. For example, under AT+QICLOSE=0 there is "auto-close when +QIURC: "closed",0 is detected". These options are stored in the browser and persist across sessions.

🗂️ The Ten Tabs

The tab order is meaningful: left to right is roughly the order you should work in. Hardware to power up → Basic to confirm the module is alive → Network to confirm it can get online → the last five are the various data protocols.

Hardware — Power-up and the serial port

Working principle: this page is the foundation of the whole tool: Control holds the two buttons of the power-up ritual (Power / Reset), Module is product identification, Serial is the UART settings, Power is low-power mode, URC governs the output port for the module's unsolicited messages, and a row of raw-byte buttons (Ctrl+Z / ESC / +++) serves as the escape hatch out of data mode. Every other tab rests on two premises: the module was powered up by the ritual and URCs go to uart1 — both are taken care of on this page. Every behavior and number in this section was measured on a physical EG800K in August 2026.

Why there is a power-up ritual: RTS = power, DTR = Reset

The control board this tool pairs with repurposes two RS-232 handshake signals; this is the key to the whole page:

SignalActually wired toLogic
RTSModule power switch Negative logic: RTS OFF = powered, RTS ON = power cut
DTRModule Reset pin DTR ON = Reset pulled high (can boot), DTR OFF = Reset pulled low

Circuit behavior (confirmed by testing): on the first connection RTS must go ON first, then OFF, or the power will not actually turn on — setting it straight to OFF does not guarantee power; DTR likewise must walk ON→OFF→ON before Reset is truly pulled high. A power cut (RTS ON) is a hard cut — the module sends no farewell message whatsoever.

Reloading the page = a power cut. When the browser reopens the serial port it raises RTS again, and the module simply loses power — after the automatic reconnect completes you must rerun the power-up ritual. Stepped on in testing: skipping the ritual and sending 17 commands straight away, every one vanished into the void (TX lines only, zero RX). Any "it was fine a moment ago, now nothing responds" — think of this first.

The Power and Reset buttons: how to press them, what you will see

The two buttons are the embodiment of the two signals in the table above, and they are linked both ways with the RTS / DTR indicators in the signal bar (grayed out and unclickable while disconnected). Web Serial cannot read back the actual state of output signals; what the signal bar shows is the value this tool believes it has sent.

  1. Power (toggle): lit green = power ON (= RTS OFF). The power-up ritual requires RTS to pass through ON→OFF: if the button is already lit, click it off first, then on.
  2. Reset (momentary): press = DTR OFF, release = DTR ON — one press-and-release is one Reset (the standard sequence pauses 0.3 seconds in between).
  3. Wait for RDY: within a few seconds the terminal shows the module's boot announcement RDY.
  4. Verify with ATI: it should reply Quectel / EG800K / Revision: … / OK. If that comes back, both the UART and the module are alive.
After power-up, first confirm echo (ATE) is on (the factory default is on), then send AT+CMEE=2 — without it you only get a bare ERROR; with it you get the readable text of +CME ERROR: …. Both are session-only and must be re-sent every time the module restarts.

The triple trap of changing the baud rate (all confirmed by testing):
① The moment OK comes back it takes effect immediately, and from the next instant this tool and the module are talking past each other;
② AT&F (factory reset) does not restore the baud rate — do not count on it to save you;
③ Without &W nothing is saved — and reconnecting = a power cut, so the module wakes at the old baud rate while your port setting is stuck at the new one: lost in both directions. That is why this tool enforces the combined ;&W form.
Four recovery steps (the confirmation dialog reminds you too): disconnect → change the baud rate in the connection area → reconnect → rerun the power-up ritual.

Power: QSCLK low-power mode

Sleep? (AT+QSCLK?): asks whether the module is allowed to sleep. Measured factory value on this unit: 0 = disabled, module always awake. This page provides the query button only: a sleeping module stops answering AT, and the manual's wake-up method is pulling DTR low — but on this board DTR is already wired as the Reset pin (see the start of this section). If you enabled sleep yourself on the command line and now cannot wake it, rerun the power-up ritual (power cycle) to escape; see the official low-power application note for details.

URC: when messages stop arriving, come here first

A URC (Unsolicited Result Code) is a message the module emits on its own, unprompted — it is the reply to no command. The boot-time RDY, TCP data arrival, MQTT messages, Wi-Fi scan results, and the GNSS firmware-load notice are all URCs. Their output port defaults from the factory to the USB port (usbat) — this tool, on the UART, receives none of them, and the symptom is textbook: every command replies OK, yet the messages never come.

The raw-byte buttons: the escape hatch out of data mode

Quite a few commands are two-stage: send the command, wait for the module's > prompt, then send the payload. Once inside this data mode, the module swallows every character you type as data — including the AT commands you meant to send. When the length is miscounted, you change your mind halfway, or a command jams, ordinary keys cannot save you; you need this row of buttons that each send a single raw byte:

ButtonSendsWhen to use it
Ctrl+Z0x1A Data mode's terminator: actually sends off what has been accumulated
ESC0x1B Cancels data mode and discards the accumulated content. The first choice for escape when a two-stage command jams and the AT port stops answering (manual §2.3.8)
+++Three + signs (raw bytes) Escapes from transparent data mode (such as FTP's COM: transfer) back to AT mode. The rules are strict: 1 second of silence before and after, and absolutely no CR/LF — measured: adding a CR renders it ineffective. It must be sent with this button, never typed on the command line
Testing overturns the manual: +++ is "abort", not "pause". The FTPS application note v1.5, page 13, says that after +++ you can return to data mode with ATO and resume the transfer; on the real device ATO only replies NO CARRIER — the transfer has already been aborted. Treat +++ as an emergency brake; do not expect to keep driving after pulling it.

Basic — SIM, diagnostics and basic status

Working principle: this page is the starting point after every connection. Once the power-up ritual is done and the terminal shows RDY, come here first to do three things: switch error messages to a readable format, confirm the SIM is ready, and identify whose card this is. After power-up: RDY does not mean the SIM is ready

RDY is the URC the module sends on its own when it finishes booting. It only means the AT interface is alive; the SIM card is still slowly initializing behind it. Measured: sending SIM-related commands the moment RDY appears returns +CME ERROR: 14 (SIM busy) or even +CME ERROR: 13 (SIM failure); wait about 6 seconds and everything works.

When writing automation scripts, do not treat RDY as the "clear to start" signal. Pick one of two correct approaches: leave a fixed buffer of about 6 seconds after RDY; or poll AT+QINISTAT and proceed only once bit 1 (CPIN ready) is set.

Echo (ATE): "module echo" and "terminal local echo" are two different things

Echo is the module sending back verbatim the characters you sent it (ATE1 on, ATE0 off); the terminal's local echo is the tool side printing what you type onto the screen itself. The two switches are independent: with both on, every character appears twice.

  • This page's echo toggle button switches module echo with a single click. The boot default is on (corroborated by the measured AT parameter E:1).
  • The state shown on the button is not remembered out of thin air — the tool self-corrects from the actual responses (receiving an echoed line counts as on); if you hand-type ATE0 / ATE1 / AT&F on the command line, the button's state follows along and never drifts.
  • The toggle is session-only: a module restart returns it to the default. To make it the boot default you must also send AT&W (this page has no button for it; hand-type it on the command line if needed).

PIN unlocking: check the remaining attempts first, then act

  1. Click PIN Left first (AT+QPINC?) to see the remaining attempts — the manual's ranges: PIN 0–3 attempts left, PUK 0–10 attempts left. Know how many shots you have before you act.
  2. When the card is waiting for a PIN, click Enter PIN: it first expands a parameter card for you to fill in the PIN before sending (command template AT+CPIN="{pin}", waits up to 5 seconds).
  3. When the PIN attempts are exhausted and the card demands a PUK, click Unlock PUK: the manual requires the PUK to be sent together with a new PIN (AT+CPIN="{puk}","{newpin}"), likewise via the parameter card, waiting up to 5 seconds.
Every wrong attempt costs one; when the PUK runs low, stop and contact the carrier — do not burn through the attempts by guessing.

Network — Registration, operators, RF

Working principle: every data feature works only if the module is registered on the cellular network and the PDP data channel is ready — this page is the dashboard and switchboard for getting on the network, and every "cannot get online" investigation starts here. Before you start: switch URCs to the UART first

From the factory, the EG800K sends its unsolicited messages (URCs) to usbat (the USB AT port), while this tool uses the UART — so not a single URC gets through: signal reports, TCP / MQTT / Wi-Fi scan results all go silent, and the symptom is "every command replies OK, but no messages ever come".

This is the number-one cause of "all URCs vanished". Go to the Hardware tab, query with AT+QURCCFG="urcport", and if it is not "uart1", switch it with the toggle button — the setting is written to NVRAM; change it once and it survives reboots.

The PDP channel: the 3GPP layer vs the TCP/IP page

A PDP context = the "data channel" the cellular network allocates; only with it do you have an IP. This group is read-only queries at the 3GPP standard layer: AT+CGDCONT? lists contexts and APNs, AT+CGACT? lists activation states (blocks up to 150 seconds; ⚠ the write form takes its parameters in the opposite order), and AT+CGPADDR lists the obtained IPs. The TCP/IP page's QIACT? / QICSGP are Quectel's own stack — not the same layer — and comparing them side by side tells you which side is broken: an IP here but none over there = the network granted it but the stack never started. This unit auto-activates a PDP and obtains an IP at boot.

AT+QGDCNT? queries cumulative data usage (first number sent, second received) — a must when metering a roaming card. ⚠ Testing overturns the button hint's "accumulates across reboots": by default the counter is not saved to NV and resets to zero on any power cut (page reloads included) — record it on the spot, or save to NV with AT+QGDCNT=1.

GNSS — Satellite positioning

Working principle: GNSS is a feature independent of the mobile network — it needs no data plan on the SIM, no PDP, and consumes no data (AGNSS excepted, see below). Once enabled, the module receives satellite signals on its own, and you poll for a fix with AT+QGPSLOC. Every timing and behavior in this section is a value measured on a physical EG800K in August 2026.

Before you start: the antenna decides everything

The number-one cause of failed fixes is not a mistyped command; it is an antenna that receives no signal. Measured comparison: indoors with a poor antenna, the module could list the positions of 38 satellites yet hear not a single one (SNR all 00); after switching to an active GNSS antenna placed by a window, a cold start got a fix within 95 seconds.

You cannot test GNSS indoors — no amount of waiting will help. With no sky view, $GNGGA reports "satellites used 00, fix quality 0", and AT+QGPSLOC forever returns error 516. Move the antenna to a window or outdoors before you start — this is not a patience problem, it is a physics problem.

Your first fix: five steps

  1. Run the power-up ritual (see the Power-Up Ritual section). ⚠ Every page reload equals a power cut: the GNSS on/off state and any half-received ephemeris are wiped, and you start over from this step.
  2. Confirm URCs go to the UART: AT+QURCCFG="urcport" must return "uart1". The factory value is "usbat"; left unchanged, many result messages get sent to the USB port and never show up here (the setting is written to NVRAM, so change it once and you are done).
  3. Turn GNSS on: click AT+QGPS=1. Within a few seconds you will see +QGPS: "firmware",0,0 (GNSS firmware loaded successfully). Clicking it again while already on returns +CME ERROR: 504, which is harmless.
  4. Check reception: click AT+QGPSGNMEA="GSV" to read the visible satellites. The terminal area automatically opens the Satellites tab and draws the signal-strength bar chart and sky view — how to read them is covered in the next section.
  5. Poll for a fix: click AT+QGPSLOC=2 every 5–10 seconds. A reply of DSAT_CME_GNSS_NOT_FIXED_NOW (error 516) means no fix yet — just keep waiting. On success it returns coordinates, and the terminal area automatically opens the Map tab and plots the position.

Reading the Satellites tab: "in view" does not mean "heard"

GSV gives four numbers per satellite: ID, elevation, azimuth, and SNR (signal-to-noise ratio, dB-Hz). The first three only say "where in the sky it should be"; only the SNR proves a signal is actually being received.

SNRMeaning

Why you must wait: the physics of a cold start, with measured times

A fix needs each satellite's precise orbit (the ephemeris), and the ephemeris is buried in a signal the satellite broadcasts at 50 bps — one satellite takes about 18–30 seconds of continuous error-free demodulation, a single bad bit means starting over, and you need at least 4 of them. That is why a "cold start" is slow. Measured on this unit (same location, active antenna, measurement resolution ±5 seconds):

ScenarioTime to first fix (measured)
Cold start (no assistance at all)95 seconds
Cold start + AGNSS52 seconds (and a rough position already comes back after about 20 seconds)
AGNSS + recent leftover ephemeris (day-to-day repeated use)25 seconds
Do not reload the page while testing. This tool's hardware design makes RTS = power, so reloading the page = a power cut = all ephemeris lost, and everything restarts from a cold start. To pause, click AT+QGPSEND; do not cut power.

AGNSS acceleration: the full procedure

Principle: AGNSS switches the ephemeris to a network download (about 32–34 KB each time), skipping the slow 50 bps demodulation. It cannot conjure satellite signal out of nothing — indoors you still get no fix; all it saves is the "waiting for the ephemeris" time.

Two prerequisites are the easiest to miss, and missing either one makes AGNSS silently do nothing at all, with no error:

The full sequence (after every boot):

AT+QIACT=1          ← open the data channel (blocks up to 150 seconds; consumes data)

How do you confirm AGNSS is actually working? This unit's firmware does not emit any notification like +QGPS: "agps" (confirmed by testing), so you look for circumstantial evidence — any one of these three will do:

  1. Query AT+QGDCNT? twice, before and after AT+QGPS=1; about 30 KB more in the receive direction = the assistance data was downloaded
  2. GSV lists the positions of a large number of satellites within seconds (SNR possibly still 00) — the positions were downloaded; demodulating them yourself could never be that fast
  3. The time field of $GNGGA has a value (time is part of the assistance data too)
The fake-fix trap: coordinates with zero satellites are not a fix. About 20 seconds after AGNSS starts, AT+QGPSLOC may return a set of coordinates, but look closely: HDOP 0.00 / alt 0.0 / nsat 00 — that is the reference-position injection from the assistance data, not a measurement, and it can be far off.

The criteria for a real fix: satellites used > 0, fix mode ≥ 2, HDOP > 0. Automation or product logic must never rely on "did coordinates come back" alone.

apflash: fast even after a power cut (with conditions)

AT+QGPSCFG="apflash" is 1 from the factory: every successful fix saves the ephemeris to flash, and the next boot imports it automatically — power-cycle within an hour and a cold start becomes a fast hot start, at zero data cost. Two limits: the ephemeris expires in roughly an hour; and you must have gotten a fix at least once before flash has anything to import — on a module that has never fixed, apflash cannot help.

After the fix: the Map tab

Every successful AT+QGPSLOC plots the position on the Map tab: the blue marker is the latest position, the cyan line is the movement track, and hovering over any track point shows local time and altitude. The summary bar shows coordinates / altitude / HDOP / satellite count, with the time converted to the local time zone by longitude.

TCP/IP — The root of every data connection

Working principle: this page is the foundation of every data protocol. The PDP context (the data channel allocated by the cellular network) is activated and deactivated only on this page; the SSL / HTTP / MQTT / FTP pages carry read-only queries only, so the same command never gets driven from two places at once. All traps and timings in this section were measured on the real device in August 2026.

Step one: activate the PDP (QICSGP / QIACT / QIDEACT)

Click Act PDP (AT+QIACT=1): it can block up to 150 seconds — send no other commands meanwhile — and from here on data charges begin (mind roaming costs). After success always click Query IP (AT+QIACT?) and confirm it returns +QIACT: 1,1,1,"IP address" — before activation it returns only OK. To hang up, click Deact PDP (AT+QIDEACT=1, up to 40 seconds), which force-closes every connection under it. Set APN (AT+QICSGP) is normally unnecessary — the module auto-syncs the network-assigned APN (measured: the 1NCE card already read back iot.1nce.net at boot); only enterprise APNs with credentials need it.

Act PDP returns ERROR, Last Error 572? This card allows only one PDP. At boot the network has already auto-activated one, and its number drifts (both 9 and 1 seen in testing), while AT+QIACT can only reach 1–8. Fix: on the Network page, AT+CGACT? to find the number → AT+CGACT=0,<number> to give up the slot → click Act PDP again.

Everything dies mid-test? AT+QIACT? lies — during PDP drift it still returns an IP; only a cross-check against AT+CGACT? reveals it. Recovery: Deact PDP → AT+CGACT=0,<drifted number> → Act PDP → verify with Ping.

The two quirks of the built-in peer tcpbin.com

Open TCP's default peer is the free echo server tcpbin.com:4242, with two measured quirks:

  • Line-by-line echo; the line must end with a newline (0A): Hello without 0A got no reply after 6 seconds; with the 0A added, the echo arrived in 0.1 seconds. Append \n with Send Text, or a trailing 0A with Send Hex.
  • 15-second idle timeout: idle connections get dropped with a +QIURC: "closed",0. This has nothing to do with QIRD (it only reads the local buffer, it never touches the network). To keep the connection, send real data at least every 10 seconds. After closed, the socket sits in closing — you must click Close Sock first before reuse, or QIOPEN returns 563.

When it goes wrong: click Last Error first, then the 30-second triage

The moment a command returns ERROR, click Last Error (AT+QIGETERROR) immediately — only the last one is kept, and once the next error overwrites it, it is gone. It queries the Quectel stack layer; for the network layer use the Network page's AT+CEER.

🔴 Data-stack degradation — the most time-consuming pit. Symptom: every connection fails, yet every self-check says all is well (QIACT? has an IP, QIGETERROR returns 0). The 30-second triage: hit the same target with Open TCP — if that fails too, the whole stack is broken, rerun the power-up ritual; if it succeeds, the problem is in the upper protocol — keep digging.

Keepalive: holds off carrier NAT, cannot hold off tcpbin

QICFG=? lists the sub-items and ranges, Keepalive? reads the current value, Keepalive On / Off toggles it — these four commands themselves cost zero data; once enabled, as long as any socket sits idle, the probe packets count against your mobile data. It cannot hold off tcpbin's 15-second timeout: measured, even enabled, the drop still came at 15.1 seconds — keepalive is a TCP-layer empty probe invisible to the application; and the minimum interval is 25 seconds, already larger than 15. To survive an application-layer timeout you must send real data (e.g. Send Hex a 0A every 10 seconds). Its real purpose is carrier NAT keep-alive (IoT-card NAT entries get reclaimed after a few idle minutes).

The data bill (estimated, not measured): one probe round trip is about 80 bytes; default idle = 30 seconds of continuous idling → about 9.4 KB per hour, about 225 KB per day, about 6.8 MB per month; idle = 600 seconds → about 11 KB per day. Prepaid total-volume cards like 1NCE should raise the idle value. With no socket open, it costs nothing at all.

MQTT — IoT messaging

Working principle: MQTT is a "broker" (message-intermediary server) protocol: devices never connect to each other directly; each connects to the broker and publishes or subscribes to messages on "topics". On the EG800K it is two-layered: first AT+QMTOPEN opens the "network connection" (TCP to the broker), then AT+QMTCONN performs the "MQTT login"; only with both layers up can you subscribe and publish. Remember first: every MQTT command's result follows the "OK first, URC later" pattern (same as FTP) — OK only means the command was accepted; success or failure comes in the result URC that follows.

This page always uses client 0; the firmware also supports multiple clients (0–5), SSL and cloud-platform authentication (confirmed by testing with =?) — see the MQTT application note for advanced usage.

Before you start: two prerequisites

  1. URCs must go to the UART: AT+QURCCFG="urcport" must return "uart1". The factory value is "usbat", and MQTT's results are all URCs — leave it unchanged and every command replies only OK with no follow-up (the Basic page has a button for it; written to NVRAM, change it once).
  2. The PDP must be active first: click AT+QIACT=1 on the TCP/IP page first (up to 150 seconds); without it, +QMTOPEN returns 3 = PDP activation failed. The whole run consumes mobile data, estimated at about 5 KB.

The random suffix on client ID and topic: a new one on every page reload

The client ID and default topic are not hard-coded: at page load a 6-hex-character suffix is generated, forming numodem-<suffix> and test/numodem-<suffix>; the Subscribe / Publish / Unsub buttons share the same set (otherwise the loopback would not line up). Two reasons:

  • An ID collision gets you kicked off: MQTT 3.1.1 §3.1.4 requires the broker to kick the earlier connection — two people on the same fixed ID kick each other, and the symptom looks like "the module drops for no reason".
  • A fixed topic receives other people's messages: you think you received your own message when you did not — worse than receiving nothing, because it hands you a false pass.
⚠ Every page reload rolls a new suffix — subscribing and publishing must happen within the same page lifetime. Besides, in this tool RTS = power, so a page reload = module power cut: the whole MQTT connection vanishes, and you start over from the power-up ritual and AT+QMTOPEN.

The full walkthrough: connect → subscribe → publish → receive your own message back

The most convincing verification is the loopback: subscribe, publish to the same topic, and receive your own message back — one pass validates the entire send/receive chain. Wait for each step's result URC before moving on:

  1. Set the protocol version: click Ver 3.1.1 (AT+QMTCFG="version",0,4; 3 = 3.1, 4 = 3.1.1). Version? queries the current value (no value = query). The Keepalive parameter card can adjust the keep-alive interval; testing works without touching it.
  2. Open the network: click Open Net (AT+QMTOPEN=0,"broker",1883). It replies OK first; success or failure comes in the URC +QMTOPEN: 0,<result> (0 = success), waiting up to 120 seconds. Open? lists the open connections (with none open it returns an empty OK — measured, normal).
  3. MQTT login: click Connect (AT+QMTCONN=0,"numodem-<suffix>"). The success URC is always +QMTCONN: 0,0,0. Public brokers need no credentials; when credentials are required, append ,"user","pass" to the parameters yourself. Conn? queries the state (1 = initial, 2 = connecting, 3 = connected, 4 = disconnecting).
  4. Subscribe: click Subscribe (AT+QMTSUB=0,1,"test/numodem-<suffix>",0, msgid fixed at 1). The success URC looks like +QMTSUB: 0,1,0,0. From then on, messages on this topic arrive as +QMTRECV URCs.
  5. Publish: click Publish (AT+QMTPUBEX, two-stage, see the next section). The success URC is +QMTPUBEX: 0,<msgid>,0.
  6. Receive it back: the publish target is the topic you are subscribed to, so immediately afterwards you see +QMTRECV carrying the topic and the message body you just sent — loopback successful. Even a Chinese payload arrives untruncated and ungarbled.

QMTPUBEX two-stage: sends automatically once the length is counted out — no Ctrl+Z

The last parameter of AT+QMTPUBEX is the length in bytes, not the message content (settled by MQTT application note §3.3.8 — the single-line form with the message stuffed in always returns ERROR). The correct flow is two-stage: send the command → the module replies with the prompt > → send exactly N bytes, and the module sends automatically once the length is counted out — no Ctrl+Z needed (unlike the data mode of the TCP page's AT+QISEND). The Publish button is fully automatic: just fill the message in the parameter card, and the length is computed from the UTF-8 byte count (one Chinese character = 3 bytes; measured, a two-character Chinese payload → 6).

  • Payload-type commands offer no "insert into command line" — the command line always appends a line ending, and that CR would be counted into the length and shift everything; send with the button.
  • The firmware also has AT+QMTPUB (the data-mode variant, ended with Ctrl+Z) — this tool uses QMTPUBEX throughout, so you need not learn both.

Reading the result codes: every command has its own value range

Never apply command A's result-code table to command B. In +QMTOPEN, 3 means "PDP activation failed"; +QMTPUBEX has no value 3 at all.

The easiest to misread is +QMTCONN: 0,1 — it could be the query response's "state 1 = initializing", or the write result's "packet being retransmitted". A single line cannot tell them apart, so this tool shows both readings side by side instead of guessing.

You need not memorize the tables: for every result URC from +QMTOPEN through +QMTRECV / +QMTSTAT, the terminal area annotates each field in plain language, following the seven reference tables of MQTT application note v1.5.

Going offline and wrapping up

  • Just stop receiving, keep the connection: click Unsub (AT+QMTUNS=0,2,"topic", msgid fixed at 2).
  • Normal disconnect: click Disconnect (AT+QMTDISC=0, sends MQTT DISCONNECT), returning +QMTDISC: 0,0. No need to click Close Net afterwards — AT+QMTCLOSE=0 is for force-closing when "QMTDISC failed and the network layer is stuck".

Disconnects you did not initiate (kicked off, keepalive timeout, network loss) are reported by the +QMTSTAT abnormal-disconnect URC (e.g. +QMTSTAT: 0,5; the terminal area annotates the reason), after which you start over from AT+QMTOPEN.

WiFiScan — Wi-Fi scanning and network positioning

Working principle: the EG800K is an LTE module with no Wi-Fi connectivity, but it carries a built-in "scan-only, never-connect" Wi-Fi receiver: it passively receives the beacon frames broadcast by nearby 2.4GHz hotspots and reports each hotspot's MAC address (BSSID), RSSI (signal strength) and channel. Scanning is pure RF reception at zero data cost; by itself it produces no coordinates — you must send the MAC + RSSI list to a cloud hotspot-location database to trade it for latitude and longitude; that is network positioning, usable indoors, no satellites needed. Every number and behavior in this section was measured on a physical EG800K in August 2026.

Working principle: the SSL page is the shared substrate of encrypted connections — the SSL context configured here and the certificates uploaded here serve SSL raw sockets, MQTT over SSL and HTTPS alike. All timings and behavior in this section were measured on a physical EG800K in August 2026.

Your first TLS connection: five steps

HTTP — Web requests

Working principle: the module's HTTP is three-phase: first set the URL (a step that is itself two-stage), then issue the request (GET / POST), and finally read the response back. No phase's result lives in the OK; each arrives later as a URC — so AT+QURCCFG="urcport" must be "uart1" (changeable on the Hardware page), or you will see none of the results. All numbers were measured on the real device in August 2026.

Before you start: have a data channel

The prerequisite is an active PDP with an IP (the TCP/IP page's AT+QIACT=1). This page's Connect group holds read-only checks only: AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = never assigned), AT+QIGETERROR (⚠ valid only for the last TCP/IP command — click it immediately after a failure).

AT+QIACT? lies. Measured: the PDP drifted mid-run — every request failed with error 716 at a fixed 30-second timeout, yet AT+QIACT? kept returning an IP. Cross-check with AT+CGACT?; a mismatch means it drifted. The fix: AT+QIDEACT=1 → AT+CGACT=0,<drifted cid> → AT+QIACT=1, then ping before continuing.

Your first GET: four steps

  1. Preliminary settings (Config group, zero data cost): set the contextid parameter card to 1 (binding the PDP context to use); keep the three switches rspout/auto, requestheader and responseheader at 0 (reasons below); AT+QHTTPCFG? reads back all settings at once for checking, AT+QHTTPCFG=? lists what can be set.
  2. Set the URL (two-stage): the AT+QHTTPURL card has a single "Send (two-stage)" button — you fill in the URL, the length is computed automatically. Flow: first send AT+QHTTPURL=<length>,80, wait for CONNECT to enter data mode, then send the URL bytes verbatim with no line ending of any kind (a CR/LF would be counted into the length). http://www.example.com/ is exactly 23 long. Afterwards click AT+QHTTPURL? to read it back; character-for-character identical = no line ending crept in.
  3. Issue the request: AT+QHTTPGET=80 (seconds to wait for the response). OK only means "command accepted"; the real result is the later URC +QHTTPGET: 0,200 — how to read it is the next section.
  4. Read the response: AT+QHTTPREAD=80. Everything after CONNECT is raw bytes (measured: example.com is 559 bytes), followed by OK — but the standalone final line +QHTTPREAD: 0 is the true end marker.

Reading +QHTTPGET: the first field is not the HTTP status code

The result URCs of GET / POST / POSTFILE are all three fields, <err>,<httprspcode>,<content_length>: err 0 = the command executed successfully; nonzero is a module-layer error (716, 711…); httprspcode is the HTTP status code, reported only when err=0 (stated in the manual; the tool has built-in annotations for 200 / 403 / 404 / 409 / 411 / 500); content_length is optional — present only when the server's response header carries CONTENT-LENGTH, so ordinary GETs often show just two fields. Hence the measured +QHTTPGET: 0,404,0 is not a failure: the command succeeded — it is the server saying not found.

Reading the response: the AT+QHTTPREAD traps

The parameter is "the maximum gap in seconds between two data packets", not a total duration. This unit's firmware takes exactly one parameter: the application note's =<wait>,<read_len> chunked form actually returns a bare ERROR (proven by probing with =?), so that button was removed — for chunked retrieval use GETEX instead.

The interlock trap: set rspout/auto to 1 and every READ-type command fails (stated in the manual). It makes the module dump responses automatically at the cost of killing all READs, which is why this button has a confirmation dialog. If READ suddenly dies across the board, check AT+QHTTPCFG? first.

Chunked retrieval: AT+QHTTPGETEX reads byte by byte

AT+QHTTPGETEX=<sec>,<start offset>,<length> uses HTTP Range to grab only the specified slice and save data. Measured (against an endpoint fixed at abcdefghijklmnop): offset 0 take 8 returns +QHTTPGET: 0,206,8 and reads out abcdefgh; offset 8 take 8 reads out ijklmnop. How to judge: the status code must be 206; a 200 with identical content every time = the server does not support Range — the module is not broken. ⚠ Runs only while requestheader=0.

POST: two-stage, and Content-Type

The AT+QHTTPPOST card is two-stage as well: you fill in the body, the length is computed automatically; first send AT+QHTTPPOST=<length>,<input sec>,<response sec>, wait for CONNECT, then send the body. Three things:

  • CONNECT can take up to 125 seconds (stated in the manual) — size the prompt timeout to the full 125 seconds; do not inherit MQTT's 5.
  • The body limit is 1 MB (measured range via =?: 1–1024000).
  • Set the Content-Type first with the contenttype parameter card (type code 0 = form-urlencoded).

Measured: POSTing Message=HelloQuectel (20 bytes) returned +QHTTPPOST: 0,200,440; the JSON that READ returned verifies the key-value arrived, the length was computed right, the Content-Type took effect, and the User-Agent the module self-reports is QUECTEL_MODULE.

Custom headers and response headers

  • reqheader/add: adds a single custom request header (the manual gives no example); the query button shows how many were added; reqheader/remove removes.
  • requestheader set to 1 = you compose the entire request header yourself; even GET becomes two-stage, and GETEX becomes unusable. Keep it 0 normally.
  • With responseheader set to 1, READ also dumps the HTTP response headers (measured: even a custom X-Test comes back). Set it back to 0 after testing.
  • closed/ind: enables the "session closed" URC report.

The file variants: POSTFILE and READFILE (UFS)

AT+QHTTPPOSTFILE="filename",<sec> sends a POST using a file on the module's file system (UFS) as the body; AT+QHTTPREADFILE="filename",<sec> saves the response as a UFS file. ⚠ This tool currently can neither upload files to UFS beforehand nor read UFS file contents back; these two commands are for pairing with firmware-side workflows.

HTTPS: the no-verification path

HTTPS = HTTP + an SSL context. The Connect group has the shortest path prepared; click the five in order:

AT+QHTTPCFG="sslctxid",1           ← HTTP shall use SSL context 1

FTP — File transfer

Working principle: FTP has two channels: the control channel carries commands, the data channel carries file contents. Login, rename, delete and size queries use the control channel only; LIST, upload and download must open a separate data connection — most of this section's oddities (615, bursts of 603) stem from exactly that. The Quectel rule running through the whole section: OK only means "command accepted"; the real result arrives later as a URC. Every response and number here was measured on a physical EG800K in August 2026.

Before you start: two prerequisites

  • The PDP must be active first: this page's first button, AT+QIACT?, does exactly this check — only a reply of +QIACT: 1,1,…,"IP" lets you continue; a bare OK means going to the TCP/IP page first and clicking Act PDP (with the PDP inactive, QFTPOPEN always fails).
  • URCs must go to the UART: FTP commands are almost all "OK first, result later by URC" — if AT+QURCCFG="urcport" is not "uart1", all you see here is a pile of OKs (set it on the Hardware page).

The login walkthrough: configure → open → wait for the URC

  1. Bind the PDP context: AT+QFTPCFG="contextid",1 (already 1 from the factory; the query button reads it back to confirm).
  2. Set the credentials: AT+QFTPCFG="account","user","password" — it must be set before QFTPOPEN.
  3. Mode and type: set transmode to 1 (passive; always use it behind NAT, mandatory for FTPS); filetype 1 for plain-text files, 0 for everything else.
  4. Log in: AT+QFTPOPEN="host",21 returns OK immediately (merely accepted); only +QFTPOPEN: 0,0 is a successful login (up to 125 seconds). Then AT+QFTPSTAT should return 1 (idle; 2 = transferring, 3 = closing).
AT+QFTPCFG="account","demo","password"

AT+QFTPOPEN="test.rebex.net",21
OK                ← only means the command was accepted

The remaining settings: AT+QFTPCFG=? lists all 10 configurable items and their ranges in one click (zero data cost). rsptimeout (20–180, default 90 seconds) is the maximum response time for most commands and also the maximum gap between two packets in data mode; ssltype / sslctxid are for FTPS (keep 0 for plain FTP; SSL parameters are set on the SSL page); data_address / cache / restenable are fine-tuning for special environments — see each button's help and the manual.

Password masking (measured, contradicting the manual): when queried, AT+QFTPCFG="account" reads the password back masked as * (the manual says it prints verbatim). But the username is still plaintext, and the password on the setting line is plaintext too — for screenshots and recordings, the setting line is the one to watch.
🔴 AT+QFTPCLOSE is asynchronous — OK does not mean it closed. Only +QFTPCLOSE: 0,0 completes the logout; meanwhile AT+QFTPSTAT returns 3 (closing), and any FTP command invariably returns +CME ERROR: 603 (server busy).

The symptom is deeply misleading: a string of 603s looks like a broken module or a server ban, when it is merely not done closing (a long detour was wasted on exactly this during testing). The wait ceiling = rsptimeout. Also, it only logs out of FTP; to reset the network entirely, click Deact PDP on the TCP/IP page.

Download: contents printed straight into the terminal (COM:)

AT+QFTPGET="filename","COM:" — after CONNECT the file content is dumped straight into the terminal, ending with +QFTPGET: 0,<bytes> (measured: readme.txt returned 0,379). The other button, chunked download, adds start-offset and length parameters and is the most recommended way to download: query the size with SIZE first, then fetch in chunks, avoiding a whole-file data blowout. AT+QFTPLEN reports how many bytes the last PUT / GET / LIST / NLST actually transferred.

Upload: two-stage, finishes automatically once the declared length is filled

AT+QFTPPUT="filename","COM:",0,<length>,1 is a two-stage command: after CONNECT (entering data mode), send exactly the declared number of bytes; the module exits data mode automatically once the count is full — no Ctrl+Z needed. This tool computes the length automatically; just paste the content into the parameter card.

AT+QFTPPUT="numodem-test.txt","COM:",0,20,1
CONNECT                        ← entering data mode
NuModem-P6-FTP-test\n          ← send exactly 20 bytes
OK

Those 20 bytes were deliberately fetched back from the host with Python ftplib during testing and compared byte for byte — an exact match. The UFS relay form: the manual also supports writing the filename as "UFS:xxx", relaying through the module's built-in storage — details in the FTPS application note; to get a PC file into UFS first, use the Upload button in the SSL page's "UFS files" group (AT+QFUPL, over the UART at zero data cost, with automatic checksum comparison).

⚠ For FTP, +++ is "abort", not "pause". The manual (FTPS AN v1.5 p13) says that after escaping you can rejoin data mode with ATO and resume — disproven by testing (two runs, same result): after the escape, AT+QFTPSTAT returns 1 (idle) instead of 2 (transferring), and ATO returns NO CARRIER — the transfer has been aborted outright, with no connection left to resume. So +++ is only for escaping a runaway data mode; it cannot pause a large download.

The correct way to send it: 1 second of silence before and after, as raw bytes, no CR (with one it does not work) — this page's +++ button already follows the rule; the ATO button is kept per the manual's semantics.

🧪 Test Methodology

This section is about how to test without arriving at false conclusions. All of it was learned the hard way.

OK almost never means done

Quectel modules share a common pattern: they return OK to acknowledge the command, while the real result arrives in a URC. This applies to QIOPEN, QSSLOPEN, QMTOPEN, QFTPOPEN and the most frequently overlooked one, QFTPCLOSE. Treating OK as completion and immediately firing the next action wasted more time on this project than anything else.

No control group, no conclusion

Two examples:

  • Certificate verification: if you only test "a bad certificate fails to connect", then "everything fails to connect" passes too. You must simultaneously prove a good certificate connects.
  • AGNSS acceleration: test 7-2 "cold start TTFF" is precisely the control group for 7-4. With no satellite signal indoors neither side gets a fix, so all you learn is "both failed".

Run a health check at the end of every test round

The module degrades. After roughly 20 consecutive open/close cycles, it enters a state where the control channel is still alive but the data channel is completely dead — and QSSLSTATE is empty, QIACT? shows an IP and QIGETERROR returns 0, so everything looks perfectly normal.

This state contaminates your test data. It happened during testing: while degraded, certain hosts also failed to connect with verification disabled, and that was nearly recorded as a certificate-verification result. Before ending each round, verify against a target known to work; only then is the data trustworthy.

How to tell: hit the same target with plain TCP AT+QIOPEN. If that fails too, the problem is not in the SSL or FTP layer — the entire data stack is broken.
Recovery: only the full power-up ritual works. QIDEACT + QIACT will not bring it back.

Zero-data probing: AT+Q...=?

The test form (=?) touches no network and costs nothing, and it returns the parameter ranges this particular firmware really supports — more trustworthy than the application note, because the note is shared across an entire product series. That is exactly how this project caught the Wi-Fi scan parameter ranges disagreeing with the manual.

To prove "it really transferred correctly", read it back from a third party

+QFTPPUT: 0,20 is just the module claiming it sent 20 bytes. The actual test pulled the file back from the PC with a different FTP client and compared it byte by byte — that is the only way to rule out both "the module miscounted" and "the server stored it wrong".

Data usage

AT+QGDCNT? returns two byte counts, "sent,received". ⚠ This counter is not stored in NV and resets to zero on every module reboot; AT+QAUGDCNT is not a cumulative counter but the "auto-save interval" setting (0 = disabled). To accumulate totals across phases you must record each segment on the spot — it cannot be reconstructed afterwards.

Reference numbers: a TLS handshake is far more expensive than intuition suggests — every handshake downloads the full certificate chain, and failed handshakes cost the same. Measured: 11 handshakes consumed TX 15.3 KB / RX 59.6 KB.

❓ FAQ

Q: I clicked Connect but the list has no ports

Check three things: (1) did you open it via file:// — Web Serial is blocked there; (2) is the USB-UART driver installed; (3) is the browser Chrome / Edge / Opera.

Q: Commands go out but the module never answers

Nine times out of ten you skipped the power-up ritual. RTS is re-asserted the moment the serial port opens, and on this board RTS is an active-low power switch — so connecting cuts the power. Switch to the Hardware tab, run Power / Reset once, and wait for RDY.

The next most likely cause is the line ending set to LF. The EG800K only accepts CR.

Q: Every command returns OK but no URC ever arrives

Send AT+QURCCFG="urcport". The factory value is usbat, so all URCs are being sent to the USB port. Change it to uart1; this writes to NVRAM, so you only do it once.

Q: The terminal is stuck; nothing I type does anything

You are most likely in data mode — some two-stage command had the wrong length, and the module is still waiting for you to finish supplying the declared byte count. Escape with the raw-byte button on the Hardware tab, sending ESC (0x1B). For FTP data mode, send +++ instead (one second of silence before and after, no CR).

Q: I keep getting +CME ERROR: 603

If you just issued AT+QFTPCLOSE, then the close has not finished. Wait for +QFTPCLOSE: 0,0 before continuing.

Q: Every connection fails, but AT+QIACT? still shows an IP

The module's data stack has degraded. Hit a known-good target with plain TCP AT+QIOPEN to confirm — if that fails too, re-run the full power-up ritual. QIDEACT + QIACT will not bring it back.

Q: I sent data to an echo server but got no echo

Check whether the payload ends with \n. Many echo services are line-based and will not send anything back without a newline. Just type the two characters \n in the field; the tool decodes them into a real newline before transmitting, and the length is computed correctly along with it.

Q: GNSS never gets a fix

First use AT+QGPSGNMEA="GSV" to check for satellites. Indoors you typically receive none, in which case this is not a configuration problem — you have no sky view.

Q: How do I change the language or theme?

Top right. 18 languages, two themes (light and dark); both choices are remembered. AT command descriptions and annotations are translated as well, not just the interface.

Q: Does this tool quietly consume my mobile data?

No. It is a pure front-end single HTML file with no backend. The only things that generate mobile traffic are the data commands you click yourself, and those buttons say so in their descriptions. Query commands and =? test commands touch no network at all.
