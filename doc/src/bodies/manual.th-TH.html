🚀 เริ่มต้นอย่างรวดเร็ว

ขั้นที่ 1 —— เปิด NuModem

เปิด NuModem_EG800.html ด้วย Chrome หรือ Edge —— ดับเบิลคลิกก็พอ ไม่ต้องตั้งเซิร์ฟเวอร์

ขั้นที่ 2 —— ต่อโมดูล

กด เชื่อมต่อ ที่มุมบนซ้าย เบราว์เซอร์จะเด้งหน้าต่างเลือกพอร์ตขึ้นมา ให้เลือกตัวแปลง USB-UART ของคุณ ลูกศรทางขวาสามารถกางเมนูดรอปดาวน์ เพื่อเลือกพอร์ตที่เคยอนุญาตไว้แล้วได้โดยตรง

หลังจากอนุญาตครั้งแรกไปแล้ว ครั้งต่อไปเปิดหน้าเว็บแล้วกด "เชื่อมต่อ" มันจะต่อให้ทันทีโดยไม่ถามอีก ถ้าคุณมีอุปกรณ์ซีเรียลหลายตัว การเลือกจากดรอปดาวน์จะเร็วกว่า

ขั้นที่ 3 —— ตรวจสอบ baud rate

เมนู baud rate ด้านบนตั้งค่าเริ่มต้นไว้ที่ 115200 ซึ่งเป็นค่าจากโรงงานของ EG800K ปกติไม่ต้องแก้

ขั้นที่ 4 —— รันพิธีกรรมเปิดเครื่อง

ขั้นนี้ข้ามไม่ได้ ในวินาทีที่เบราว์เซอร์เปิดพอร์ตซีเรียล มันจะดึง RTS ขึ้นใหม่ และ RTS บนบอร์ดควบคุมนี้คือสวิตช์ไฟเลี้ยงแบบลอจิกกลับด้าน —— นั่นแปลว่า พอเชื่อมต่อปุ๊บ โมดูลก็ถูกตัดไฟทันที รายละเอียดดูหัวข้อถัดไป

อาการคลาสสิกที่สุดของการข้ามพิธีกรรมเปิดเครื่องคือ คำสั่งที่คุณส่งเห็นในเทอร์มินัลครบ แต่ไม่มีการตอบกลับใด ๆ เลย นั่นไม่ใช่ baud rate ผิด ไม่ใช่สายสลับขา แต่คือโมดูลไม่มีไฟเลี้ยงเลยต่างหาก

🔌 พิธีกรรมเปิดเครื่อง (หัวข้อที่สำคัญที่สุด)

EG800K ไม่ได้เสียบไฟแล้วบูตเอง บอร์ดควบคุมนี้ต่อสัญญาณขาออก RS-232 สองเส้นเข้ากับขาควบคุมของโมดูล:

สัญญาณต่อไปที่ไหนลอจิก
RTSสวิตช์ไฟเลี้ยงโมดูล ลอจิกกลับด้าน: RTS OFF = มีไฟ, RTS ON = ตัดไฟ
DTRขา Reset ของโมดูล DTR ON = ดึง Reset ขึ้น (บูตได้), OFF = ดึง Reset ลง

ขั้นตอนมาตรฐาน

สลับไปแท็บ Hardware ที่นั่นมีปุ่มเฉพาะสองปุ่ม:

  1. Power —— ทำให้ RTS วิ่งผ่าน ON → OFF หนึ่งรอบ ปุ่มติดสีเขียวหมายถึงไฟเลี้ยงเปิดแล้ว (คือ RTS อยู่ที่ OFF)
    ⚠ การตั้งเป็น OFF ตรง ๆ ไม่รับประกันว่าจะมีไฟ ต้อง ON ก่อนแล้วค่อย OFF เสมอ
  2. หยุดหนึ่งวินาที
  3. Reset —— ปุ่มนี้เป็นแบบ "กดค้างถึงจะทำงาน": ตอนกด DTR จะลงไป OFF ตอนปล่อยจะกลับเป็น ON กดค้างไว้ราว 300 มิลลิวินาที
  4. รอจนเทอร์มินัลขึ้น RDY จากการทดสอบจริงจะขึ้นภายในไม่กี่วินาที

คุณจะกด RTS / DTR บนแถบสัญญาณโดยตรงก็ได้ ผลเหมือนกัน เพียงแต่ต้องนับลำดับเอง

ยืนยันอย่างไรว่าบูตสำเร็จ

เทอร์มินัลควรพ่นข้อความเหล่านี้ออกมาตามลำดับ:

RDY              ← โมดูลบูตเสร็จแล้ว
+CFUN: 1         ← เปิดภาค RF แล้ว
+CPIN: READY     ← SIM พร้อม
+QUSIM: 1
+QIND: SMS DONE  ← เริ่มต้นระบบ SMS เสร็จแล้ว
+QIND: PB DONE   ← เริ่มต้นสมุดโทรศัพท์เสร็จแล้ว

จากนั้นส่ง ATI หนึ่งบรรทัดเพื่อยืนยัน ควรได้ยี่ห้อ รุ่น และเวอร์ชันเฟิร์มแวร์สามบรรทัดตามด้วย OK

⚠ ทุกครั้งที่รีเฟรชหน้าเว็บ ต้องรันพิธีกรรมเปิดเครื่องใหม่ การโหลดหน้าใหม่จะเปิดพอร์ตซีเรียลใหม่ และการเปิดพอร์ตซีเรียลใหม่จะ assert RTS ใหม่ —— เท่ากับตัดไฟโมดูลอีกรอบ นี่คือสาเหตุที่เครื่องมือนี้ถูกเข้าใจผิดว่า "โมดูลพัง" บ่อยที่สุด

สองคำสั่งที่ควรส่งทันทีหลังบูต

คำสั่งทำไม
ATE1 เปิด echo โมดูลจะสะท้อนคำสั่งที่ได้รับกลับมาเหมือนเดิมหนึ่งครั้ง ทำให้เทียบได้ว่า "สิ่งที่คุณส่ง" กับ "สิ่งที่โมดูลได้รับจริง" ตรงกันไหม พิมพ์ผิดเมื่อไหร่เห็นทันที
AT+CMEE=2 เปลี่ยนข้อความข้อผิดพลาดให้เป็นคำบรรยาย ถ้าไม่เปิด ข้อผิดพลาดจะเป็นแค่ ERROR แห้ง ๆ เปิดแล้วถึงจะเห็นข้อความที่อ่านรู้เรื่องอย่าง +CME ERROR: SIM not inserted

ทั้งสองคำสั่งนี้เป็น session-only พอโมดูลรีบูตต้องส่งใหม่

🔴 เมื่อไม่ได้รับ URC ใด ๆ เลย สิ่งแรกที่ต้องตรวจคือ AT+QURCCFG="urcport" ค่าจากโรงงานส่ง URC (ข้อความรายงานเชิงรุก) ไปที่ USB AT port เครื่องมือนี้ที่วิ่งบน UART จึงรับไม่ได้แม้แต่บรรทัดเดียว —— อาการคือ "คำสั่งตอบ OK หมด แต่ไม่มีข้อความตามมาเลย" ทั้งการระบุตำแหน่ง GNSS, ข้อมูล TCP ที่มาถึง, ข้อความ MQTT และผลสแกน Wi-Fi เงียบหมด วิธีแก้: AT+QURCCFG="urcport","uart1" คำสั่งนี้เขียนลง NVRAM มีผลข้ามการรีบูต

เอนจินคำอธิบาย

นี่คือหัวใจของ NuModem มันทำสองอย่าง:

  • อธิบายคำสั่งที่คุณส่ง —— เช่นเมื่อส่ง AT+QSSLSEND=4,18 ข้าง ๆ จะเขียนว่า "ส่งข้อมูลความยาวคงที่ 18 bytes ไปยัง clientID 4: หลังโมดูลตอบพรอมต์ > ต้องส่งให้ครบ 'พอดี' 18 ไบต์ถึงจะยิงออก ไม่ต้องส่ง Ctrl+Z"
  • ตีความคำตอบของโมดูล —— โดยเฉพาะรหัสที่เป็นตัวเลขล้วน เช่น +QFTPSIZE: 627,550 จะถูกแยกเป็นสองชั้น: "ข้อผิดพลาด 627: FTP ไม่ได้ดำเนินการตามที่ร้องขอ; เซิร์ฟเวอร์ตอบ 550: ไม่ได้ดำเนินการ: ไฟล์หรือไดเรกทอรีไม่มีอยู่"
คำอธิบายจะเปลี่ยนตามค่าพารามิเตอร์ที่คุณกรอกจริง ปุ่มเดียวกันกรอกค่าต่างกัน ตัวเลขในคำอธิบายก็เปลี่ยนตาม —— มันไม่ใช่ข้อความอธิบายตายตัว

ตัวปิดบรรทัด

ทางขวาของช่องป้อนข้อความเลือกตัวปิดบรรทัดได้ EG800K ต้องใช้ CR เท่านั้น ถ้าเลือก LF โมดูลจะไม่ตอบอะไรเลย นี่คือค่าที่พลาดกันบ่อยที่สุด

อื่น ๆ

  • ด้านล่างแสดงจำนวนไบต์ RX / TX สะสมและชื่อพอร์ตปัจจุบัน
  • มุมบนขวามีปุ่มเรียงกันแถวหนึ่ง: สวิตช์คำอธิบาย, ตัวปิดบรรทัด, timestamp, เลื่อนอัตโนมัติ, ล้างจอ
  • พื้นที่เทอร์มินัลยังมีอีกสองแท็บคือสถานะดาวเทียมและแผนที่ ซึ่งจะมีเนื้อหาหลังจากระบุตำแหน่ง GNSS สำเร็จ

🚦 แถบสัญญาณ RS-232

หลังเชื่อมต่อ ใต้แถบหัวเรื่องจะมีไฟสัญญาณโผล่ขึ้นมาทั้งแถว แบ่งเป็นสองกลุ่ม

DCD / DSR / CTS / RI บวกกับตัวบ่งชี้อีกสองตัวคือ ACT (มีข้อมูลไหลอยู่) และ ERR (framing/parity error)

Web Serial อ่านย้อนสถานะสัญญาณที่ตัวเองส่งออกไปไม่ได้ ไฟสามดวงในกลุ่ม LOCAL จึงแสดง "ค่าที่เครื่องมือนี้คิดว่าตัวเองส่งออกไป" ไม่ใช่ค่าที่อ่านกลับจากฮาร์ดแวร์จริง ถ้าจะยืนยันว่าคำสั่งมีผลจริง ให้ดูข้อความระบบในเทอร์มินัล (แบบ RTS → ON) จะแม่นกว่า

ทุกช่องมีคำอธิบายของตัวเอง (เอาเมาส์ไปวางแล้วจะขึ้น) ซึ่งเขียนตามช่วงค่าที่ทดสอบจริงบนเครื่อง ไม่ใช่ลอกจากคู่มือ เช่น "จำนวนรอบ" ของการสแกน Wi-Fi เขียนว่า 1-3 เพราะ AT+QWIFISCAN=? ตอบช่วงนี้จริง —— ค่า 1-6 ที่เอกสาร application note เขียนไว้นั้นผิด

การส่งข้อมูลแบบสองขั้น

คำสั่งบางตัวไม่ได้จบในบรรทัดเดียว ขั้นตอนของมันคือ:

ส่งคำสั่ง  →  โมดูลตอบ > หรือ CONNECT  →  ส่งไบต์ให้ครบ N ไบต์พอดี  →  โมดูลตอบผลลัพธ์

ปุ่มประเภทนี้จะมีช่อง "เนื้อหาข้อมูล" แยกต่างหาก และความยาวจะถูกคำนวณและเติมลงในคำสั่งอัตโนมัติ คุณไม่ต้องนับเอง คำสั่งที่อยู่ในกลุ่มนี้ได้แก่ AT+QISEND, AT+QSSLSEND, AT+QMTPUBEX, AT+QHTTPURL, AT+QHTTPPOST, AT+QFTPPUT

คำนวณความยาวผิดแล้วจบไม่สวย โมดูลจะรอไปเรื่อย ๆ จนกว่าจะได้ไบต์ครบตามที่คุณประกาศ ระหว่างนั้นพอร์ต AT อยู่ใน "โหมดข้อมูล" —— อะไรที่คุณพิมพ์ต่อจากนั้นจะถูกกลืนไปเป็นข้อมูลหมด

วิธีเอาตัวรอด: ใช้ปุ่มส่งไบต์ดิบในแท็บ Hardware ส่ง ESC (0x1B) ออกไปหนึ่งตัว ไม่ต้องตัดการเชื่อมต่อ ไม่ต้องรีบูตโมดูล

การถอดรหัสเกิดขึ้นก่อนส่งออก และความยาวก็นับจากจำนวนไบต์หลังถอดรหัส เช่น hello\n ในช่องคือ 7 อักขระ แต่ส่งออกไปเป็น 6 ไบต์ ความยาวที่เติมในคำสั่งจึงเป็น 6

ทำไมเรื่องนี้ถึงสำคัญ: เซิร์ฟเวอร์ทดสอบจำนวนมากสะท้อนกลับทีละบรรทัด (ส่งอะไรไปก็คืนมาแบบนั้น แต่ต้องเจอตัวขึ้นบรรทัดใหม่ก่อนถึงจะทำงาน) ถ้าท้าย payload ไม่มี \n คุณจะไม่มีวันได้รับคำตอบ —— และมันจะดูเหมือน "การเชื่อมต่อเสีย"

ป้ายเวลาหมดเวลา

คำสั่ง AT บางตัวบล็อกนานมาก ป้าย ⏱ บนปุ่มคือเวลารอสูงสุดตามที่คู่มือระบุ เช่น AT+QIACT=1 นานสุด 150 วินาที, AT+COPS=? นานสุด 300 วินาที เมื่อเห็นว่าไม่ตอบนาน ๆ ให้ดูป้ายนี้ก่อน ส่วนใหญ่แค่ยังไม่ถึงเวลาเท่านั้น

กล่องยืนยัน

กล่องยืนยันจะเด้งเฉพาะการกระทำที่จะทำให้พอร์ต AT ค้างในโหมดข้อมูล หรือการกระทำที่ย้อนกลับไม่ได้ (ลบไฟล์บนเครื่องปลายทาง, รีบูตโมดูลด้วยซอฟต์แวร์, เปลี่ยน baud rate) แค่ "จะกินปริมาณข้อมูล" เฉย ๆ จะไม่ขวางคุณ —— คำเตือนประเภทนั้นย้ายไปอยู่ในคำอธิบายของปุ่มแทน

สวิตช์ฝั่งเครื่องมือ

ปุ่มส่วนน้อยจะมีช่องติ๊กเล็ก ๆ อยู่ข้างใต้ นั่นคือพฤติกรรมฝั่งเครื่องมือ ไม่ใช่คำสั่ง AT เช่นใต้ AT+QICLOSE=0 มีตัวเลือก "ปิดอัตโนมัติเมื่อตรวจพบ +QIURC: "closed",0" ตัวเลือกเหล่านี้ถูกเก็บไว้ในเบราว์เซอร์ เปิดครั้งหน้าก็ยังอยู่

🗂️ สิบแท็บ

ลำดับของแท็บมีความหมาย: จากซ้ายไปขวาคือลำดับที่คุณควรใช้งานคร่าว ๆ Hardware เปิดเครื่อง → Basic ยืนยันว่าโมดูลยังมีชีวิต → Network ยืนยันว่าขึ้นเน็ตได้ → ห้าแท็บหลังจากนั้นคือโปรโตคอลข้อมูลแบบต่าง ๆ

Hardware —— การเปิดเครื่องและพอร์ตซีเรียล

หลักการทำงาน: หน้านี้คือรากฐานของเครื่องมือทั้งชุด: Control คือปุ่มสองปุ่มของพิธีกรรมเปิดเครื่อง (Power / Reset), Module คือการระบุตัวตนผลิตภัณฑ์, Serial คือการตั้งค่า UART, Power คือโหมดประหยัดพลังงาน, URC จัดการพอร์ตส่งออกของข้อความที่โมดูลส่งมาเอง และยังมีแถวปุ่มไบต์ดิบ (Ctrl+Z / ESC / +++) ไว้เป็นทางหนีฉุกเฉินจากโหมดข้อมูล แท็บอื่นทุกแท็บตั้งอยู่บนเงื่อนไขเบื้องต้นสองข้อ: โมดูลถูกเปิดตามพิธีกรรมแล้ว และ URC วิ่งผ่าน uart1 —— ทั้งสองเรื่องนี้ทำให้เสร็จได้ในหน้านี้ พฤติกรรมและตัวเลขทั้งหมดในหัวข้อนี้คือค่าที่วัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

ทำไมต้องมีพิธีกรรมเปิดเครื่อง: RTS = ไฟเลี้ยง, DTR = Reset

บอร์ดควบคุมที่ใช้คู่กับเครื่องมือนี้เอาสัญญาณ handshake ของ RS-232 สองเส้นไปใช้งานอย่างอื่น นี่คือกุญแจสู่การเข้าใจทั้งหน้า:

สัญญาณต่อกับอะไรจริง ๆลอจิก
RTSสวิตช์ไฟเลี้ยงของโมดูล ลอจิกกลับขั้ว: RTS OFF = จ่ายไฟ, RTS ON = ตัดไฟ
DTRขา Reset ของโมดูล DTR ON = ดึง Reset ขึ้นสูง (บูตได้), DTR OFF = ดึง Reset ลงต่ำ

คุณสมบัติของวงจร (ยืนยันจากการทดสอบจริง): การเชื่อมต่อครั้งแรก RTS ต้องON ก่อนแล้วค่อย OFF ไฟถึงจะเปิดจริง —— ตั้ง OFF ตรง ๆ ไม่รับประกันว่ามีไฟ; DTR ก็ต้องเดิน ON→OFF→ON Reset ถึงจะถูกดึงขึ้นสูงจริง การตัดไฟ (RTS ON) เป็นการตัดแบบดิบ โมดูลจะไม่ส่งข้อความอำลาใด ๆ ทั้งสิ้น

รีเฟรชหน้าเว็บ = ตัดไฟ เมื่อเบราว์เซอร์เปิดพอร์ตซีเรียลใหม่ RTS จะถูกดึงขึ้นอีกครั้ง โมดูลไฟดับทันที —— หลังเชื่อมต่ออัตโนมัติเสร็จต้องรันพิธีกรรมเปิดเครื่องใหม่ บทเรียนจากการทดสอบจริง: ข้ามพิธีกรรมแล้วส่งคำสั่งไป 17 คำสั่ง หายเงียบทั้งหมด (มีแต่บรรทัด TX, RX เป็นศูนย์) อาการแบบ "เมื่อกี้ยังดี ๆ อยู่ ตอนนี้ไม่ตอบอะไรเลย" ให้นึกถึงเรื่องนี้ก่อนเสมอ

ปุ่ม Power กับ Reset: กดอย่างไร จะเห็นอะไร

ปุ่มสองปุ่มนี้คือร่างจำแลงของสัญญาณสองเส้นในตารางข้างบน และเชื่อมโยงสองทางกับตัวบ่งชี้ RTS / DTR บนแถบสัญญาณ (ตอนยังไม่เชื่อมต่อจะเป็นสีจางกดไม่ได้) Web Serial อ่านสถานะจริงของสัญญาณขาออกกลับมาไม่ได้ สิ่งที่แถบสัญญาณแสดงคือค่าตามการรับรู้ที่เครื่องมือนี้ส่งออกไป

  1. Power (แบบสลับ): สว่างเขียว = ไฟ ON (= RTS OFF) พิธีกรรมเปิดเครื่องต้องให้ RTS เดินผ่าน ON→OFF: ถ้าปุ่มสว่างอยู่แล้ว ให้กดปิดก่อนแล้วค่อยกดเปิด
  2. Reset (momentary): กดลง = DTR OFF, ปล่อย = DTR ON, กดหนึ่งครั้งปล่อยหนึ่งครั้งคือ Reset หนึ่งรอบ (จังหวะมาตรฐานหยุดตรงกลาง 0.3 วินาที)
  3. รอ RDY: ภายในไม่กี่วินาทีเทอร์มินัลจะแสดงประกาศบูตของโมดูล RDY
  4. ยืนยันด้วย ATI: ควรตอบ Quectel / EG800K / Revision: … / OK ถ้าตอบออกมาได้ = ทั้ง UART และโมดูลยังมีชีวิตอยู่
หลังเปิดเครื่องแนะนำให้ยืนยันก่อนว่า echo (ATE) เปิดอยู่ (ค่าจากโรงงานคือเปิด) แล้วค่อยส่ง AT+CMEE=2 —— ถ้าไม่เปิดจะเห็นแค่ ERROR แห้ง ๆ เปิดแล้วถึงจะได้ข้อความอ่านรู้เรื่องแบบ +CME ERROR: … ทั้งคู่เป็น session-only โมดูลรีบูตเมื่อไหร่ต้องส่งใหม่ทุกครั้ง

AT Params (AT&V): แสดงค่าปัจจุบันของพารามิเตอร์ AT แบบตัวอักษรเดี่ยวทั้งหมด คำสั่งตัวอักษรเดี่ยวอย่าง ATE / ATQ / ATV ไม่มีรูปแบบคำสั่งอ่านค่าของตัวเอง มีแต่คำสั่งนี้เท่านั้นที่อ่านได้ เครื่องนี้วัดจริงได้ E:1 Q:0 V:1 S3:13 S4:10 —— echo เปิด, รหัสผลลัพธ์เป็นโหมดข้อความ, ท้ายบรรทัด = CR (ASCII 13) ซึ่งคือเงื่อนไขเบื้องต้นที่เครื่องมือนี้ใช้แยกวิเคราะห์คำตอบ

Baud? (AT+IPR?): ถาม baud rate ปัจจุบันของ UART ค่าจากโรงงานคือ 115200
Baud List (AT+IPR=?): ตอบกลับมาสองรายการ —— รายการแรกคือ baud rate ที่ตรวจจับอัตโนมัติได้ รายการหลังคือค่าที่ใช้ได้เฉพาะโหมดตายตัว หลังจากรันปุ่มนี้แล้ว เมนูดรอปดาวน์ของ Set Baud จะเปลี่ยนเป็นรายการที่เครื่องนี้รายงานจริง ผลวัดจริงพบว่ารายการที่สองของเครื่องนี้ไล่ไปจนถึง 1000000 bps —— ตารางใน §3.4 ของคู่มือไม่มีค่านี้

Set Baud (AT+IPR={rate};&W, การ์ดพารามิเตอร์): กดแล้วจะมีกล่องยืนยันเด้งขึ้นมาก่อน —— นี่คือปุ่มที่ล็อกตัวเองไว้นอกประตูได้ง่ายที่สุดของทั้งหน้า

กับดักสามชั้นของการเปลี่ยน baud rate (ยืนยันจากการทดสอบจริงครบทุกข้อ):
① OK ตอบปุ๊บมีผลทันที วินาทีถัดไปเครื่องมือนี้กับโมดูลก็คุยกันคนละภาษาแล้ว;
② AT&F (รีเซ็ตค่าโรงงาน) ไม่เปลี่ยน baud rate กลับมาให้ —— อย่าหวังพึ่งมัน;
③ ไม่ใส่ &W = ไม่บันทึก —— และการเชื่อมต่อใหม่ = ตัดไฟ โมดูลจะตื่นขึ้นที่ baud rate เก่า แต่การตั้งค่าพอร์ตของคุณค้างอยู่ที่ค่าใหม่ ขาดการติดต่อซ้อนสองชั้น เครื่องมือนี้จึงบังคับใช้รูปแบบรวม ;&W
การกู้คืนสี่ขั้น (กล่องยืนยันก็จะเตือนด้วย): ตัดการเชื่อมต่อ → แก้ baud rate ในส่วนเชื่อมต่อ → เชื่อมต่อใหม่ → รันพิธีกรรมเปิดเครื่องใหม่

URC (Unsolicited Result Code, รหัสผลลัพธ์ที่ไม่ได้ร้องขอ) คือข้อความที่โมดูล "พ่นออกมาเองโดยไม่มีใครขอ" ไม่ใช่คำตอบของคำสั่งใด ๆ —— RDY ตอนบูต, ข้อมูล TCP มาถึง, ข้อความ MQTT, ผลสแกน Wi-Fi, การแจ้งโหลดเฟิร์มแวร์ GNSS ล้วนเป็น URC ทั้งนั้น พอร์ตส่งออกของมัน ค่าจากโรงงานคือพอร์ต USB (usbat) —— เครื่องมือนี้เดิน UART จึงรับไม่ได้เลยสักข้อความเดียว อาการคลาสสิกมาก: คำสั่งตอบ OK หมด แต่รอข้อความเท่าไหร่ก็ไม่มา

กด Reset แล้วรอ RDY เท่าไหร่ก็ไม่มา ดูก่อนว่าปุ่ม Power สว่างหรือยัง —— โมดูลไม่มีไฟ กด Reset กี่ครั้งก็ไร้ผล; การเชื่อมต่อครั้งแรกไฟเลี้ยงต้องเดินผ่าน ON→OFF
คำสั่งตอบ OK หมด แต่ URC ไม่มาสักที แปดสิบเปอร์เซ็นต์คือ urcport ยังอยู่ที่ usbat ค่าโรงงาน: กด URC Port? ถาม แล้วกด URC → UART แก้; ยังไม่ได้ผลค่อยเช็ค URC Switch สวิตช์รวม
พอร์ต AT อยู่ ๆ ก็ "กลืนคำสั่ง" พิมพ์อะไรก็ไม่ตอบ ติดอยู่ในโหมดข้อมูล ตัวอักษรที่พิมพ์ถูกเก็บเป็นข้อมูลไปหมด —— กด ESC เพื่อหนีออกมา

Basic —— SIM, การวินิจฉัย และสถานะพื้นฐาน

หลักการทำงาน: หน้านี้คือจุดเริ่มต้นหลังการเชื่อมต่อทุกครั้ง เมื่อรันพิธีกรรมเปิดเครื่องเสร็จ และเทอร์มินัลแสดง RDY แล้ว ให้มาที่นี่ทำสามอย่างก่อน: เปลี่ยนข้อความข้อผิดพลาดเป็นรูปแบบที่อ่านรู้เรื่อง, ยืนยันว่า SIM พร้อม, และดูว่าซิมใบนี้คือใคร ทั้งหน้ายกเว้น AT&F กับการปลดล็อก PIN / PUK เป็นการอ่านค่าอย่างเดียวทั้งหมด —— กดแล้วไม่เปลี่ยนสถานะของโมดูล; คำสั่งที่กระทบสถานะการเชื่อมต่อรวมอยู่ในแท็บอื่นอย่าง Network, TCP/IP ตัวอย่างในหัวข้อนี้ล้วนเป็นค่าวัดจริงกับ EG800K ตัวจริง (เฟิร์มแวร์ EG800KCNGCR07A06M04) เมื่อเดือนสิงหาคม 2026

หลังเปิดเครื่อง: RDY ไม่ได้แปลว่า SIM พร้อม

RDY คือ URC ที่โมดูลส่งออกมาเองเมื่อบูตเสร็จ มันบอกแค่ว่าอินเทอร์เฟซ AT มีชีวิตแล้ว ซิมการ์ดยังค่อย ๆ เริ่มต้นระบบอยู่ข้างหลัง ทดสอบจริง: พอ RDY โผล่ก็ส่งคำสั่งเกี่ยวกับ SIM ทันที จะได้ +CME ERROR: 14 (SIM busy) หรือกระทั่ง +CME ERROR: 13 (SIM failure); รอราว 6 วินาทีแล้วค่อยส่ง ทุกอย่างก็ปกติ

เวลาเขียนสคริปต์อัตโนมัติ อย่าใช้ RDY เป็นสัญญาณ "เริ่มงานได้" วิธีที่ถูกเลือกหนึ่งจากสอง: หลัง RDY เว้นบัฟเฟอร์ตายตัวราว 6 วินาที; หรือโพล AT+QINISTAT รอจน bit 1 (CPIN พร้อม) ติดแล้วค่อยไปต่อ

echo (ATE): "เสียงสะท้อนจากโมดูล" กับ "local echo ของเทอร์มินัล" เป็นคนละเรื่อง

echo คือการที่โมดูลส่งตัวอักษรที่คุณส่งไปสะท้อนกลับมาเหมือนเดิม (ATE1 เปิด, ATE0 ปิด); ส่วน local echo ของเทอร์มินัลคือฝั่งเครื่องมือพิมพ์ตัวอักษรที่คุณกด ขึ้นจอเองก่อน สวิตช์สองตัวนี้เป็นอิสระต่อกัน: ถ้าเปิดทั้งคู่ ตัวอักษรทุกตัวจะปรากฏสองครั้ง

  • ปุ่มสลับ echo ในหน้านี้สลับ echo ของโมดูลได้ในปุ่มเดียว ค่าเริ่มต้นตอนบูตคือเปิด (มีพารามิเตอร์ AT E:1 จากการวัดจริงยืนยัน)
  • สถานะที่แสดงบนปุ่มไม่ได้จำมาลอย ๆ —— เครื่องมือปรับแก้อัตโนมัติตามคำตอบจริง (เห็นบรรทัด echo เมื่อไหร่ถือว่าเปิด); คุณพิมพ์ ATE0 / ATE1 / AT&F เองในบรรทัดคำสั่ง สถานะปุ่มก็จะตามไปด้วย ไม่หลุดจากกัน
  • การสลับเป็น session-only: โมดูลรีบูตก็กลับสู่ค่าเริ่มต้น ถ้าอยากเขียนเป็นค่าเริ่มต้นตอนบูตต้องส่ง AT&W เพิ่มเอง (หน้านี้ไม่ได้ทำปุ่มนี้ไว้ ต้องการก็พิมพ์เองในบรรทัดคำสั่ง)

AT&F: กลับค่าโรงงาน —— ขอบเขตผลกระทบ

ปุ่ม Factory Reset รีเซ็ตการตั้งค่า AT กลับเป็นค่าโรงงาน เป็นขั้นแรกเวลารับช่วงโมดูลที่ถูกตั้งค่ามั่วมา นี่คือปุ่มเดียวในหน้านี้ที่กดแล้วมีกล่องยืนยันเด้งก่อน ขอบเขตผลกระทบที่ยืนยันจากการทดสอบจริงแล้ว: จะตั้ง echo กลับเป็นเปิด (สถานะปุ่มสลับ echo จะตามให้อัตโนมัติ), ไม่กระทบ baud rate; ส่วนการตั้งค่ารายการอื่นถูกคืนค่าหรือไม่ ให้ดูรายการ AT&F ในคู่มือยืนยันทีละข้อ

ปุ่ม ICCID (AT+QCCID) ถามหมายเลขซีเรียลของการ์ด ทดสอบจริงตอบ +QCCID: 89882280666176614687 ⚠ ในคู่มือไม่มีคำสั่ง AT+CCID —— คำสั่งที่เจอบ่อยในบทเรียนของโมดูลยี่ห้ออื่นใช้ที่นี่ไม่ได้ ต้องใช้ AT+QCCID เฉพาะของ Quectel

ปลดล็อก PIN: เช็คจำนวนครั้งที่เหลือก่อน แล้วค่อยลงมือ

  1. กด PIN Left ก่อน (AT+QPINC?) เพื่อดูจำนวนครั้งที่ลองได้ —— ช่วงตามคู่มือ: PIN เหลือ 0–3 ครั้ง, PUK เหลือ 0–10 ครั้ง ก่อนลงมือให้รู้ก่อนว่าตัวเองเหลือกระสุนกี่นัด
  2. ตอนการ์ดรอ PIN ให้กด Enter PIN: จะกางการ์ดพารามิเตอร์ออกมาก่อน ให้คุณกรอก PIN แล้วค่อยส่ง (แม่แบบคำสั่ง AT+CPIN="{pin}", รอนานสุด 5 วินาที)
  3. เมื่อ PIN ถูกใช้จนหมดและการ์ดเปลี่ยนไปขอ PUK ให้กด Unlock PUK: คู่มือกำหนดว่า PUK ต้องส่งพร้อม PIN ใหม่ (AT+CPIN="{puk}","{newpin}") เดินผ่านการ์ดพารามิเตอร์เหมือนกัน รอนานสุด 5 วินาที
ส่งผิดหนึ่งครั้งก็หายไปหนึ่งครั้ง; เมื่อ PUK ใกล้หมดให้หยุดมือแล้วติดต่อผู้ให้บริการ อย่าเดาจนจำนวนครั้งไหม้หมด

Network —— การลงทะเบียน, ผู้ให้บริการ, RF

หลักการทำงาน: ฟังก์ชันข้อมูลทุกอย่างจะใช้ได้ก็ต่อเมื่อลงทะเบียนกับเครือข่ายมือถือแล้ว และช่องทางข้อมูล PDP พร้อมแล้ว —— หน้านี้คือแดชบอร์ดและสวิตช์ของการเข้าเครือข่าย การไล่ปัญหา "ต่อเน็ตไม่ได้" เริ่มจากที่นี่ทั้งหมด ตัวเลขในหัวข้อนี้ล้วนวัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

ก่อนเริ่ม: สลับ URC มาที่ UART ก่อน

EG800K จากโรงงานส่งข้อความรายงานอัตโนมัติ (URC) ไปที่ usbat (พอร์ต USB AT) แต่เครื่องมือนี้เดิน UART —— URC ทุกข้อความจะรับไม่ได้เลย: การรายงานสัญญาณ, ผล TCP / MQTT / การสแกน Wi-Fi เงียบหมด อาการคือ "คำสั่งตอบ OK หมด แต่ไม่มีข้อความ"

สาเหตุอันดับหนึ่งของ "URC หายทั้งหมด" คือตัวนี้ ไปที่แท็บ Hardware กด AT+QURCCFG="urcport" เพื่อถาม ถ้าไม่ใช่ "uart1" ให้ใช้ปุ่มสลับแก้ —— การตั้งค่าเขียนลง NVRAM แก้ครั้งเดียวมีผลข้ามการรีบูต

ช่องทาง PDP: ชั้น 3GPP vs หน้า TCP/IP

PDP context = "ช่องทางข้อมูล" ที่เครือข่ายมือถือจัดสรรให้ มีมันถึงจะมี IP กลุ่มนี้เป็นการถามค่าอย่างเดียวของชั้นมาตรฐาน 3GPP: AT+CGDCONT? แสดง context กับ APN, AT+CGACT? แสดงสถานะเปิดใช้ (บล็อกได้นานสุด 150 วินาที; ⚠ รูปแบบเขียนค่าลำดับพารามิเตอร์กลับกัน), AT+CGPADDR แสดง IP ที่ได้มา ส่วน QIACT? / QICSGP ของหน้า TCP/IP คือ สแต็กของ Quectel เอง ไม่ใช่ชั้นเดียวกัน —— เทียบคู่กันจะแยกได้ว่าฝั่งไหนเสีย: ฝั่งนี้มี IP ฝั่งโน้นไม่มี = เครือข่ายให้แล้วแต่สแต็กยังไม่เริ่ม เครื่องนี้บูตแล้วเปิดใช้ PDP รับ IP อัตโนมัติ

AT+QGDCNT? ถามปริมาณข้อมูลสะสม (ตัวเลขแรกคือส่งออก ตัวที่สองคือรับเข้า) ซิมโรมมิ่งทดสอบปริมาณข้อมูลต้องใช้ตัวนี้ ⚠ การทดสอบจริงหักล้างคำใบ้บนปุ่มที่ว่า "สะสมข้ามการรีบูต": ตัวนับค่าเริ่มต้นไม่บันทึกลง NV ตัดไฟเมื่อไหร่ (รวมโหลดหน้าเว็บใหม่) ก็กลับเป็นศูนย์ —— ต้องจดทันที หรือใช้ AT+QGDCNT=1 บันทึกลง NV

สนามรบไล่ปัญหา: ซิมใบนี้อนุญาต PDP เดียวเท่านั้น

หน้า TCP/IP กด AT+QIACT=1 แล้วตอบ ERROR (572,operation not allowed)? บทหนังตายตัวของซิมใบนี้: หลังบูตชั้น 3GPP เปิดใช้ PDP ไปแล้วหนึ่งช่องโดยอัตโนมัติ แต่หมายเลข context จะลอยไปมา (ทดสอบจริงเคยเจอทั้ง 1 และ 9); เปิดช่องที่สองจะตอบ +CME ERROR: 100 ⇒ เครือข่ายอนุญาตแค่ PDP เดียว; ขณะที่ contextID ของ QIACT มีช่วงแค่ 1–8 ถ้า PDP ถูกเปิดไว้ที่ 9 สแต็กของ Quectel ก็แตะไม่ถึงเลย วิธีแก้สองขั้น (ทำหนึ่งรอบหลังบูตทุกครั้ง):

AT+CGACT?             ← ดูว่าเป็น cid ไหน (หมายเลขลอยไปมา ขั้นนี้ข้ามไม่ได้)
AT+CGACT=0,<cid นั้น>   ← ให้ชั้น 3GPP สละโควตา
AT+QIACT=1            ← หน้า TCP/IP; ตอบ +QIACT: 1,1,1,"10.187.7.8" คือสำเร็จ

QICSGP ตั้ง APN ซิมใบนี้ข้ามได้ —— ทดสอบจริงโมดูลจะซิงก์ APN ที่เครือข่ายจัดให้เองอัตโนมัติ (iot.1nce.net); จำเป็นเฉพาะซิม APN องค์กรที่ต้องใช้บัญชีรหัสผ่าน

ทดสอบอยู่ดี ๆ ทุกอย่างหมดเวลาพร้อมกัน? ให้สงสัย PDP ลอยก่อน ทดสอบจริงตอน HTTP ล้มเหลวติดต่อกันทั้งหมด (ข้อผิดพลาด 716, หมดเวลาคงที่ 30 วินาที) AT+QIACT? ก็ยังตอบ IP ตามปกติ —— ตอนนั้นมันหลอกคุณได้ ต้องเทียบไขว้กับ AT+CGACT? (ทดสอบจริง: 1,0 กับ 9,1 = ลอยไปที่ 9) วิธีแก้: AT+QIDEACT=1 → AT+CGACT=0,<cid ที่ลอยไป> → AT+QIACT=1 แล้ว ping ยืนยัน

GNSS —— การระบุตำแหน่งด้วยดาวเทียม

หลักการทำงาน: GNSS เป็นฟังก์ชันที่เป็นอิสระจากเครือข่ายมือถือ —— ไม่ต้องมี SIM ที่ออนไลน์ได้ ไม่ต้องใช้ PDP ไม่กินปริมาณข้อมูล (ยกเว้น AGNSS ดูด้านล่าง) เมื่อเปิดแล้วโมดูลจะรับสัญญาณดาวเทียมด้วยตัวเอง คุณใช้ AT+QGPSLOC โพลผลการระบุตำแหน่ง ตัวเลขวินาทีและพฤติกรรมทั้งหมดในหัวข้อนี้คือค่าที่วัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

ก่อนเริ่ม: เสาอากาศคือตัวตัดสินทุกอย่าง

สาเหตุอันดับหนึ่งของการระบุตำแหน่งล้มเหลวไม่ใช่การส่งคำสั่งผิด แต่คือเสาอากาศรับสัญญาณไม่ได้ ผลเปรียบเทียบจากการทดสอบจริง: ในอาคารกับเสาอากาศที่ไม่ดี โมดูลแสดงตำแหน่งของดาวเทียมได้ถึง 38 ดวง แต่ไม่ได้ยินเลยสักดวงเดียว (SNR เป็น 00 ทั้งหมด); พอเปลี่ยนเป็นเสาอากาศ GNSS แบบแอ็กทีฟ (active) แล้ววางไว้ริมหน้าต่าง การเริ่มแบบเย็นก็ระบุตำแหน่งสำเร็จภายใน 95 วินาที

ในอาคารทดสอบ GNSS ไม่ได้ รอเท่าไหร่ก็ไม่มีประโยชน์ เมื่อไม่มีมุมมองท้องฟ้า $GNGGA จะตอบว่า "ใช้ดาวเทียม 00 ดวง คุณภาพการระบุตำแหน่ง 0" และ AT+QGPSLOC จะตอบข้อผิดพลาด 516 ไปตลอด ให้ย้ายเสาอากาศไปริมหน้าต่างหรือกลางแจ้งก่อนแล้วค่อยเริ่ม —— นี่ไม่ใช่ปัญหาความอดทน แต่เป็นปัญหาทางฟิสิกส์

การระบุตำแหน่งครั้งแรก: ห้าขั้นตอน

  1. รันพิธีกรรมเปิดเครื่อง (ดูหัวข้อ "พิธีกรรมเปิดเครื่อง") ⚠ ทุกครั้งที่รีเฟรชหน้าเว็บเท่ากับตัดไฟ สถานะการเปิด GNSS และข้อมูลวงโคจรดาวเทียม (ephemeris) ที่รับมาได้ครึ่งทางจะถูกล้างทิ้งทั้งหมด ต้องเริ่มใหม่จากขั้นนี้
  2. ยืนยันว่า URC วิ่งผ่าน UART: AT+QURCCFG="urcport" ต้องตอบ "uart1" ค่าจากโรงงานคือ "usbat" ถ้าไม่แก้ ข้อความผลลัพธ์จำนวนมาก จะถูกส่งไปพอร์ต USB แล้วที่นี่จะมองไม่เห็นอะไรเลย (ค่านี้เขียนลง NVRAM แก้ครั้งเดียวพอ)
  3. เปิด GNSS: กด AT+QGPS=1 ภายในไม่กี่วินาทีจะเห็น +QGPS: "firmware",0,0 (โหลดเฟิร์มแวร์ GNSS สำเร็จ) ถ้าเปิดอยู่แล้วแล้วกดซ้ำจะตอบ +CME ERROR: 504 ซึ่งไม่มีอันตราย
  4. ดูการรับสัญญาณ: กด AT+QGPSGNMEA="GSV" เพื่ออ่านดาวเทียมที่มองเห็น พื้นที่เทอร์มินัลจะเปิดแท็บดาวเทียมให้อัตโนมัติ พร้อมวาดกราฟแท่งสัญญาณและแผนภาพท้องฟ้า —— วิธีอ่านดูในหัวข้อถัดไป
  5. โพลตำแหน่ง: กด AT+QGPSLOC=2 ทุก 5–10 วินาที ถ้าตอบ DSAT_CME_GNSS_NOT_FIXED_NOW (ข้อผิดพลาด 516) แปลว่ายังล็อกตำแหน่งไม่ได้ รอต่อไปก็พอ เมื่อสำเร็จจะตอบพิกัดกลับมา และพื้นที่เทอร์มินัลจะเปิดแท็บแผนที่อัตโนมัติพร้อมวาดตำแหน่งลงไป

การเร่งด้วย AGNSS: ขั้นตอนฉบับเต็ม

หลักการ: AGNSS เปลี่ยนไปดาวน์โหลด ephemeris จากเครือข่ายแทน (ครั้งละประมาณ 32–34 KB) ข้ามการดีมอดูเลตช้า ๆ ที่ 50 bps ไปเลย มันเสกสัญญาณดาวเทียมจากความว่างเปล่าไม่ได้ —— อยู่ในอาคารก็ยังล็อกตำแหน่งไม่ได้เหมือนเดิม สิ่งที่มันประหยัดมีแค่เวลา "รอ ephemeris" เท่านั้น

เงื่อนไขเบื้องต้นสองข้อที่พลาดกันบ่อยที่สุด ขาดข้อใดข้อหนึ่ง AGNSS ก็จะนิ่งเงียบไม่ทำอะไรเลย โดยไม่แจ้งข้อผิดพลาด:

จะยืนยันได้อย่างไรว่า AGNSS ทำงานจริง? เฟิร์มแวร์ของเครื่องนี้ไม่ส่งข้อความแจ้งอย่าง +QGPS: "agps" (ยืนยันจากการทดสอบจริงแล้ว) ต้องดูหลักฐานแวดล้อม เลือกดูข้อใดข้อหนึ่งจากสามข้อนี้ก็พอ:

  1. AT+QGDCNT? เช็คสองครั้งก่อนและหลัง AT+QGPS=1 ถ้าฝั่งรับเพิ่มขึ้นราว 30 KB = ดาวน์โหลดข้อมูลช่วยเหลือแล้ว
  2. GSV แสดงตำแหน่งของดาวเทียมจำนวนมากภายในไม่กี่วินาที (SNR อาจยังเป็น 00) —— ตำแหน่งพวกนั้นถูกดาวน์โหลดมา การดีมอดูเลตเองไม่มีทางเร็วขนาดนั้น
  3. ช่องเวลาของ $GNGGA มีค่า (เวลาก็เป็นส่วนหนึ่งของข้อมูลช่วยเหลือ)
กับดักการระบุตำแหน่งปลอม: พิกัดที่มากับดาวเทียมศูนย์ดวงไม่ใช่การระบุตำแหน่ง หลังเริ่ม AGNSS ราว 20 วินาที AT+QGPSLOC อาจตอบพิกัดออกมาหนึ่งรายการ แต่ดูให้ดี: HDOP 0.00 / alt 0.0 / nsat 00 (คือ HDOP 0.00, ความสูง 0.0, ใช้ดาวเทียม 00 ดวง) —— นั่นคือตำแหน่งอ้างอิงที่ถูกฉีดเข้ามาจากข้อมูลช่วยเหลือ ไม่ใช่ผลการวัดจริง ความคลาดเคลื่อนอาจมหาศาล

เกณฑ์ตัดสินการระบุตำแหน่งจริง: จำนวนดาวเทียมที่ใช้ > 0, โหมดระบุตำแหน่ง ≥ 2, HDOP > 0 เวลาเขียนระบบอัตโนมัติหรือลอจิกของผลิตภัณฑ์ จะดูแค่ "มีพิกัดตอบกลับมาหรือไม่" อย่างเดียวไม่ได้

AT+QGPSCFG="apflash" มีค่าจากโรงงานเป็น 1 อยู่แล้ว: ทุกครั้งที่ระบุตำแหน่งสำเร็จจะบันทึก ephemeris ลง flash แล้วนำเข้าอัตโนมัติตอนบูตครั้งถัดไป —— ตัดไฟแล้วเปิดใหม่ภายในหนึ่งชั่วโมง การเริ่มแบบเย็นจะกลายเป็นการเริ่มแบบร้อนที่รวดเร็ว โดยไม่กินปริมาณข้อมูลเลย ข้อจำกัดมีสองข้อ: ephemeris หมดอายุในราวหนึ่งชั่วโมง และต้องเคยระบุตำแหน่งสำเร็จมาก่อนสักครั้งหนึ่ง ใน flash ถึงจะมีของให้นำเข้า —— โมดูลที่ไม่เคยระบุตำแหน่งสำเร็จเลย apflash ช่วยอะไรไม่ได้

หลังระบุตำแหน่งสำเร็จ: แท็บแผนที่

ทุกครั้งที่ AT+QGPSLOC สำเร็จ ตำแหน่งจะถูกวาดลงแท็บแผนที่: หมุดสีน้ำเงินคือตำแหน่งล่าสุด เส้นสีฟ้าอมเขียว (cyan) คือเส้นทางการเคลื่อนที่ เอาเมาส์ชี้ที่จุดใดบนเส้นทางก็จะเห็นเวลาท้องถิ่นและความสูงของจุดนั้น แถบสรุปแสดงพิกัด / ความสูง / HDOP / จำนวนดาวเทียม และเวลาจะถูกแปลงเป็นโซนเวลาท้องถิ่นตามลองจิจูดโดยอัตโนมัติ

TCP/IP —— รากของการเชื่อมต่อข้อมูล

หลักการทำงาน: หน้านี้คือรากฐานของโปรโตคอลข้อมูลทั้งหมด PDP context (ช่องทางข้อมูลที่เครือข่ายมือถือจัดสรรให้) เปิดใช้และปิดใช้ได้ที่หน้านี้เท่านั้น หน้า SSL / HTTP / MQTT / FTP มีแต่การถามค่าอย่างเดียว เพื่อกันไม่ให้คำสั่งเดียวกันสองที่เหยียบกันเอง กับดักและตัวเลขวินาทีในหัวข้อนี้ล้วนวัดจริงกับเครื่องจริงเมื่อเดือนสิงหาคม 2026

ขั้นแรก: เปิดใช้ PDP (QICSGP / QIACT / QIDEACT)

กด Act PDP (AT+QIACT=1): บล็อกได้นานสุด 150 วินาที ระหว่างนั้นอย่าส่งคำสั่งอื่น และจากจุดนี้เริ่มเกิดปริมาณข้อมูล (โรมมิ่งระวังค่าใช้จ่าย) สำเร็จแล้วต้องกด Query IP (AT+QIACT?) ยืนยันว่าตอบ +QIACT: 1,1,1,"ที่อยู่ IP" —— ก่อนเปิดใช้จะตอบแค่ OK จะวางสายกด Deact PDP (AT+QIDEACT=1, นานสุด 40 วินาที) ซึ่งจะบังคับปิดการเชื่อมต่อทั้งหมดที่อยู่ใต้มัน ส่วน Set APN (AT+QICSGP) ปกติไม่ต้องกด —— โมดูลจะซิงก์ APN ที่เครือข่ายจัดให้เองอัตโนมัติ (ทดสอบจริงซิม 1NCE บูตแล้วอ่านกลับมาเป็น iot.1nce.net อยู่แล้ว) จำเป็นเฉพาะ APN องค์กรที่ต้องใช้บัญชีรหัสผ่าน

Act PDP ตอบ ERROR, Last Error 572? ซิมใบนี้อนุญาต PDP แค่เส้นเดียว ตอนบูตเครือข่ายเปิดใช้ให้เองไปแล้วหนึ่งช่องและหมายเลขจะลอยไปมา (ทดสอบจริงเคยเจอ 9 กับ 1) แต่ AT+QIACT แตะได้แค่ 1–8 วิธีแก้: หน้า Network ใช้ AT+CGACT? ดูหมายเลข → AT+CGACT=0,<หมายเลข> สละโควตา → แล้วค่อยกด Act PDP

ทดสอบครึ่งทางแล้วพังหมด? AT+QIACT? หลอกคุณได้ —— ตอน PDP ลอย มันก็ยังตอบ IP ตามปกติ ต้องเทียบไขว้กับ AT+CGACT? ถึงจะมองออก การกู้คืน: Deact PDP → AT+CGACT=0,<หมายเลขที่ลอยไป> → Act PDP → Ping ยืนยัน

เปิดการเชื่อมต่อ: OK แปลว่าแค่ "รับคำสั่งไว้แล้ว"

กด Open TCP แล้วกรอกโฮสต์กับพอร์ตในการ์ดพารามิเตอร์ (AT+QIOPEN=1,0,"TCP","โฮสต์",พอร์ต,0,0; context 1, connectID 0, โหมด buffer ตั้งตายตัวไว้แล้ว) OK แปลว่าแค่รับคำสั่งไว้ สำเร็จหรือไม่ดูที่ URC +QIOPEN: 0,<err>: 0 = สำเร็จ นานสุด 150 วินาที; 563 = connectID ยังเปิดค้างอยู่ ให้กด Close Sock ก่อน All Socks (AT+QISTATE) แสดง socket ทั้งหมด state 2 = เชื่อมต่อแล้ว

ในโหมด buffer ข้อมูลที่รับมาจะไม่ปรากฏในเทอร์มินัลเอง: โมดูลส่งแค่การแจ้ง +QIURC: "recv",0 ต้องกด Read Data (AT+QIRD=0,1500) ดึงออกมา และอ่านซ้ำจนกว่าจะตอบ +QIRD: 0 —— อ่านไม่เกลี้ยงจะไม่มีการแจ้งครั้งถัดไป Unread Len (AT+QIRD=0,0) ถามยอดรับรวม / อ่านแล้ว / ยังไม่อ่าน รับส่งเสร็จกด Close Sock (AT+QICLOSE=0, นานสุด 10 วินาที) ⚠ ไม่ได้รับการแจ้ง recv เลย? ไปหน้า Hardware เช็ค AT+QURCCFG="urcport" ว่าเป็น uart1 หรือไม่ —— ค่าโรงงานคือพอร์ต USB URC วิ่งไปที่นั่นหมด

นิสัยสองอย่างของ tcpbin.com ปลายทางในตัว

ปลายทางค่าเริ่มต้นของ Open TCP คือ echo server ฟรี tcpbin.com:4242 ทดสอบจริงพบนิสัยสองอย่าง:

  • echo ทีละบรรทัด ท้ายต้องมีขึ้นบรรทัดใหม่ (0A): ส่ง Hello โดยไม่มี 0A รอ 6 วินาที ไม่มีคำตอบ พอเติม 0A ก็ได้รับกลับใน 0.1 วินาทีทันที Send Text ให้ปิดท้ายด้วย \n, Send Hex ปิดท้ายด้วย 0A
  • หมดเวลาเมื่อว่างงาน 15 วินาที: ว่างงานก็ถูกตัดการเชื่อมต่อและได้รับ +QIURC: "closed",0 เรื่องนี้ไม่เกี่ยวกับ QIRD (มันอ่านแค่บัฟเฟอร์ในเครื่อง ไม่แตะเครือข่าย) จะรักษาการเชื่อมต่อต้องส่งข้อมูลภายในทุก 10 วินาที หลังได้รับ closed แล้ว socket ค้างที่ closing ต้องกด Close Sock ก่อนถึงจะใช้ซ้ำได้ ไม่งั้น QIOPEN ตอบ 563

คำสั่งตอบ ERROR ให้กด Last Error ทันที (AT+QIGETERROR) —— มันเก็บแค่รายการสุดท้าย ถูกข้อผิดพลาดถัดไปทับก็หายไปเลย มันถามชั้นสแต็กของ Quectel; ชั้นเครือข่ายใช้ AT+CEER ของหน้า Network

🔴 สแต็กข้อมูลเสื่อมสภาพ —— หลุมที่เสียเวลาที่สุด อาการ: การเชื่อมต่อทั้งหมดล้มเหลว แต่การตรวจตัวเองบอกปกติหมด (QIACT? มี IP, QIGETERROR ตอบ 0) ทดสอบจริงเปิดปิด SSL ติดต่อกันราว 20 ครั้งแล้วถูกกระตุ้น ขนาด QIOPEN ของ TCP ล้วนยังตอบ 552; QIDEACT + QIACT ช่วยไม่ได้ มีแต่รันพิธีกรรมเปิดเครื่องใหม่เท่านั้นที่กู้คืนได้

วิธีจำแนก 30 วินาที: ใช้ Open TCP ยิงเป้าหมายเดียวกัน —— ล้มเหลวด้วย = สแต็กทั้งตัว พังแล้ว รันพิธีกรรมเปิดเครื่องใหม่; สำเร็จ = ปัญหาอยู่ที่โปรโตคอลชั้นบน ตรวจต่อ

QICFG=? แสดงรายการย่อยกับช่วงค่า, Keepalive? ถามค่าปัจจุบัน, Keepalive On / Off เปิดปิด —— คำสั่งสี่ปุ่มนี้ตัวมันเองไม่กินปริมาณข้อมูล; เปิดใช้แล้วขอแค่มี socket ว่างงานค้างอยู่ แพ็กเก็ตตรวจสอบก็จะนับเข้าปริมาณข้อมูลมือถือ มันกันหมดเวลา 15 วินาทีของ tcpbin ไม่ได้: ทดสอบจริงเปิดแล้วก็ยังถูกปิดที่ 15.1 วินาที —— keepalive เป็นการตรวจสอบเปล่าในชั้น TCP แอปพลิเคชันมองไม่เห็น; แถม interval ต่ำสุด 25 วินาที ใหญ่กว่า 15 อยู่แล้วโดยกำเนิด จะสู้หมดเวลาชั้นแอปพลิเคชันได้มีแต่ส่งข้อมูลจริง (เช่นทุก 10 วินาทีใช้ Send Hex ส่ง 0A) ประโยชน์ตัวจริงของมันคือ keepalive สำหรับ NAT ของผู้ให้บริการ (ซิม IoT ว่างงานไม่กี่นาที NAT ก็ถูกเรียกคืน)

บัญชีปริมาณข้อมูล (ประมาณการ ไม่ใช่ค่าวัดจริง): การตรวจสอบไปกลับหนึ่งรอบราว 80 bytes; ค่าเริ่มต้น idle = 30 วินาที ว่างงานต่อเนื่อง → ราวชั่วโมงละ 9.4 KB, วันละราว 225 KB, เดือนละราว 6.8 MB; idle = 600 วินาที → วันละราว 11 KB ซิมพรีเพดแบบเหมาปริมาณอย่าง 1NCE ต้องปรับ idle ให้ใหญ่ขึ้น ไม่มี socket เปิดอยู่ก็ไม่กินปริมาณข้อมูลเลย

MQTT —— การส่งข้อความ IoT

หลักการทำงาน: MQTT เป็นโปรโตคอลแบบ "broker (เซิร์ฟเวอร์ตัวกลางรับส่งข้อความ)": อุปกรณ์ไม่เชื่อมต่อกันตรง ๆ แต่ต่างฝ่ายต่างต่อเข้า broker แล้ว publish หรือ subscribe ข้อความบน "หัวข้อ (topic)" บน EG800K มันเป็นสองชั้น: ใช้ AT+QMTOPEN เปิด "การเชื่อมต่อเครือข่าย" ก่อน (TCP ต่อไปยัง broker) แล้วใช้ AT+QMTCONN ทำ "การล็อกอิน MQTT" สองชั้นผ่านหมดถึงจะ subscribe กับ publish ได้ จำไว้ก่อนเลย: ผลลัพธ์ของคำสั่ง MQTT เป็นแบบ "OK ก่อน แล้ว URC ตามมา" ทั้งหมด (เหมือน FTP) —— OK แปลว่าแค่รับคำสั่งไว้ สำเร็จหรือไม่ดูที่ URC ผลลัพธ์ที่ตามมา

หน้านี้ใช้ client 0 ตายตัว; เฟิร์มแวร์ยังรองรับหลาย client (0–5), SSL และการยืนยันตัวตนกับแพลตฟอร์มคลาวด์ (ยืนยันด้วย =? จากการทดสอบจริงแล้ว) การใช้งานขั้นสูงดู application note ของ MQTT

ก่อนเริ่ม: เงื่อนไขเบื้องต้นสองข้อ

  1. URC ต้องเดิน UART: AT+QURCCFG="urcport" ต้องตอบ "uart1" ค่าโรงงานคือ "usbat" ขณะที่ผลลัพธ์ MQTT เป็น URC ทั้งหมด —— ไม่แก้ ทุกคำสั่งจะตอบแค่ OK แล้วเงียบหาย (หน้า Basic มีปุ่ม; เขียนลง NVRAM แก้ครั้งเดียวพอ)
  2. PDP ต้องเปิดใช้ก่อน: ไปหน้า TCP/IP กด AT+QIACT=1 ก่อน (นานสุด 150 วินาที); ไม่เปิด +QMTOPEN จะตอบ 3 = เปิดใช้ PDP ล้มเหลว ตลอดกระบวนการเกิดปริมาณข้อมูล ประมาณราว 5 KB

ส่วนท้ายสุ่มของ client ID กับหัวข้อ: รีเฟรชทีไรเปลี่ยนชุดใหม่

client ID กับหัวข้อค่าเริ่มต้นไม่ได้เขียนตายตัว: ตอนโหลดหน้าเว็บจะสุ่มส่วนท้ายเลขฐานสิบหก 6 ตัวอักษรอัตโนมัติ ประกอบเป็น numodem-<ส่วนท้าย> กับ test/numodem-<ส่วนท้าย> ปุ่ม Subscribe / Publish / Unsub สามปุ่มใช้ชุดเดียวกันร่วมกัน (ไม่งั้นลูปสะท้อนกลับตัวเองจะจับคู่ไม่ติด) เหตุผลมีสองข้อ:

  • ชื่อชนกันจะถูกเตะหลุด: MQTT 3.1.1 §3.1.4 กำหนดให้ broker เตะตัวที่ต่ออยู่ก่อน ให้หลุดออกไป —— สองคนใช้ ID ตายตัวเดียวกันก็จะเตะกันไปมา อาการดูเหมือน "โมดูลหลุดการเชื่อมต่อแบบงง ๆ"
  • หัวข้อตายตัวจะได้รับข้อความของคนอื่น: คุณนึกว่าที่รับมาคือของที่ตัวเองส่ง แต่จริง ๆ ไม่ใช่ —— แบบนี้แย่กว่ารับไม่ได้ เพราะมันให้ผลผ่านแบบปลอม
⚠ ทุกครั้งที่รีเฟรชหน้าเว็บ ส่วนท้ายจะเปลี่ยนชุดใหม่ —— subscribe กับ publish ต้องทำให้จบภายในวงจรชีวิตหน้าเว็บครั้งเดียวกัน อีกอย่างเครื่องมือนี้ RTS = ไฟเลี้ยง โหลดหน้าใหม่ = โมดูลไฟดับ การเชื่อมต่อ MQTT หายทั้งยวง ต้องเริ่มใหม่ตั้งแต่พิธีกรรมเปิดเครื่องและ AT+QMTOPEN

เส้นทางฉบับเต็ม: เชื่อมต่อ → subscribe → publish → รับข้อความตัวเองกลับมา

การพิสูจน์ที่น่าเชื่อที่สุดคือลูปสะท้อนกลับตัวเอง: subscribe แล้ว publish ไปหัวข้อเดียวกัน รับข้อความของตัวเองกลับมาเอง ตรวจครบทั้งสายรับส่งในรอบเดียว แต่ละขั้นรอ URC ผลลัพธ์ก่อนแล้วค่อยไปต่อ:

  1. ตั้งเวอร์ชันโปรโตคอล: กด Ver 3.1.1 (AT+QMTCFG="version",0,4; 3 = 3.1, 4 = 3.1.1) กด Version? ดูค่าปัจจุบันได้ (ไม่ใส่ค่า = ถาม) การ์ดพารามิเตอร์ Keepalive ปรับช่วง keepalive ได้ ไม่ปรับก็ทดสอบได้
  2. เปิดเครือข่าย: กด Open Net (AT+QMTOPEN=0,"broker",1883) ตอบ OK ก่อน สำเร็จหรือไม่ดู URC +QMTOPEN: 0,<result> (0 = สำเร็จ) รอนานสุด 120 วินาที กด Open? ดูการเชื่อมต่อที่เปิดอยู่ได้ (ไม่มีการเชื่อมต่อตอบ OK เปล่า ๆ ทดสอบจริงเป็นเรื่องปกติ)
  3. ล็อกอิน MQTT: กด Connect (AT+QMTCONN=0,"numodem-<ส่วนท้าย>") URC สำเร็จตายตัวคือ +QMTCONN: 0,0,0 broker สาธารณะไม่ต้องใช้บัญชีรหัสผ่าน; ถ้าต้องใช้ให้เติม ,"user","pass" ท้ายพารามิเตอร์เอง กด Conn? ดูสถานะ (1 = เริ่มต้น, 2 = กำลังเชื่อมต่อ, 3 = เชื่อมต่อแล้ว, 4 = กำลังตัดการเชื่อมต่อ)
  4. subscribe: กด Subscribe (AT+QMTSUB=0,1,"test/numodem-<ส่วนท้าย>",0, msgid ตายตัว 1) URC สำเร็จหน้าตาแบบ +QMTSUB: 0,1,0,0 จากนั้นข้อความของหัวข้อนี้จะเข้ามาเป็น URC +QMTRECV ทั้งหมด
  5. publish: กด Publish (AT+QMTPUBEX, แบบสองขั้น ดูย่อหน้าถัดไป) URC สำเร็จคือ +QMTPUBEX: 0,<msgid>,0
  6. รับกลับมา: เป้าหมายที่ publish คือหัวข้อที่ subscribe อยู่พอดี ถัดมาติด ๆ จะเห็น +QMTRECV พ่วงหัวข้อกับเนื้อหาข้อความเมื่อกี้มาด้วย —— ลูปสะท้อนกลับตัวเองสำเร็จ payload อักษรหลายไบต์ (เช่นอักษรจีน) ก็ไม่ถูกตัดทอน ไม่เพี้ยน

QMTPUBEX แบบสองขั้น: นับครบความยาวส่งเองอัตโนมัติ ไม่ต้องใช้ Ctrl+Z

พารามิเตอร์ตัวท้ายของ AT+QMTPUBEX คือความยาว (จำนวนไบต์) ไม่ใช่เนื้อหาข้อความ (application note ของ MQTT §3.3.8 ปิดคดี —— วิธีส่งบรรทัดเดียวแบบยัดข้อความจะตอบ ERROR แน่นอน) ขั้นตอนที่ถูกคือแบบสองขั้น: ส่งคำสั่ง → โมดูลตอบพรอมต์ > → ส่งให้ครบ N ไบต์พอดี โมดูลนับครบความยาวก็ส่งออกเองอัตโนมัติ ไม่ต้องใช้ Ctrl+Z (ต่างจากโหมดข้อมูลของ AT+QISEND ในหน้า TCP) กด Publish แล้วอัตโนมัติทั้งหมด: แค่กรอกเนื้อหาข้อความในการ์ดพารามิเตอร์ ความยาวคำนวณจากจำนวนไบต์ UTF-8 ให้เอง (อักษร CJK ตัวละ 3 ไบต์ ทดสอบจริงคำภาษาจีนสองตัวอักษร → 6)

  • คำสั่งประเภทมี payload ไม่มีตัวเลือก "ใส่ในบรรทัดคำสั่ง" —— การส่งจากบรรทัดคำสั่งจะเติมท้ายบรรทัดเสมอ CR ตัวนั้นจะถูกนับเข้าความยาวแล้วเหลื่อม ให้ส่งด้วยปุ่ม
  • เฟิร์มแวร์ยังมี AT+QMTPUB (ตัวแปรแบบโหมดข้อมูล ต้องปิดท้ายด้วย Ctrl+Z) —— เครื่องมือนี้ใช้ QMTPUBEX ทั้งหมด ไม่ต้องเรียนสองชุด

การตีความรหัสผลลัพธ์: แต่ละคำสั่งมีช่วงค่าไม่เหมือนกัน

อย่าเอาตารางรหัสผลลัพธ์ของคำสั่ง A ไปครอบคำสั่ง B 3 ของ +QMTOPEN คือ "เปิดใช้ PDP ล้มเหลว" แต่ +QMTPUBEX ไม่มีค่า 3 อยู่เลยด้วยซ้ำ

ตัวที่อ่านผิดง่ายที่สุดคือ +QMTCONN: 0,1 —— มันอาจเป็นคำตอบของการถามที่แปลว่า "สถานะ 1 = กำลังเริ่มต้น" หรือเป็นผลของการเขียนที่แปลว่า "กำลังส่งแพ็กเก็ตซ้ำ" ก็ได้ ดูบรรทัดเดียวแยกไม่ออก เครื่องมือนี้จึงแสดงการอ่านทั้งสองแบบคู่กัน ไม่เดามั่ว

คุณไม่ต้องท่องตาราง: URC ผลลัพธ์ทั้งหมดตั้งแต่ +QMTOPEN ถึง +QMTRECV / +QMTSTAT พื้นที่เทอร์มินัลจะใส่คำอธิบายภาษาคนตามตารางเทียบทั้งเจ็ดของ application note MQTT v1.5 ให้ทีละช่อง

ออฟไลน์กับการปิดงาน

  • แค่อยากหยุดรับข้อความ แต่คงการเชื่อมต่อไว้: กด Unsub (AT+QMTUNS=0,2,"หัวข้อ", msgid ตายตัว 2)
  • ออฟไลน์แบบปกติ: กด Disconnect (AT+QMTDISC=0, ส่ง MQTT DISCONNECT) ตอบ +QMTDISC: 0,0 หลังจากนั้นไม่ต้องกด Close Net อีก —— AT+QMTCLOSE=0 มีไว้บังคับปิดตอน "QMTDISC ล้มเหลว ชั้นเครือข่ายค้าง" เท่านั้น

การหลุดที่ไม่ได้เกิดจากคุณกด (ถูกเตะ, keepalive หมดเวลา, เน็ตขาด) จะถูกรายงานด้วย URC หลุดผิดปกติ +QMTSTAT (เช่น +QMTSTAT: 0,5 พื้นที่เทอร์มินัลจะอธิบายสาเหตุให้) ตอนนั้นต้องเริ่มใหม่จาก AT+QMTOPEN

กลุ่มปุ่ม QuecLocator (QLBS): ก่อนกดดูความจริงก่อน

QuecLocator คือบริการระบุตำแหน่งบนคลาวด์ของ Quectel: AT+QLBS (ปุ่ม Locate) คำสั่งเดียว เฟิร์มแวร์เก็บวัตถุดิบเอง ส่งไปเซิร์ฟเวอร์ค้นฐานข้อมูล แล้วส่งพิกัดกลับมา ความจริงสามข้อ:

  1. ต้องมี token และเป็นบริการเก็บเงิน เอกสารทางการเขียนชัดว่าต้องติดต่อฝ่ายซัพพอร์ตของ Quectel เพื่อขอ (ไม่มีสมัครเองได้) token ของเครื่องนี้จากโรงงานว่างเปล่า
  2. เอกสารทางการ EG800K ทั้ง 16 ฉบับไม่มีฉบับไหนพูดถึง QuecLocator เอกสารประยุกต์ที่มีในมือเป็นของ EC200U / EG915U (ไวยากรณ์กับรหัสข้อผิดพลาดทดสอบจริงแล้วตรงกัน) ไม่ใช่เอกสารทางการของเครื่องนี้
  3. โปรเจกต์นี้ตัดสินแล้วว่าไม่ใช้ (2026-08-29): ลอจิกระบุตำแหน่งถูกล็อกอยู่ในเฟิร์มแวร์ บริการเลิกเมื่อไหร่ คำสั่ง AT ทั้งเส้นก็ใช้ไม่ได้ทันที เปลี่ยนผู้ให้บริการไม่ได้ (ฟอรัม Quectel ยืนยันแล้วว่าซีรีส์ BG95 หยุดซัพพอร์ต) ปุ่มยังเก็บไว้ เผื่อแค่ "ถ้าได้ token ฟรีจะได้ลองยืนยันมือ"
+QLBS: 702 คือ "เซิร์ฟเวอร์หมดเวลา" ไม่ใช่ปัญหา token โปรเจกต์นี้เคยตีความ 702 ผิดเป็น "ไม่มี token" อยู่สามสัปดาห์เต็ม —— ความจริงคือตอนนั้นลืมเปิดใช้ PDP ก่อน โมดูลต่อเซิร์ฟเวอร์ไม่ได้เลย รอจนครบเวลา (ค่าโรงงาน 60 วินาที) ก็ตอบ 702 การทดลองเทียบเมื่อ 2026-08-29 (token ว่างตลอด): PDP ไม่ได้เปิดตอบ 702; เปิดแล้วตอบ 10002 (token ไม่มีอยู่) —— เซิร์ฟเวอร์จากไต้หวันต่อได้ ที่ขาดมีแค่ token ก่อนส่ง AT+QLBS ต้อง AT+QIACT=1 ก่อนเสมอ (เกิดปริมาณข้อมูล)

71 เมตรคือ "ค้นตารางแล้วเจอ" ไม่ใช่ "ความแม่นยำการวัด" การระบุตำแหน่งด้วยสถานีฐานคือใช้ Cell ID ไปเปิดพิกัดจดทะเบียนของสถานีฐานต้นนั้น cell เดียวกันตอบจุดเดิมตลอด —— เปลี่ยนสถานีฐานหนึ่งต้น ความคลาดเคลื่อนอาจเป็นระดับกิโลเมตร; ±1051 เมตรที่บริการรายงานเองต่างหากคือการประเมินที่ซื่อสัตย์ อีกอย่าง Cell ID กับ TAC เป็นเลขฐานสิบหก ก่อนค้นตารางต้องแปลงเป็นฐานสิบ (เครื่องมือจัดการให้ในตัวแล้ว)

SSL —— ช่องทาง TLS

หลักการทำงาน: หน้า SSL คือชั้นล่างที่ใช้ร่วมกันของการเชื่อมต่อเข้ารหัส —— SSL context ที่ตั้งไว้ที่นี่กับใบรับรองที่อัปโหลด ใช้ได้พร้อมกันทั้ง SSL raw socket, MQTT over SSL และ HTTPS ตัวเลขวินาทีและพฤติกรรมในหัวข้อนี้คือค่าวัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

การเชื่อมต่อ TLS ครั้งแรก: ห้าขั้นตอน

  1. รันพิธีกรรมเปิดเครื่อง (ดูหัวข้อ "พิธีกรรมเปิดเครื่อง") แล้วกด AT+QIACT? ยืนยันช่องทางข้อมูล —— ต้องตอบ +QIACT: 1,1,…,"IP" ออกมาได้ ไม่มีก็ AT+QIACT=1 ก่อน
  2. ตั้ง context: sslversion กรอก 4 (ทุกเวอร์ชัน เข้ากันได้ดีที่สุด), ciphersuite กรอก 0XFFFF (ทุกชุด), seclevel กรอก 0 ไปก่อน —— ยืนยันว่าช่องทางผ่านก่อน การตรวจสอบเก็บไว้ทีหลัง
  3. เปิดการเชื่อมต่อ: กด AT+QSSLOPEN (เลขท้าย 0) กรอกโฮสต์กับพอร์ต ในการ์ดพารามิเตอร์ ⚠ OK แปลว่าแค่ "รับคำสั่งไว้" สำเร็จหรือไม่ต้องรอ URC: +QSSLOPEN: 4,0 ถึงจะคือสำเร็จ (ทดสอบจริง handshake 2.0 วินาที)
  4. ส่งข้อมูล: กด AT+QSSLSEND (แบบสองขั้น) —— เห็น > แล้วส่งเนื้อหา นับครบความยาวที่ประกาศไว้ก็ส่งออกอัตโนมัติ ไม่ต้องใช้ Ctrl+Z (เพดานต่อแพ็กเก็ต 1460 bytes) ฝั่งโน้นตอบกลับจะเห็น +QSSLURC: "recv",4
  5. อ่านกลับและปิด: AT+QSSLRECV (ครั้งละไม่เกิน 1500) อ่านจนเจอ +QSSLRECV: 0 แปลว่าเก็บเกลี้ยงแล้ว ไม่ใช่ข้อผิดพลาด AT+QSSLCLOSE=4 ปิด (ค่าเริ่มต้นรอนานสุด 10 วินาที; อีกปุ่มระบุจำนวนวินาทีได้ 0 = ทันที)

รายการย่อยค่าโรงงานหน้าที่และประเด็นจากการทดสอบจริง
sslversion—เวอร์ชันโปรโตคอล; 4 = รองรับทั้งหมด
ciphersuite—ชุดเข้ารหัส; 0XFFFF = รองรับทั้งหมด
seclevel00 = ไม่ตรวจสอบ, 1 = ตรวจสอบเซิร์ฟเวอร์ (ต้องอัปโหลดใบรับรอง CA ก่อน), 2 = ยืนยันสองทาง (ต้องมีใบรับรองไคลเอนต์ + คีย์ส่วนตัวเพิ่ม)
cacert—เส้นทางใบรับรอง CA รูปแบบ "UFS:ชื่อไฟล์" ไฟล์ต้องอยู่ใน UFS แล้ว (ดูหัวข้อถัดไป)
sni🔴 0 ต่อ virtual host / CDN ต้องเปิด —— IP เดียวแขวนหลายโดเมน ถ้าไม่ส่ง SNI จะได้ใบรับรองที่ไม่ตรง การตรวจสอบพังแน่นอนด้วย 566
ignorelocaltime🔴 1 สถานะโรงงานต่อให้เปิด seclevel 1 ก็ไม่ตรวจอายุใบรับรอง จะตรวจให้ตั้ง 0 และนาฬิกาโมดูลต้องตรง

🔴 ค่าโรงงานสามตัวรวมกัน = ไม่ตรวจสอบใบรับรองเลยแม้แต่น้อย (seclevel 0, sni 0, ignorelocaltime 1) จะตรวจจริงต้องตั้งให้ถูกทั้งสามตัว แถมสามค่านี้กับ cacert ไม่คงอยู่ข้ามการรีบูต (ยืนยันจากการทดสอบจริง) บูตทุกครั้งกลับเป็นค่าโรงงาน; ส่วนไฟล์ใบรับรองใน UFS ตัดไฟก็ไม่หาย

กลุ่มไฟล์ UFS: ใบรับรองเข้าโมดูลได้อย่างไร

UFS คือหน่วยเก็บแฟลชในตัวโมดูล ทดสอบจริงความจุรวม 280 KB แต่ละไฟล์กินหนึ่งบล็อก 4 KB ใบรับรองต้องอัปโหลดมาที่นี่ก่อน cacert ถึงจะมีไฟล์ให้ชี้ การอัปโหลดเดิน UART ไม่กินปริมาณข้อมูลเลย ไฟล์ไบนารีก็ส่งเข้าได้ การ์ด Upload: เลือกไฟล์แล้วชื่อกับขนาดกรอกให้อัตโนมัติ ส่งแล้วเครื่องมือรอโมดูลตอบ CONNECT ก่อนถึงจะส่งไบต์ดิบ (รอไม่ได้ก็ไม่ส่ง) เมื่อเสร็จ เอนจินคำอธิบายจะเทียบให้อัตโนมัติระหว่างขนาดกับ checksum ที่โมดูลรายงาน: ✅ = ครบถ้วนไม่ผิดเพี้ยน, ❌ = ส่งพัง ให้ลบก่อนแล้วส่งใหม่

AT+QFUPL="badssl-root.pem",1939,10
CONNECT                   ← ตามด้วยส่ง 1939 bytes
+QFUPL: 1939,4f64         ← ขนาดที่รับจริง,checksum คำอธิบายเทียบให้อัตโนมัติ ✅

พฤติกรรมจากการทดสอบจริงสองอย่างที่คู่มือไม่ได้บอกชัด: (1) รูปแบบรหัสข้อผิดพลาด FILE ไม่คงเส้นคงวา —— ส่งซ้ำชื่อเดิมตอบเป็นข้อความ file already exist แต่หมดเวลาตอบเป็นตัวเลข 421 เครื่องมือนี้อ่านได้ทั้งสองแบบ; (2) กรอกช่องขนาดใหญ่กว่าจริง โมดูลหมดเวลาแล้ว ก็ยังเซฟเนื้อหาที่รับจริงเป็นไฟล์อยู่ดี —— การเทียบ checksum จะจับได้

สนามจริงของการตรวจสอบใบรับรอง: วิธีทดสอบเป็นคู่

ขั้นตอน: อัปโหลดใบรับรองราก → cacert ชี้ไปที่มัน → seclevel 1 → sni 1 → ต่อพอร์ต 443 ของเป้าหมาย ที่ต้องอัปโหลดคือใบรับรองรากชั้นบนสุดของเชน (เชนของ badssl.com มีสี่ชั้น ให้อัปโหลด ISRG Root X1 ตัวยอดสุด) ทดสอบแค่ "ใบรับรองเสียต่อไม่ได้" ยังไม่พอ —— กรณี "ต่อไม่ได้ทั้งหมด" ก็ผ่านเหมือนกัน ต้องทดสอบเป็นคู่: ใบรับรองดีต้องต่อได้ ใบรับรองเสียต้องต่อไม่ได้ เป็นจริงทั้งสองทางถึงจะนับ ทดสอบจริงเทียบ 2×5:

รายการทดสอบเชิงลบให้เลี่ยง expired —— ค่าโรงงาน ignorelocaltime เป็น 1 การหมดอายุโดยตัวมันเอง จะไม่ถูกกัน (ในตารางบนมันถูกกันเพราะขณะเดียวกันไม่ได้อยู่ใต้รากที่อัปโหลดด้วย) จะทดสอบเดี่ยวให้ใช้ wrong.host อีกอย่างระวังปริมาณข้อมูล: ทุก handshake ดาวน์โหลดเชนใบรับรองครบชุด ล้มเหลวก็จ่ายเท่ากัน ทดสอบจริง handshake 30 ครั้งราว 150–200 KB

🔴 กับดัก: เปิดปิดติดต่อกันราว 20 ครั้ง สแต็กข้อมูลเสื่อมทั้งยวง

อาการ: AT+QSSLOPEN ทั้งหมดตอบ 552 หมด ขนาด seclevel 0 ก็ต่อไม่ได้ ทั้งที่การตรวจตัวเองทุกข้อบอกปกติ วิธีจำแนก 30 วินาที: ใช้ TCP ล้วนด้วย AT+QIOPEN ยิงเป้าหมายเดียวกัน —— ล้มเหลวด้วยคือสแต็กข้อมูลพังแล้ว อย่าไปไล่การตั้งค่า SSL ต่อ รีสตาร์ต PDP ช่วยไม่ได้ มีแต่พิธีกรรมเปิดเครื่องแบบเต็มเท่านั้นที่กู้คืนได้ ความเสื่อมจะปนเปื้อนข้อมูลทดสอบ ตัดสินผิดเป็น "ถูกการตรวจสอบใบรับรองกัน" ได้ง่าย —— ก่อนทำการทดสอบเป็นคู่ให้รีบูตล้างให้สะอาดก่อน

HTTP —— คำขอเว็บ

หลักการทำงาน: HTTP ของโมดูลเป็นแบบสามขั้น: ตั้ง URL ก่อน (ขั้นนี้เองก็เป็นสองขั้นย่อยอีกที) แล้วยิงคำขอ (GET/POST) สุดท้ายจึงอ่านคำตอบกลับมา ผลลัพธ์ของแต่ละขั้นไม่ได้อยู่ใน OK แต่มาทีหลังเป็น URC —— ดังนั้น AT+QURCCFG="urcport" ต้องเป็น "uart1" (แก้ได้ที่หน้า Hardware) ไม่อย่างนั้นจะไม่เห็นผลลัพธ์สักอย่าง ตัวเลขทั้งหมดเป็นค่าวัดจริงกับเครื่องจริงเมื่อ 2026-08

ก่อนเริ่ม: ต้องมีช่องทางข้อมูลก่อน

เงื่อนไขคือ PDP เปิดใช้งานแล้วและได้ IP มาแล้ว (AT+QIACT=1 ที่หน้า TCP/IP) กลุ่ม Connect ของหน้านี้มีแต่การตรวจสอบแบบอ่านอย่างเดียว: AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = ไม่ได้รับค่ามา), AT+QIGETERROR (⚠ มีผลกับคำสั่ง TCP/IP ตัวสุดท้ายเท่านั้น ล้มเหลวแล้วต้องกดทันที)

AT+QIACT? โกหกได้ ทดสอบจริงเคยเจอ PDP หลุดกลางคัน: คำขอล้มเหลวทั้งหมด หมดเวลาที่ 30 วินาทีเป๊ะ แล้วตอบข้อผิดพลาด 716 แต่ AT+QIACT? ยังตอบ IP มาเหมือนเดิม ใช้ AT+CGACT? เทียบไขว้ ไม่ตรงกันคือหลุดแล้ว วิธีแก้: AT+QIDEACT=1 → AT+CGACT=0,<cid ที่หลุด> → AT+QIACT=1 ping ผ่านแล้วค่อยทำต่อ

GET ครั้งแรก: สี่ขั้นตอน

  1. ตั้งค่าเบื้องต้น (กลุ่ม Config ไม่กินปริมาณข้อมูล): การ์ดพารามิเตอร์ contextid ตั้ง 1 (ผูกกับ PDP context ที่จะใช้); สวิตช์สามตัว rspout/auto, requestheader, responseheader คงไว้ที่ 0 (เหตุผลอยู่ด้านล่าง); AT+QHTTPCFG? อ่านการตั้งค่าทั้งหมดกลับมาตรวจทีเดียว AT+QHTTPCFG=? แสดงรายการที่ตั้งได้
  2. ตั้ง URL (สองขั้น): การ์ด AT+QHTTPURL มีปุ่มเดียวคือ "ส่ง (สองขั้น)" —— คุณกรอก URL ส่วนความยาวโปรแกรมคำนวณให้เอง ลำดับ: ส่ง AT+QHTTPURL=<ความยาว>,80 ก่อน รอ CONNECT เข้าโหมดข้อมูล แล้วส่งไบต์ของ URL ออกไปตามเดิม ห้ามเติมตัวจบบรรทัดใด ๆ (CR/LF จะถูกนับรวมเข้าไปในความยาว) http://www.example.com/ ยาวพอดี 23 ส่งเสร็จกด AT+QHTTPURL? อ่านกลับมา ตรงกันทุกตัวอักษร = ตัวจบบรรทัดไม่ได้ปนเข้าไป
  3. ยิงคำขอ: AT+QHTTPGET=80 (จำนวนวินาทีที่รอคำตอบ) OK แปลว่าแค่ "รับคำสั่งไว้" ผลลัพธ์จริงคือ URC ที่มาทีหลัง +QHTTPGET: 0,200 การอ่านค่าดูหัวข้อถัดไป
  4. อ่านคำตอบ: AT+QHTTPREAD=80 หลัง CONNECT เป็นไบต์ดิบทั้งหมด (ทดสอบจริง example.com ได้ 559 bytes) ตามด้วย OK —— แต่บรรทัดเดี่ยวสุดท้าย +QHTTPREAD: 0 ต่างหากคือเครื่องหมายจบ

อ่านค่า +QHTTPGET: ช่องแรกไม่ใช่รหัสสถานะ HTTP

URC ผลลัพธ์ของ GET/POST/POSTFILE เป็นสามช่องเหมือนกันหมด <err>,<httprspcode>,<content_length>: err 0 = คำสั่งทำงานสำเร็จ ไม่ใช่ 0 คือข้อผิดพลาดระดับโมดูล (716, 711…); httprspcode คือรหัสสถานะ HTTP รายงานเฉพาะตอน err=0 เท่านั้น (คู่มือระบุไว้ชัด; เครื่องมือมีคำอธิบายเทียบ 200/403/404/409/411/500 มาให้ในตัว); content_length เป็นตัวเลือก —— มีก็ต่อเมื่อส่วนหัวคำตอบของเซิร์ฟเวอร์มี CONTENT-LENGTH GET ทั่วไปมักมีแค่สองช่อง ดังนั้น +QHTTPGET: 0,404,0 ที่วัดได้จริง ไม่ใช่ความล้มเหลว: คำสั่งสำเร็จแล้ว เซิร์ฟเวอร์ต่างหากที่บอกว่าหาไม่เจอ

อ่านคำตอบ: กับดักของ AT+QHTTPREAD

พารามิเตอร์คือ "จำนวนวินาทีสูงสุดระหว่างข้อมูลสองแพ็กเก็ต" ไม่ใช่เวลารวม เฟิร์มแวร์ของเครื่องนี้รับพารามิเตอร์เดียวเท่านั้น: วิธีอ่านแบบแบ่งช่วง =<wait>,<read_len> ในคู่มือประยุกต์ ทดสอบจริงตอบ ERROR เปล่า ๆ (=? ยืนยันแล้ว) ปุ่มถูกถอดออกไปแล้ว —— การดึงกลับแบบแบ่งช่วงให้ใช้ GETEX แทน

กับดักล็อกกันเอง: rspout/auto ตั้ง 1 เมื่อไร กลุ่ม READ ล้มเหลวหมด (คู่มือระบุไว้ชัด) มันทำให้โมดูลพ่นคำตอบออกมาเอง ราคาที่จ่ายคือ READ ตายเรียบ ปุ่มนี้จึงมีกล่องยืนยัน READ พังหมดกะทันหันเมื่อไร ให้ตรวจ AT+QHTTPCFG? ก่อน

ดึงกลับแบบแบ่งช่วง: AT+QHTTPGETEX อ่านทีละ byte

AT+QHTTPGETEX=<วินาที>,<ออฟเซตเริ่มต้น>,<ความยาว> เดิน HTTP Range ดึงเฉพาะช่วงที่ระบุ ประหยัดปริมาณข้อมูล ทดสอบจริง (เนื้อหาของ endpoint คงที่เป็น abcdefghijklmnop): ออฟเซต 0 ดึง 8 ตอบ +QHTTPGET: 0,206,8 อ่านได้ abcdefgh; ออฟเซต 8 ดึงอีก 8 อ่านได้ ijklmnop การอ่านค่า: รหัสสถานะต้องเป็น 206; ถ้าตอบ 200 แล้วเนื้อหาเหมือนเดิมทุกครั้ง = เซิร์ฟเวอร์ไม่รองรับ Range ไม่ใช่โมดูลเสีย ⚠ สั่งได้เฉพาะตอน requestheader=0 เท่านั้น

POST: สองขั้นกับ Content-Type

การ์ด AT+QHTTPPOST ก็เป็นสองขั้นเช่นกัน: คุณกรอก body ส่วนความยาวคำนวณให้อัตโนมัติ ส่ง AT+QHTTPPOST=<ความยาว>,<วินาทีป้อนข้อมูล>,<วินาทีรอคำตอบ> ก่อน รอ CONNECT แล้วค่อยส่ง body สามเรื่องที่ต้องรู้:

  • CONNECT อาจต้องรอนานถึง 125 วินาที (คู่มือระบุไว้ชัด) —— เวลาหมดอายุของการรอพรอมต์ต้องตั้งให้ถึง 125 วินาที อย่าเอา 5 วินาทีของ MQTT มาใช้ต่อ
  • เพดาน body 1 MB (=? ทดสอบจริงได้ช่วง 1–1024000)
  • Content-Type ตั้งด้วยการ์ดพารามิเตอร์ contenttype ให้เรียบร้อยก่อน (รหัสชนิด 0 = form-urlencoded)

ทดสอบจริง: POST Message=HelloQuectel (20 bytes) ตอบ +QHTTPPOST: 0,200,440; JSON ที่ READ ได้กลับมายืนยันได้ว่าคู่คีย์-ค่าไปถึงจริง ความยาวคำนวณถูก และ Content-Type มีผล ส่วน User-Agent คือชื่อที่โมดูลรายงานตัวเอง QUECTEL_MODULE

ส่วนหัวที่กำหนดเองและส่วนหัวคำตอบ

  • reqheader/add: เพิ่มส่วนหัวคำขอที่กำหนดเองทีละรายการ (คู่มือไม่ได้ให้ตัวอย่างมา); ปุ่มถามใช้ดูได้ว่าตอนนี้เพิ่มไปกี่รายการ; reqheader/remove ใช้ลบ
  • requestheader ตั้ง 1 = ประกอบส่วนหัวคำขอทั้งชุดเอง ขนาด GET ยังกลายเป็นสองขั้น แถม GETEX ใช้ไม่ได้ ปกติคงไว้ที่ 0
  • responseheader ตั้ง 1 แล้ว READ จะพ่นส่วนหัวคำตอบ HTTP ออกมาด้วย (ทดสอบจริงแม้แต่ X-Test ที่กำหนดเองก็ได้กลับมา) ทดสอบเสร็จให้กลับไปเป็น 0
  • closed/ind: เปิดการรายงาน URC ของ "session ถูกปิด"

เวอร์ชันไฟล์: POSTFILE กับ READFILE (UFS)

AT+QHTTPPOSTFILE="ชื่อไฟล์",<วินาที> ใช้ไฟล์ในระบบไฟล์ของโมดูล (UFS) เป็น body ส่ง POST; AT+QHTTPREADFILE="ชื่อไฟล์",<วินาที> เก็บคำตอบเป็นไฟล์ ใน UFS ⚠ เครื่องมือนี้ตอนนี้ยังอัปโหลดไฟล์เข้า UFS ก่อนไม่ได้ และอ่านเนื้อหาไฟล์ ใน UFS กลับมาก็ไม่ได้ สองคำสั่งนี้เตรียมไว้ให้ใช้ร่วมกับกระบวนการฝั่งเฟิร์มแวร์

HTTPS: เส้นทางที่ไม่ตรวจสอบใบรับรอง

HTTPS = HTTP + SSL context กลุ่ม Connect เตรียมเส้นทางที่สั้นที่สุดไว้แล้ว กดห้าปุ่มตามลำดับ:

AT+QHTTPCFG="sslctxid",1           ← HTTP ระบุให้ใช้ SSL context 1
AT+QSSLCFG="sslversion",1,4        ← เวอร์ชัน TLS ปล่อยให้เซิร์ฟเวอร์เจรจา
AT+QSSLCFG="ciphersuite",1,0XFFFF  ← ชุดเข้ารหัสเปิดหมด
AT+QSSLCFG="seclevel",1,0          ← ไม่ตรวจสอบใบรับรอง (ดูด้านล่าง)
AT+QSSLCFG="sni",1,1               ← เปิด SNI (ค่าโรงงานคือ 0!)

จากนั้นเปลี่ยน URL ให้ขึ้นต้นด้วย https:// แล้ว GET/READ ตามปกติ —— ทดสอบจริงอ่าน HTML กลับมาได้ตรงกับเวอร์ชันไม่เข้ารหัสทุกตัวอักษร seclevel=0 (ไม่ตรวจสอบใบรับรอง) คือเส้นทางเดียวที่เครื่องมือนี้เดินได้จนจบ —— จะตรวจสอบใบรับรองต้องเขียนใบรับรอง CA ลง UFS ก่อน; รายละเอียด SSL (AT+QSSLCFG=? แสดงรายการย่อยทั้งหมด, negotiatetime ปรับจำนวนวินาทีรอ handshake) ดูหัวข้อ "SSL —— ช่องทาง TLS" SNI ค่าโรงงานคือ 0: ไม่เปิดแล้วเว็บ HTTPS ที่ใช้ IP ร่วมกันจะให้ใบรับรองที่ไม่ตรงมา ตรวจเมื่อไรก็พังเมื่อนั้น เชนใบรับรองคือตัวกินปริมาณข้อมูลหลัก: HTTPS GET หนึ่งรอบราว 8–15 KB แบบไม่เข้ารหัสแค่ราว 1 KB

การเปลี่ยนเส้นทางและการเก็บงาน

การเปลี่ยนเส้นทาง (คู่มือไม่ได้เขียนไว้ ทดสอบจริงจนกระจ่าง): โมดูลตาม 302 ให้อัตโนมัติ แต่ รับเฉพาะ Location ที่เป็นเส้นทางสัมบูรณ์ —— เส้นทางสัมพัทธ์ตอบข้อผิดพลาด 711 ล้มเหลวทันทีใน 1 มิลลิวินาที การเก็บงาน: AT+QHTTPSTOP (กลุ่ม Close) ยกเลิกคำขอที่กำลังทำอยู่และตัด session; สถานะดูแปลก ๆ หรือเจอข้อผิดพลาด 704 (โหมดข้อมูลถูกยึด) ให้กดปุ่มนี้เก็บกวาดให้สะอาดก่อน

FTP —— การส่งไฟล์

หลักการทำงาน: FTP มีสองช่องทาง: ช่องควบคุมเดินคำสั่ง ช่องข้อมูลเดินเนื้อหาไฟล์ การล็อกอิน เปลี่ยนชื่อ ลบ ถามขนาด เดินแค่ช่องควบคุม; LIST อัปโหลด ดาวน์โหลด ต้องเปิดการเชื่อมต่อข้อมูลอีกเส้นหนึ่ง —— เรื่องประหลาดเกินครึ่งของหัวข้อนี้ (615, 603 รัวติดกัน) มาจากตรงนี้ทั้งนั้น กฎทั่วไปของ Quectel ที่ใช้ตลอดทั้งหัวข้อ: OK แปลว่าแค่ "รับคำสั่งไว้" ผลลัพธ์จริงมาทีหลังในรูป URC คำตอบและตัวเลขในหัวข้อนี้เป็นค่าวัดจริงกับ EG800K ตัวจริงเมื่อเดือนสิงหาคม 2026

ก่อนเริ่ม: เงื่อนไขสองข้อ

  • PDP ต้องเปิดใช้งานก่อน: ปุ่มแรกของหน้านี้ AT+QIACT? คือการตรวจข้อนี้ —— ต้องตอบ +QIACT: 1,1,…,"IP" ออกมาได้ถึงจะไปต่อ ถ้าตอบแค่ OK ให้ไปที่หน้า TCP/IP กด Act PDP ก่อน (PDP ไม่เปิดใช้งาน QFTPOPEN ล้มเหลวแน่นอน)
  • URC ต้องเดิน UART: คำสั่ง FTP เกือบทั้งหมดเป็นแบบ "OK ก่อน ผลลัพธ์ตามมาเป็น URC" ถ้า AT+QURCCFG="urcport" ไม่ใช่ "uart1" ตรงนี้จะเห็นแต่ OK กองพะเนิน (ตั้งค่าที่หน้า Hardware)

ลำดับการล็อกอิน: ตั้งค่า → เปิด → รอ URC

  1. ผูก PDP context: AT+QFTPCFG="contextid",1 (ค่าโรงงานเป็น 1 อยู่แล้ว ปุ่มถามใช้อ่านกลับมายืนยันได้)
  2. ตั้งบัญชีและรหัสผ่าน: AT+QFTPCFG="account","บัญชี","รหัสผ่าน" ต้องตั้งให้เสร็จก่อน QFTPOPEN
  3. โหมดและชนิดไฟล์: transmode ตั้ง 1 (passive; อยู่หลัง NAT ใช้ตัวนี้เสมอ FTPS บังคับ); filetype ไฟล์ข้อความล้วนใช้ 1 นอกนั้นใช้ 0
  4. ล็อกอิน: AT+QFTPOPEN="โฮสต์",21 ตอบ OK ทันที (แค่รับไว้) รอ +QFTPOPEN: 0,0 ถึงจะคือล็อกอินสำเร็จ (นานสุด 125 วินาที) แล้วกด AT+QFTPSTAT ควรตอบ 1 (ว่าง; 2 = กำลังส่ง, 3 = กำลังปิด)
AT+QFTPCFG="account","demo","password"
AT+QFTPCFG="transmode",1
AT+QFTPOPEN="test.rebex.net",21
OK                ← แปลว่าแค่รับคำสั่งไว้
+QFTPOPEN: 0,0    ← บรรทัดนี้ต่างหากคือล็อกอินสำเร็จ

รายการตั้งค่าที่เหลือ: AT+QFTPCFG=? กดทีเดียวแสดงรายการที่ตั้งได้ครบทั้ง 10 รายการพร้อมช่วงค่า (ไม่กินปริมาณข้อมูล) rsptimeout (20–180 ค่าเริ่มต้น 90 วินาที) คือเวลาตอบสูงสุดของคำสั่งส่วนใหญ่ และเป็นระยะห่างสูงสุดระหว่างข้อมูลสองแพ็กเก็ตในโหมดข้อมูลด้วย; ssltype / sslctxid ใช้กับ FTPS (FTP ล้วนคงไว้ที่ 0 พารามิเตอร์ SSL ตั้งที่หน้า SSL); data_address / cache / restenable เป็นการปรับละเอียดสำหรับสภาพแวดล้อมพิเศษ ดูหน้าที่ได้จากคำอธิบายของแต่ละปุ่มและคู่มือ

การปิดบังรหัสผ่าน (จากการทดสอบจริง ไม่ตรงกับคู่มือ): ถาม AT+QFTPCFG="account" แล้วรหัสผ่านที่อ่านกลับมาถูกบังเป็น * (คู่มือบอกว่าพิมพ์ออกมาตามเดิม) แต่ชื่อบัญชียังเป็นข้อความล้วน และรหัสผ่านในบรรทัดที่ตั้งค่าก็เป็นข้อความล้วนเช่นกัน เวลาจับภาพหรืออัดวิดีโอสิ่งที่ต้องระวังคือบรรทัดตั้งค่า
🔴 AT+QFTPCLOSE เป็นแบบอะซิงโครนัส —— OK ไม่ได้แปลว่าปิดเรียบร้อยแล้ว ต้องรอ +QFTPCLOSE: 0,0 ถึงจะนับว่าออกจากระบบเสร็จ; ระหว่างนั้น AT+QFTPSTAT ตอบ 3 (กำลังปิด) และคำสั่ง FTP ใด ๆ ก็ตามตอบ +CME ERROR: 603 ทั้งหมด (เซิร์ฟเวอร์ไม่ว่าง)

อาการนี้ชวนเข้าใจผิดอย่างยิ่ง: 603 รัวเป็นชุดดูเหมือนโมดูลเสียหรือถูกเซิร์ฟเวอร์บล็อก ทั้งที่จริงแค่ยังปิดไม่เสร็จ (วันที่ทดสอบจริงก็หลงทางเพราะเรื่องนี้ไปพักใหญ่) เพดานเวลารอ = rsptimeout อีกอย่างมันออกจากระบบแค่ FTP; จะรีเซ็ตเครือข่ายให้หมดจดต้องไปที่หน้า TCP/IP กด Deact PDP

จัดการไดเรกทอรีและไฟล์: ใช้เซิร์ฟเวอร์เหมือนโปรแกรมจัดการไฟล์

ชุดคำสั่งจัดการไฟล์ฝั่งเซิร์ฟเวอร์ครบชุด (LIST / NLST / MLSD ต้องเปิดการเชื่อมต่อข้อมูล นอกนั้นเดินแค่ช่องควบคุม) คำตอบเมื่อสำเร็จเป็น +QFTPXXX: 0,… เหมือนกันหมด —— ตัวเลขตัวแรกเป็น 0 ก็คือสำเร็จ:

คำสั่งทำอะไรคำตอบเมื่อสำเร็จ (ทดสอบจริง)
AT+QFTPPWDถามไดเรกทอรีทำงานปัจจุบัน+QFTPPWD: 0,"/"
AT+QFTPCWDเปลี่ยนไดเรกทอรีทำงาน การทำงานหลังจากนี้ยึดตัวนี้เป็นฐาน+QFTPCWD: 0,0

ลูกเล่น (ทดสอบจริงผ่านตลอดสาย): ใช้ SIZE เป็นตัวตรวจว่ามีอยู่จริงหรือไม่ —— เปลี่ยนชื่อแล้วถามชื่อเก่าตอบ +QFTPSIZE: 627,550 ถามชื่อใหม่ตอบ 0,20; ลบแล้วถามอีกทีก็เป็น 627,550 ไม่ดาวน์โหลดสักไบต์เดียวก็ยืนยันได้ทุกขั้นตอน 627,550 เป็นรหัสข้อผิดพลาดสองชั้น: 627 = ชั้นโมดูล "FTP ไม่ได้ทำการกระทำที่ร้องขอ", 550 = ชั้นโปรโตคอล FTP เซิร์ฟเวอร์ตอบว่า "ไม่มีไฟล์หรือไดเรกทอรีนี้" คำอธิบายของเครื่องมือนี้จะแปลแยกให้เป็นชั้น ๆ

ดาวน์โหลด: เนื้อหาพิมพ์ออกที่เทอร์มินัลตรง ๆ (COM:)

AT+QFTPGET="ชื่อไฟล์","COM:" —— หลัง CONNECT เนื้อหาไฟล์พ่นออกที่เทอร์มินัลเลย ปิดท้ายด้วย +QFTPGET: 0,<จำนวนไบต์> (ทดสอบจริง readme.txt ตอบ 0,379) อีกปุ่มคือดาวน์โหลดเป็นก้อน มีพารามิเตอร์จุดเริ่มกับความยาวเพิ่มมา เป็นวิธีดาวน์โหลดที่แนะนำที่สุด: ถามขนาดด้วย SIZE ก่อน แล้วค่อยทยอยดึงเป็นก้อน เลี่ยงการดึงทั้งไฟล์จนปริมาณข้อมูลบาน AT+QFTPLEN ถามว่า PUT / GET / LIST / NLST ครั้งก่อนส่งไปจริงกี่ byte

อัปโหลด: สองขั้น ส่งครบความยาวที่ประกาศไว้ก็จบเอง

AT+QFTPPUT="ชื่อไฟล์","COM:",0,<ความยาว>,1 เป็นคำสั่งแบบสองขั้น: รอ CONNECT (เข้าโหมดข้อมูล) แล้วส่งไบต์ออกไปให้พอดีกับความยาวที่ประกาศไว้ โมดูลนับครบก็ออกจากโหมดข้อมูลเอง ไม่ต้องส่ง Ctrl+Z เครื่องมือนี้คำนวณความยาวให้อัตโนมัติ วางเนื้อหาลงการ์ดพารามิเตอร์ก็พอ

AT+QFTPPUT="numodem-test.txt","COM:",0,20,1
CONNECT                        ← เข้าโหมดข้อมูล
NuModem-P6-FTP-test\n          ← ส่งออกไปพอดี 20 bytes
OK
+QFTPPUT: 0,20                 ← เซิร์ฟเวอร์รับได้ 20 bytes

20 bytes ชุดนี้ตอนทดสอบจริงจงใจดึงกลับมาจากฝั่งเครื่องโฮสต์ด้วย Python ftplib เทียบทีละไบต์ —— ตรงกันทั้งหมด รูปแบบผ่าน UFS: คู่มือรองรับการเขียนชื่อไฟล์เป็น "UFS:xxx" ให้ผ่านพื้นที่เก็บข้อมูลในตัวโมดูลอีกทอด รายละเอียดดูคู่มือประยุกต์ FTPS; ต้องเอาไฟล์จากคอมพิวเตอร์เข้า UFS ก่อน ใช้ปุ่ม Upload ในกลุ่ม "ไฟล์ UFS" ของหน้า SSL (AT+QFUPL เดิน UART ไม่กินปริมาณข้อมูล เทียบ checksum ให้อัตโนมัติ)

⚠ +++ สำหรับ FTP คือ "ยกเลิก" ไม่ใช่ "หยุดชั่วคราว" คู่มือ (FTPS AN v1.5 p13) เขียนว่าหลังหนีออกมาแล้วใช้ ATO กลับเข้าโหมดข้อมูลส่งต่อได้ ทดสอบจริงไม่เป็นเช่นนั้น (ทดสอบสองครั้งผลตรงกัน): หลังหนีออกมา AT+QFTPSTAT ตอบ 1 (ว่าง) ไม่ใช่ 2 (กำลังส่ง) และ ATO ตอบ NO CARRIER —— การส่งถูกยกเลิกไปทั้งยวงแล้ว ไม่มีการเชื่อมต่อให้กู้คืน ดังนั้น +++ ใช้ได้แค่หนีออกจาก โหมดข้อมูลที่คุมไม่อยู่ เอามาหยุดการดาวน์โหลดไฟล์ใหญ่ชั่วคราวไม่ได้

วิธีส่งที่ถูกต้อง: เงียบ 1 วินาทีทั้งก่อนและหลัง ส่งเป็นไบต์ดิบ ห้ามเติม CR (เติมแล้วไม่ทำงาน) —— ปุ่ม +++ ของหน้านี้ส่งตามกฎนี้อยู่แล้ว; ส่วนปุ่ม ATO คงไว้ตามความหมายในคู่มือ

อาการสาเหตุและวิธีแก้
+CME ERROR: 603 รัวเป็นชุด ① หลัง QFTPCLOSE ยังปิดไม่เสร็จ (QFTPSTAT ตอบ 3) —— รอ +QFTPCLOSE: 0,0; ② ก่อนหน้านี้เคยเกิด 615 —— หลัง 615 คำสั่ง FTP ทุกตัวตอบ 603 ทั้งหมด จนกว่าจะปิดอย่างถูกต้อง
+CME ERROR: 615 เปิดการเชื่อมต่อข้อมูลล้มเหลว: ช่องควบคุมปกติ ช่องข้อมูลตายเรียบ (SIZE ตอบได้ แต่ PUT / GET / LIST ล้มหมด) ส่วนใหญ่เป็นปัญหาฝั่งเซิร์ฟเวอร์ —— dlptest ทดสอบจากเส้นทางเครือข่ายสองเส้นที่ต่างกันก็ล้มเหลวทั้งคู่ ส่วน rebex ไม่ล้มเลยตลอดการทดสอบ; ให้อ่านด้วย rebex ส่วนการเขียนค่อยใช้ dlptest และทำให้จบในรอบเดียว
627,550 ไม่มีไฟล์หรือไดเรกทอรีนี้ —— ชื่อไฟล์หรือเส้นทางพิมพ์ผิด กด QFTPPWD / QFTPLIST ยืนยันก่อนว่าตัวเองอยู่ตรงไหน
รีบูตแล้ว PUT ตัวแรกก็ 615 เลย สแต็กข้อมูลเสื่อม: QFTPCLOSE กับการรีสตาร์ต PDP ก็กู้ไม่ได้ มีแต่พิธีกรรมเปิดเครื่องแบบเต็มเท่านั้นที่กู้คืนได้ วิธีจำแนก: ใช้ AT+QIOPEN ของหน้า TCP/IP ยิงเป้าหมายเดียวกัน —— ล้มเหลวด้วยคือสแต็กพังทั้งยวง อย่าไปไล่การตั้งค่า FTP ต่อ
คำสั่งตอบ OK แล้วไม่เกิดอะไรขึ้นเลย URC ผลลัพธ์วิ่งไปออกพอร์ต USB แล้ว —— ตรวจ AT+QURCCFG="urcport" ว่าเป็น uart1 หรือเปล่า
AT+QFTPOPEN ล้มเหลวตั้งแต่ต้น PDP ไม่ได้เปิดใช้งาน —— กด AT+QIACT? ของหน้านี้ก่อน ไม่มี IP ก็ไปที่หน้า TCP/IP กด Act PDP

ไม่มีกลุ่มควบคุมก็อย่าเพิ่งสรุป

สองตัวอย่าง:

  • การตรวจสอบใบรับรอง: ถ้าทดสอบแค่ "ใบรับรองเสียแล้วต่อไม่ได้" กรณี "ต่อไม่ได้ทั้งหมด" ก็ผ่านเหมือนกัน ต้องพิสูจน์พร้อมกันด้วยว่าใบรับรองดีต่อได้
  • การเร่งด้วย AGNSS: ข้อ 7-2 "TTFF แบบเริ่มเย็น" ก็คือกลุ่มควบคุมของข้อ 7-4 อยู่แล้ว ถ้าอยู่ในอาคารที่ไม่มีสัญญาณดาวเทียม ทั้งสองฝั่งก็ระบุตำแหน่งไม่ได้ ทดสอบไปก็ได้แค่ "ล้มเหลวทั้งคู่"

รันการตรวจสุขภาพหนึ่งครั้งท้ายการทดสอบทุกรอบ

โมดูลจะเสื่อมสภาพ หลังจากเปิดปิดการเชื่อมต่อติดต่อกันราว 20 ครั้ง มันจะเข้าสู่สภาวะที่ "ช่องควบคุมยังมีชีวิต แต่ช่องข้อมูลตายสนิท" —— แถม QSSLSTATE ว่างเปล่า, QIACT? มี IP, QIGETERROR ตอบ 0 มันดูปกติทุกประการ

สภาวะนี้จะปนเปื้อนข้อมูลการทดสอบ เคยเกิดขึ้นจริงมาแล้ว: ระหว่างช่วงที่เสื่อมสภาพ โฮสต์บางตัวต่อไม่ได้แม้แต่ตอน "ปิดการตรวจสอบ" เกือบจะถูกตัดสินว่าเป็นผลของการตรวจสอบใบรับรองไปแล้ว ก่อนจบทุกรอบให้ตรวจสอบด้วยเป้าหมายที่รู้แน่ว่าต่อได้หนึ่งครั้ง ข้อมูลถึงจะเชื่อถือได้

วิธีแยกแยะ: ใช้ AT+QIOPEN แบบ TCP ล้วนยิงไปที่เป้าหมายเดียวกัน ถ้ามันล้มเหลวด้วย ก็ไม่ใช่ปัญหาของชั้น SSL / FTP แต่เป็นสแตกข้อมูลทั้งก้อนที่พัง
วิธีกู้คืน: มีแต่พิธีกรรมเปิดเครื่องแบบเต็มเท่านั้นที่ได้ผล QIDEACT + QIACT กู้ไม่ขึ้น

การตรวจสอบแบบไม่กินปริมาณข้อมูล: AT+Q...=?

รูปแบบทดสอบ (=?) ไม่แตะเครือข่ายและไม่เสียเงิน แถมสิ่งที่ตอบกลับมาคือช่วงพารามิเตอร์ที่เฟิร์มแวร์ตัวนี้รองรับจริง —— น่าเชื่อถือกว่าเอกสาร application note เพราะเอกสารนั้นใช้ร่วมกันทั้งซีรีส์ โปรเจกต์นี้ก็ใช้วิธีนี้แหละจับได้ว่าช่วงพารามิเตอร์การสแกน Wi-Fi ไม่ตรงกับคู่มือ

การพิสูจน์ว่า "ส่งไปถูกต้องจริง" ต้องอ่านกลับมาจากบุคคลที่สาม

+QFTPPUT: 0,20 เป็นแค่โมดูลรายงานตัวเองว่ามันส่งไป 20 bytes การทดสอบจริงคือใช้ FTP client อีกตัวจากฝั่งคอมพิวเตอร์ดึงไฟล์กลับมาเทียบทีละไบต์ —— แบบนี้ถึงจะตัดความเป็นไปได้ทั้ง "โมดูลนับผิด" และ "เซิร์ฟเวอร์เก็บเสีย" ออกไปพร้อมกัน

ปริมาณข้อมูล

AT+QGDCNT? ตอบจำนวนไบต์สองค่าคือ "ส่ง,รับ" ⚠ ตัวนับนี้ไม่ถูกเก็บใน NV โมดูลรีบูตทีไรก็กลับเป็นศูนย์; AT+QAUGDCNT ไม่ใช่ตัวนับสะสม แต่เป็นการตั้งค่า "ช่วงเวลาบันทึกอัตโนมัติ" (0 = ปิดใช้งาน) ถ้าจะสะสมข้ามช่วงต้องจดค่าทันทีในทุกช่วง ย้อนกลับมาเก็บทีหลังไม่ได้

ตัวเลขอ้างอิง: TLS handshake แพงกว่าที่สัญชาตญาณบอกมาก ทุกครั้งที่ handshake ต้องดาวน์โหลดเชนใบรับรองทั้งชุด และ handshake ที่ล้มเหลวก็ต้องจ่ายเงินเหมือนกัน ทดสอบจริง 11 ครั้ง handshake ใช้ไป TX 15.3 KB / RX 59.6 KB

ถาม: ตอบ +CME ERROR: 603 ไม่หยุด

ถาม: การเชื่อมต่อล้มเหลวทั้งหมด แต่ AT+QIACT? ยังแสดงว่ามี IP

ถาม: ส่งข้อมูลไปที่ echo server แล้วไม่ได้รับเสียงสะท้อนกลับ

ตรวจว่าท้าย payload มี \n หรือไม่ บริการ echo จำนวนมากทำงานทีละบรรทัด ถ้าไม่มีตัวขึ้นบรรทัดใหม่ก็จะไม่ส่งกลับ ในช่องกรอกแค่พิมพ์อักขระสองตัวว่า \n ก็พอ เครื่องมือจะถอดรหัสเป็นตัวขึ้นบรรทัดใหม่จริงก่อนส่งออก และคำนวณความยาวให้ถูกต้องตามไปด้วย

ถาม: GNSS ระบุตำแหน่งไม่ได้สักที
