🎯 Introduction

NuModem EG800 est une console de pilotage de modem 4G tenant dans un fichier HTML unique. Elle envoie des commandes AT directement aux modules Quectel EG800K via la Web Serial API du navigateur : rien à installer, aucun logiciel en dehors du pilote, aucun serveur backend.

En quoi diffère-t-elle d'un terminal série ordinaire ? En ceci : elle comprend les commandes AT. Chaque commande que vous envoyez, chaque ligne que le module renvoie, est immédiatement accompagnée d'une explication en langage humain — y compris pour les codes d'erreur purement numériques.

Ce que couvre ce manuel
De l'ouverture de la page au branchement du module et au rituel de démarrage, jusqu'au principe de fonctionnement et à la méthode de test de chaque groupe de commandes AT des dix onglets. Toutes les descriptions de comportement proviennent de mesures réelles menées en août 2026 sur un EG800K physique, et non d'une recopie du manuel — là où le manuel se trompe, ce texte le dit franchement.

🚀 Démarrage rapide

Étape 1 — Ouvrir NuModem

Ouvrez NuModem_EG800.html dans Chrome ou Edge — un double-clic suffit, aucun serveur nécessaire.

Étape 2 — Brancher le module

Cliquez sur Connecter en haut à gauche. Le navigateur ouvre la fenêtre de sélection de port : choisissez votre pont USB-UART. La flèche à droite déroule une liste permettant de choisir directement un port déjà autorisé.

Une fois l'autorisation accordée, les ouvertures suivantes se connectent directement au clic sur « Connecter », sans nouvelle question. Si vous avez plusieurs périphériques série, la liste déroulante est plus rapide.

Étape 3 — Vérifier le débit

Le sélecteur de débit, en haut, est réglé sur 115200 par défaut : c'est la valeur d'usine de l'EG800K, il n'y a en général rien à changer.

Étape 4 — Exécuter le rituel de démarrage

Cette étape ne se saute pas. À l'instant où le navigateur ouvre le port série, RTS est remis à l'état haut, or sur cette carte de contrôle RTS est un interrupteur d'alimentation à logique inversée — autrement dit le module est coupé au moment même où vous vous connectez. Détails dans la section suivante.

Le symptôme typique quand on saute le rituel de démarrage : vos commandes s'affichent bien dans le terminal, mais il n'y a strictement aucune réponse. Ce n'est ni un mauvais débit ni un câblage inversé : le module n'est tout simplement pas alimenté.

🔌 Rituel de démarrage (la section la plus importante)

L'EG800K ne démarre pas du seul fait d'être alimenté. Cette carte de contrôle relie deux signaux de sortie RS-232 aux broches de commande du module :

SignalRelié àLogique
RTSInterrupteur d'alimentation du module Logique inversée : RTS OFF = alimenté, RTS ON = coupé
DTRBroche Reset du module DTR ON = Reset au niveau haut (démarrage possible), OFF = Reset au niveau bas

Procédure standard

Passez à l'onglet Hardware : deux boutons dédiés s'y trouvent.

  1. Power — fait passer RTS par ON → OFF une fois. Le bouton en vert signifie que l'alimentation est active (c'est-à-dire RTS sur OFF).
    ⚠ Mettre directement OFF ne garantit pas la mise sous tension, il faut impérativement passer par ON puis OFF.
  2. Attendez une seconde.
  3. Reset — c'est un bouton « à maintenir enfoncé » : à l'appui DTR passe à OFF, au relâchement il revient à ON. Maintenez environ 300 millisecondes.
  4. Attendez que RDY apparaisse dans le terminal. En pratique, cela survient en quelques secondes.

Vous pouvez aussi cliquer directement sur RTS / DTR dans la barre de signaux : l'effet est identique, mais l'ordre des opérations est à votre charge.

Comment vérifier que le démarrage a réussi

Le terminal doit cracher ceci, dans l'ordre :

RDY ← démarrage du module terminé
+CFUN: 1 ← radio activée
+CPIN: READY ← SIM prête
+QUSIM: 1
+QIND: SMS DONE ← initialisation SMS terminée
+QIND: PB DONE ← initialisation du répertoire terminée

Envoyez ensuite ATI pour vérifier : le module doit répondre trois lignes (marque, modèle, version de firmware) suivies de OK.

⚠ Chaque rechargement de la page impose de refaire le rituel de démarrage. Recharger la page rouvre le port série, et rouvrir le port série ré-asserte RTS — donc le module vient d'être coupé une nouvelle fois. C'est la raison pour laquelle, avec cet outil, on croit le plus souvent à tort que « le module est mort ».

Les deux commandes à envoyer juste après le démarrage

CommandePourquoi
ATE1 Active l'écho. Le module renvoie tel quel ce qu'il a reçu, ce qui permet de comparer dans le terminal « ce que vous avez envoyé » et « ce que le module a réellement reçu » : une faute de frappe saute aux yeux.
AT+CMEE=2 Passe les messages d'erreur en texte. Sans cela, une erreur se réduit à un ERROR sec ; avec, vous obtenez des messages lisibles du type +CME ERROR: SIM not inserted.

Ces deux commandes ne valent que pour la session : il faut les renvoyer après chaque redémarrage du module.

🔴 Quand aucune URC n'arrive, la première chose à vérifier est AT+QURCCFG="urcport". En sortie d'usine, le module envoie les URC (messages spontanés) vers le port AT USB ; cet outil, qui passe par l'UART, n'en reçoit aucune — le symptôme est « toutes les commandes répondent OK, mais plus rien ne suit », et le positionnement GNSS, l'arrivée de données TCP, les messages MQTT et les résultats de scan Wi-Fi restent tous muets. Solution : AT+QURCCFG="urcport","uart1", écrite en NVRAM et donc conservée au redémarrage.

📟 Terminal

La moitié droite, c'est le terminal. Sa plus grande différence avec un terminal série ordinaire : chaque ligne est annotée.

Les quatre couleurs sont modifiables : cliquez sur le carré de couleur pour ouvrir le sélecteur.

Moteur d'annotation

C'est le cœur de NuModem. Il fait deux choses :

  • Expliquer la commande que vous envoyez — par exemple, pour AT+QSSLSEND=4,18, l'annotation indique « envoi d'une longueur fixe de 18 octets vers le clientID 4 : une fois que le module a affiché l'invite >, il faut envoyer “exactement” 18 octets pour que l'émission parte ; pas besoin de Ctrl+Z ».
  • Interpréter la réponse du module — surtout celles qui ne sont que des chiffres. Par exemple, +QFTPSIZE: 627,550 est décomposé en deux niveaux : « erreur 627 : FTP n'a pas exécuté l'action demandée ; le serveur répond 550 : action non exécutée, fichier ou répertoire inexistant ».
L'annotation suit les paramètres que vous avez réellement saisis. Le même bouton avec des valeurs différentes produit des chiffres différents dans l'annotation — ce n'est pas un texte d'explication figé.

Fin de ligne

La fin de ligne se choisit à droite du champ de saisie. L'EG800K exige CR ; avec LF, le module ne répond jamais. C'est le réglage sur lequel on se fait avoir le plus souvent.

Divers

  • En bas s'affichent les compteurs cumulés d'octets RX / TX et le nom du port courant.
  • En haut à droite, une rangée de boutons : annotations, fin de ligne, horodatage, défilement automatique, effacement.
  • La zone terminal comporte aussi deux onglets, État des satellites et Carte, qui se remplissent une fois le positionnement GNSS obtenu.

🎛️ Fonctionnement du panneau de commandes AT

La moitié gauche, ce sont dix onglets et plus de deux cents boutons. Avant d'examiner les onglets un par un, comprenez ces quelques mécanismes communs : ils resservent sur chacune des pages.

Deux types de boutons

StyleComportement
Bouton normalUn clic envoie directement
Cadre pointilléDes paramètres sont à renseigner. Une fois remplis, vous pouvez « Envoyer », ou « Insérer dans la ligne de commande » pour déposer la commande assemblée dans le champ de saisie du bas et la retoucher vous-même

Champs de paramètres

Chaque champ a sa propre explication (elle apparaît au survol de la souris) ; elle donne les plages mesurées sur le matériel, pas celles recopiées du manuel. Par exemple, le « nombre de tours » du scan Wi-Fi est annoncé 1-3, parce que AT+QWIFISCAN=? renvoie effectivement cette plage — le 1-6 de la note d'application est faux.

Envoi de données en deux temps

Certaines commandes ne se terminent pas sur une seule ligne. Leur déroulé est le suivant :

Envoi de la commande → le module répond > ou CONNECT → envoi d'exactement N octets → le module renvoie le résultat

Ces boutons possèdent un champ « contenu des données » distinct, et la longueur est calculée automatiquement puis insérée dans la commande : vous n'avez rien à compter. Appartiennent à cette catégorie AT+QISEND, AT+QSSLSEND, AT+QMTPUBEX, AT+QHTTPURL, AT+QHTTPPOST, AT+QFTPPUT.

Une longueur mal calculée fait très mal. Le module attend jusqu'à avoir reçu le nombre d'octets que vous avez déclaré ; pendant ce temps, le port AT est en « mode données » — tout ce que vous tapez ensuite est avalé comme donnée.

Pour s'en sortir : envoyez un ESC (0x1B) avec le bouton d'octets bruts de l'onglet Hardware. Pas besoin de fermer la connexion ni de redémarrer le module.

Séquences d'échappement

Le champ de contenu des données est une zone de texte sur une seule ligne : impossible d'y taper un saut de ligne, une tabulation ou d'autres caractères de contrôle. Ces champs acceptent donc des séquences d'échappement :

NotationOctet envoyé
\n0x0A saut de ligne
\r0x0D retour chariot
\t0x09 tabulation
\00x00 NUL
\xHHOctet quelconque, HH en hexadécimal
\\La barre oblique inverse elle-même

Le décodage a lieu avant l'envoi, et la longueur est calculée sur les octets décodés. Par exemple, hello\n compte 7 caractères dans le champ mais 6 octets à l'émission : la longueur inscrite dans la commande sera donc 6.

Pourquoi c'est important : beaucoup de serveurs de test renvoient l'écho ligne par ligne (ils renvoient ce qu'on leur envoie, mais n'agissent qu'à la vue d'un saut de ligne). Si le payload ne se termine pas par \n, vous n'obtiendrez jamais de réponse — et cela ressemblera à une « connexion cassée ».

Indication de délai

Certaines commandes AT bloquent longtemps. Le symbole ⏱ sur un bouton donne le temps d'attente maximal annoncé par le manuel, par exemple 150 secondes pour AT+QIACT=1, 300 secondes pour AT+COPS=?. Quand une réponse tarde, regardez d'abord cette indication : le plus souvent, le délai n'est simplement pas écoulé.

Boîtes de confirmation

Seules les actions qui bloquent le port AT en mode données ou qui sont irréversibles (suppression d'un fichier distant, redémarrage logiciel du module, changement de débit) déclenchent une confirmation. Le simple fait de « consommer du trafic » ne vous barre pas la route — ce type d'avertissement figure plutôt dans l'explication du bouton.

Options locales

Sous quelques boutons figure une petite case à cocher : c'est un comportement côté outil, pas une commande AT. Par exemple, sous AT+QICLOSE=0 : « fermer automatiquement à la détection de +QIURC: "closed",0 ». Ces options sont mémorisées dans le navigateur et sont toujours là à la réouverture.

🗂️ Les dix onglets

L'ordre des onglets a un sens : de gauche à droite, c'est à peu près l'ordre dans lequel vous devez opérer. Hardware pour démarrer → Basic pour vérifier que le module est vivant → Network pour vérifier l'accès au réseau → les cinq suivants sont les différents protocoles de données.

Hardware — démarrage et port série

Principe de fonctionnement : cette page est la fondation de tout l'outil : Control regroupe les deux boutons du rituel de démarrage (Power / Reset), Module l'identification du produit, Serial les réglages UART, Power la basse consommation, URC le port de sortie des messages spontanés du module, plus une rangée de boutons d'octets bruts qui servent d'issue de secours en mode données. Tous les autres onglets reposent sur deux prérequis : le module a été démarré selon le rituel et les URC passent par uart1 — ces deux choses se règlent ici. Tous les comportements et chiffres de cette section sont des mesures d'août 2026 sur un EG800K réel.

Pourquoi un rituel de démarrage : RTS = alimentation, DTR = Reset

La carte de contrôle associée à cet outil détourne deux signaux de contrôle RS-232 de leur rôle habituel — c'est la clé de toute cette page :

SignalRéellement câblé surLogique
RTSInterrupteur d'alimentation du module Logique inversée : RTS OFF = sous tension, RTS ON = hors tension
DTRBroche Reset du module DTR ON = Reset au niveau haut (démarrage possible), DTR OFF = Reset au niveau bas

Particularité du circuit (confirmée par mesure) : à la première connexion, RTS doit passer par ON puis OFF pour que l'alimentation s'enclenche réellement — mettre OFF directement ne garantit pas la mise sous tension ; DTR doit lui aussi suivre ON→OFF→ON pour que Reset monte vraiment. La coupure (RTS ON) est brutale : le module n'envoie aucun message d'adieu.

Recharger la page = couper le courant. Quand le navigateur rouvre le port série, il relève RTS et le module perd instantanément l'alimentation — après la reconnexion automatique, il faut refaire le rituel de démarrage. Vécu en test : 17 commandes envoyées en sautant le rituel, toutes parties sans retour (que des lignes TX, zéro RX). Devant tout « ça marchait il y a une seconde, plus rien ne répond », pensez d'abord à cela.

Boutons Power et Reset : comment appuyer, ce que vous verrez

Ces deux boutons incarnent les deux signaux du tableau ci-dessus et sont couplés dans les deux sens avec les indicateurs RTS / DTR de la barre de signaux (grisés et inactifs hors connexion). Web Serial ne peut pas relire l'état réel des signaux de sortie : la barre affiche la valeur que cet outil croit avoir envoyée.

  1. Power (à bascule) : vert allumé = alimentation ON (= RTS OFF). Le rituel exige que RTS passe par ON→OFF : si le bouton est déjà allumé, éteignez-le puis rallumez-le.
  2. Reset (momentary) : appui = DTR OFF, relâchement = DTR ON, un appui-relâchement = un Reset (la séquence standard marque une pause de 0.3 seconde au milieu).
  3. Attendre RDY : en quelques secondes, le terminal affiche l'annonce de démarrage du module RDY.
  4. Vérifier avec ATI : la réponse doit être Quectel / EG800K / Revision: … / OK. Si elle arrive, l'UART et le module sont tous deux vivants.
Après le démarrage, vérifiez d'abord que l'écho (ATE) est actif (il l'est en sortie d'usine), puis envoyez AT+CMEE=2 — sans lui, vous ne verrez qu'un aride ERROR ; avec lui, vous obtenez le texte lisible +CME ERROR: …. Les deux réglages ne valent que pour la session : à refaire à chaque redémarrage du module.

Le triple piège du changement de débit (intégralement confirmé par mesure) :
① Dès que OK revient, le changement est immédiat : l'instant d'après, cet outil et le module ne parlent plus la même langue ;
② AT&F (réinitialisation d'usine) ne remet pas le débit d'origine — n'espérez pas qu'il vous sauve ;
③ Sans &W, rien n'est enregistré — or reconnexion = coupure de courant : le module se réveillerait à l'ancien débit alors que votre port resterait réglé sur le nouveau, double perte de contact. C'est pourquoi cet outil impose la forme combinée ;&W.
Récupération en quatre étapes (rappelées aussi dans la boîte de confirmation) : déconnecter → changer le débit dans la zone de connexion → reconnecter → refaire le rituel de démarrage.

Power : basse consommation QSCLK

Sleep? (AT+QSCLK?) : interroge si le module a le droit de s'endormir. Mesuré ici : 0 en sortie d'usine = désactivé, module toujours éveillé. Cette page ne propose que le bouton d'interrogation : un module endormi cesse de répondre aux commandes AT, et la méthode de réveil du manuel est d'abaisser DTR — or sur cette carte, DTR est déjà câblé sur la broche Reset (voir le début de cette section). Si vous avez activé le sommeil depuis la ligne de commande et que le module ne se réveille plus, refaites le rituel de démarrage (coupure puis remise sous tension) pour vous en sortir ; détails dans la note d'application officielle sur la basse consommation.

URC : quand aucun message n'arrive, venez ici en premier

Un URC (Unsolicited Result Code, code de résultat non sollicité) est un message que le module « émet spontanément, sans qu'on le lui demande », et non la réponse à une commande — le RDY du démarrage, l'arrivée de données TCP, les messages MQTT, les résultats de scan Wi-Fi, la notification de chargement du firmware GNSS en sont tous. Son port de sortie est par défaut le port USB (usbat) — cet outil, qui passe par l'UART, n'en reçoit alors aucun ; le symptôme est très typique : toutes les commandes répondent OK, mais les messages ne viennent jamais.

Boutons d'octets bruts : l'issue de secours du mode données

Beaucoup de commandes sont en deux temps : on envoie la commande, on attend l'invite > du module, puis on envoie le corps. Une fois entré dans ce mode données, le module avale comme données chaque caractère que vous tapez — y compris les commandes AT que vous voudriez lancer. Longueur mal calculée, changement d'avis en cours de route, commande bloquée : les touches ordinaires ne peuvent plus rien, il faut cette rangée de boutons qui envoient chacun un octet brut :

BoutonEnvoieQuand l'utiliser
Ctrl+Z0x1A Terminateur du mode données : expédie réellement le contenu accumulé
ESC0x1B Annule le mode données et jette le contenu accumulé. Touche d'évasion de premier choix quand une commande en deux temps est bloquée et que le port AT ne répond plus (§2.3.8 du manuel)
+++Trois signes + (octets bruts) Pour s'échapper du mode données transparent (par ex. un transfert FTP en COM:) et revenir en mode AT. La règle est stricte : 1 seconde de silence avant et après, jamais de CR/LF — mesuré : avec un CR ajouté, la séquence est sans effet ; il faut passer par ce bouton, pas par la ligne de commande
La mesure contredit le manuel : +++ est un « abandon », pas une « pause ». La note d'application FTPS v1.5, page 13, affirme qu'après +++ on peut reprendre le transfert en mode données avec ATO ; sur le matériel réel, ATO ne renvoie que NO CARRIER : le transfert a déjà été abandonné. Considérez +++ comme un frein d'urgence, sans espérer repartir une fois arrêté.

Basic — SIM, diagnostic et états de base

Principe de fonctionnement : cette page est le point de départ après chaque connexion. Une fois le rituel de démarrage exécuté et RDY affiché dans le terminal, venez ici faire trois choses : passer les messages d'erreur dans un format lisible, vérifier que la SIM est prête, et identifier la carte. À part AT&F et le déverrouillage PIN / PUK, toute la page n'est que consultation en lecture seule — les appuis ne modifient pas l'état du module ; les commandes qui touchent à l'état de connexion sont regroupées dans les autres onglets, Network, TCP/IP, etc. Tous les échantillons de cette section sont des valeurs mesurées en août 2026 sur un EG800K réel (firmware EG800KCNGCR07A06M04).

Après le démarrage : RDY ne veut pas dire SIM prête

RDY est l'URC que le module émet spontanément à la fin de son démarrage. Il signifie seulement que l'interface AT est vivante ; la SIM, elle, s'initialise encore tranquillement derrière. Mesuré : envoyer une commande SIM dès l'apparition de RDY renvoie +CME ERROR: 14 (SIM busy), voire +CME ERROR: 13 (SIM failure) ; en attendant environ 6 secondes avant d'envoyer, tout se passe bien.

Dans un script d'automatisation, ne prenez pas RDY comme signal de « feu vert ». Deux bonnes pratiques au choix : laisser systématiquement environ 6 secondes de marge après RDY ; ou interroger AT+QINISTAT en boucle et attendre que le bit 1 (CPIN prêt) s'allume avant de continuer.

Écho (ATE) : « écho du module » et « écho local du terminal » sont deux choses distinctes

L'écho, c'est le module qui renvoie tels quels les caractères que vous lui envoyez (ATE1 actif, ATE0 inactif) ; l'écho local du terminal, c'est l'outil qui affiche lui-même à l'écran ce que vous tapez. Les deux interrupteurs sont indépendants : avec les deux actifs, chaque caractère apparaît deux fois.

  • Le bouton bascule d'écho de cette page commute l'écho du module d'une seule touche. Actif par défaut au démarrage (confirmé par le paramètre AT mesuré E:1).
  • L'état affiché sur le bouton n'est pas mémorisé à l'aveugle — l'outil se recale automatiquement sur les réponses réelles (une ligne d'écho reçue = écho considéré actif) ; si vous tapez ATE0 / ATE1 / AT&F à la main dans la ligne de commande, l'état du bouton suit aussi, sans décrochage.
  • La bascule ne vaut que pour la session : au redémarrage, le module revient à sa valeur par défaut. Pour l'inscrire comme réglage de démarrage, il faut envoyer en plus AT&W (pas de bouton prévu pour cela sur cette page ; tapez-le dans la ligne de commande si besoin).

Network — enregistrement, opérateur, radio

Principe de fonctionnement : pour que toute fonction de données marche, il faut être enregistré sur le réseau mobile et disposer d'un canal de données PDP prêt — cette page est le tableau de bord et les interrupteurs de l'accès réseau, et tout diagnostic « pas de connexion » commence ici. Toutes les valeurs de cette section sont des mesures d'août 2026 sur un EG800K réel.

Avant de commencer : basculez d'abord les URC vers l'UART

En sortie d'usine, l'EG800K envoie ses messages spontanés (URC) vers usbat (port AT USB) ; cet outil passe par l'UART — aucun URC n'arrive alors : rapports de signal, résultats TCP / MQTT / scan Wi-Fi, tout reste muet ; le symptôme est « toutes les commandes répondent OK, mais aucun message ».

C'est la cause numéro un de « tous les URC ont disparu ». Allez dans l'onglet Hardware, interrogez avec AT+QURCCFG="urcport" ; si la réponse n'est pas "uart1", corrigez avec le bouton de bascule — le réglage s'écrit en NVRAM, une seule fois suffit, il survit aux redémarrages.

Enregistré mais toujours pas d'accès aux données ? Canal PDP : couche 3GPP vs page TCP/IP

Le contexte PDP est le « canal de données » attribué par le réseau mobile : sans lui, pas d'IP. Ce groupe interroge en lecture seule la couche standard 3GPP : AT+CGDCONT? liste les contextes et APN, AT+CGACT? liste les états d'activation (blocage jusqu'à 150 secondes ; ⚠ la forme d'écriture prend les paramètres dans l'ordre inverse), AT+CGPADDR liste les IP obtenues. Les QIACT? / QICSGP de la page TCP/IP appartiennent à la pile propre à Quectel, pas à la même couche — comparer les deux côte à côte permet de localiser la panne : une IP ici mais pas là-bas = le réseau a donné le canal, mais la pile ne l'a pas activé. Cet exemplaire active automatiquement le PDP et obtient une IP dès le démarrage.

AT+QGDCNT? interroge le trafic cumulé (premier nombre = émis, second = reçu), incontournable pour mesurer la consommation d'une carte en itinérance. ⚠ La mesure contredit l'infobulle du bouton (« cumul à travers les redémarrages ») : par défaut, le compteur n'est pas stocké en NV et retombe à zéro à la moindre coupure (rechargement de page compris) — notez la valeur sur-le-champ, ou stockez en NV avec AT+QGDCNT=1.

Dépannage vécu : cette carte n'autorise qu'un seul PDP

Sur la page TCP/IP, AT+QIACT=1 répond ERROR (572,operation not allowed) ? Scénario systématique avec cette carte : après le démarrage, la couche 3GPP a déjà activé automatiquement un PDP, mais le numéro de contexte flotte (mesuré : 1 et 9 selon les fois) ; en ouvrir un second renvoie +CME ERROR: 100 ⇒ le réseau n'autorise qu'un seul PDP ; or la plage de contextID de QIACT s'arrête à 1–8 : quand le PDP est ouvert sur le 9, la pile Quectel ne peut tout simplement pas l'atteindre. Solution en deux étapes (une fois après chaque démarrage) :

AT+CGACT? ← voir quel est le cid (le numéro flotte, étape non facultative)
AT+CGACT=0,<ce cid> ← la couche 3GPP libère la place
AT+QIACT=1 ← page TCP/IP ; +QIACT: 1,1,1,"10.187.7.8" = succès

Régler l'APN avec QICSGP est superflu avec cette carte — mesuré : le module synchronise tout seul l'APN attribué par le réseau (iot.1nce.net) ; ce n'est nécessaire qu'avec les cartes à APN d'entreprise exigeant identifiant et mot de passe.

Tout part soudain en timeout en plein test ? Suspectez d'abord une dérive du PDP. Mesuré : pendant une série d'échecs HTTP complets (erreur 716, timeout fixe de 30 secondes), AT+QIACT? continuait de renvoyer une IP — à ce moment-là il ment, il faut croiser avec AT+CGACT? (mesuré : 1,0 et 9,1 = dérive vers le 9). Solution : AT+QIDEACT=1 → AT+CGACT=0,<le cid de dérive> → AT+QIACT=1, puis validez par un ping.

GNSS — positionnement par satellite

Principe de fonctionnement : le GNSS est une fonction indépendante du réseau mobile — pas besoin d'une SIM connectée, pas besoin de PDP, aucune consommation de données (AGNSS excepté, voir plus bas). Une fois activé, le module reçoit lui-même les signaux des satellites, et vous interrogez le résultat de positionnement avec AT+QGPSLOC. Toutes les durées et tous les comportements de cette section sont des valeurs mesurées en août 2026 sur un EG800K réel.

Avant de commencer : l'antenne décide de tout

La première cause d'échec de positionnement n'est pas une mauvaise commande, c'est une antenne qui ne capte rien. Comparaison mesurée : en intérieur, avec une antenne médiocre, le module pouvait situer 38 satellites sans en entendre un seul (SNR tous à 00) ; après passage à une antenne GNSS active placée près d'une fenêtre, le fix à froid est arrivé en moins de 95 secondes.

Le GNSS ne se teste pas en intérieur, et attendre n'y change rien. Sans vue du ciel, $GNGGA répond « 00 satellite utilisé, qualité de fix 0 », et AT+QGPSLOC renvoie éternellement l'erreur 516. Déplacez l'antenne près d'une fenêtre ou dehors avant de commencer — ce n'est pas une question de patience, c'est de la physique.

Premier fix : cinq étapes

  1. Exécuter le rituel de démarrage (voir la section « Rituel de démarrage »). ⚠ Chaque rechargement de la page équivaut à une coupure d'alimentation : l'état d'activation du GNSS et les éphémérides reçues à moitié sont remis à zéro, et tout reprend à cette étape.
  2. Vérifier que les URC passent par l'UART : AT+QURCCFG="urcport" doit répondre "uart1". La valeur d'usine est "usbat" ; sans ce changement, beaucoup de messages de résultat partent vers le port USB et rien n'apparaît ici (réglage écrit en NVRAM, à faire une seule fois).
  3. Activer le GNSS : appuyez sur AT+QGPS=1. En quelques secondes apparaît +QGPS: "firmware",0,0 (firmware GNSS chargé avec succès). Appuyer alors qu'il est déjà actif renvoie +CME ERROR: 504, sans conséquence.
  4. Regarder la réception : appuyez sur AT+QGPSGNMEA="GSV" pour lire les satellites visibles. La zone terminal ouvre automatiquement l'onglet État des satellites et trace l'histogramme des signaux et la vue du ciel — la lecture est expliquée au paragraphe suivant.
  5. Interroger la position : appuyez sur AT+QGPSLOC=2 toutes les 5–10 secondes. Une réponse DSAT_CME_GNSS_NOT_FIXED_NOW (erreur 516) signifie que le fix n'est pas encore obtenu : continuez simplement d'attendre. En cas de succès, des coordonnées sont renvoyées, et la zone terminal ouvre automatiquement l'onglet Carte pour y tracer la position.

Lire la page des satellites : « voir » ne veut pas dire « entendre »

Dans le GSV, chaque satellite porte quatre nombres : identifiant, élévation, azimut et SNR (rapport signal/bruit, dB-Hz). Les trois premiers disent seulement « où il devrait se trouver dans le ciel » ; seul le SNR prouve qu'un signal est réellement reçu.

Pourquoi il faut attendre : la limite physique du démarrage à froid et les temps mesurés

Le fix exige l'orbite précise de chaque satellite (les éphémérides), et ces éphémérides sont enfouies dans le signal que le satellite diffuse à 50 bps — il faut environ 18–30 secondes de décodage continu et sans faute par satellite, un seul bit erroné et tout recommence, et il en faut au moins 4. Voilà pourquoi le « démarrage à froid » est lent. Mesures locales (même lieu, antenne active, résolution de mesure ±5 secondes) :

Démarrage à froid + AGNSS52 secondes (avec, dès 20 secondes environ, une première position grossière)

Ne rechargez pas la page pendant les tests. Le matériel de cet outil fait de RTS l'interrupteur d'alimentation : recharger la page = couper le courant = perdre toutes les éphémérides, et tout repart d'un démarrage à froid. Pour faire une pause, appuyez sur AT+QGPSEND, ne coupez pas l'alimentation.

Accélération AGNSS : la procédure complète

Principe : l'AGNSS fait télécharger les éphémérides par le réseau (environ 32–34 Ko à chaque fois), court-circuitant le lent décodage à 50 bps. Il ne peut pas créer un signal satellite à partir de rien — en intérieur, toujours aucun fix ; il n'économise que le temps « d'attente des éphémérides ».

  3. Le champ heure du $GNGGA est renseigné (l'heure fait aussi partie des données d'assistance)
Piège du faux fix : des coordonnées avec zéro satellite ne sont pas un fix. Environ 20 secondes après le lancement de l'AGNSS, AT+QGPSLOC peut renvoyer des coordonnées, mais regardez de près : HDOP 0.00 / alt 0.0 / nsat 00 — c'est l'injection de la position de référence contenue dans les données d'assistance, pas une mesure, et l'erreur peut être énorme.

Critères d'un vrai fix : satellites utilisés > 0, mode de fix ≥ 2, HDOP > 0. Un automatisme ou une logique produit ne doit jamais se contenter de « des coordonnées sont-elles revenues ».

apflash : rapide même après une coupure de courant (sous conditions)

Deux limites : les éphémérides expirent en une heure environ ; et il faut avoir déjà réussi un fix au moins une fois pour que la flash contienne quelque chose à importer — sur un module qui n'a jamais obtenu de fix, apflash n'aide en rien.

Après le fix : la page Carte

La barre de synthèse montre coordonnées / altitude / HDOP / nombre de satellites, l'heure étant convertie automatiquement dans le fuseau local d'après la longitude.

TCP/IP — la racine des connexions de données

Principe de fonctionnement : cette page est la fondation de tous les protocoles de données. Le contexte PDP (le canal de données attribué par le réseau mobile) ne s'active et ne se désactive que sur cette page ; les pages SSL / HTTP / MQTT / FTP ne contiennent que des interrogations en lecture seule, pour éviter qu'une même commande se marche dessus depuis deux endroits. Tous les pièges et durées de cette section sont des mesures d'août 2026 sur le matériel réel.

Première étape : activer le PDP (QICSGP / QIACT / QIDEACT)

Appuyez sur Act PDP (AT+QIACT=1) : blocage jusqu'à 150 secondes, n'envoyez aucune autre commande pendant ce temps ; le trafic commence à partir de là (en itinérance, attention aux coûts). Après le succès, appuyez impérativement sur Query IP (AT+QIACT?) et vérifiez la réponse +QIACT: 1,1,1,"adresse IP" — avant activation, elle ne renvoie que OK. Pour raccrocher, appuyez sur Deact PDP (AT+QIDEACT=1, 40 secondes maximum), qui ferme de force toutes les connexions en dessous. Set APN (AT+QICSGP) est inutile en temps normal — le module synchronise tout seul l'APN attribué par le réseau (mesuré : la carte 1NCE relit iot.1nce.net dès le démarrage) ; seuls les APN d'entreprise à identifiants en ont besoin.

Act PDP répond ERROR, Last Error 572 ? Cette carte n'autorise qu'un seul PDP. Au démarrage, le réseau en a déjà activé un et son numéro flotte (mesuré : 9 et 1 selon les fois) ; AT+QIACT ne peut atteindre que 1–8. Solution : page Network, AT+CGACT? pour lire le numéro → AT+CGACT=0,<numéro> pour libérer la place → puis Act PDP.

Tout tombe en plein test ? AT+QIACT? ment — en cas de dérive du PDP, il renvoie encore une IP ; seul le croisement avec AT+CGACT? révèle le problème. Récupération : Deact PDP → AT+CGACT=0,<numéro de dérive> → Act PDP → validation par Ping.

Ouvrir une connexion : OK signifie seulement « commande reçue »

Appuyez sur Open TCP et remplissez hôte et port dans la carte de paramètres (AT+QIOPEN=1,0,"TCP","hôte",port,0,0 ; contexte 1, connectID 0, mode buffer déjà figés). OK signifie seulement que la commande est acceptée ; le verdict vient de l'URC +QIOPEN: 0,<err> : 0 = succès, jusqu'à 150 secondes ; 563 = le connectID est encore ouvert, appuyez d'abord sur Close Sock. All Socks (AT+QISTATE) liste tous les sockets, state 2 = connecté.

Les deux caprices du pair intégré tcpbin.com

Le pair par défaut d'Open TCP est le serveur d'écho gratuit tcpbin.com:4242, avec deux caprices mesurés :

  • Écho ligne par ligne, saut de ligne (0A) obligatoire en fin : Hello sans 0A, 6 secondes sans réponse ; avec le 0A, réponse en 0.1 seconde. Terminez Send Text par \n, Send Hex par 0A.
  • Timeout d'inactivité de 15 secondes : à l'inactivité, la connexion est coupée et vous recevez +QIURC: "closed",0. QIRD n'y change rien (il ne lit que le tampon local, sans toucher au réseau). Pour maintenir la connexion, envoyez des données au moins toutes les 10 secondes. Après le closed, le socket reste en closing : il faut d'abord appuyer sur Close Sock avant de le réutiliser, sinon QIOPEN répond 563.

🔴 Dégradation de la pile de données — le piège le plus chronophage. Symptôme : toutes les connexions échouent systématiquement, mais tous les autodiagnostics disent que tout va bien (QIACT? a une IP, QIGETERROR répond 0). Discriminant en 30 secondes : visez la même cible avec Open TCP — échec aussi = toute la pile est morte, refaites le rituel de démarrage ; succès = le problème est dans le protocole du dessus, continuez à chercher.

Keepalive : tient tête au NAT de l'opérateur, pas à tcpbin

QICFG=? liste les sous-réglages et leurs plages, Keepalive? lit la valeur actuelle, Keepalive On / Off commute — ces quatre commandes sont en elles-mêmes à zéro trafic ; une fois activé, tant qu'un socket reste inactif, les paquets de sonde comptent dans le trafic mobile. Il ne tient pas tête au timeout de 15 secondes de tcpbin : mesuré, coupure à 15.1 secondes malgré l'activation — le keepalive est une sonde vide de la couche TCP, invisible pour l'application ; et l'intervalle minimal est de 25 secondes, déjà supérieur à 15. Pour survivre à un timeout applicatif, il faut envoyer de vraies données (par ex. un 0A en Send Hex toutes les 10 secondes). Son vrai rôle est le maintien du NAT de l'opérateur (le NAT des cartes IoT est recyclé après quelques minutes d'inactivité).

Comptabilité du trafic (estimation, non mesurée) : une sonde aller-retour vaut environ 80 bytes ; idle par défaut = 30 secondes d'inactivité continue → environ 9.4 KB par heure, environ 225 KB par jour, environ 6.8 MB par mois ; idle = 600 secondes → environ 11 KB par jour. Avec une carte prépayée au volume comme 1NCE, augmentez l'idle. Sans socket ouvert, aucune consommation.

MQTT — messagerie IoT

Principe de fonctionnement : MQTT est un protocole à « broker (serveur intermédiaire de messages) » : les appareils ne se connectent pas entre eux, chacun se connecte au broker et publie ou s'abonne à des « sujets (topics) ». Sur l'EG800K, il est à deux étages : d'abord AT+QMTOPEN ouvre la « connexion réseau » (TCP jusqu'au broker), puis AT+QMTCONN effectue la « connexion MQTT » ; il faut les deux étages pour s'abonner et publier. À retenir d'emblée : tous les résultats des commandes MQTT suivent le modèle « OK d'abord, URC ensuite » (comme FTP) — OK signifie seulement que la commande est acceptée, le verdict vient de l'URC de résultat qui suit.

Cette page utilise systématiquement le client 0 ; le firmware supporte aussi plusieurs clients (0–5), SSL et l'authentification des plateformes cloud (confirmé par mesure avec =?) ; usages avancés dans la note d'application MQTT.

Avant de commencer : deux prérequis

  1. Les URC doivent passer par l'UART : AT+QURCCFG="urcport" doit répondre "uart1". La valeur d'usine est "usbat", or tous les résultats MQTT sont des URC — sans ce changement, chaque commande répond OK puis plus rien (bouton disponible sur la page Basic ; écrit en NVRAM, une seule fois suffit).
  2. Le PDP doit être activé : appuyez d'abord sur AT+QIACT=1 dans la page TCP/IP (150 secondes maximum) ; sinon +QMTOPEN répond 3 = échec d'activation du PDP. Toute la séquence consomme des données, environ 5 KB estimés.

Suffixe aléatoire du client ID et des sujets : il change à chaque rechargement

Le client ID et le sujet par défaut ne sont pas figés : au chargement de la page, un suffixe de 6 caractères hexadécimaux est généré, formant numodem-<suffixe> et test/numodem-<suffixe> ; les trois boutons Subscribe / Publish / Unsub partagent le même (sinon la boucle de retour ne se referme pas). Deux raisons :

  • Une collision de nom fait éjecter : MQTT 3.1.1 §3.1.4 impose au broker d'éjecter le premier connecté — deux personnes avec le même ID fixe s'éjectent mutuellement, symptôme d'apparence « déconnexions inexpliquées du module ».
  • Un sujet fixe reçoit les messages des autres : vous croyez recevoir le vôtre, mais non — c'est pire que de ne rien recevoir, car cela donne un faux succès.
⚠ À chaque rechargement de page, le suffixe change — l'abonnement et la publication doivent se faire dans le même cycle de vie de la page. D'autant que dans cet outil RTS = alimentation : recharger la page = couper le module, et toute la connexion MQTT disparaît ; il faut reprendre au rituel de démarrage et à AT+QMTOPEN.

Parcours complet : connexion → abonnement → publication → réception de son propre message

La validation la plus probante est la boucle de retour : s'abonner, publier sur le même sujet, recevoir son propre message — toute la chaîne d'émission-réception validée d'un coup. Attendez l'URC de résultat à chaque étape avant de continuer :

  1. Fixer la version du protocole : appuyez sur Ver 3.1.1 (AT+QMTCFG="version",0,4 ; 3 = 3.1, 4 = 3.1.1). Version? interroge la valeur actuelle (sans valeur = interrogation). La carte de paramètres Keepalive règle l'intervalle de maintien, mais le test marche sans y toucher.
  2. Ouvrir le réseau : appuyez sur Open Net (AT+QMTOPEN=0,"broker",1883). D'abord OK, puis le verdict dans l'URC +QMTOPEN: 0,<result> (0 = succès), attente jusqu'à 120 secondes. Open? liste les connexions ouvertes (sans connexion, réponse OK vide, mesuré normal).
  3. Connexion MQTT : appuyez sur Connect (AT+QMTCONN=0,"numodem-<suffixe>"). L'URC de succès est toujours +QMTCONN: 0,0,0. Les brokers publics n'exigent pas d'identifiants ; quand il en faut, ajoutez vous-même ,"user","pass" après les paramètres. Conn? interroge l'état (1 = initial, 2 = en connexion, 3 = connecté, 4 = en déconnexion).
  4. S'abonner : appuyez sur Subscribe (AT+QMTSUB=0,1,"test/numodem-<suffixe>",0, msgid figé à 1). L'URC de succès ressemble à +QMTSUB: 0,1,0,0. Dès lors, les messages de ce sujet arrivent en URC +QMTRECV.
  5. Publier : appuyez sur Publish (AT+QMTPUBEX, en deux temps, voir le paragraphe suivant). L'URC de succès est +QMTPUBEX: 0,<msgid>,0.
  6. Recevoir en retour : la cible de publication étant le sujet abonné, apparaît aussitôt +QMTRECV avec le sujet et le corps du message tout juste envoyé — boucle de retour réussie. Un payload en chinois passe sans troncature ni caractères corrompus.

QMTPUBEX en deux temps : envoi automatique à longueur atteinte, sans Ctrl+Z

Le dernier paramètre d'AT+QMTPUBEX est la longueur (en bytes), pas le contenu du message (tranché par la note d'application MQTT §3.3.8 — l'envoi sur une seule ligne avec le message dedans répond invariablement ERROR). La bonne procédure est en deux temps : envoyer la commande → le module répond l'invite > → envoyer exactement N bytes ; le module expédie automatiquement dès que la longueur est atteinte, sans Ctrl+Z (différent du mode données d'AT+QISEND de la page TCP). Le bouton Publish fait tout : remplissez seulement le contenu dans la carte de paramètres, la longueur est calculée automatiquement en bytes UTF-8 (un caractère chinois = 3 bytes ; mesuré : un mot de deux caractères chinois → 6).

  • Les commandes à payload n'offrent pas « recopier dans la ligne de commande » — la ligne de commande ajoute toujours une fin de ligne, et ce CR entrerait dans le décompte de longueur et décalerait tout ; envoyez par le bouton.
  • Le firmware possède aussi AT+QMTPUB (variante en mode données, terminée par Ctrl+Z) — cet outil utilise exclusivement QMTPUBEX, inutile d'apprendre les deux.

Lire les codes de résultat : chaque commande a son propre domaine de valeurs

N'appliquez pas la table de codes de la commande A à la commande B. Le 3 de +QMTOPEN signifie « échec d'activation du PDP », alors que +QMTPUBEX n'a même pas de valeur 3.

Le plus trompeur est +QMTCONN: 0,1 — il peut être la réponse d'interrogation « état 1 = en initialisation », ou le résultat d'écriture « retransmission de paquet en cours ». Une ligne seule ne permet pas de trancher : cet outil affiche donc les deux lectures côte à côte, sans deviner.

Pas besoin d'apprendre les tables par cœur : pour tous les URC de résultat, de +QMTOPEN à +QMTRECV / +QMTSTAT, la zone terminal annote chaque champ en clair d'après les sept tables de correspondance de la note d'application MQTT v1.5.

Déconnexion et clôture

  • Arrêter seulement la réception, en gardant la connexion : appuyez sur Unsub (AT+QMTUNS=0,2,"sujet", msgid figé à 2).
  • Déconnexion propre : appuyez sur Disconnect (AT+QMTDISC=0, envoie un DISCONNECT MQTT), réponse +QMTDISC: 0,0. Inutile d'appuyer ensuite sur Close Net — AT+QMTCLOSE=0 sert à forcer la fermeture quand « QMTDISC a échoué et la couche réseau est coincée ».

Les déconnexions que vous n'avez pas demandées (éjection, timeout de keepalive, perte réseau) sont rapportées par l'URC de déconnexion anormale +QMTSTAT (ex. : +QMTSTAT: 0,5, la zone terminal annote la cause) ; il faut alors reprendre à AT+QMTOPEN.

WiFiScan — scan Wi-Fi et positionnement par réseau

Principe de fonctionnement : l'EG800K est un module LTE, sans aucune capacité d'accès Internet par Wi-Fi, mais il embarque un récepteur Wi-Fi « qui scanne sans se connecter » : il reçoit passivement les trames beacon diffusées par les points d'accès 2.4GHz alentour et rapporte pour chacun l'adresse MAC (BSSID), le RSSI (force du signal) et le canal. Le scan est de la pure réception RF, zéro trafic de données ; il ne produit pas de coordonnées par lui-même — il faut envoyer la liste MAC + RSSI à une base de données de points d'accès dans le cloud pour obtenir latitude et longitude ; c'est le positionnement par réseau, utilisable en intérieur, sans satellite. Tous les chiffres et comportements de cette section sont des valeurs mesurées en août 2026 sur un EG800K réel.

SSL — le tunnel TLS

Principe de fonctionnement : la page SSL est le socle partagé des connexions chiffrées — le contexte SSL réglé ici et les certificats téléversés servent à la fois au socket SSL brut, à MQTT over SSL et à HTTPS. Toutes les durées et tous les comportements de cette section sont des valeurs mesurées en août 2026 sur un EG800K réel.

Première connexion TLS : cinq étapes

  1. Exécuter le rituel de démarrage (voir la section « Rituel de démarrage »), puis appuyer sur AT+QIACT? pour vérifier le canal de données — il faut obtenir +QIACT: 1,1,…,"IP" ; sinon, d'abord AT+QIACT=1.
  2. Régler le contexte : sslversion à 4 (toutes versions, compatibilité maximale), ciphersuite à 0XFFFF (toutes les suites), seclevel à 0 pour commencer — validez d'abord que le tunnel passe, la vérification viendra ensuite.
  3. Ouvrir la connexion : appuyez sur AT+QSSLOPEN (dernier chiffre 0), remplissez hôte et port dans la carte de paramètres. ⚠ OK signifie seulement « commande acceptée » ; le verdict est dans l'URC : +QSSLOPEN: 4,0 seul signe le succès (poignée de main mesurée à 2.0 secondes).
  4. Envoyer des données : appuyez sur AT+QSSLSEND (en deux temps) — après le >, envoyez le corps ; expédié automatiquement dès que la longueur annoncée est atteinte, sans Ctrl+Z (limite de 1460 bytes par paquet). La réponse du pair arrive en +QSSLURC: "recv",4.
  5. Relire et fermer : AT+QSSLRECV (limite de 1500 par lecture) ; obtenir +QSSLRECV: 0 signifie que tout est vidé, pas une erreur. AT+QSSLCLOSE=4 ferme (attente par défaut de 10 secondes maximum ; un autre bouton accepte un délai en secondes, 0 = immédiat).

Le groupe de fichiers UFS : comment les certificats entrent dans le module

L'UFS est le stockage flash intégré du module : capacité totale mesurée de 280 KB, chaque fichier occupant un bloc de 4 KB. Les certificats doivent d'abord être téléversés ici pour que cacert ait un fichier à pointer. Le téléversement passe par l'UART, zéro trafic de données, et les fichiers binaires passent aussi. Carte Upload : après le choix du fichier, nom et taille se remplissent seuls ; à l'envoi, l'outil attend le CONNECT du module avant d'expédier les octets bruts (sans lui, rien ne part). À la fin, le moteur d'annotation compare automatiquement la taille et le checksum rapportés par le module : ✅ = intact, ❌ = transfert corrompu, supprimez puis retéléversez.

HTTP — requêtes web

Principe de fonctionnement : le HTTP du module est en trois temps : d'abord définir l'URL (cette étape est elle-même en deux temps), puis émettre la requête (GET / POST), enfin relire la réponse. Le résultat de chaque temps n'est jamais dans le OK mais dans l'URC qui arrive ensuite — AT+QURCCFG="urcport" doit donc valoir "uart1" (modifiable sur la page Hardware), sans quoi aucun résultat ne sera visible. Toutes les données sont des mesures d'août 2026 sur le matériel réel.

Avant de commencer : disposer d'un canal de données

Prérequis : PDP activé et IP obtenue (le AT+QIACT=1 de la page TCP/IP). Le groupe Connect de cette page ne contient que des contrôles en lecture seule : AT+CPIN? / AT+CGATT? / AT+CGREG? / AT+QIACT?, AT+QIDNSCFG=1 (DNS 0.0.0.0 = non attribué), AT+QIGETERROR (⚠ ne vaut que pour la dernière commande TCP/IP : appuyez immédiatement après l'échec).

AT+QIACT? ment. Mesuré : dérive du PDP en cours de route, toutes les requêtes échouent avec un timeout fixe de 30 secondes et l'erreur 716, mais AT+QIACT? continue de renvoyer une IP. Croisez avec AT+CGACT? : une incohérence = dérive. Réparation : AT+QIDEACT=1 → AT+CGACT=0,<cid de dérive> → AT+QIACT=1, puis un ping réussi avant de continuer.

Premier GET : quatre étapes

  1. Réglages préalables (groupe Config, zéro trafic) : carte de paramètres contextid à 1 (lie le PDP context à utiliser) ; les trois interrupteurs rspout/auto, requestheader, responseheader restent à 0 (raisons plus bas) ; AT+QHTTPCFG? relit tous les réglages d'un coup pour contrôle, AT+QHTTPCFG=? liste les réglages possibles.
  2. Définir l'URL (en deux temps) : la carte AT+QHTTPURL n'a qu'un bouton « Envoyer (en deux temps) » — vous remplissez l'URL, la longueur est calculée par le programme. Déroulé : envoi de AT+QHTTPURL=<longueur>,80, attente du CONNECT qui entre en mode données, puis envoi des octets de l'URL tels quels, sans aucune fin de ligne (un CR/LF serait compté dans la longueur). http://www.example.com/ fait exactement 23. Après l'envoi, relisez avec AT+QHTTPURL? : identique au caractère près = aucune fin de ligne ne s'est glissée.
  3. Émettre la requête : AT+QHTTPGET=80 (secondes d'attente de la réponse). OK signifie seulement « commande acceptée » ; le vrai résultat est l'URC ultérieur +QHTTPGET: 0,200, lecture au paragraphe suivant.
  4. Lire la réponse : AT+QHTTPREAD=80. Après CONNECT, ce ne sont que des octets bruts (mesuré : 559 bytes pour example.com), puis OK — mais c'est le +QHTTPREAD: 0 sur sa propre ligne finale qui marque la fin.

Lire +QHTTPGET : le premier champ n'est pas le code d'état HTTP

Les URC de résultat de GET / POST / POSTFILE ont tous trois champs : <err>,<httprspcode>,<content_length> : err 0 = commande exécutée avec succès, non nul = erreur de la couche module (716, 711…) ; httprspcode est le code d'état HTTP, rapporté seulement quand err=0 (écrit dans le manuel ; l'outil annote 200 / 403 / 404 / 409 / 411 / 500 avec sa table intégrée) ; content_length est optionnel — présent seulement si l'en-tête de réponse porte CONTENT-LENGTH, un GET ordinaire n'a souvent que deux champs. Ainsi le +QHTTPGET: 0,404,0 mesuré n'est pas un échec : la commande a réussi, c'est le serveur qui dit « introuvable ».

Lire la réponse : les pièges d'AT+QHTTPREAD

Le paramètre est « l'intervalle maximal en secondes entre deux paquets », pas la durée totale. Le firmware de cet exemplaire n'accepte qu'un seul paramètre : la lecture par tranches =<wait>,<read_len> de la note d'application répond un ERROR nu (confirmé par sonde =?) ; le bouton a été retiré — pour la récupération par tranches, utilisez GETEX.

Piège de verrouillage croisé : dès que rspout/auto vaut 1, toute la famille READ échoue (écrit dans le manuel). Il fait cracher la réponse automatiquement par le module, au prix de l'anéantissement des READ, d'où la boîte de confirmation sur ce bouton. Si les READ tombent tous d'un coup, vérifiez d'abord AT+QHTTPCFG?.

Récupération par tranches : AT+QHTTPGETEX lit byte par byte

AT+QHTTPGETEX=<secondes>,<offset de départ>,<longueur> passe par HTTP Range pour ne prendre que le fragment voulu et économiser du trafic. Mesuré (contenu du point de terminaison figé à abcdefghijklmnop) : offset 0, longueur 8 → +QHTTPGET: 0,206,8, lecture abcdefgh ; offset 8, encore 8 → lecture ijklmnop. Lecture : le code d'état doit être 206 ; un 200 avec le même contenu à chaque fois = le serveur ne supporte pas Range, le module n'est pas en cause. ⚠ Exécutable seulement quand requestheader=0.

POST : deux temps et Content-Type

La carte AT+QHTTPPOST est aussi en deux temps : vous remplissez le body, la longueur est calculée ; envoi de AT+QHTTPPOST=<longueur>,<secondes de saisie>,<secondes de réponse>, attente du CONNECT, puis envoi du body. Trois choses :

  • Le CONNECT peut se faire attendre jusqu'à 125 secondes (écrit dans le manuel) — réglez le timeout d'attente de l'invite à 125 secondes pleines, ne recyclez pas les 5 secondes de MQTT.
  • Body limité à 1 MB (plage mesurée par =? : 1–1024000).
  • Réglez le Content-Type au préalable avec la carte de paramètres contenttype (code de type 0 = form-urlencoded).

Mesuré : POST de Message=HelloQuectel (20 bytes) → +QHTTPPOST: 0,200,440 ; le JSON relu par READ prouve que la paire clé-valeur est arrivée, que la longueur était juste et que le Content-Type a agi ; le User-Agent auto-déclaré du module est QUECTEL_MODULE.

En-têtes personnalisés et en-têtes de réponse

  • reqheader/add : ajoute un en-tête de requête personnalisé (le manuel ne donne pas d'exemple) ; le bouton d'interrogation compte les en-têtes déjà ajoutés ; reqheader/remove les retire.
  • requestheader à 1 = vous composez vous-même tout l'en-tête de requête, même le GET devient en deux temps, et GETEX devient inutilisable. Restez à 0 en temps normal.
  • responseheader à 1 : READ crache aussi l'en-tête de réponse HTTP (mesuré : même un X-Test personnalisé revient). Repassez à 0 après le test.
  • closed/ind : active l'URC de notification « session fermée ».

Version fichier : POSTFILE et READFILE (UFS)

AT+QHTTPPOSTFILE="fichier",<secondes> envoie un POST dont le body est un fichier du système de fichiers du module (UFS) ; AT+QHTTPREADFILE="fichier",<secondes> enregistre la réponse dans un fichier UFS. ⚠ Cet outil ne sait actuellement ni téléverser un fichier vers l'UFS ni relire le contenu d'un fichier UFS : ces deux commandes servent avec un flux côté firmware.

HTTPS : le chemin sans vérification

HTTPS = HTTP + contexte SSL. Le groupe Connect prépare le chemin le plus court, cinq boutons dans l'ordre :

AT+QHTTPCFG="sslctxid",1 ← HTTP utilisera le contexte SSL 1
AT+QSSLCFG="sslversion",1,4 ← version TLS laissée à la négociation du serveur
AT+QSSLCFG="ciphersuite",1,0XFFFF ← toutes les suites de chiffrement
AT+QSSLCFG="seclevel",1,0 ← pas de vérification de certificat (voir plus bas)
AT+QSSLCFG="sni",1,1 ← activer SNI (0 en usine !)

Ensuite, une URL en https:// et GET / READ fonctionnent comme d'habitude — mesuré : le HTML relu est identique au caractère près à la version en clair. seclevel=0 (sans vérification) est le seul chemin que cet outil peut parcourir jusqu'au bout — pour vérifier le certificat, il faut d'abord écrire le certificat CA dans l'UFS ; détails SSL (AT+QSSLCFG=? liste tous les sous-réglages, negotiatetime règle l'attente de la poignée de main) dans la section « SSL — le tunnel TLS ». SNI vaut 0 en usine : sans lui, les sites HTTPS sur IP partagée reçoivent un certificat discordant et la vérification échoue aussitôt. La chaîne de certificats est le gros du trafic : un cycle de GET HTTPS pèse environ 8–15 KB, contre environ 1 KB en clair.

Redirections et clôture

Redirections (absentes du manuel, clarifiées par mesure) : le module suit automatiquement les 302, mais n'accepte que les Location en chemin absolu — un chemin relatif répond directement l'erreur 711, échec immédiat en 1 milliseconde. Clôture : AT+QHTTPSTOP (groupe Close) annule la requête en cours et coupe la session ; état bizarre ou erreur 704 (mode données occupé) : appuyez d'abord sur ce bouton pour nettoyer.

FTP — transfert de fichiers

Principe de fonctionnement : FTP a deux canaux : le canal de contrôle transporte les commandes, le canal de données transporte le contenu des fichiers. Connexion, renommage, suppression, taille passent seulement par le canal de contrôle ; LIST, envoi et téléchargement exigent l'ouverture d'une connexion de données supplémentaire — la plupart des bizarreries de cette section (rafales de 615, 603) viennent de là. Règle Quectel qui traverse toute la section : OK signifie seulement « commande acceptée », le vrai résultat arrive ensuite par URC. Toutes les réponses et tous les chiffres sont des mesures d'août 2026 sur un EG800K réel.

Avant de commencer : deux prérequis

  • Le PDP doit être activé : le premier bouton de cette page, AT+QIACT?, sert exactement à ce contrôle — il faut obtenir +QIACT: 1,1,…,"IP" pour continuer ; un simple OK = allez d'abord appuyer sur Act PDP dans la page TCP/IP (PDP inactif, QFTPOPEN échoue à coup sûr).
  • Les URC doivent passer par l'UART : les commandes FTP sont presque toutes « OK d'abord, résultat par URC ensuite » ; si AT+QURCCFG="urcport" n'est pas "uart1", vous ne verrez ici qu'une pile de OK (réglage sur la page Hardware).

Parcours de connexion : réglages → ouverture → attente de l'URC

  1. Lier le PDP context : AT+QFTPCFG="contextid",1 (1 en sortie d'usine ; le bouton d'interrogation permet de le relire pour confirmer).
  2. Régler les identifiants : AT+QFTPCFG="account","compte","motdepasse", obligatoirement avant QFTPOPEN.
  3. Mode et type : transmode à 1 (passif ; derrière un NAT, toujours lui, et obligatoire en FTPS) ; filetype à 1 pour les fichiers texte, 0 pour le reste.
  4. Se connecter : AT+QFTPOPEN="hôte",21 répond OK immédiatement (simple acceptation) ; attendez +QFTPOPEN: 0,0, seul signe de connexion réussie (125 secondes maximum). Ensuite AT+QFTPSTAT doit répondre 1 (inactif ; 2 = transfert en cours, 3 = fermeture en cours).
AT+QFTPCFG="account","demo","password"
AT+QFTPCFG="transmode",1
AT+QFTPOPEN="test.rebex.net",21
OK ← signifie seulement que la commande est acceptée
+QFTPOPEN: 0,0 ← c'est cette ligne qui signe la connexion réussie

Autres réglages : AT+QFTPCFG=? liste d'un geste les 10 réglages possibles et leurs plages (zéro trafic). rsptimeout (20–180, 90 secondes par défaut) est le temps de réponse maximal de la plupart des commandes, et aussi l'intervalle maximal entre deux paquets en mode données ; ssltype / sslctxid servent au FTPS (en FTP pur, laissez 0 ; les paramètres SSL se règlent sur la page SSL) ; data_address / cache / restenable sont des micro-réglages pour environnements particuliers : voir les infobulles des boutons et le manuel.

Masquage du mot de passe (mesuré, contraire au manuel) : à la relecture par AT+QFTPCFG="account", le mot de passe est masqué en * (le manuel annonce un affichage tel quel). Mais le compte reste en clair, et le mot de passe de la ligne d'écriture est lui aussi en clair : dans une capture ou une vidéo, c'est cette ligne qu'il faut surveiller.
🔴 AT+QFTPCLOSE est asynchrone — OK ne veut pas dire fermé. Il faut attendre +QFTPCLOSE: 0,0 pour que la déconnexion soit achevée ; entre-temps, AT+QFTPSTAT répond 3 (fermeture en cours) et toute commande FTP répond invariablement +CME ERROR: 603 (serveur occupé).

Symptôme extrêmement trompeur : une rafale de 603 ressemble à un module mort ou à un bannissement par le serveur, alors que la fermeture n'est simplement pas finie (le jour de la mesure, un long détour a été perdu là-dessus). Attente maximale = rsptimeout. Par ailleurs, il ne déconnecte que le FTP ; pour une remise à zéro réseau complète, Deact PDP sur la page TCP/IP.

Téléchargement : le contenu s'imprime directement dans le terminal (COM:)

AT+QFTPGET="fichier","COM:" — après le CONNECT, le contenu du fichier est craché directement dans le terminal, terminé par +QFTPGET: 0,<bytes> (mesuré : readme.txt répond 0,379). L'autre bouton, téléchargement par blocs, ajoute les paramètres de départ et de longueur — la méthode la plus recommandée : interrogez la taille avec SIZE, puis prenez par blocs, pour éviter qu'un fichier entier n'explose le trafic. AT+QFTPLEN interroge combien de bytes le dernier PUT / GET / LIST / NLST a réellement transférés.

Envoi : en deux temps, clôture automatique à la longueur annoncée

AT+QFTPPUT="fichier","COM:",0,<longueur>,1 est une commande en deux temps : après le CONNECT (entrée en mode données), envoyez exactement le nombre de bytes annoncé ; le module quitte le mode données automatiquement au compte atteint, sans Ctrl+Z. Cet outil calcule la longueur tout seul : collez le contenu dans la carte de paramètres.

AT+QFTPPUT="numodem-test.txt","COM:",0,20,1
CONNECT ← entrée en mode données
NuModem-P6-FTP-test\n ← envoyer exactement 20 bytes
OK
+QFTPPUT: 0,20 ← le serveur a reçu 20 bytes

Ces 20 bytes ont été exprès rapatriés côté hôte avec Python ftplib et comparés byte par byte — correspondance parfaite. Forme avec relais UFS : le manuel accepte aussi un nom de fichier écrit "UFS:xxx", transitant par le stockage intégré du module ; détails dans la note d'application FTPS ; pour amener d'abord un fichier du PC dans l'UFS, utilisez le bouton Upload du groupe « fichiers UFS » de la page SSL (AT+QFUPL, par l'UART, zéro trafic, checksum comparé automatiquement).

⚠ Pour FTP, +++ est un « abandon », pas une « pause ». Le manuel (FTPS AN v1.5 p13) écrit qu'après l'échappement, ATO ramène en mode données pour reprendre le transfert : infirmé par mesure (deux essais, même résultat) : après l'échappement, AT+QFTPSTAT répond 1 (inactif) et non 2 (transfert en cours), et ATO répond NO CARRIER — le transfert a été intégralement abandonné, aucune connexion à reprendre. +++ ne sert donc qu'à s'évader d'un mode données hors de contrôle, pas à mettre en pause un gros téléchargement.

La bonne façon de l'envoyer : 1 seconde de silence avant et après, en octets bruts, sans CR (avec, il est sans effet) — le bouton +++ de cette page respecte déjà cette règle ; le bouton ATO est conservé au sens du manuel.

🧪 Méthode de test

Cette section explique « comment tester sans aboutir à de fausses conclusions ». Tout y a été appris en se cognant pour de vrai.

Un OK ne signifie presque jamais que c'est terminé

Les modules Quectel de ce type ont un schéma commun : un OK d'abord, qui signifie « commande acceptée », puis le vrai résultat par URC. Sont dans ce cas QIOPEN, QSSLOPEN, QMTOPEN, QFTPOPEN, et le plus souvent oublié, QFTPCLOSE. Prendre le OK pour la fin et enchaîner immédiatement l'action suivante est ce qui a fait perdre le plus de temps sur ce projet.

Pas de conclusion sans groupe témoin

Deux exemples :

  • Validation de certificat : si l'on teste seulement que « le mauvais certificat ne passe pas », « rien ne passe » satisfait aussi le test. Il faut prouver en même temps que le bon certificat passe.
  • Accélération AGNSS : le 7-2 « TTFF à froid » est par nature le témoin du 7-4. En intérieur, sans signal satellite, aucun des deux n'aboutit ; le test ne donne que « les deux ont échoué ».

Un contrôle de santé à la fin de chaque série de tests

Le module se dégrade. Après une vingtaine d'ouvertures/fermetures de connexion consécutives, il entre dans un état où « le canal de contrôle est encore vivant, mais le canal de données est totalement mort » — et par-dessus le marché QSSLSTATE est vide, QIACT? montre une IP, QIGETERROR répond 0 : tout a l'air parfaitement normal.

Cet état pollue les données de test. Cela s'est produit pendant les mesures : durant la phase de dégradation, certains hôtes étaient injoignables même « vérification désactivée », et cela a failli être imputé à la validation de certificat. Avant de clore chaque série, revalidez avec une cible connue pour être joignable : à ce prix seulement les données sont fiables.

Méthode de discrimination : viser la même cible avec un AT+QIOPEN en TCP pur. Si cela échoue aussi, le problème n'est pas dans la couche SSL / FTP : c'est toute la pile de données qui est cassée.
Récupération : seul le rituel de démarrage complet fonctionne. QIDEACT + QIACT ne rattrapent rien.

Sondage sans trafic : AT+Q...=?

La forme de test (=?) ne touche pas au réseau et ne coûte rien, et elle renvoie les plages de paramètres réellement prises en charge par ce firmware — plus fiable que la note d'application, qui est écrite pour toute une série de produits. C'est par cette astuce que ce projet a détecté que les plages du scan Wi-Fi ne correspondaient pas au manuel.

Prouver que « la transmission est vraiment correcte » suppose une relecture par un tiers

+QFTPPUT: 0,20 n'est qu'une auto-déclaration du module : il dit avoir envoyé 20 bytes. En pratique, le fichier a été récupéré depuis le PC avec un autre client FTP, puis comparé octet par octet — c'est la seule façon d'écarter simultanément « le module a mal compté » et « le serveur a mal enregistré ».

Trafic

AT+QGDCNT? renvoie deux compteurs d'octets, « émis, reçus ». ⚠ Ce compteur n'est pas stocké en NV : il repart de zéro à chaque redémarrage du module ; AT+QAUGDCNT n'est pas un compteur cumulé, c'est le réglage de l'« intervalle de sauvegarde automatique » (0 = désactivé). Pour cumuler sur plusieurs phases, il faut relever à chaque étape, sur le moment : rien ne se rattrape après coup.

Ordres de grandeur : un handshake TLS coûte bien plus cher que l'intuition ne le suggère, car chaque handshake télécharge la chaîne de certificats complète, et un handshake raté se paie tout autant. Mesuré : 11 handshakes ont consommé 15,3 Ko en TX et 59,6 Ko en RX.

❓ Questions fréquentes

Q : J'ai cliqué sur Connecter, mais la liste ne contient aucun port

Vérifiez trois choses : (1) la page est-elle ouverte en file:// — Web Serial est alors bloqué ; (2) le pilote du pont USB-UART est-il installé ; (3) le navigateur est-il bien Chrome / Edge / Opera.

Q : Les commandes partent, mais le module ne répond absolument pas

Neuf fois sur dix, le rituel de démarrage n'a pas été fait. À l'instant où le port série est ouvert, RTS est remis à l'état haut, or sur cette carte RTS est un interrupteur d'alimentation à logique inversée — se connecter revient donc à couper le courant. Passez à l'onglet Hardware, faites un Power / Reset, attendez RDY.

Vient ensuite la fin de ligne réglée sur LF. L'EG800K n'accepte que CR.

Q : Toutes les commandes répondent OK, mais aucune URC n'arrive

Envoyez AT+QURCCFG="urcport". La valeur d'usine est usbat : les URC partent toutes vers le port USB. Passez à uart1 ; c'est écrit en NVRAM, donc à faire une seule fois.

Q : Le terminal est bloqué, plus rien ne réagit à la frappe

Vous êtes très probablement en mode données — la longueur d'une commande en deux temps a été mal calculée et le module attend toujours que vous complétiez le compte d'octets. Sortez-en en envoyant ESC (0x1B) avec le bouton d'octets bruts de l'onglet Hardware. Pour le mode données de FTP, il faut envoyer +++ (1 seconde de silence avant et après, sans CR).

Q : Je reçois en boucle +CME ERROR: 603

Si vous venez d'envoyer AT+QFTPCLOSE, c'est que la fermeture n'est pas terminée. Attendez l'apparition de +QFTPCLOSE: 0,0 avant de continuer.

Q : Toutes les connexions échouent, mais AT+QIACT? montre encore une IP

La pile de données du module s'est dégradée. Visez une cible connue pour être joignable avec un AT+QIOPEN en TCP pur — si cela échoue aussi, refaites le rituel de démarrage complet. QIDEACT + QIACT ne rattrapent rien.

Q : J'ai envoyé des données à un serveur d'écho mais je ne reçois aucun écho

Vérifiez si le payload se termine par \n. Beaucoup de services d'écho fonctionnent ligne par ligne : sans saut de ligne, rien n'est renvoyé. Il suffit de taper les deux caractères \n dans le champ ; l'outil les décode en véritable saut de ligne avant l'envoi, et la longueur est calculée en conséquence.

Q : Le GNSS n'arrive jamais à se positionner

Commencez par AT+QGPSGNMEA="GSV" pour voir s'il y a des satellites. En intérieur, on n'en capte généralement aucun : ce n'est alors pas un problème de configuration, c'est qu'il n'y a pas de vue du ciel.

Q : Comment changer de langue ou de thème ?

En haut à droite. 18 langues, deux thèmes (clair et sombre) ; les choix sont mémorisés. Les explications et les annotations des commandes AT sont traduites elles aussi, pas seulement l'interface.

Q : Cet outil consomme-t-il mon forfait data en douce ?

Non. C'est un fichier HTML unique, purement front-end, sans backend. Le seul trafic mobile généré vient des commandes de type data que vous déclenchez vous-même, et l'explication de ces boutons le dit clairement. Les commandes d'interrogation et les formes de test =? ne touchent jamais au réseau.
